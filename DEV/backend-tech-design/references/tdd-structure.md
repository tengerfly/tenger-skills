# 技术方案结构范式（TDD Structure）

> 定位：技术方案**怎么写、包含哪些章节**的唯一权威范式。写任何技术方案前，先按本范式确定「章节清单」（必须 + 根据需求开关的可选），再逐章成文。
> 本范式是权威；`assets/` 模板是本范式的骨架，二者冲突时以本范式为准。

---

## 一、整体结构（两层）

技术方案文档包 = **总技术文档 `overview.md`（L1 总览）** + **N 个模块技术方案 `NN_xxx.md`（L2 细节）**。

```
TDD/
├── overview.md      # L1 总览：选型 + 架构图 + 模块边界 + 关联 + 表结构
├── 01_xxx.md        # L2 模块技术方案
├── 02_xxx.md
└── ...
```

---

## 二、总技术文档 `overview.md` 章节范式

### 2.1 必须章节（每个技术方案都要有，缺一不可）

| # | 章节 | 内容 | 为什么必须 |
|---|------|------|-----------|
| 1 | 文档元数据 | 项目 / 版本 / 档位 / 需求来源 | 可追溯 |
| 2 | 技术选型总览 | 语言/数据库/缓存/检索/队列/Docker + 理由 + 备选 | 定技术底座 |
| 3 | 系统架构图 | Mermaid 分层架构 | 全局视图 |
| 4 | 模块清单与边界 | 每模块应做 / 不应做 | 划清职责 |
| 5 | 模块关联关系图 | Mermaid + 关联表 | 模块间协作 |
| 6 | 全局表结构设计 | 所有表 + 全部字段 | 数据底座 |

> **背景与约束量化（元数据必填）**：文档元数据必须写明**量化业务约束**，作为容量规划/选型的输入——`QPS/TPS 峰值`、`P99/P95 延迟`、`数据规模（条数/日增量）`、`一致性需求`、`合规要求`、`可用性/容灾要求（RTO/RPO）`。凡 PRD 未给出、本方案又必须的量级，进「方案假设」并在 Scope Gate 显式呈现待用户拍板（见 `socratic-grilling.md` §一）。缺量化约束的元数据视为 P0。

### 2.2 可选章节（根据需求 / 档位开关）

| # | 章节 | 触发条件（开关规则） |
|---|------|---------------------|
| 7 | 缓存设计 | 需求有热点数据 / 会话 / 排行榜 / 分布式锁 |
| 8 | 消息队列设计 | 需求有异步通知 / 削峰 / 解耦 |
| 9 | 检索设计 | 需求有全文搜索 / 复杂过滤 / 聚合 |
| 10 | 全局技术规范 | 企业级必选；快速可选 |
| 11 | 部署架构 | 企业级必选；快速简化 |
| 12 | 监控告警 | 企业级必选 |
| 13 | 性能与容量规划 | 高并发 / 大流量必选；按 `decision-rules.md` §十给量化计算过程 |
| 14 | 安全合规 | 敏感数据 / 合规需求必选 |
| 15 | 弹性与容错 | 企业级必选；超时/重试/熔断/降级/限流分层定义（内层预算 < 外层预算，层间击穿终态回填责任方写明） |
| 16 | 架构决策记录（ADR） | 企业级必选；只记真有取舍的（决策 / 备选项 / 选定理由 / 影响与代价） |
| 17 | 上线与回滚 | 企业级必选；灰度策略 / 数据迁移 / 回滚步骤 / 验证清单 |
| 18 | 技术债登记 | 默认保留；显式登记为赶进度妥协的设计 |
| 19 | 成本评估 | 企业级必选；量化云资源成本与性价比对比 |
| 20 | 故障演练 | 企业级可选；Chaos 用例验证降级/熔断/主备切换 |

## 三、模块技术方案 `NN_xxx.md` 章节范式

### 3.1 必须章节

| # | 章节 | 内容 |
|---|------|------|
| 1 | 模块概述与边界 | 应做 / 不应做 |
| 2 | 上下游依赖 | 上游 / 下游 / 传递方式 |
| 3 | 核心流程设计 | 流程图 / 时序图 / 状态机（能画必画） |
| 4 | 接口 / 服务设计 | 接口 / 方法 / 入参出参 |
| 5 | 数据模型 | 引用总文档表 |
| 6 | 实现细节与决策 | 逐功能点展开到可编码：每一步怎么做 + 关键工程决策（存哪/怎么传/大小上限/断点续传/并发/安全…）及结论 |
| 9 | TDD 测试用例（模板排 §9） | Gherkin + 代码级（先测试后实现） |

### 3.2 可选章节（模板 §7/§8）

| # | 章节 | 触发条件 |
|---|------|---------|
| 7 | 关键技术点与难点（含性能与容量） | 有并发 / 事务 / 缓存 / 幂等 / 性能难点 |
| 8 | 异常与边界处理 | 有复杂异常场景（建议保留） |

### 3.3 接口出参 DTO 硬约束（防前后端漂移 · P0 红线）

> 严重教训（学径项目 2026-09）：TDD / FTDD 均规定 `libs/shared` 为 DTO 单一来源，但实际 `libs/shared` 只装了枚举 + 分页，视图类型（PlanSummary / KpItem / ModelView / SkillView …）后端写在各 service、前端写在 `api/*.ts`，互不引用、各自漂移 → 联调爆发 `GET /graph/tags` 裸数组 vs `{tags}`、`SkillView.isBuiltin` vs `source` 等 P0 错位。

- **硬约束 1（出参 DTO 落共享包）**：每个接口的出参类型（视图 / 列表包裹）**必须定义为 `libs/shared/dto` 下的类型文件**，后端 service `import type` 返回、前端 `import type` 消费，**禁止两端各写一份**。
- **硬约束 2（列表响应统一包裹）**：列表类接口只允许一种包裹 `{ items, total }`（或 `{ list, total }`，全项目二选一并写进共享类型），**禁止裸数组直接返回**。
- **硬约束 3（派生 UI 字段由后端给出）**：UI 展示用的派生布尔 / 标签（`isBuiltin` 等）在后端 DTO 内计算后返回，不在前后端靠"约定"各自转换。
- **硬约束 4（设计文档列 DTO 清单）**：模块技术方案「接口设计」章节必须列出**本模块出参 DTO 的文件路径（位于 `libs/shared/dto`）**，作为开发期前后端 `import` 的单一真相源；未列 = 该章节 P0 不完整。
- 验收联动：Code-Review `contract-checklist.md` §8.4 将「`libs/shared` 未承载视图 DTO」判为 P0 结构性风险；凡 `request<T>` 的 `T` 非共享类型，前端侧判 P0 待核（见 Frontend-Tech-Design `fetch-guide.md` §五）。

## 四、开关规则（根据需求文档自己定义）

### 4.1 需求关键词 → 可选章节开关

| 需求文档出现 | 开启章节 |
|-------------|---------|
| 搜索 / 检索 / 筛选 / 全文 | 检索设计 |
| 通知 / 提醒 / 异步 / 消息 / 推送 | 消息队列设计 |
| 热点 / 缓存 / 会话 / 排行榜 / 限流 / 锁 | 缓存设计 |
| 文件 / 图片 / 上传 / 附件 | 对象存储 |
| 敏感 / 隐私 / 合规 / 权限 / 审计 | 安全合规 |

### 4.2 档位 → 可选章节开关

| 档位 | 默认开启 |
|------|---------|
| 企业级生产 | 全局技术规范 + 部署架构 + 监控告警 + 上线与回滚 + 成本评估（高并发再加性能规划；技术债默认保留） |
| 快速实现 | 可选章节默认关闭或简化，只保留最小可用 |

### 4.3 开关判定流程

1. 读需求文档，扫描关键词 → 命中则开启对应可选章节；
2. 看档位 → 企业级默认开「全局规范 / 部署 / 监控 / 弹性与容错 / ADR / 上线回滚 / 成本」，快速默认关；
3. 生成「本次技术方案的章节清单」（必须 + 已开启可选），**写前先列清单**，缺章节或多余章节都要有依据。

## 五、范式落地方式

- SKILL.md 流水线步骤 3 / 5：先按本范式确定章节清单，再成文；
- `assets/overview-template.md` / `assets/module-template.md`：本范式的骨架，含 `【必须】` / `【可选】` 标记；
- 每个可选章节被跳过时，在文档末尾「章节开关说明」里留痕（为何开启 / 为何关闭）。
