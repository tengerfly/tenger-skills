# 架构模式解剖（Architecture Patterns）

> 用途：服务拆分、架构风格选型时的决策参考。每个模式给「一句话定义 + 适用场景 + 目录结构 + 反模式 + When 选它」。

---

## 一、Modular Monolith（模块化单体，默认首选）

- **一句话**：一个部署单元，内部按业务域切模块，模块间只走事件/接口，禁止 import 对方内部实现。
- **适用**：小团队、MVP、量级未达微服务阈值（见 `decision-rules.md` §一）。
- **目录结构**：
  ```
  app/
  ├── modules/
  │   ├── orders/      # 订单域（handler/logic/schema/db 自治）
  │   ├── payments/    # 支付域
  │   └── users/       # 用户域
  └── ../../shared/          # 仅真正通用：日志/鉴权/DB 连接
  ```
- **反模式**：模块间直接 import；一模块查另一模块的表（数据主权被破坏）。
- **When 选它**：不确定要不要微服务时；团队未在生产跑多服务时。

---

## 二、Clean Architecture（依赖倒置）

- **一句话**：依赖指向内层（Entity ← UseCase ← Interface ← 外层），业务核心不依赖框架/DB。
- **适用**：业务规则复杂、需要长期演进与可测试性。
- **目录结构**：
  ```
  src/
  ├── domain/          # 实体 + 业务规则（零依赖）
  ├── application/     # 用例编排（依赖 domain）
  ├── interfaces/      # 端口（Repository/网关抽象）
  └── infrastructure/  # 实现（DB/HTTP/队列，依赖 interfaces）
  ```
- **反模式**：domain 层 import 框架；把 DB 模型直接当领域实体。
- **When 选它**：领域逻辑重、要单测隔离、团队接受分层成本时。

---

## 三、Hexagonal（端口与适配器）

- **一句话**：核心通过「端口」与外部交互，外部世界都是「适配器」可插拔。
- **适用**：需要替换外部依赖（DB/第三方）而不改业务核心。
- **目录结构**：
  ```
  src/
  ├── core/            # 端口 + 业务逻辑
  └── adapters/
      ├── in/          # REST/CLI/消息入口适配器
      └── out/         # DB/外部 API/队列出口适配器
  ```
- **反模式**：业务逻辑直接 new 具体适配器，绕过端口。
- **When 选它**：外部依赖多变、强调可替换性时。

---

## 四、DDD（领域驱动设计）

- **一句话**：以「限界上下文 + 聚合 + 领域事件」建模，业务复杂时让代码结构对齐业务。
- **适用**：核心业务复杂、规则多、团队能投入建模成本。
- **核心概念**：
  - **限界上下文**：一个业务域的边界，服务拆分以它为准；
  - **聚合**：一致性边界，跨聚合改动用领域事件，不在同一事务里跨聚合强一致；
  - **领域事件**：聚合状态变更的事实，驱动 Outbox / CQRS。
- **反模式**：贫血模型（只有 getter/setter 无行为）；一个事务横跨多聚合。
- **When 选它**：业务规则复杂到分层/模块化都难以表达时。

---

## 五、CQRS / Event Sourcing

- **CQRS 一句话**：读写分离成两条模型/两条链路，各自独立演进、独立扩容。
- **Event Sourcing 一句话**：不存当前状态，存「事件序列」，状态由事件重放得到。
- **适用**：读写比例悬殊、需要审计全历史、复杂协作（如 Figma 实时协作用 CRDT）。
- **反模式**：为「将来可能」的读需求提前上 CQRS（做减法铁律，需求真出现再上）。
- **When 选它**：读模型与写模型差异大、或需事件审计/溯源时才上；否则普通读写分离即可。

---

## 六、模式速选表

| 信号 | 选模式 |
|---|---|
| 不确定/小团队/量级小 | Modular Monolith（默认） |
| 业务规则复杂、要可测 | Clean / Hexagonal |
| 核心域规则多、要长期演进 | DDD |
| 读写模型差异大 / 需审计 | CQRS / Event Sourcing |
| 已在生产跑多服务、需独立扩缩容 | 微服务 |

> 参考：mehdihadeli/awesome-software-architecture、pin0513/awesome-software-design。
