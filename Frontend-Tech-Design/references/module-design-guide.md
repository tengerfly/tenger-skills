# 模块技术方案编写指南

> 用途：指导每个模块 `NN_xxx.md` 的写法——边界、页面组件拆分、hooks 数据流、fetch 对接、测试用例。

---

## 一、模块边界写法

每个模块必须写清「应该做什么 / 不应该做什么」：

| 应做（前端技术职责） | 不应做（明确排除） |
|---------------------|-------------------|
| 本模块承载哪些页面、提供哪些 hooks、消费哪些接口 | 明确排除（如：不负责权限校验，由公共权限层承接） |

- 边界要**技术化、可执行**——写清「这个模块管哪些页面、复用哪些组件、调用哪些接口、暴露哪些 hooks」；
- 负向边界越清楚，模块间越不打架；与 PRD 模块划分对齐，但此处聚焦**前端技术职责**。

## 二、上下游依赖

| 方向 | 模块/系统 | 传递产物/前提 | 方式 |

## 四、hooks 数据流设计

| hook | 职责 | 依赖接口 | 返回 |
|------|------|---------|------|
| `useUserList` | 列表数据获取 + 筛选分页 | `userApi.getUserList` | `{ list, total, loading, error, fetchList }` |
| `useUserForm` | 表单值与提交 | `userApi.createUser` / `updateUser` | `{ form, submitting, submit }` |

> 数据流原则：页面容器组合 hooks → hooks 调用业务 api → 数据经 props 下发到业务组件。组件自身不直接调 api。

---

## 五、fetch 接口对接

| 前端方法 | 后端接口（TDD） | 方法 | 入参 | 出参 |
|---------|----------------|------|------|------|
| `userApi.getUserList` | `/api/users` | GET | page/pageSize/keyword | UserListResult |
| `userApi.createUser` | `/api/users` | POST | CreateUserPayload | User |
| `userApi.updateUser` | `/api/users/:id` | PUT | id + payload | User |
| `userApi.deleteUser` | `/api/users/:id` | DELETE | id | void |

> 与后端 TDD 接口一一对应，字段类型与后端表结构/接口定义对齐。

## 六、状态管理设计

- 局部状态：列表筛选、分页、表单值用组件/hooks 局部 state；
- 全局状态：仅登录态、主题、权限等跨模块共享态进 `store/`；
- 服务端状态：列表/详情数据用 TanStack Query 或 `useFetch` 管理缓存与请求态。

---

## 七、关键技术点

每个模块写清 1~3 个前端关键难点及其方案：

| 难点 | 方案 |
|------|------|
| 列表大数据渲染 | 虚拟滚动（`@tanstack/react-virtual`）+ 分页 |
| 表单校验 | 受控组件 + 校验 schema（zod）+ 错误态展示 |
| 请求竞态 | AbortController 取消 + 请求去重 |
| 权限控制 | `usePermission` + 路由守卫 + 按钮级权限 |

## 八、实现细节与决策（逐功能点展开到可编码）

> 目标：让开发拿到的方案"可直接编码"，不必回头确认。把每个功能点"前端每一步怎么实现"写清楚，凡真实工程会遇到的决策点都要给出结论，不能一句话带过。

### 8.1 逐功能点展开（功能点 → 实现步骤 → 决策点）

对模块内每个功能点，按三栏展开——功能点 + 实现步骤（前端每一步怎么做）+ 关键决策点与结论：

| 功能点 | 实现步骤（前端每一步怎么做） | 关键决策点 + 结论 |
|---|---|---|
| 文件上传 | ① 选文件 → ② 前端分片/整传 → ③ 进度展示 → ④ 秒传校验 → ⑤ 失败重试 | 分片 or 整传=分片（>50MB）；断点续传=需要（进度条+断点重传）；秒传=hash 去重；取消=AbortController；重试=失败自动重试 3 次 |

### 8.2 常见前端工程决策点清单（逐个过一遍，缺一不可）

写每个涉及的功能点时，主动过一遍下列决策点：能确定的写结论、前置已明确的标「继承 PRD/TDD」、确实无法确定的才标「待用户确认」：
- 数据从哪来（接口 / 本地 / 状态）；
- 请求怎么发（fetch 封装 / 取消 / 重试）；
- 加载 / 失败 / 空态怎么呈现；
- 竞态 / 取消怎么处理；
- 权限怎么校验（路由守卫 / 按钮级）；
- 超大列表 / 大文件怎么处理（虚拟滚动 / 分片）。

## 九、异常与边界处理

| 异常场景 | 处理方案 |
|---------|---------|
| 接口加载中 | loading 骨架屏 / 占位 |
| 接口失败 | 错误态 + 重试按钮（`refetch`） |
| 空数据 | 空状态占位 + 引导文案 |
| 未登录/无权限 | 路由守卫跳登录 / 隐藏按钮 |
| 请求超时/取消 | AbortController + 统一 ApiError 提示 |
