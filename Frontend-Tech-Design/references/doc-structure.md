# 技术方案文档结构指南

> 用途：定义前端技术方案文档「**应包含哪些方面**」以及每个方面的写法与深度要求。写方案前先锁定维度，**逐模块套用同一套模板**。

---

## 一、两级结构总览

一份前端技术方案文档包分两级，由粗到细：

| 层级 | 文件 | 承载内容 | 消费方 |
|------|------|---------|--------|
| **L1 总技术文档** | `overview.md` | 选型、架构、页面/组件清单、目录结构、模块边界、全局规范（**10 个方面**） | 全员对齐、排期评审 |
| **L2 模块技术方案** | `NN_xxx.md` | 单模块的页面组件拆分、hooks、接口对接、测试用例（**9 个方面**） | 开发据此实现 |

**铁律**：L1 只写全局与边界，不展开单模块实现细节；单模块细节一律下沉 L2；**一个模块 = 一份 `NN_xxx.md`**。

---

## 二、总技术文档 `overview.md` —— 10 个方面深度要求

### 1. 文档元数据
- 项目名称、需求来源（PRD / 原型 / 后端 TDD 路径）、实现档位、固定技术栈、责任架构师、日期；
- 一句话说明本文件是「L1 总文档」，模块细节在 `NN_xxx.md`。

### 2. 技术选型总览
- 用「选型 + 档位 + 理由 + 备选」表格列出：框架、构建、组件库、状态管理、路由、CSS、请求、测试、主题、国际化、浏览器兼容性；
- 每项必须有理由，禁止拍脑袋；规则见 `tech-stack-guide.md`。

### 3. 前端架构图（Mermaid，强制）
- 分层架构：用户层 → 路由层 → 页面容器 → 组件层 → hooks → 状态/请求 → 样式层 → 后端；
- 标注数据流方向，禁止死循环、必须有终态。

### 4. 页面清单
- **页面 = 路由**，逐页列：路由路径、页面名称、所属模块、职责、对应原型文件；
- 页面清单来自 PRD `页面视图.md` 与原型图，一一对应。

### 5. 组件清单
- 基础组件（跨项目复用）：列出组件 + 职责 + 来源（组件库 / 自研）；
- 业务组件（模块内复用）：列出组件 + 分层 + 职责 + 复用范围；
- 基础支持（横切关注点）：路由守卫、错误边界、请求层、主题切换、国际化。

### 6. 工程目录结构
- 给出完整目录树：`src/api` / `components` / `hooks` / `pages` / `styles` / `features` / `router` / `store` / `locales` / `utils` / `types` / `test`；
- 模块化开发：业务模块进 `features/<模块>/`（components + hooks + 入口）。

### 7. 模块清单与边界（应做 / 不应做）
- 每个模块一行：文件名 + 模块名 + 应做（管哪些页面/提供哪些 hooks/消费哪些接口）+ 不应做（负向边界）+ 关键产出；
- 这是各模块文档的目录索引，与 PRD 模块划分对齐。

### 8. 全局技术规范
- **fetch 封装**：贴 `request.ts` 核心实例（baseURL/超时/token/统一错误/取消）；
- **命名规范**：文件/目录、接口方法（getXxx/createXxx/updateXxx/deleteXxx）、hooks 前缀 `use`、CSS 类名；
- **环境变量**：`VITE_API_BASE_URL` 等；
- **错误处理**：ApiError 承载、ErrorBoundary 兜底、401 跳登录；
- **权限**（企业级）：路由守卫 + 按钮级权限。

### 9. 测试策略
- 测试框架（Vitest + RTL）、测试对象（页面/组件/hooks）、覆盖要求（渲染/交互/数据流/边界/异常）、AC 追溯。

### 10. 模块关联关系图（Mermaid + 关联表）
- 关联图标注模块间前端关联（路由跳转 / 共享组件 / 共享状态 / 接口依赖）；
- 关联表逐边回答：谁提供什么 → 谁消费什么 → 方式。

## 三、模块技术方案 `NN_xxx.md` —— 9 个方面深度要求

### 1. 模块概述与边界
- 定位与职责一句话；「应做 / 不应做」表格写清前端技术职责（承载哪些页面、提供哪些 hooks、消费哪些接口）与负向边界。

### 2. 上下游依赖
- 上游（页面入口来源/路由）、下游（下游模块/页面）、接口（后端服务）；
- 与总文档「模块关联关系图」一致。

### 3. 页面与组件拆分
- 页面清单（本模块）：页面 + 路由 + 职责 + 对应原型文件；
- 组件拆分表：组件 + 分层 + 职责 + 复用范围；
- 页面组件结构图（Mermaid，推荐）：页面容器 → 各子组件/hooks。

### 4. hooks 数据流设计
- 每个 hook：职责 + 依赖接口 + 返回结构；
- 数据流原则：页面容器组合 hooks → hooks 调业务 api → 数据经 props 下发组件。

### 5. fetch 接口对接
- 表格：前端方法 ↔ 后端接口（TDD）↔ 方法 ↔ 入参 ↔ 出参；
- 与后端 TDD 接口一一对应，字段类型对齐。

### 6. 状态管理设计
- 按「局部 / 全局 / 服务端」三类划分状态归属与管理方式。

### 7. 关键技术点与难点
- 写清 1~3 个前端难点 + 方案（虚拟滚动 / 表单校验 / 请求竞态 / 权限控制等）。

### 8. 异常与边界处理
- 覆盖：加载中、失败、空数据、无权限、超时/取消，每项给处理方案。

### 9. TDD 测试用例
- Gherkin 场景（承接 PRD 的 AC）+ 组件测试骨架 + hooks 测试骨架 + 覆盖矩阵；
- 覆盖：渲染 / 交互 / 数据流 / 边界 / 异常。

---

## 四、按模块套用规则

1. 总文档 §7「模块清单与边界」敲定后，**每个模块独立成文 `NN_xxx.md`**，逐一套用 §三 的 9 方面；
2. 编号连续（`01_xxx.md` `02_xxx.md` …），与总文档模块序号一致；
3. 模块文档的「上下游依赖」「fetch 接口对接」必须回链总文档关联图与后端 TDD 接口，不得自造接口；
4. 测试用例编号 `TC-Mxx-nnn` 承接 PRD 的 `AC-Mxx-nnn`，保证 REQ ↔ AC ↔ TC 双向追溯。
