# 前端选型拷问协议（grill-me 式单步拷问）

> 执行范围：FTDD 的选型澄清、Scope Gate、模块级组件拆分与数据流决策。吸收 grill-me / grill-with-docs 的决策树 + 单步提问法，内嵌执行，不依赖外部 skill。
> ⛔ BLOCKING：决策点未过「收敛证明」前，禁止写入 overview 或模块文档。

## 一、心智模型：决策树

- 每个决策点（选型/组件拆分/hooks 与状态归属/fetch 边界/异常策略）是一棵决策树：答案会解开依赖它的下一层问题。
- 每轮只问「前置已定、现在就能答」的 frontier 问题；一次一问，答后消化再进下一轮。
- 用户回答冒出的新问题进下一轮；frontier 清空才算该点收敛。
- 未获用户拍板的默认（组件库版本/兼容目标/状态归属/超时策略）标为待验证或【方案假设】，安排回访裁决，不得静默消化。

## 二、提问纪律

1. 每个问题写成「问题 + 推荐答案 + 理由」；无方向时给 2~3 个差异化选项 + 场景例子。
2. 推荐答案只是建议，最终仍须用户逐点拍板。
3. 一次一问：不连环轰炸、不提前抛出依赖未定的问题。
4. 回答质量门槛：抽象/口号回答（看情况、尽量、按需、后续优化）一律不放行，追问到能落到具体页面、组件、版本或异常。
5. 只给结论不给理由时追问：为什么现在就需要？不用会怎样？缺了它哪条链路走不通？

## 三、固定三问（每个决策点至少各过一轮）

1. 这个方案在什么场景下会失败/不成立？（弱网、无权限、空数据、兼容旧浏览器、接口异常）
2. 页面、数据或交互量涨 10 倍，这套拆分/状态/渲染方案还成立吗？
3. 漏掉了什么？（换角色、入口、异常、重复点击、离开页面后再看一遍）

## 四、边界拷问

- 这版明确不做/不支持的页面、设备、浏览器、交互是什么？说不出 → 边界未想清。
- 组件库与自研的适用边界在哪：哪些页面统一用库、哪些自研，为什么？
- 状态放哪层（本地/服务端/共享）？谁拥有并修改？
- 数据从哪来、由谁刷新？接口失败/超时由谁兜底？
- 权限、主题、i18n、空态等多规则冲突时谁优先？

## 五、数据流/交互节点拷问

关键链路（取数/表单提交/上传下载/权限路由/弱网/大列表）先拆节点序列（触发 → 取数 → 渲染 → 提交 → 反馈 → 跳转/刷新），再逐节点过问，禁止只走正常主链路。

| 拷问维度 | 该问的问题 |
|---|---|
| 触发与前置 | 什么动作触发？需要什么已就绪？没就绪/未授权会怎样？ |
| 数据 | 数据从哪个接口/缓存/本地来？空、旧、超时怎么办？ |
| 用户操作 | 用户做什么？过程中 loading/禁用/反馈是什么？ |
| 分支 | 下一步有几条路？成功/失败/取消/重复各走哪？ |
| 异常与恢复 | 弱网/离线/接口失败/重复提交/中途离开时，用户看到什么、还能做什么？ |
| 终态 | 完成后去哪？返回/刷新后与提交前状态一致吗？ |

逐节点记录「节点 / 触发 / 数据来源 / 用户动作 / 分支条件 / 异常恢复」，闭环并经用户确认后再写入模块文档。

## 六、收敛证明（一个决策点何时算定稿）

同时满足四条才允许定稿：

1. 结论可落到具体页面、组件、版本或状态归属，不是「看情况/尽量」。
2. 已记录：方案 + 理由 + 备选 + 已拷问的失败/涨 10 倍/漏项。
3. 待验证项（浏览器兼容、组件库版本等）有验证动作与回退方案。
4. 用户对定稿复述点头。

## 七、雷区（出现即自查补问）

- 用户回答一两句，就开始写 overview/模块文档 → 收敛证明未齐。
- 把 PRD/TDD 没写、本方案新增的决策当“默认/继承”直接定稿 → 新增决策必须单独拷问。
- 只问选型正向，不逼失败/涨 10 倍/漏项 → 补固定三问。
- 关键数据流只画成功主链路 → 逐节点补异常、弱网、重复与失败恢复。
- 把「推荐答案」当最终答案 → 仍要用户逐点拍板。
