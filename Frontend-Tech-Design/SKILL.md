# 前端技术方案文档（FTDD）编写 Skill

> **术语**：本 Skill 中 FTDD = **Frontend Technical Design Document（前端技术方案文档）**；同时全程遵循 **Test-Driven Development（测试驱动开发）**——先写测试用例、再写代码。

## 一、角色定位与第一原则

你是 **前端技术专家 / 前端架构师**。你的使命是：依据已定稿的 PRD 需求文档、高保真原型图与后端技术文档（TDD），产出一份**可落地、可评审、可 TDD 开发**的前端技术方案文档包。

**第一原则**：「先定选型与边界，再逐模块展开；每个模块先有测试用例，后有实现方案。」

- 前端技术方案是 PRD（`PRD-Design`）与后端 TDD（`Backend-Tech-Design`）的前端承接方——PRD 只写需求、后端 TDD 只写后端实现，这里才写**页面、组件、hooks、路由、状态、请求封装、样式架构**等前端实现内容；
- 原型图（`Prototype-Design`）是理解页面结构与交互的**直接输入**，页面清单、组件拆分必须与原型一一对应；
- 后端 TDD（`Backend-Tech-Design`）中的接口清单是前端 **fetch 请求封装与接口对接**的唯一依据。

### 1.1 固定技术栈（不询问，直接采用）

| 项 | 固定选型 | 说明 |
|----|---------|------|
| 包管理器 | pnpm | 统一依赖管理与 workspace |
| 构建工具 | Vite | 开发快、生态成熟 |
| 语言 | TypeScript | 严格模式，全量类型 |
| 框架 | React 18+ | **hooks 为主**，函数组件 + 自定义 hooks |
| 请求 | 原生 fetch | 封装实例，见 §七 |
| CSS | 预编译（Sass/SCSS） | 模块化 + 全局样式抽离，见 §八 |
| 测试 | Vitest + React Testing Library | 测试先行，见 §九 |

### 1.2 需要询问用户的技术选型（见第五节澄清规程）

| 选型项 | 是否必问 | 默认/推荐 |
|--------|---------|----------|
| 实现档位（企业级生产 / demo） | **每次必问** | 企业级生产 |
| 组件库 | **每次必问** | 让用户决定，给推荐 |
| 暗黑模式 / 主题切换 | **每次必问** | 按需开启 |
| 国际化 i18n | **每次必问** | 按需开启 |
| 浏览器兼容性 | **每次必问** | 不指定则用 Vite 默认 |
| 状态管理 | 推荐默认 | Zustand（轻）/ Redux Toolkit（复杂） |
| 路由 | 推荐默认 | React Router v6 |

## 二、何时使用（When to Use）

**✅ 适用**：
- 已有 PRD（+ 原型图 + 后端 TDD），要写前端技术方案 / 前端技术设计 / 前端架构设计 / FTDD 文档；
- 需求与后端接口定稿后，前端开发启动前，需要落前端选型与模块方案。

**❌ 不适用**：
- 写需求（用 `PRD-Design`）、评审需求（用 `PRD-Review`）、出原型（用 `Prototype-Design`）、写后端技术方案（用 `Backend-Tech-Design`）；
- 纯运维 / 部署 / 后端架构方案。

## 三、技术方案文档的内容维度（先定模板，再按模块写）

> 一份前端技术方案文档包由「**L1 总技术文档** + **L2 模块技术方案**」两级构成。写方案前必须先锁定每级应包含哪些方面（维度），**逐模块套用同一套维度模板**，缺一不可。

### 3.1 总技术文档 `overview.md` —— 10 个方面

| # | 方面（维度） | 回答的问题 |
|---|------------|-----------|
| 1 | 文档元数据 | 项目、输入来源、实现档位、版本 |
| 2 | 技术选型总览 | 用什么 + 为什么 + 备选 |
| 3 | 前端架构图 | 分层结构与数据流长什么样 |
| 4 | 页面清单 | 有哪些页面、对应哪些路由与模块 |
| 5 | 组件清单 | 基础/业务组件与基础支持有哪些 |
| 6 | 工程目录结构 | 代码如何模块化组织 |
| 7 | 模块清单与边界 | 每个模块做什么、不做什么 |
| 8 | 全局技术规范 | fetch 封装 / 命名 / 环境变量 / 错误 / 权限 |
| 9 | 测试策略 | 怎么测、覆盖什么 |
| 10 | 模块关联关系图 | 模块间如何关联 |

### 3.2 模块技术方案 `NN_xxx.md` —— 9 个方面

| # | 方面（维度） | 回答的问题 |
|---|------------|-----------|
| 1 | 模块概述与边界 | 本模块做什么、不做什么 |
| 2 | 上下游依赖 | 依赖谁、被谁依赖、对接哪些接口 |
| 3 | 页面与组件拆分 | 本模块有哪些页面与组件 |
| 4 | hooks 数据流设计 | 逻辑怎么写、数据怎么流 |
| 5 | fetch 接口对接 | 对接后端哪些接口 |
| 6 | 状态管理设计 | 状态放哪、怎么管 |
| 7 | 关键技术点与难点 | 难点是什么、怎么解 |
| 8 | 异常与边界处理 | 异常/边界怎么兜底 |
| 9 | TDD 测试用例 | 怎么测、测什么 |

### 3.3 按模块套用的铁律

- **一个模块 = 一份 `NN_xxx.md`**，逐模块套用 §3.2 的 9 方面维度模板，缺一不可；
- 总文档 §3.1 的「模块清单与边界」是各模块文档的目录索引；模块文档的「上下游依赖」「fetch 接口对接」必须与总文档关联图、后端 TDD 接口一致；
- 模板只定骨架，每个方面的写法与深度要求见 `references/doc-structure.md`。

## 四、核心流水线（端到端闭环）

```
输入（优先读项目 `.spec/` 已有 PRD + 原型 + 后端 TDD；缺失回退用户指定）
        │
        ▼
[1] 输入解析 + 浏览器工具检测（Playwright → browser-use → 其他如 agent-browser，全无则报错提醒安装，不跳过）
        │
        ▼
[2] 技术选型澄清（档位必问 + 组件库必问 + 暗黑/国际化/兼容性必问）
        │
        ▼
[3] 生成总技术文档 overview.md（维度见 §3.1：选型 + 架构图 + 页面组件清单 + 目录结构 + 模块边界 + 全局规范）
        │
        ▼
[4] ◉ Scope 确认 Gate（选型 + 模块边界，人工放行）
        │
        ▼
[5] 逐模块生成技术方案 NN_xxx.md（维度见 §3.2：页面组件拆分 + hooks + fetch 对接 + 测试用例）
        │
        ▼
[6] 全局一致性检查（页面/组件/hooks/接口/测试用例编号）
        │
        ▼
[7] 归档 .spec/FTDD/VN/
```

### 步骤 1：输入解析 + 浏览器工具检测

- **优先读项目 `.spec/` 已有产出**：
  - PRD：`.spec/PRD/VN/`（**先读 `PRD速查表.md` 建六大索引**；overview + 模块文档按需按锚点回读）；
  - 原型：`.spec/原型/`（HTML 原型 + README）；
  - 后端 TDD：`.spec/TDD/VN/`（overview + 模块文档，取接口清单）。
  - 缺失则回退到用户指定路径 / 粘贴内容。
- **评审任务清单检测（闭环修复入口）**：检查 `.spec/技术方案评审/任务清单.md`，筛出 `已确认` 且 `修改方` 含 `Frontend-Tech-Design` 的任务——这些是本次必须修复的问题点/优化点，逐条纳入对应模块方案（新建时融入设计，改稿时作为变更项处理）；
- **检测浏览器工具（强制）**：
  - 检测顺序：**Playwright 优先 → browser-use 次之 → 其他浏览器工具（如 CodeBuddy 的 agent-browser）**——列举不穷举，凡能驱动真实浏览器打开页面/交互/截图的工具均算；任一可用 → 用于查阅组件库 / Vite / React 官方文档与版本兼容性；
  - **全部不可用 → 直接报错提醒用户安装**，**不跳过、不静默降级**：
    > `【环境错误】未检测到任何可用的浏览器工具（Playwright / browser-use / agent-browser 等）。请先安装并启用任一浏览器工具后再继续，否则无法保证选型与文档的版本准确性。`
  - 与后端 `Backend-Tech-Design`（不可用则跳过）**不同**——前端技术方案高度依赖组件库与构建工具的官方版本信息，缺浏览器工具会导致选型失真，必须报错中断。

### 步骤 2：技术选型澄清（见第五节规程）

- 一次只问一个问题，推荐答案前置；
- 档位、组件库、暗黑模式/主题、国际化、浏览器兼容性为**必问项**，缺一不放行。

### 步骤 3：生成总技术文档 `overview.md`

依据 `assets/overview-template.md`（维度见 §3.1 的 10 方面）：技术选型总览 + **前端架构图（Mermaid）** + **页面清单（路由 + 职责 + 对应模块）** + **组件清单（公共组件 + 业务组件 + 基础支持）** + **工程目录结构** + 模块清单与边界（应做/不应做）+ 模块关联关系图 + **全局技术规范（fetch 封装实例 / hooks 规范 / CSS 规范 / 命名 / 错误处理 / 权限 / 环境变量）** + 测试策略。

### 步骤 4：Scope 确认 Gate（强制暂停）

向用户呈现：技术选型清单 + 各模块「应做/不应做」+ 页面与组件清单预览。**等待用户确认「选型与边界无误」才放行**；有异议回到步骤 2。

### 步骤 5：逐模块生成技术方案 `NN_xxx.md`

依据 `assets/module-template.md`（维度见 §3.2 的 9 方面）：模块概述与边界 + 页面与组件拆分 + **hooks 数据流设计** + **fetch 接口对接（引用后端 TDD 接口）** + 状态管理设计 + 关键技术点 + 异常与边界处理 + **TDD 测试用例（组件测试 + hooks 测试）**。

### 步骤 6：全局一致性检查

页面与组件命名统一、hooks 与状态划分一致、fetch 接口与后端 TDD 接口一一对应、模块间依赖与总文档关联图一致、测试用例编号连续且与 PRD 的 AC 可追溯。

### 步骤 7：归档

落盘至 `.spec/FTDD/VN/`（overview.md + NN_xxx.md）。
- **回填评审任务清单**：若本次处理了 `.spec/技术方案评审/任务清单.md` 中归本 skill 的 `已确认` 任务，逐条把状态改为 `已修复`，并在 `修改说明` 写明改了哪个文档哪一节、怎么改；归 `Backend-Tech-Design` 或 `双方` 的任务只改自己负责的部分，其余保留原状态。

## 五、技术选型澄清规程（Socratic Protocol）

> 吸收 `grill-with-docs` 方法论内联实现：一次只问一个问题、推荐答案前置、先探索再提问。

### 5.1 实现档位（每次必问，推荐企业级）

| 档位 | 特征 | 典型选择 |
|------|------|---------|
| **企业级生产**（默认） | 工程质量优先：完整测试、错误边界、权限路由、监控埋点、性能优化、代码规范（ESLint/Prettier/Husky）、CI/CD | 组件库 + 状态管理 + 路由 + i18n + 主题 + 测试全覆盖 |
| **demo 快速实现** | 以实现为主：最小可用、快速跑通、够用即可 | 精简配置、少量公共组件、测试只覆盖核心路径 |

> 判定口径：用户明确要「demo / 快速 / 先跑通 / 做个样例」才走 demo 档；其余一律企业级。

### 5.2 组件库（每次必问，让用户决定）

- 先探索 PRD/原型得出「表单密集型 / 数据展示型 / 中后台 / C 端营销」等形态，再推荐；
- 让用户在「使用组件库 / 自研组件」中决定，使用组件库时再定具体库；
- 推荐参考：Ant Design（中后台首选）、Arco Design（字节中后台）、Naive UI（TS 友好）、Element Plus（Vue，仅当框架切 Vue 时）；
- 用户选「不用组件库」→ 走自研组件路线，总文档需补「基础组件自研清单」。

### 5.3 暗黑模式 / 主题切换（每次必问）

- 问：是否需要暗黑模式？是否需要主题切换（多套配色）？
- 需要 → 总文档补「主题方案」：CSS 变量 token + `data-theme` 切换 + 主题持久化；组件库需确认支持主题定制；
- 不需要 → 明确写入 Out-of-Scope，仍要求样式用 CSS 变量组织（便于后续加主题）。

### 5.4 国际化 i18n（每次必问）

- 问：是否需要多语言？
- 需要 → 总文档补「i18n 方案」：`react-i18next`（默认）+ 文案抽离 + 语言包结构；组件库需确认支持国际化；
- 不需要 → 明确写入 Out-of-Scope，但仍要求 UI 文案集中管理（禁止散落硬编码）。

### 5.5 浏览器兼容性（每次必问）

- 问：是否有目标浏览器范围？
- 用户指定 → 以指定范围为准，Vite 用 `@vitejs/plugin-legacy` 或 `build.target` 适配，CSS 需加对应前缀；
- 用户不指定 → **以 Vite 默认浏览器目标为准**（现代浏览器），并在总文档显式声明。

### 5.6 推荐默认项（用户无偏好直接采用，不追问）

| 项 | 默认 | 说明 |
|----|------|------|
| 框架 | React 18+（hooks 为主） | 与固定技术栈一致 |
| 状态管理 | Zustand（轻量）｜Redux Toolkit（复杂全局态） | 按复杂度取舍 |
| 路由 | React Router v6 | 数据路由 + 懒加载 + 权限守卫 |
| CSS 预编译 | Sass（SCSS） | 见 §八 |
| CSS 模块化 | CSS Modules | 组件级样式隔离 |
| 测试 | Vitest + React Testing Library | 见 §九 |

## 六、页面与组件设计规范

### 6.1 页面清单（总文档 §4）

- **页面 = 路由**：每个页面一个路由，命名语义化（`/login` `/users` `/users/:id`）；
- 页面清单来自 PRD 速查表「页面/视图索引」与各模块 §3.1、原型布局清单，逐页标注：路由路径、页面职责、所属模块、对应原型文件；
- 页面只做「编排」，不承载复杂逻辑——逻辑下沉到 hooks 与组件。

### 6.2 组件分层（总文档 §5）

| 分层 | 定义 | 示例 |
|------|------|------|
| 基础组件 | 无业务语义、跨项目复用 | Button / Modal / Table / Form |
| 业务组件 | 有业务语义、模块内复用 | UserCard / OrderList / 上传组件 |
| 页面容器 | 页面级编排组件 | `pages/users/index.tsx` |

- 组件拆分原则：单一职责、可复用优先、props 契约清晰（用 TypeScript 约束）；
- 详见 `references/component-design-guide.md`。

### 6.3 hooks 优先（模块化开发核心）

- **逻辑一律抽成自定义 hooks**（`useXxx`），组件只负责渲染与绑定；
- 数据获取 → `useFetch` / `useQuery`；表单 → `useForm`；权限 → `useAuth` / `usePermission`；主题 → `useTheme`；
- hooks 目录组织：`src/hooks/`（通用）+ `src/features/<模块>/hooks/`（模块私有）；
- 详见 `references/component-design-guide.md` §hooks。

## 七、fetch 请求封装规范

- **统一用原生 fetch，不引入 axios**；封装统一入口 `src/api/request.ts`；
- 必须覆盖：baseURL、超时（AbortController）、错误统一（ApiError）、token 注入、请求/响应拦截、取消支持；
- 接口按业务域拆分 `src/api/<模块>.ts`，方法签名与后端 TDD 接口一一对应；
- **完整可运行实例见 `references/fetch-guide.md`**（含类型定义 + 业务方法示例）。

---

## 八、CSS 架构规范

1. **预编译**：统一 Sass（SCSS），禁止裸 CSS；
2. **模块化**：组件级样式用 CSS Modules（`*.module.scss`），样式随组件隔离；
3. **全局样式抽离**：`src/styles/` 集中管理——
   - `variables.scss`（设计 token：颜色/字号/间距/圆角/阴影，CSS 变量）
   - `mixins.scss`（复用 mixin）
   - `global.scss`（reset + 全局基础样式）
   - `theme.scss`（暗黑模式 / 主题切换，可选）
4. **命名规范**：BEM 或驼峰，语义化；颜色一律引用变量，禁止写死色值；
5. 详见 `references/css-guide.md`。

## 九、TDD 测试用例规范

- **先写测试用例，后写实现方案**——测试用例是前端开发 TDD 先写测试的直接输入源；
- 测试框架：Vitest + React Testing Library；组件测试 + hooks 测试（`renderHook`）；
- 测试用例承接 PRD 的 AC 编号（`AC-Mxx-nnn`），覆盖：渲染 / 交互 / 数据流 / 边界 / 异常；
- 详见 `references/test-guide.md`。

## 十、模块边界与关联关系

- **每个模块必须写「应该做什么 / 不应该做什么」**：负向边界写清楚，页面与组件归属才不打架（与 PRD 模块划分对齐，但此处聚焦**前端技术职责**：管哪些页面、提供哪些 hooks、消费哪些接口）；
- **模块关联关系**：两个模块有前端关联（路由跳转 / 共享组件 / 共享状态 / 接口依赖）时，必须在总文档关联图与关联表中显式体现，标注关联类型与传递产物。

## 十一、常见错误对照表

| 常见错误 | 纠正方式 |
|---|---|
| 未问档位就直接按企业级写 | 步骤 2 档位每次必问 |
| 未问组件库就默认 Ant Design | 组件库每次必问，让用户决定 |
| 未问暗黑模式/国际化/浏览器兼容性 | 三项每次必问，缺一不放行 |
| 任何浏览器工具都不可用却继续产出 | 报错提醒用户安装，不跳过 |
| 用 axios 而非 fetch | 统一原生 fetch 封装 |
| 组件里堆满业务逻辑 | 逻辑下沉 hooks，组件只渲染 |
| CSS 全局样式与组件样式混在一起 | 全局抽离 `src/styles/`，组件用 CSS Modules |
| 页面清单与原型对不上 | 逐页标注对应原型文件 |
| fetch 接口与后端 TDD 接口脱节 | 接口按业务域拆分，一一对应 |
| 测试用例只写正向渲染 | 补交互/数据流/边界/异常用例 |
| 测试用例与 PRD 的 AC 脱节 | 测试用例标注对应 AC 编号 |
| 模块文档漏写某个维度 | 对照 §3.2 的 9 方面逐项补齐 |
