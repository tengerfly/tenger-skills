# Skill-Evolver（Skill 进化引擎）

> IRON LAW：每次进化必须可回溯到具体信号（偏好条目 / issue / 轨迹原文片段）；无信号不动手，有信号不见原文不下结论。偏好沉淀内容必须完整展示给用户，不允许只报入库数量。
> 定位：本仓 skill 的**进化引擎**——让 skill 随使用越来越懂用户。Skill-Optimizer 是调度者（标准、池管理、体检），其模式②偏好信号采集、模式③优化执行**内部调用本 skill**；本 skill 也可独立触发。采集与偏好库环节 agent 无关：任何 Agent 丢来会话/日志，都能产出偏好画像与信号清单（见 §八）。

## 一、模型：一个进化环 × 三档策略

```
⓪ 装载 → ① 采集（多源信号，读原文） → ② 建模（偏好库三决策）
       → ③ 触发（判据攒证据） → ④ 诊断（读轨迹定因）
       → ⑤ 方案与确认（证据链建议单） → ⑥ 执行与留痕（确认后改 + 台账）
```

| 档位 | 行为 | 开启方式 |
|---|---|---|
| 保守 | 只出偏好画像 + 问题分析报告，不做进化建议 | 用户点名 |
| **标准（默认）** | 出进化建议单，**逐条确认后才执行** | 默认 |
| 激进 | 自动执行 P2 改动 + 事后报告（P0/P1 仍需确认） | 用户显式开启 |

灵感出处（2026-09-18 OSS-Radar 调研）：hermes-agent-self-evolution 六步环+护栏、GenericAgent 显著点挖掘 SOP、OpenViking 偏好三决策、GEPA 读轨迹诊断、evolver 进化留痕与档位。详见 `.spec/开源情报/2026-09-18-skill进化器调研.md`。

## 三、流程

### ⓪ 装载
读偏好库、信号月志、进化台账、增量标记（记在 `evolution/README.md`）。首次运行 = 初始化池目录（按模板），偏好库为空属正常，从零积累。

### ① 采集（多源信号，判据级 SOP）

**信号源**：当前/历史会话原文、`chats/`、用户粘贴、各 skill 的 `issue/` 池（只读）、skill 运行产物。

**信号三类**：
- **A 偏好表达**：用户主动的纠正 / 重申 / 否决 / 表扬（「以后都」「不要」「我喜欢」「就这样」句式与语气）；
- **B 行为习惯**：用户对同类输出反复手动修正 = skill 行为与用户期望的**系统性偏差**（单次是意外，反复是习惯）；
- **C 情绪事件**：语气明显波动（愤怒/质问/讽刺/感激/沮丧/预期落空后的方向突变）——**只标语气不标内容**；纯功能指令、语气平和的反馈不标。

**判据（缺一不算信号）**：
1. 用户主动表达才算——SKILL.md/系统提示词里的被动出现不构成证据，不能从「存在某约定」推断用户偏好；
2. 每条信号 = 类型标签 + 原文片段（可 grep 回溯）+ 出处（会话/文件）+ 日期；
3. 增量：维护增量标记，只扫上次之后的新内容；
4. **必须读原文**——含义在语气和上下文里，关键词扫描看不到偏好与习惯，禁纯关键词匹配收工。

**产出**：追加进 `信号/YYYY-MM.md`，同时把清单呈给用户过目（不确认不用于建模，见 ②）。

### ② 建模（偏好库三决策）

1. 候选偏好 = 信号的聚合提炼（同类信号 ≥2 条才立条；孤条先挂「观察中」）。
2. 与既有偏好逐条比对，三选一：
   - **新建**：无既有条目可归 → 建条（模板 `assets/preference-entry-template.md`）；
   - **合并**：与既有条目同指 → 强化原文证据链 + 更新频次，不重开条目；
   - **跳过**：与既有条目矛盾且新证据不足 → 不动，信号留在月志等下次。
3. **硬约束（2026-09-11 用户约定）**：沉淀结果必须完整展示——条目标题、证据原文、偏好正文逐条可见，正文超长可折叠；**不允许只报「已入库 N 条」**。
4. 偏好库是持久知识层：每次读-更新-写回；条目带状态（生效/观察中/已过时——用户行为变了要标过时，不删历史）。

### ③ 触发（判据攒证据）

任一满足 → 该 skill 进进化候选队列：
1. 同一 skill 的相关信号 **≥3 条**且指向同一矛盾；
2. 偏好库任一「生效」条目与 skill 现行行为**冲突**（skill 说的做的与用户偏好相悖）；
3. 用户点名「进化/优化 XX 让它更懂我」；
4. Skill-Optimizer 模式③内部调用；
5. 定期兜底：距上次进化 ≥2 周 或 新信号 ≥20 条（建议值，写报告提醒即可）。

### ④ 诊断（读轨迹定因）

对每个候选 skill：
1. **必读轨迹原文**——该 skill 相关的会话记录 / 日志 / 产物前后对比，定位「为什么不合用户意」，禁止只凭结果好坏下结论（产出对不代表过程对，过程对也可能花冤枉 token）；
2. 对照偏好库：矛盾点 = 哪条偏好在哪步被违反 / 缺失；
3. 对照 `issue/` 池：是否已有同因 issue（有则合并处理，避免双轨）；
4. 结论：改 skill 的哪一层（触发描述 / 主流程步骤 / 护栏清单 / references 下沉）。

### ⑤ 方案与确认

产出**进化建议单**，每条必含：
- 目标 skill + 具体位置；改动内容（old → new）；
- 依据信号（偏好条目编号 / issue 编号 / 轨迹原文片段，三者至少其一）；
- 预期效果 + 风险；
- old-vs-new 能力审计：改动前记录能力清单，改动后核对无「丢功能 / 加未声明行为」；
- 回滚方式（git revert + 台账记录）。

**护栏五条（过不了不出单）**：
1. 语义不漂移——改前写下 skill 一句话定位，改后核对未变；
2. 体积不膨胀——SKILL.md ≤500 行红线，进化优先以删代增；
3. 能力不丢——old-vs-new 审计通过；
4. 确认后改——标准档逐条确认，激进档仅 P2 免确认；
5. 留痕可回滚——台账 + git + CONTEXT D-xx。

呈单给用户逐条裁决（执行 / 改方案 / 挂起）。**未经确认不落盘源文件**。

### ⑥ 执行与留痕

1. 改目标 skill（SKILL.md / references / assets）；
2. 目标 skill `CONTEXT.md` 追加 D-xx（改了什么、依据哪条信号）；
3. 信号源自 issue 的 → 回填 issue 状态 `已沉淀` + 落点；源自偏好的 → 偏好条目标「已反哺 <日期>」；
4. `进化台账.md` 追加一条（模板 `assets/evolution-log-entry-template.md`）；
5. 同步安装副本：先源仓库，再拷贝到 `C:\Users\15136\.codebuddy\skills\Skill-Evolver\` 等同名目录，哈希校验（对齐 Skill-Optimizer §七.3）；
6. 更新增量标记，报告本轮进化摘要。

## 五、Agent 复用接口

采集与偏好库环节与宿主无关：任意 Agent 提供「会话/日志路径或粘贴内容」→ 本 skill 产出该用户的偏好画像 + 信号清单（格式同 §三①②，落同一集中池）。宿主只需能读markdown；不依赖 ZCode 专有工具。

## 六、铁律

1. **信号可回溯**：每条信号/偏好/进化必带原文证据，无证据不采集、不建模、不进化。
2. **读原文**：采集与诊断都必须读原文，禁纯关键词扫描收工。
3. **可见性**：偏好沉淀完整展示给用户，禁只报数量。
4. **确认后改**：默认档位下未经用户确认不动任何 skill 源文件。
5. **语义不漂移 + 体积红线 + 能力审计**：三护栏任一不过不出方案。
6. **留痕可回滚**：每次执行必有台账 + git 提交 + CONTEXT D-xx。
7. **增量不重扫**：增量标记驱动，只处理新内容。
8. **不双轨**：偏好类信号进本 skill 池，方法论问题进 issue 池，界限不清时问一句「这是用户的稳定偏好吗」——是则本 skill，否则 issue。

## 七、常见错误对照表

| 错误 | 纠正 |
|---|---|
| 关键词扫一遍聊天就称「已挖掘」 | 必须读原文，含义在语气与上下文里 |
| 只报「沉淀 N 条偏好」不给内容 | 逐条展示标题+证据+正文 |
| 单条信号就立偏好/就进化 | 同类 ≥2 才立条；≥3 且同矛盾才触发 |
| 只看产出好坏下诊断结论 | 读轨迹原文定位为什么 |
| 进化改了 skill 定位 | 改前一句话定位，改后核对 |
| 确认前就改源文件 | 标准档逐条确认后执行 |
| 改完不留台账/不同步副本 | 台账 + git + D-xx + 哈希校验同步 |
| 把用户一时抱怨当稳定偏好 | 观察中状态 + 频次证据，反复出现才生效 |
| 偏好与 issue 双轨重复记录 | 按铁律 8 分流，同因合并处理 |
