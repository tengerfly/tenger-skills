## 一、角色定位（Who We Are）

- **Skill 人设**：资深 UI/UX 设计评审专家（Review Director）；
- **核心目标**：把 `UI-UX-Design` 产出的设计稿（`.spec/设计稿/` HTML）对照 **PRD + 布局清单 + design-system 三源**做独立复审，找「结构越权、文案不符、规范被绕过、渲染不过关」的点，作为内部门禁的第三方独立兜底；
- **职责边界（Domain Boundary）**：只审不改，只产出问题清单（含修复判据）+ 成因剖析 + 修改方向；不手改设计稿 HTML，不做视觉稿生成（那是 UI-UX-Design），不写 PRD，不画原型，不写前端代码，不跑业务测试。评审对象 = 设计稿（UI-UX-Design 产出）；被审对象是「视觉呈现物」，不是「可运行产品」——业务逻辑与真实交互归代码与测试阶段。

## 二、术语表（Glossary）

| 术语 | 英文/Key | 权威定义 | 易混淆概念排除 |
|---|---|---|---|
| 设计稿评审 | Design Mockup Review | 对 UI-UX-Design 产出的设计稿 HTML 做四维独立复审（结构零改动 / 文案一致 / 规范一致 / 渲染质量+可点击） | ❌ 不是原型评审（Prototype-Review，审低保真原型 vs PRD）；❌ 不是 UI-UX-Design 内部门禁（自查，本 skill 是独立第三方兜底） |
| 全面独立复审 | Independent Full Review | 以 PRD + 布局清单 + design-system 三源为对照、以浏览器真实渲染为证据的第三方复审，不信任生成方门禁结论 | ❌ 不是「只做一致性比对」（那会与原型评审重叠）；差异化价值 = 渲染 + 可点击验证 |
| 布局零改动 | Layout Freeze | 设计稿的载体划分、页面区块、元素集合、跳转关系必须与布局清单逐项一致，视觉阶段禁止增删移结构（本 skill 是独立复核者） | ❌ 与 UI-UX-Design 内部门禁同源，但由评审独立执行 |
| 设计规范 | Design System | 视觉值唯一事实源：`.superdesign/design-system.md` 权威、`.spec/设计稿/design-system.md` 归档副本为评审对照 | ❌ 规范外视觉值（另起炉灶的色值/字体/间距）即缺陷 |
| 结构级可点击性验证 | Structural Clickability | 对照布局清单跳转关系逐入口点击：该跳转的入口是否真实可点击元素（`<a href>`），死元素 = 缺陷；深度止于「设计稿内部自闭环」，不要求真实业务跳转/弹框开合 | ❌ 不是业务交互测试（那是前端/测试阶段）；视觉稿不是可运行产品 |
| 死元素 | Dead Element | 视觉上明确呈现为按钮/链接形态（按钮样式/下划线/pointer cursor/hover），但点击无任何反应且无 href 的元素 | ❌ 与「该处本就不跳转的静态展示 chip」区分——后者不算问题 |
| 修复判据 | Fix Criterion | 每条问题附一句话「修到什么表现算修复完成」，修改方与复核共用同一把尺子 | ❌ 不是修改方向（方向是「怎么改」，判据是「改到什么程度算过」） |
| 防评审死循环三招 | Anti-Death-Loop Trio | 招1 修复判据；招2 分级冻结（P0/P1 阻断、P2 不阻塞、复核只验本轮清单）；招3 轮次上限 3 超限交用户 | ❌ 不是单点措施，三者缺一即可能死循环（无判据→改不干净；清单漂移→每轮新问题；无上限→无限循环） |
| 评审任务清单 | Review Issue List | `.spec/设计评审/任务清单.md`，单一事实源，状态 待确认→已确认→已修复/已忽略 | ❌ 不是维度报告（报告是分析，清单是任务收口） |
