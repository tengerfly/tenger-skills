# 全方位优化检查清单（优化模式标准）

> 优化模式的固定标准：八维度逐项核验，先自优化（含修订标准）再优化目标 skill。**逐项走完，每项有结论（修 / 不修 + 理由），不凭感觉。**
> 维度二~六的判据来源 = `assets/skill-writing-standard.md`（编写规范）；维度八判据来源 = `assets/vibe-principles-mapping.md`（心法映射表）。

## 使用前提

1. 优化对象 = 本 skill（Skill-Optimizer）时，先检查六份标准本身是否有 issue 待修 → **先修标准，再用修订后的标准执行本次优化**；
2. 优化对象 = 其他 skill 时，先确认本 skill 自身无 P0 未修项（有则先自优化）。

## 维度一：问题修复（issue 驱动）

- [ ] 读 `../../../issue/<目标skill>/` 全部「待处理 / 处理中」项，按等级排序（P0 → P1 → P2）
- [ ] 逐条修复：改 SKILL.md / references / assets 对应位置
- [ ] 每条修复后回填：状态 → `已沉淀` + 沉淀目标 + 沉淀位置
- [ ] 不修的条目：状态 → `已忽略` + 理由（须向用户说明）

## 维度二：入口·触发精准（判据见编写规范 §一）

- [ ] description 说清 what + when 两件事
- [ ] 关键词轰炸四维齐备：核心能力 / ≥5 动作动词 / ≥5 对象名词 / 自然口语短语
- [ ] 唯一触发短语计数：<3 弱 / 5~8 好 / >10 优
- [ ] 与其他 skill 触发词不重叠（重叠时写出差异化场景）
- [ ] 不遗漏能力、不过度承诺
- [ ] 「何时使用」只在 description，正文无残留的 When to Use 章节

**量化 eval（触发准确率，用户点名触发问题或 description 改动后必做）**：
- [ ] 生成 ~20 个触发样本：该触发（正例）/ 不该触发（负例）各 8~10 条，60/40 训练/测试划分
- [ ] **负例取「近似项」**：与技能共享关键词 / 概念、但实际该走别的技能或该由模型直接做——别用明显不相关的（「写个斐波那契」对 PDF 技能测不出任何东西）
- [ ] **样本要有实质复杂度**：模型只对无法轻松搞定、多步或专业化的任务才查技能；「读这个文件」这类一步查询即便描述匹配也不会触发，不适合当样本
- [ ] 每条查询跑 **3 次**取稳定触发率（单次会骗人）
- [ ] 盲测：仅凭触发词判断是否该调起本 skill（不让模型看 description）
- [ ] 分析假阳（不该触发却触发）+ 假阴（该触发没触发），逐条记录
- [ ] 迭代调 description，最多 5 轮；**按测试集分数选最优版**（按训练集选会过拟合）

## 维度三：省·上下文体积（判据见编写规范 §二）

- [ ] **SKILL.md ≤ 500 行（硬红线）**：超限强制下沉 references，正文留一句入口
- [ ] references 按**领域**组织（非按类型）、只嵌套一层、可从 SKILL.md 直达
- [ ] 大文件（>100 行）顶部有目录（TOC）
- [ ] 每个 reference 在 SKILL.md 的**对应步骤**标注何时加载（不是开头一次性列）
- [ ] 同一规则不在 SKILL.md 与 references / shared 重复定义（只活在一处，其余引用）
- [ ] 反复重写 / 需确定性的代码封装进 scripts/（不加载只调用）
- [ ] 只出现在产出里的素材进 assets/（永不读只引用）
- [ ] description 压缩到触发语义清晰的最短表述

**精简原则**：删冗余不删规则；下沉不删除；每处精简可追溯到具体位置。

## 维度四：准·指令写法（判据见编写规范 §三）

- [ ] **Iron Law 置顶**：frontmatter 之后第一条即铁律；单条、绝对措辞（NEVER/ALWAYS/MUST）、无回旋余地；针对「模型最可能犯的那**一个**错」
- [ ] Red Flag 是**撤退机制**（症状 → 回到第 N 步重查），不是又一份禁令
- [ ] 指令写成「该问的问题」而非「该找的答案」，并写明答案意味着什么
- [ ] 反模式清单来自「模型的懒惰默认是什么」的挖掘，逐条禁具体行为（非「不要写坏代码」）
- [ ] 自由度与脆弱度匹配（高：给目标 / 中：给偏好模式 / 低：写死命令参数，见编写规范 §3.5）
- [ ] 最可能犯的错：斩钉截铁的铁律放开头

## 维度五：稳·流程稳定（判据见编写规范 §四）

- [ ] 长流程有可打勾的工作流清单；复杂步骤用子步骤；条件步骤标 `(conditional)`
- [ ] 关键步骤标 `⚠️ REQUIRED`（绝不跳过）/ `⛔ BLOCKING`（不完成不许往下）
- [ ] 确认门覆盖四类触发：破坏性操作 / 高成本生成 / 基于分析落地变更 / 用户偏好影响输出
- [ ] 有交付前检查清单（Pre-Delivery Checklist），每条**看产物即可判真假**（反例「确保质量良好」/ 正例「无残留 TODO/FIXME」）
- [ ] 分析类 skill 给优先级分级（P0-P3），界定重点
- [ ] （可选）`$ARGUMENTS` + `argument-hint` 支持只跑局部（本仓库以自然语言驱动为主，确有场景才引入）

## 维度六：简洁不落俗（判据见编写规范 §五）

- [ ] 无空洞承诺性措辞（「确保高质量」「力求完美」「无缝」「赋能」等）
- [ ] 无套话开场 / 收尾 / 过渡（「首先…其次…最后」「值得注意的是」「综上所述」）
- [ ] 无冗余引导语、无空泛强调副词堆叠
- [ ] 无 emoji 滥用 / 加粗泛滥 / 为表格而表格
- [ ] 一句话能说清的不写三句
- [ ] 信息不重复：同一句话不在文件内出现两次以上
- [ ] **归位检查（防凌乱，判据见编写规范 §八）**：新增内容已归入「主流程某步 / 某类规范 §4.x / 铁律 / references」之一定位；无 `三·附`、`-附加`、`补充说明` 这类补丁式章节名；铁律 / 错误表 / 检查项三者在说同一件事时已合并

## 维度七：术语一致

- [ ] SKILL.md 与该 skill 的 CONTEXT.md 术语表无冲突
- [ ] 与仓库全局约定（根 README、跨 skill 机制如 issue 池 / 浏览器工具策略）无冲突

## 维度八：心法注入（判据见 `assets/vibe-principles-mapping.md`）

- [ ] 判断目标 skill 属于映射总表哪几类（输入 / 开发 / 规划 / 评审 / 产出 / 分析 / 自动化）
- [ ] 按所属类别，把对应心法落到 SKILL.md 的流程 / 铁律环节（落到执行步骤，不是贴表）
- [ ] 心法落地后不与其他维度冲突（如「做减法」与「稳·流程」的 Gate 不打架）

## 收尾动作（八维度全部完成后）

1. **old-vs-new 能力审计**：改动前记录目标 skill 能力清单（触发词覆盖、模式/维度、产出物、铁律），改动后逐项对比——确认无「丢功能 / 引入未声明行为 / 声称支持却没实现」；每项变更追溯到 issue / 核验发现；
2. **同步验证（强制）**：本次改动涉及的关键事实 / 术语 / 编号 / 旧词，对照 `assets/self-audit-checklist.md` 维度五做全仓 grep 清零 + 与 CONTEXT.md 术语表比对——「改一处、别处失同步」须在收尾前检净，清零才算完成；
3. 目标 skill 的 CONTEXT.md 决策日志追加一条 `D-xx`（改了什么、依据哪条 issue / 核验发现）；
4. 回填 issue 状态（已沉淀 / 已忽略）；
5. 输出优化摘要：改了哪些文件、为什么、依据是什么，逐项可追溯。
