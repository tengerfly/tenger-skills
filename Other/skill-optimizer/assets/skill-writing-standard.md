## 一、入口：description

模型只靠 frontmatter description 决定是否使用。须同时说清：

1. 做什么（一句话能力）。
2. 何时用（用户自然语言：动词 + 场景 + 同义表达）。

**关键词轰炸四维**（description 即「触发关键词网」，四维齐备才算够）：

| 维 | 内容 | 例 |
|---|---|---|
| 核心能力 | 第一句说清做什么 | 「代码评审（后端 + 前端，支持分端单批）」 |
| 动作动词 | 用户会说的动词 ≥5 个 | 评审 / 检测 / 审查 / 走查 / 检查 |
| 对象名词 | 用户会提到的对象 ≥5 个 | PRD / 原型 / 设计稿 / TDD / FTDD / 代码 |
| 口语短语 | 用户真会打的原话 | 「帮我 review」「看看这段代码有没有问题」 |

检查：用户最可能说的 3~5 种说法，description 是否都能命中；统计唯一触发短语 <3 弱 / 5~8 好 / >10 优。

**两条硬规则（都易犯）**：

1. **「何时使用」只能放 description，不许放 SKILL.md 正文**——正文在触发之后才加载，为时已晚。
2. **description 禁止剧透工作流**——只写触发条件，不写「怎么做」。
   > 实测：描述写了「任务间做代码评审」，agent 就只做了一次评审，而正文流程图要求两次；改成纯触发描述后，agent 才正确读了正文。**描述里总结流程 = 给 agent 一条跳过正文的捷径。**

对照：`❌ 用于 TDD——先写测试、看它失败、写最小实现、重构` / `✅ 用于实现任何功能或修 bug 之前，写实现代码之前`。

**「强势」倾向**：模型有「少触发」倾向——把该用的场景写进去，即使用户没提 skill 名。例：「凡是用户提到仪表盘、数据可视化、内部指标……就用这个 skill，哪怕他没说『仪表盘』」。

## 二、省：上下文是公共资源

硬红线：SKILL.md ≤ 500 行；超出拆走，正文只留入口。

**四级加载模型（渐进式披露，L1~L4）**：

| 层 | 内容 | 加载时机 |
|---|---|---|
| L1 元数据 | frontmatter（name + description） | 决定是否触发，最先加载 |
| L2 指令 | SKILL.md 正文（流程/铁律） | 触发后加载，常驻 |
| L3 引用 | references/ 知识 | 按需加载，不预载 |
| L4 脚本 | scripts/ 可执行代码 | 不加载，只调用 |

规则：反复写的代码进 scripts；反复读的知识进 references；只进产物的进 assets。

**references 组织四条**：

1. **按领域组织，不按类型**（`palettes/`、`renderings/` 优于 `checklists/`、`templates/`）——用户只取一个领域时只加载那一个文件。
2. **只嵌套一层**，全部可从 SKILL.md 直达。
3. **每个文件在 SKILL.md 标注「何时加载」**（写在那一步里，不写开头）。
4. **大文件（>100 行）顶部加目录（TOC）**，让模型先预览范围。

**信息单一归属**：同一规则只活在一处，其余位置只写引用（`见 ../../../shared/xxx.md §Y`）；SKILL.md 与 references 之间不得重复定义。

**交叉引用写法**：

- ✅ 写明依赖强度：`**REQUIRED SUB-SKILL：** 用 X` / `**REQUIRED BACKGROUND：** 必须先理解 Y`；
- ❌ 不用 `@path/SKILL.md` 这类**强制立即加载**语法——那会在需要之前烧掉大量上下文；
- 引用只给路径与「何时读」，不给全文复述。

## 三、准：引导注意力

| 脾气 | 症状 | 对策 |
|---|---|---|
| 泛泛说废话 | 注意力不聚焦 | 写「该问的问题」，不写「该找的答案」 |
| 默认模式改不掉 | 每次都犯同一错 | 禁令清单逐条点名反面教材 |
| 压力下走捷径 | 改改试试 | 铁律 + Red Flag 放开头 |

### 3.1 Iron Law（铁律置顶）

问自己：**「模型用这个 skill 时最可能犯的那一个错是什么？」**——写一条规则阻止它，放在 frontmatter 之后最顶部。

写法要求：单条、全大写强调、绝对措辞（NEVER / ALWAYS / MUST）、无回旋余地（禁「尝试」「尽量」「考虑」）。

| 领域 | Iron Law 示例 |
|---|---|
| Bug 诊断 | 未完成根因调查前，禁止给出修复。 |
| 测试 | 没有失败的测试，禁止写生产代码。 |
| 完成声明 | 没有新鲜的验证证据，禁止声明完成。 |
| 评审 | 只审不改——问题进清单，改动归产出方。 |
| 库迁移 | 每个迁移脚本必须有回滚脚本；没有回滚就不执行。 |

### 3.2 Red Flags（撤退信号）

铁律配「症状清单」，让模型识别自己正在漂移并**回退到指定步骤**——这是「回滚机制」，不是又一份禁令。

```markdown
Red Flags（命中任一即回到第 1 步重查）：
- 「我猜问题可能是…」（在猜，不是在分析）
- 还没搞清根因就开始改代码
- 改完能跑但说不清为什么能跑
```

### 3.3 问题式指令

给具体问题，不给模糊指令；并写出**答案意味着什么**。

| 模糊指令（坏） | 问题式（好） |
|---|---|
| 检查是否违反单一职责 | 问：这个模块有几个必须修改它的理由？超过一个，多半违反 SRP |
| 注意竞态条件 | 问：两个请求同时到达这段代码会发生什么？ |
| 处理好边界情况 | 问：这个值是 null 会怎样？是 0？是空数组？是负数？ |
| 保护好这一对操作 | 问：从检查权限到执行动作之间，状态可能被改掉吗？ |

### 3.4 懒惰默认值挖掘法

反模式清单不是凭空写——问：**「模型在这个任务上的懒惰默认长什么样？」**然后明令禁止。例：多余 try-catch + console.log、一次性逻辑过度抽象成工具函数、复述代码的注释、为不会变的配置建配置项、AI 味配色与套话。

### 3.5 自由度匹配脆弱度

指令的松紧随操作脆弱度调整，不一刀切：

| 自由度 | 场景 | 写法 |
|---|---|---|
| 高（纯文本） | 允许多条有效路径 | 给目标与约束，不规定路径 |
| 中（伪代码 / 参数） | 有偏好模式、容许变化 | 给推荐模式 + 允许偏离条件 |
| 低（具体脚本 / 脆弱操作） | 一致性至关重要 | 写死命令与参数，不给替代方案 |

- 引导式提问：面向思路狭窄的用户要当思路放大器——竞品/参考引导、「问题 + 2~3 选项 + 例子」、专家视角纠偏，不照单全收。

### 3.6 形式必须匹配失败类型（最易搞反）

写规则前先判断基线失败属于哪类；**用错形式会让效果变差**：

| 基线失败 | 正确形式 | 错误形式 |
|---|---|---|
| 压力下违反规则（知道却犯） | 禁令 + 借口对照表 + Red Flags | 软建议（「优先…」「考虑…」） |
| 遵守了，但输出形状不对（啰嗦、结论埋在中间、复述需求） | **正向配方/契约**：说清输出「是」什么、由哪些部分按什么顺序组成 | 禁令清单（「不要复述」「禁止啰嗦」） |
| 漏掉某个必备要素 | **结构性**：在它要填的模板里加 REQUIRED 字段/槽位 | 模板旁边写散文提醒 |
| 行为应随条件变化 | **条件式**：绑定可观察的谓词（「若简报存在则引用它」） | 无条件规则 + 豁免条款 |

**两条附加铁律**：

- **不留「细微差别条款」**：`不要 X，除非重要` 会把规则重新变成可谈判；真例外要写成独立的条件式。
- **豁免条款不生效**：`此限制不适用于代码块` 仍会压制代码块；要么重构让规则触及不到，要么别写。

### 3.7 纪律型用铁律，技术型讲道理

同一条准则在不同技能类型下写法不同（与 3.6 同源）：

| 类型 | 写法 | 例 |
|---|---|---|
| **纪律型**（守规则类：测试先行、证据门禁、根因调查） | Iron Law + 借口对照表 + Red Flags；绝对语言 | 「没有失败的测试，不许写生产代码」 |
| **技术型 / 参考型**（怎么做类：写代码、设计、文档） | **解释「为什么」**，给判据与示例；避免僵硬 MUST | 「测试难写说明设计难用——先简化接口」 |

> **自查**：如果你发现自己在技术型技能里通篇写全大写 ALWAYS/NEVER，先停下来——多数情况改成「讲清理由 + 给判据」效果更好、更耐久。

### 3.8 流程图只用于该用的地方

- **用**：非显然的决策点、「A vs B」选择、可能提前停止的流程循环。
- **不用**：参考资料（用表格/列表）、代码示例（用代码块）、线性步骤（用编号列表）、无语义标签（step1/helper2）。

## 四、稳：流程立稳

1. 工作流清单：关键步骤标 ⚠️ REQUIRED / ⛔ BLOCKING，复杂步骤用子步骤（1.1 / 1.2），条件步骤标 `(conditional)`。
2. 确认节点 Gate：需拍板点逐条编号列清单一次性呈现，确认后记结论，未确认不推进。
3. Pre-Delivery Checklist：定义怎么算做完。
4. 优先级分级：P0-P3 让模型知道重点。

### 确认门（Gate）四类触发——命中任一必须停下问

1. **破坏性操作**：删除 / 覆盖 / 修改已有产物；
2. **高成本生成**：烧额度、跑长任务、外部付费调用；
3. **基于分析落地变更**：分析出了建议，要动手改之前；
4. **用户偏好影响输出**：风格、范围、取舍由用户口味决定时。

**批准的重量不随任务简单度缩放**：任务越简单，产物（设计/说明）越短，但「先说意图 → 等批准 → 再动手」这一步不省。经验上，简单任务恰恰是未经检验的假设浪费最多的地方。

### Pre-Delivery Checklist 判据：可验证

每条必须具体到「看产物就能判真假」，否则不算检查项：

| 坏（不可验证） | 好（可验证） |
|---|---|
| 确保质量良好 | 无残留占位符（TODO / FIXME / xxx） |
| 注意可访问性 | 所有图片有 alt 文本 |
| 做好样式 | 所有可点击元素有 cursor-pointer；过渡 150~300ms |

按类别分组（正确性 / 质量 / 完整性），每条独立可勾。

参数系统（可选）：`$ARGUMENTS` + `argument-hint`，支持只跑局部。本仓库以自然语言「跳过 X / 只跑 X」为主，仅在确有斜杠调用场景时引入。

## 五、简洁不落俗

AI 写的 skill 天然臃肿，做完只做减法。

删除：空洞承诺（确保高质量/力求完美/无缝/赋能）；套话开场收尾过渡；冗余引导语；副词堆叠；emoji 滥用、加粗泛滥、无信息表格。

简洁判据：一句话能说清不用三句；删不承载信息的词；优先动词短语。

**禁口语化直接入 skill（硬标准）**：用户原话须提炼成简明准确可操作的专业表述再落笔；skill 全程简明扼要。

**信息不重复**：先说过的规则后面只引用不重述（判据：同一句话在文件中出现两次以上即冗余）。

**精简的正确做法**：删不承重的部分，但**读 transcript 而不只看产出**——如果 skill 让模型把时间花在无产出的事上，删掉造成那段行为的文字，再看结果。删内容与改内容一样要重测。

## 八、归位原则（防凌乱）

> **根因**：skill 是多轮吸收的产物。凌乱不是错别字，而是**每轮都把新内容追加到「最近的地方」**——在末尾补一节、加个「附」、塞进某步的最后一行，从不做归位。三轮吸收下来，清单淹没流程，读者要跳来跳去（`三·附` 就是典型标本）。

**四条规则**：

1. **先问归属，再落笔**。新内容进来前先判定它属于哪一类：
   - 主流程的**某一步** → 放进那一步（读者恰在这一刻需要它）
   - **某类规范 / 判据** → 放进 §4.x 对应领域
   - **红线**（最不能犯的错）→ 铁律，且只留 ≤8 条
   - **可查材料**（清单 / 模板 / 细则）→ 下沉 references，正文只留「何时加载」
   - 找不到归属 = 结构本身缺一类，**先补结构再写内容**。
2. **禁止补丁式章节名**。`三·附`、`模式③-附加`、`补充说明`、`其他`、`杂项` 这类名字是「没归位」的显式信号；确需新增章节时，纳入既有编号体系。
3. **三份清单分工**（同一件事不许说三遍）：**铁律 = 红线**（≤8 条，不重复章节内容）｜**常见错误对照表 = 易犯错 + 纠正**｜**§4.x 各条 = 判据 / DoD**。同一件事出现在两处 → 合并到「最该在」的那一处，另一处只留引用。
4. **被连续追加 3 次以上的小节**：说明它承担了多种职责 → 拆分，或把细节下沉 references。

**归位自查三问**（每次沉淀 / 吸收后过一遍）：

- 读者执行到**哪一步**时才需要这条内容？→ 放到那一步，或那一步引用的规范
- 它和现存的哪条**重复或冲突**？→ 合并到最该在的那一处，另一处留引用
- **删掉它，主流程会缺什么**？→ 说不清就是冗余，先删再看
