# Fact-Check —— AI 回答辨伪核验

> IRON LAW：**没有证据，不下判定**——每条断言的结论必须挂证据（实验输出 / 官方文档原文 + 链接 / 源码 `文件:行号` / 多独立源交叉）；查不到证据就诚实标 `❓ 未证实`，绝不因为「AI 说得很自信」就默认相信，也绝不把「再问一遍 AI」当验证。本条是仓库 `../../shared/evidence-before-claims.md`（自己声明的证据门禁）在「核验外部内容」上的对应物：那边管自己的声明，这边管别人的断言。
> **红线：查不到 ≠ 可以编**。确实不知道、网络上也搜不到 → 唯一合法输出是 ❓ + 说明原因；**为完成核验而编造证据（假链接 / 假文档引文 / 假实验输出 / 假「多源一致」）一次都不行**——那等于给错误盖了「已验证」章，比不核验更坑。
> 定位：AI 输出的**采纳前信任门禁**。用户拿到 AI 的方案/结论/知识点，在投入半天功夫照做或记进脑子之前，先把其中的事实断言过一遍证据关。只核验不重写：输出判定 + 证据链 + 修正版说法；不代写完整替代方案——那只是又一次待核验对象。

## 问题记录与恢复（执行必需）

发现失败、阻塞或用户纠正时，在下一安全节点按 `../../shared/problem-recording.md` 记录；根因未明不丢事实。恢复/交付前核对未决项，沿用已有详情与唯一索引。此规则优先于旧的仅收尾埋点/不确定不记表述，不增加轻量任务的正式建档要求。

## 一、为什么需要：AI 错误的五种常见形态

核验策略针对 AI 最常犯、用户最难自查的五种错误设计：

| 错误形态 | 典型样子 | 核验抓手 |
|---|---|---|
| 版本错位 | 给已废弃 API / 尚不存在的「新能力」，或记错用户版本 | 文档对齐用户实际版本；实验在用户版本跑 |
| 库记混 | 把 A 库的 API/配置安到 B 库头上 | 官方文档原文比对 + 本地 node_modules 源码 |
| 条件普适化 | 需特定前提（flag/平台/版本区间）才成立，说成总是成立 | 反证搜索 + 变化边界条件的实验 |
| 半真半假 | 框架正确、夹带一个错误细节（最骗人） | 拆原子断言逐条验，不做整体打分 |
| 一本正经编造 | 不存在的 API/参数/配置项/数据 | 官方源直接查证，查无此物即证伪 |

**观点/建议类**（「推荐用 X」「Y 是最佳实践」）不可证伪：不给真假判定，只列支持/反对的证据与权衡，并明说「这是权衡不是事实」。

## 二、流程：四步

### ① 拆解 —— 原子断言 + 承重标记

把待核验内容拆成**一条只说一件事**的原子断言，逐条标注：

- **类型**：`可执行`（代码/API/行为/配置效果）/ `文档`（语法/语义/标准）/ `事实`（版本支持/数据/史实）/ `观点`（建议/权衡）
- **承重**：错了会导致整个方案塌掉、或用户会直接照做/记走的断言——核验火力优先给承重断言，不平均用力
- **判定基准**：版本敏感断言以用户实际环境为准（在当前工作区就读 package.json 等拿真实版本；拿不到且影响判定 → 问，或按声明版本验并标注差异）

### ② 取证 —— 按证据层级选路径

证据可信度从高到低，**能往上够就往上够**：

| 层级 | 路径 | 适用 |
|---|---|---|
| L1 可执行实验（金标准） | 最小 PoC：`node -e` / 临时脚本 / 最小 HTML / 小测试用例，系统临时目录跑、跑完清理 | 可执行类断言——跑一遍胜过读十篇文档 |
| L2 官方文档 / 规范原文 | 官方 docs / MDN / RFC / 官方仓库 README + CHANGELOG | 文档类、事实类断言 |
| L3 源码 | 本地 node_modules / GitHub 源码搜索 | 库行为断言（文档没写清 / 疑似库记混） |
| L4 多独立源交叉 | ≥2 个**互相独立**的权威源一致 | 冷门事实（无单一官方出处） |

取证三规矩：

1. **先定判据再跑实验**：动手前写清「输出什么算对、什么算错」，防跑完再编理由。
2. **反证搜索必做**：每条断言除找正证外，主动搜反例（`<关键词> + not working / gotcha / deprecated / breaking change`）；命中反证必须处理（降 ⚠️ 或 ❌），不许绕开。
3. **独立源才叫交叉**：多篇博客一致 ≠ 证据（SEO 互抄常见）；「官方文档 + 可执行行为 + 源码」才是真独立。**同一个 AI 的自我确认（「你确定吗」→「我确定」）不是证据**——它会自信地重复甚至编新理由。

配套规则：

- **版本对齐**：官方文档站默认展示最新版，用户可能在旧版——判定注明「依据版本 X 的文档/实验；你的版本 Y 注意 Z」。
- **CSS/渲染类断言**：环境里有浏览器工具就搭最小页面截图验证（增强项，非硬依赖）；没有则退 L2/L3。
- **网络不可用**：L1/L3（本地实验/本地源码）照常可用；纯文档类断言只能标 ❓ 待网络恢复，不降格为猜测。
- **源码导读类产物**（带 `文件:行号` 锚点的文档，如 Source-Reading 产出）：L3 = 锚点「行号+内容」双匹配批量核验（`grep -nF` 逐条对行上内容，只核「行存在」不算验）；官方数据类断言对发布说明/blog 取原文；发现锚点不精确（挂在阶段入口而非调用点）或内容级错误（如"已废弃的机制其实还在用"）→ 判定后**回写修正原产物**并在报告记录修正清单（2026-09-19 react/vue3 两轮实测：各抓出 2 处锚点不精确 + 1 条内容级 ❌）。

### ③ 判定 —— 四值 + 证据链

每条断言按此格式出结论：

```
[✅|⚠️|❌|❓] 断言原文
  证据：实验输出 | 文档引文 + 链接 | 源码 文件:行号 | 独立源列表
  ⚠️ 时：边界条件（版本/环境/前提，一个不能省）
  ❌ 时：修正版说法（同样要挂证据）
  ❓ 时：说明原因（查了哪些源/关键词、为何拿不到证据）+ 下一步怎么验（要跑的命令 / 要查的文档入口）
```

- ✅ **证实**：有正证且反证搜索未命中
- ⚠️ **条件成立**：特定前提下方成立——必须写清边界；这是 AI 错误里最常见的一类
- ❌ **证伪**：有明确反证——给修正版说法，修正版自身也要过证据
- ❓ **未证实**：证据不足或无法本地复现——诚实标注并**说明原因**（确实不知道 / 网络搜不到 / 实验跑不了 / 文档打不开，查了什么、在哪查的）；**宁 ❓ 不猜**——「查不到」既不等于错误也不等于正确，更不等于可以编一个结果

### ④ 报告 —— 就地或落盘

- **轻量**（单条/几条断言，如一个知识点）：对话内直接给判定结论。
- **正式**（整篇方案/长回答/多轮核验）：落盘 `.spec/事实核验/YYYY-MM-DD-<主题>.md`：TL;DR（承重断言结论表 + 可否放心采纳）→ 逐条判定明细 → 未证实清单与后续动作。

**不给「综合可信度评分」**：半真半假的内容综合分没有意义。总评只按承重断言表述：**承重全 ✅ → 可采纳；任一承重 ❌/⚠️ → 先处理该条再动手；承重 ❓ → 该条没验透之前不动手。**

## 三、铁律

1. **没有证据不下判定**（IRON LAW，见页首）。
2. **禁止编造核验（红线）**：确实不知道、网络搜不到、实验跑不了 → 唯一合法输出是 ❓ + 说明原因（查了什么、在哪查的、为何没结果）；绝不为了让报告「完整/好看」而编造出处、引文、实验输出或「多源一致」。❓ 是合法结论不是失败——一次诚实的 ❓ 好过一次漂亮的假 ✅。
3. **L1 优先**：能跑的先跑，跑不动才退 L2/L3/L4；实验环境贴近用户环境。
4. **只核验不重写**：输出判定与修正版说法；承重断言 ❌ 后的完整替代方案交 Backend/Frontend-Tech-Design（那又是一轮「方案 → 核验」）。
5. **四值判定，宁 ❓ 不猜**。
6. **每条必做反证搜索**：只找正证只完成一半，天然偏确认偏误。
7. **修正版同样要挂证据**：❌ 的修正说法不能又是一个无证据断言。
8. **收尾沉淀判定**：本轮发现典型 AI 错误模式（新式版本错位/库记混案例）→ 提示用户可沉淀到仓库根 `../../bug-patterns/` 集中池（与 Bug-Fix 同池）或记入 memory；用户确认才落，不强制。

## 四、输入与边界

**输入**：粘贴的 AI 回答 / 口述方案要点 / 一个知识点 + 疑问。用户环境信息（版本号、package.json、工作区路径）有则用、无则问或标注假设。

**边界**：

- 已写完代码的验收测试 → `auto-test`
- 代码质量 / 契约一致性评审 → `Code-Review`
- 技术方案文档（TDD/FTDD）的结构与闭环评审 → `Tech-Review`
- 完整竞品/市场分析 → `Competitive-Analysis`（其中的竞品数据断言可单独拿来核，属事实断言）
- 本 skill 只管**断言对不对**：一个说法、方案里的关键事实假设、一个知识点；不审文档结构、不跑项目级测试、不重写完整方案
- 链外独立 skill，不占主链 14 节点；主链产出的方案若用户要求「先核验再采纳」，可在评审节点前插入本 skill
