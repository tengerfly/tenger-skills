# 自洽检查清单（模式④ 体检标准）

> 模式④ 的固定标准：把目标 skill 当产品查 bug——七维逐项核验（机械 grep + AI 通读双通道），每条发现必须有**位置 + 现象 + 修复方向 + 修复判据**，不凭感觉。
> 范围默认 = 目标 skill 全套文件 + 其在全仓的交叉引用；也可全仓逐 skill 体检。

## 使用前提

1. **定位目标 skill（三方式）**：显式路径（用户给出目录）/ 当前目录上下文（用户已在某 skill 目录内）/ 名称匹配（按用户称呼在工作区搜索同名 skill 目录）；三者都不明确时按上下文推断并**向用户确认**；
2. 读全目标 skill 文件：SKILL.md / README.md / CONTEXT.md / assets/* / references/*；
3. 记录 **SKILL.md 行数**（关键指标）；
4. 交叉引用范围：根 README.md、../../WorkFlow/（若被链引用）、其他 skill 对该 skill 的引用、../../issue/ 池、../../chats/（若提及）。

## 七维核验（逐维走完，每项有结论）

### 维度一：术语·命名一致（A 与 A1 是同一个吗）

- [ ] 同一概念在全文是否有同指异名（A / A1 / 多种叫法）、中英混用、大小写不一致 → 建「概念-叫法」映射并标推荐名
- [ ] 与 CONTEXT.md 术语表逐条比对（术语表是权威对齐源）：正文 / README / references 的叫法与术语表冲突？
- [ ] 全仓对同一文件的叫法是否一致（例：`页面清单.md` 旧称是否仍残留在业务文件中）
- [ ] 机械核验：术语表每个术语 grep 一次，记录命中文件；标「废弃 / 已撤销」的旧术语是否仍在业务文件中出现（历史决策记录除外）

### 维度二：逻辑闭环（断头 / 悬空）

- [ ] 悬空引用：正文「见 §X / 见 3.2 / 见 D-xx / 见第 X 步」→ 目标存在且标题 / 编号对得上
- [ ] 文件引用：正文、资源清单提到的 references / assets / 模板文件实际存在；反过来说存在的文件是否被正文引用（孤儿文件）
- [ ] 承诺-落地：宣称「有检测 / 有 Gate / 会提示用户」→ 流水线或步骤里确有对应动作；声明「不做什么」是否真有对应拦截
- [ ] 产物闭环：每个步骤产出物是否被下一步消费；落盘路径与仓库目录约定一致
- [ ] 枚举一致：并列项数量前后一致（铁律 X 条、标签 X 个、维度 X 维、模式 X 个、步骤数、X 份标准等）
- [ ] frontmatter 与正文能力一致；流水线图与正文步骤一一对应
- [ ] **声明-承接**：本 skill 声明「必须有 / 必做」的产物节、字段、清单项，是否在其 assets 模板与 references 里真实存在（**SKILL 声明有、模板未承接 = 断头**）
- [ ] 与全仓事实一致：本 skill 提到的跨 skill 协作（谁改、往哪回填、产物路径）与仓库约定一致（评审闭环映射 / .spec 目录 / 浏览器依赖组 / Workflow 链）
- [ ] **中央约定不重复**：`../../shared/*.md` 已声明「唯一权威 / 不得重复定义」的规则（检测顺序、两级行为、报错文案、门禁轮次口径、双基准术语、分级定义），逐一全仓 grep 各 skill 是否**只引用不复制**；重复定义处清零

### 维度三：文句质量

- [ ] 病句、成分残缺、读不通的句子
- [ ] 错别字、术语笔误（如 `browser-user` vs `browser-use`、`@viTest` vs `@vitest` 类）
- [ ] 模板占位符未替换（`<Skill-Name>`、`YYYY-MM-DD`、`{{VERSION}}` 等残留）
- [ ] 半截话、被截断的清单、重复段落

### 维度四：声明-流程一致（依赖与处理匹配）

- [ ] 凡声明「硬依赖 / 前置条件 / 必须 X / 需要 Y 工具」→ 流程里必须有对应「检测 → 阻塞/跳过 → 报错文案」步骤；找不到即缺陷（例：说要求浏览器插件却没有硬门禁）
- [ ] 反之：流程里有「检测 X / 处理 X 不可用」→ 前置声明处是否讲清（防只有流程没有声明）
- [ ] 软硬分级与全仓策略一致（浏览器工具两级策略：硬依赖 vs 软检测，对照根 README 分组）
- [ ] 「可选 / 跳过 / 降级」表述与实际分支一致（说跳过就真能跳过，说硬性就真会停）

### 维度五：跨位置同步（迭代失同步）

- [ ] 列出本次涉及的关键事实 / 数值 / 术语（编号、链节点、目录名、文件引用、版本约束等）
- [ ] 每个关键事实全仓 grep，比对所有命中位置是否一致（只改一处 = 检出）
- [ ] **范围引用同步（2026-09-17 沉淀）**：扩展清单 / 枚举（新增组、节、条目、档位）后，全仓 grep 所有「范围引用」并同步（如「A~M 组」「12 条」「六查」「N 维」）——只扩清单不改上级引用 = 失同步
- [ ] **同批吸收后跨文件口径比对（2026-09-17 沉淀）**：一次多文件吸收 / 批量改动后，对同类数值与口径（时长、阈值、档位、编号）做一次跨文件 grep 比对，防「同一规则多处表述不一」（如「<300ms」与「200-500ms」张力）
- [ ] 决策日志 D-xx 与正文状态一致（正文说的编号 / 名称与 CONTEXT 决策一致）
- [ ] description（frontmatter）与正文能力 / 触发词一致
- [ ] SKILL / README / CONTEXT 三件套对同一事实描述一致（本仓库最常失同步处：节点编号、评审节点、浏览器依赖组、skill 数量、产物目录、**轮次超限口径、设计稿/原型基准归属**）

### 维度六：简洁不落俗 / 文风（AI 味排查）

- [ ] 空洞承诺性措辞：`确保高质量` `力求完美` `极大地提升` `无缝` `赋能` `很好地` 等无法检查的形容词
- [ ] 套话开场 / 收尾 / 过渡：`首先…其次…最后` `值得注意的是` `综上所述` `不难发现` `下面我们来`
- [ ] 冗余引导语：`需要说明的是` `这里要强调的是` `正如前面提到的`
- [ ] 空泛强调副词堆叠（`非常` `极其` `充分` `全面` 连用）
- [ ] emoji 滥用、加粗泛滥、为表格而表格（无信息量的堆砌）
- [ ] 冗余表述：一句话能说清却写三句
- [ ] 信息重复：同一规则在 SKILL.md 与其 references / shared 中重复定义（应只活在一处，其余引用）

> 收尾提示：优化模式改完任何文件后，把本维度作为**强制收尾验证**执行（旧词 / 数值清零），防「只改一处、别处失同步」。

### 维度七：安全审计（危险指令 / 凭据 / 依赖 / 外联）

> 依据：skills-security-check、daymade security_scan.py（gitleaks 硬门禁）、浙大 agentskills 论文（42,447 技能 26.1% 有漏洞，带脚本漏洞概率高 2.12 倍）。

- [ ] 危险/破坏性指令：`rm -rf`、`curl | bash`、`Start-Process -WindowStyle Hidden` 跑删除、格式化/覆盖磁盘、镜像式清理（`robocopy /MIR` 无 `/XJ`）等——须有明确安全约束或禁止
- [ ] 硬编码凭据：API key / token / 密码 / 密钥明文出现在 SKILL.md / references / scripts 中
- [ ] 外联风险：脚本静默外发数据 / 访问不明远程地址 / 安装未声明依赖
- [ ] 依赖风险：脚本依赖的外部工具/包是否安全、是否声明版本
- [ ] 带脚本的 skill 重点查（漏洞概率更高）：scripts/ 内容逐行过一遍危险操作与凭据

## 输出（先优点，后清单）

**先列「做得好」≥2 条**：引用具体行 / 具体做法（禁填充式恭维）——即使 skill 较弱也要找出可救之处。这不是客套：写清「哪条做法在起作用」，才能保证后续修改不把它改坏，也让用户知道哪些能力是已验证资产。

再出问题清单，每条含：`# | 等级 | 维度 | 位置（文件/节） | 现象 | 修复方向 | 修复判据`

- 等级：P0 = 阻断性 / 明显错误（引用断裂、术语冲突影响执行）；P1 = 不一致但不阻塞；P2 = 轻微（文句 / 建议）
- 修复方向：改哪份文件哪个位置、怎么改（**只说「可以优化」= 不合格**）
- 修复判据：怎么算修好了（改后应达到的状态，如「旧称全仓 grep 清零」）

## 处理后闭环

1. 问题清单**逐条向用户裁决**：当场修 / 记 issue（来源=体检，按 issue-template 落 `../../issue/<skill>/<日期>/`）/ 忽略（说明理由）；
2. 当场修的每条 → 目标 skill CONTEXT.md 决策日志记一条 `D-xx`；
3. 输出体检小结（查了哪些文件 / 发现几条 / 每条去向），与用户确认后收尾。

## 红线

1. **只出清单不改文**（除非用户对具体条目说「当场修」）；
2. 每条发现**必带位置**（可回溯），禁止无定位问题；
3. **零幻觉**：现象必须来自实际文件内容，机械核验有输出为准；
4. 与 issue 池 / 优化模式的区别：体检是「存量体检」，改动逐条经批准，不擅自进入优化。

## 元反模式（体检者自身要避免）

- 只给含糊赞美（「结构不错」）而不指出**具体**哪里有效；
- 只罗列问题不给可执行修复（修复方向 / 判据缺一即不合格）；
- 按**个人品味**审——判据须来自既有文档（编写规范 / 优化清单 / 本文）；
- 对简单 skill 建议**过度工程**（加流程、加文件、加 Gate）；
- 把 skill **有意省略**的功能当缺失（先判断「简洁」是否正是它的设计目的）；
- 过程已发现的问题**未全部进清单**（出清单前须回核准备笔记逐条过，防遗漏——2026-09-17 教训）。
