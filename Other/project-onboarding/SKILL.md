# Project Onboarding

## 问题记录与恢复（执行必需）

发现失败、阻塞或用户纠正时，在下一安全节点按 `../../shared/problem-recording.md` 记录；根因未明不丢事实。恢复/交付前核对未决项，沿用已有详情与唯一索引。此规则优先于旧的仅收尾埋点/不确定不记表述，不增加轻量任务的正式建档要求。

## Purpose

把一个新项目或陌生旧项目转成**可理解、可追踪、可交接、可继续交付**的工程基线。它是 `CREATE`、`CHANGE`、`DEFECT`、`REFACTOR`、`INCIDENT` 和 `OPTIMIZE` 的共同入口，尤其适用于旧项目接管。

## Trigger

触发于：

- 用户说“接手/接管/盘点/了解这个旧项目”，或“旧项目按现在工程体系重跑/接入新流程/流程补齐”；
- 准备在陌生项目上迭代、修 Bug、重构或上线；
- 项目缺少架构、测试、发布、日志或监控基线；
- 需要确认“现在系统到底是什么状态”，而不是直接按猜测改代码。

如果已有清晰、最新且有证据的基线，可只针对缺失部分运行；不能为了形式重复盘点无关内容。

## Inputs

优先读取：

1. 项目路径、分支、工作区状态和用户授权范围；
2. `README`、`PROJECT.md`、`PLAN.md`、CI/CD 配置、构建和部署说明；
3. 包管理器、锁文件、运行时版本、环境变量样例和入口；
4. 代码目录、API、数据库/数据迁移、外部服务和关键用户旅程；
5. 测试、覆盖率、构建产物和最近发布记录；
6. `web-monitor`、`server-log`、`server-monitor` 的接入状态、导出记录或接口契约（若存在）；
7. 用户明确要做的后续模式：`CREATE` / `CHANGE` / `DEFECT` / `REFACTOR` / `INCIDENT` / `OPTIMIZE`。

## Preconditions

- 先确认当前目录、分支和工作区是否有用户未提交变更；不重置、不清理、不覆盖。
- 只做只读盘点和经授权的本地验证；不默认访问生产、不修改外部仓库、不发送真实通知、不执行部署。
- 发现凭证、个人数据、客户数据或私有配置时，只记录其存在和风险，不把秘密复制进基线。
- 任何结论必须标记为 `FACT`、`EVIDENCE`、`INFERENCE`、`ASSUMPTION` 或 `OPEN`；旧系统的偶然行为不能自动变成产品需求。

## Responsibilities

只负责：

- 判断项目模式和盘点范围；
- 收集可复核的工程事实；
- 建立架构、行为、接口/数据、测试、可观测性和发布基线；
- 识别未知项、风险和下一步路由；
- 为下游 Workflow 提供明确的入口、证据和停止条件。

## Non-goals

不负责：

- 修复 Bug、实施功能、重构代码或改变业务行为；
- 猜测用户真正想要的产品规则；
- 因为发现代码质量差就直接替换技术栈；
- 用一次成功构建宣称项目“健康”；
- 把监控接入、日志缺失或测试缺失隐藏为“后续再说”。

## Procedure

### 1. 分类项目与任务模式

记录：项目是新建、已有项目接管还是外部交付项目；目标模式、平台、环境、风险等级和本轮边界。若用户只说“改一下”，先把它标为 `OPEN`，不得擅自归类为 `CHANGE` 或 `REFACTOR`。

### 1.1 存量项目接管与工程流程补齐

这是本入口的一种任务，不新建“迁移”生命周期或另一个 Skill。它不等于 REFACTOR（改内部结构），也不等于“全流程测试”（auto-test 验证现有实现）。先做只读盘点，终点默认是缺口报告和补齐计划，不默认重写业务、替换框架或部署。

在现有 baseline 的 unknowns-and-risks.md 内增加阶段缺口矩阵：

| 阶段/产物 | 现有路径与版本 | 证据/Gate 是否仍有效 | 可复用/需补齐/已失效/不适用 | 缺口与理由 | 后续 Skill / 需用户确认 |
|---|---|---|---|---|---|

按本次范围覆盖需求/范围决策、原型/UI、技术设计、代码审查、auto-test；发布/运维未授权则列不在本次执行范围。旧 PIPELINE、旧 PRD 和测试报告只读引用；旧代码行为标现状证据，不自动认作正确需求，旧测试结果不冒充本次实测。

把矩阵和拟走路线交用户确认。仅补工程基线可按 CHANGE 记录；新增行为、结构改造、缺陷和优化按各自意图路由并分清授权。需要补产品基线时从 prd-workflow 的缺失阶段补证、确认，再沿合法边推进；不能因为“重跑一遍”把所有阶段伪造通过。仅要求测试时交 auto-test，缺验收依据则记录边界，不自动启动全量产品重做。

### 2. 建立工作区安全快照

记录分支、commit、工作区状态、忽略文件、运行时版本和可用命令。对所有探测命令记录：命令、时间、退出码、关键输出和是否改变文件。优先静态读取，运行验证前先确认脚本不会部署、迁移或清理数据。

### 3. 盘点构建与运行路径

识别：入口、包管理器、安装/启动/测试/类型检查/lint/build 命令、环境变量、服务依赖、端口、容器、CI、部署方式和回滚入口。命令不确定时先读脚本和 CI，不凭经验执行。

### 4. 建立架构地图

以模块和依赖为单位记录前端、后端、任务、存储、外部服务、鉴权、消息、定时任务和关键边界。对每个边界标注：已证实、推断、未知、风险。避免只列目录；必须说明关键请求/数据如何流动。

### 5. 建立行为基线

选择不超过本轮范围的关键用户旅程和服务主链，记录入口、前置条件、正常结果、失败结果、权限差异、幂等/重试和可恢复动作。对于没有测试的行为，可通过只读运行、现有日志或用户确认建立临时 characterization evidence，并标明证据来源。

### 6. 建立 API 与数据清单

盘点对外接口、事件、数据库/文件/缓存、迁移、外部依赖和兼容性约束。记录“当前观察到的行为”与“应该如此的产品规则”两列；两者不一致时转交 `Impact-Analysis`、`Defect-Triage` 或用户确认，不能由本 Skill 决定。

### 7. 建立测试基线

记录现有测试层级、可运行命令、通过/失败/跳过、覆盖率（若可信）、不稳定测试、缺失的主链和回归保护。区分“没有测试”和“测试通过”；没有证据就标 `OPEN`。

### 8. 建立可观测性基线

检查前端错误/性能/行为、服务结构化日志、请求关联 ID、主机/服务指标、告警和发布版本关联。优先建立 `traceId`、`reqId`/`sessionId`、`appVersion`、环境和 commit 的关联关系。对于 `web-monitor`、`server-log`、`server-monitor` 未接入或接入不完整的情况，写入缺口和后续 Gate，不直接改外部项目。

### 9. 建立发布与回滚基线

记录环境、版本/构建号、发布方式、迁移顺序、灰度/开关、回滚路径、发布后观察窗口和责任边界。回滚“理论上可以”不算基线，必须有可执行证据或明确 `OPEN`。

### 10. 汇总未知项并路由

把问题分成：产品语义不明、工程事实缺失、质量风险、运行风险、权限/合规风险。输出下一步推荐：

- 新项目 → `PRD-Workflow`；
- 旧流程接入 → 先交阶段缺口矩阵与补齐计划，经确认后仅补缺失/失效阶段；
- 功能/规则变化 → `CHANGE` → `Impact-Analysis`；
- 行为偏离已批准基线 → `DEFECT` → `Defect-Triage`；
- 内部治理且默认不改外部行为 → `REFACTOR` → `Refactor-Planning`；
- 生产高影响问题 → `INCIDENT` → `Incident-Response`；
- 指标/成本/行为驱动的改进 → `OPTIMIZE` → `Product-Analytics` / `Optimization-Planning`。

## Outputs

在项目中生成或更新：

```text
.spec/baseline/
├── project-profile.yaml
├── architecture-map.md
├── behavior-baseline.md
├── api-and-data-inventory.md
├── test-baseline.md
├── observability-baseline.md
├── release-baseline.md
└── unknowns-and-risks.md
```

同时在项目状态或工作流清单中登记：

- `baselineId`、采集时间（使用绝对日期，如 `2026-09-20`）、commit、环境；
- 每条事实的证据位置；
- 当前生命周期模式和推荐下游；
- 未完成项、阻塞项、风险等级和负责人/确认人；
- 不得写入秘密、真实 token 或未经授权的客户数据。

模板见 `assets/baseline-pack-template.md`，分类和证据规则见 `references/onboarding-checklist.md`。

## Evidence

合格证据至少包括：

- 仓库状态、文件/配置、命令输出或 CI 记录；
- 真实可复现的构建/测试/运行结果；
- 日志、监控、发布记录或用户明确确认；
- 对推断和未知项的明确标记。

“看过代码”“应该支持”“模型认为”不是工程证据。

## Gate

只有同时满足以下条件才能通过 `ONBOARDING_BASELINE_READY`：

1. 项目模式、范围、分支和快照明确；
2. 八份基线文件齐全，或每个缺失项都有原因、风险和后续责任；
3. 关键主链、构建/测试/发布路径有证据或明确 `OPEN`；
4. 旧行为与目标产品规则没有被混为一谈；
5. 关键日志/监控/版本关联缺口已登记；
6. 下游模式和第一步行动明确；
7. 未改动代码、未执行未授权外部操作。

否则输出 `BASELINE_INCOMPLETE`，停在当前 Skill；不要用下游开发掩盖上游未知。

## Failure Route

- 工作区有未提交变更：保留现场，生成快照，暂停任何写操作。
- 无法安全运行项目：记录阻塞命令和原因，转 `Technical-Discovery`，不编造结果。
- 需求与现状冲突：转 `Impact-Analysis` / `Defect-Triage`，等待产品裁决。
- 生产风险或数据安全风险：停止盘点之外的操作，转 `Incident-Response` 或人工确认。
- 证据不足：标记 `OPEN` 并列出最小补证动作，不得升级为确定结论。

## Downstream Contract

下游只能消费本 Skill 已登记的基线和证据：

- `PRD-Workflow` 消费产品目标与未知项，不把技术猜测写成需求；
- `DEV-Workflow` 消费架构、依赖、运行和约束事实；
- `auto-test` 消费行为、测试缺口和回归风险；
- `Release-Workflow` 消费发布、回滚和观察基线；
- `Operations-Workflow` 消费可观测性、版本关联和运行风险；
- `Refactor-Planning` 消费内部质量目标，但必须保留行为基线。

## State Changes

建议状态：

```text
ONBOARDING_REQUESTED
→ DISCOVERY_IN_PROGRESS
→ BASELINE_INCOMPLETE | ONBOARDING_BASELINE_READY
→ CREATE / CHANGE / DEFECT / REFACTOR / INCIDENT / OPTIMIZE
```

任何状态转移都要写入工作流记录，包含时间、操作者、证据和 Gate 结果。
