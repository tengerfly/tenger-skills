# Skill-Optimizer（Skill 元优化器）

> **定位**：本仓库各专业 Skill 的「运维 + 迭代器」。它不参与任何一次具体业务交付，只做四件事——**记录** skill 运行中暴露的问题、**挖掘**历史聊天记录里的优化点、**体检** skill 文档的自洽一致性、**优化** skill 本身（方法论、体积、触发、术语）。
>
> **一句话原则**：评审闭环管「这一次交付物」，本 skill 管「每一次都犯的方法论问题」。

## 一、核心模型：一个问题池 + 四个模式

问题池 `issue/` 是唯一事实源，四个模式围绕它工作：

| 模式 | 触发 | 干什么 | 产物 |
|---|---|---|---|
| ① 记录 | 用户喊「记个问题 / 复盘这次运行」 | 把问题写入 issue 池 | `issue/<skill>/<日期>/xx.md` |
| ② 挖掘 | 用户给聊天记录（chats/ 或粘贴） | 从记录提取优化点 | 提取清单 → 确认后落 issue |
| ③ 优化 | 用户喊「优化 / 精简 / 迭代 XX」 | 读 issue 做全方位优化，沉淀回 skill | 各 skill 的 SKILL.md / references / CONTEXT.md |
| ④ 体检 | 用户喊「体检 / 检查 XX」「XX 自洽吗 / 前后一致吗」 | 五维自洽体检，出问题清单 | 问题清单 → 用户逐条裁决（当场修 / 记 issue / 忽略） |

**标准先行**：每个模式都有固定标准——记录按 `assets/issue-template.md`、挖掘按 `assets/signal-checklist.md`、优化按 `assets/optimize-checklist.md`、体检按 `assets/self-audit-checklist.md`。执行严格按标准逐项走，保证每次流程固定，不凭感觉发挥。

**自我指涉（含标准）**：本 skill 自身也是被优化对象，其问题（**含四份标准本身的问题**）记到 `issue/Skill-Optimizer/`，可自优化；**优化顺序永远是「先优化自己——先修订标准，再用修订后的标准干活——再优化其他 skill」**。

**长期迭代**：这是一个持续过程——issue 池不断积累，优化按需 / 周期性进行，不是一次性动作。

## 二、问题池（issue/）

- **路径**：仓库根目录 `issue/`
- **结构**：`issue/<skill名称>/<日期目录>/<问题文件>` —— 每个 skill 一个文件夹，每天一个子文件夹，当天的问题文件都放日期目录里
- **问题文件命名**：`<序号>-<简短标题>.md`，序号在日期目录内从 `01` 递增（如 `01-澄清缺入口导致返工.md`）
- **模板**：`assets/issue-template.md`

```
issue/
├── Skill-Optimizer/
│   └── 2026-09-04/
│       └── 01-xxx.md
├── Prototype-Design/
│   └── 2026-09-04/
│       ├── 01-xxx.md
│       └── 02-xxx.md
└── ...
```

## 三、问题字段与状态机

每个问题文件必填：

| 字段 | 说明 |
|---|---|
| 标题 | 一句话说清问题 |
| 归属 skill | 由目录决定，文件内也标注 |
| 来源 | 4 种：`埋点` / `挖掘` / `体检` / `用户`（谁记的） |
| 等级 | `P0` / `P1` / `P2` |
| 标签 | 10 个预定义标签（见下，可多选） |
| 现象 | 发生了什么 |
| 期望 vs 实际 | 应该怎样 vs 实际怎样 |
| 修复方向 | 建议怎么改 |
| 优化状态 | `待处理` / `处理中` / `已沉淀` / `已忽略` |
| 沉淀目标 / 位置 | 状态为「已沉淀」时必填 |

**等级**（与 Testing / Code-Review 同口径）：

| 等级 | 含义 |
|---|---|
| P0 | 方法论硬伤 / 每次必犯 / 阻塞性 |
| P1 | 明显影响 / 高频 |
| P2 | 轻微 / 建议 |

**标签（预定义枚举，10 个）**：

| 标签 | 含义 |
|---|---|
| 触发识别 | description 触发不准：该触发没触发 / 误触发 |
| 流程缺陷 | 执行步骤/流程有漏洞、不闭环 |
| 边界不清 | 应做/不应做没界定，越界或漏做 |
| 术语文案 | 术语与 CONTEXT 冲突、文案不当 |
| 产物格式 | 产出物结构/模板不规范 |
| 接口契约 | 前后端契约不一致（主要影响 Tech-Design/Dev） |
| 工具依赖 | 浏览器工具 / lint / 环境依赖问题 |
| 性能体积 | SKILL.md 过大/冗余/加载慢/token 超载 |
| 正面参考 | 用户明确认可、值得沉淀的做法 |
| 反面参考 | 用户明确否定的做法，作为坏案例 |

**状态机**：

```
待处理 → 处理中 → 已沉淀（强制填沉淀目标 + 沉淀位置）
              ↘ 已忽略
```

## 四、模式 ① 记录（兜底）

**触发**：用户说「记个问题」「这个 skill 刚才哪里不好」「复盘一下这次运行」。

**流程**：
1. 定位目标 skill（用户点名，或根据上下文判断后**向用户确认**）；
2. 提炼问题：现象、期望 vs 实际、等级、标签、修复方向；
3. 写 `issue/<skill>/<日期>/<序号>-<标题>.md`（按 `assets/issue-template.md`）；
4. 向用户确认等级 / 标签 / 归属无误。

> 这是「兜底」通道：各 skill 的埋点（见 `references/instrumentation-guide.md`）漏了、或用户事后才想起来时，用这里补记。

## 五、模式 ② 挖掘（从聊天记录提取优化点）

**触发**：用户给聊天记录——丢进 `chats/` 目录（支持多个子文件夹 + 多个文件）或直接粘贴文本。

**流程**：
1. **输入**：读 `chats/` 目录下的记录文件（.md / .txt / .json / .html），或直接用用户粘贴的文本；
2. **扫信号**：按 `assets/signal-checklist.md` 逐类识别——
   - 🔴 负面：`不对` / `重来` / `怎么又` / `别乱发挥` / `不是我要的` / 反复返工、用户纠正、质疑；
   - 🟢 正面：`好` / `不错` / `就这样` / `这个思路对` / `以后都这样`；
   - 🔁 返工：同一任务多轮重做、评审-改-再评审循环；
   - 🎯 触发痕迹：哪个 skill 被调起、产出什么、在哪一步被你打断；
3. **提炼**：信号聚合 → 每条问题提炼成「现象 + 期望 vs 实际 + 归属 skill + 等级 + 标签 + 修复方向」；
4. **确认**：把提取清单列给用户逐条过目（增删 / 改归属 / 改等级标签），**确认后才落盘**；
5. **落盘**：写入 `issue/<skill>/<日期>/<序号>-<标题>.md`。

## 六、模式 ③ 优化（全方位沉淀）

**触发**：用户说「优化 XX」「精简 XX」「迭代 XX」「让 XX 更贴合我的需求」。

**顺序**：**先优化本 skill（Skill-Optimizer）自己——含先修订四份标准（标准有问题时），再用修订后的标准执行 → 再优化目标 skill**。

**全方位核验维度**（按 `assets/optimize-checklist.md` 逐项执行）：

| 维度 | 检查什么 |
|---|---|
| ① 问题修复 | 读 `issue/<目标skill>/` 里「待处理 / 处理中」的项，逐条修 |
| ② 性能体积 | SKILL.md / references 是否过大冗余 → 精简、下沉 references、压缩描述 |
| ③ 触发精准 | description 触发词是否准确、是否误触发 / 漏触发 |
| ④ 术语一致 | 与 CONTEXT.md 术语是否冲突 |

**流程**：
1. 读 `issue/<目标skill>/`，列出待修问题；
2. 按 optimize-checklist 对目标 skill 做四维度核验；
3. 改动 SKILL.md / references / assets（只动有依据的，见铁律）；
4. 在目标 skill 的 `CONTEXT.md` 决策日志追加一条 `D-xx`（记录：改了什么、依据哪条 issue）；
5. 回填 issue 状态：已解决 → `已沉淀` + 沉淀目标 + 沉淀位置（文件 / D-xx）；不处理 → `已忽略` + 理由。

## 七、模式 ④ 体检（自洽检查）

**触发**：用户说「体检 / 检查 XX skill」「看看 XX 自洽吗 / 前后一致吗 / 逻辑有没有闭环」。

**干什么**：把目标 skill 当产品查 bug——按 `assets/self-audit-checklist.md` 做**五维自洽体检**：
① **术语·命名一致**——同一概念同指异名（A / A1）、与 CONTEXT.md 术语表冲突、旧术语残留；
② **逻辑闭环**——悬空引用（「见 §X / D-xx / 某文件」目标不存在或编号对不上）、流程断头、宣称的 Gate/检测没落地、并列枚举数量前后不一致；
③ **文句质量**——病句、错别字、模板占位符没替换；
④ **声明-流程一致**——凡声明「硬依赖 / 前置 / 需要 X（如浏览器工具）」，正文必须有对应「检测 → 阻塞/跳过 → 报错」步骤，两边对不上即缺陷；
⑤ **跨位置同步**——关键事实 / 编号 / 术语 / 引用分散在多文件时只改一处 = 失同步，按关键事实全仓 grep 比对检出。

**范围（默认）**：目标 skill 全套文件（SKILL.md / README.md / CONTEXT.md / assets / references）+ 它在全仓的交叉引用（根 README / Workflow / 其他 skill / issue 池）。也可全仓体检（逐 skill 跑，产出汇总）。

**流程**：
1. 定位目标 skill（用户点名，或根据上下文判断后向用户确认）；
2. 加载 `assets/self-audit-checklist.md`，按五维逐项核验（机械 grep + AI 通读双通道）；
3. 产出**问题清单**：每条含 等级（P0/P1/P2）+ 位置（文件/节）+ 现象 + 修复方向 + 修复判据；
4. **逐条向用户裁决**：当场修 → 改完在目标 skill CONTEXT.md 记一条 D-x；记 issue → 按 `assets/issue-template.md` 落 `issue/<skill>/<日期>/`（来源填「体检」）；忽略 → 说明理由；
5. 输出体检小结：查了哪些文件、发现几条、每条去向，与用户确认后收尾。

> 与模式③的区别：③ 优化是「有 issue / 明确诉求才改」；④ 体检是「存量体检、只出问题清单，改动逐条经你批准」。体检发现的可修项可顺手记入 issue 池，交下次优化模式统一修。

## 八、铁律（强制，7 条）

1. **标准先行**：任何模式执行前先加载对应标准（模板 / 信号清单 / 优化清单 / 自洽检查清单），按标准逐项走；标准本身缺失或有问题 → 记 issue 并先修标准，不凭感觉替代。
2. **改动有依据**：每个优化改动都能追溯到一条 issue 或一次明确核验发现（含模式④体检经你批准的条目），不凭空重构。
3. **先己后人**：优化顺序永远是先优化 Skill-Optimizer 自己（含先修订标准），再优化其他 skill。
4. **沉淀留痕**：每次优化改动，必须在目标 skill 的 CONTEXT.md 决策日志记一条 D-xx。
5. **字段必填**：问题文件的等级、标签、优化状态三字段必填。
6. **确认后落盘**：挖掘模式提取清单，未经用户确认不落盘。
7. **零加戏**：优化只针对确认过的问题与体检发现，不擅自增删 skill 功能或重写风格。

## 九、常见错误对照表

| 常见错误 | 纠正方式 |
|---|---|
| 优化时凭感觉大改，没有 issue 依据 | 每个改动回溯到 issue 或体检发现 |
| 直接优化别的 skill，跳过了自优化 | 先优化 Skill-Optimizer 自己 |
| 优化完不写 CONTEXT.md 决策日志 | 追加 D-xx，记录改动与依据 |
| 挖掘出的问题没经用户确认就落盘 | 先列清单确认，再落盘 |
| 问题文件缺等级/标签/状态 | 三字段必填 |
| 「已沉淀」却忘了填沉淀目标/位置 | 已沉淀必须可追溯 |
| 体检只口头说、不出问题清单 | 按 `assets/self-audit-checklist.md` 逐维核验，每条带位置/修复方向/判据 |
| 体检当场修了却没记 D-x | 当场修的每条在目标 skill CONTEXT.md 决策日志留痕 |
| 改完 skill 不查其他位置是否同步 | 收尾强制同步验证：旧词/编号/术语全仓清零 |
