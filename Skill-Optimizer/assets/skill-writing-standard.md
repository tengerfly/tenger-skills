# Skill 编写规范（通用底座）

> 定位：本文件是「一个 Skill 该怎么写」的通用规范，是 `optimize-checklist.md` 维度二~六的判据来源。写新 skill、优化存量 skill 时对照执行。
> 一句话：**Skill 是给 AI 的操作手册——入口、省、准、稳 + 简洁不落俗。**

## 一、入口：description 决定能不能被「看见」

模型决定「要不要用这个 skill」时，手里只有 frontmatter 里这一句话。写不好 = 入口堵死。

**要求**：description 同时说清两件事——
1. **做什么（what）**：一句话说清能力；
2. **何时用（when）**：用户会说的自然语言，覆盖 **动词 + 场景 + 同义表达**。

❌ `description: 代码审查工具`
✅ `description: 代码审查。当用户说「帮我 review」「检查代码」「审查 PR」「看看这段代码有没有问题」时使用。`

**检查**：用户最可能说的 3-5 种口语说法，description 里有没有对应的词能命中？

## 二、省：上下文是公共资源，别硬塞

**硬红线：SKILL.md ≤ 500 行**，超出的部分拆走，正文只留一句入口。

| 资源 | 放什么 | 加载时机 |
|---|---|---|
| `references/` | 给模型**读**的知识 | 按需加载（执行到那步才读） |
| `scripts/` | 给模型**执行**的脚本 | 不加载，只调用 |
| `assets/` | 用在产出里的**素材** | 永不读，只在生成结果时引用 |

**拆的规则**：
- references 按领域组织，**只嵌套一层**；
- 同一段代码被反复重写、或需要确定性结果 → 封装进 `scripts/`（如 `rotate_pdf.py`），模型只需知道「有这个脚本 + 参数」，不必读内容；
- 会被反复读的知识进 references，会被反复写的代码进 scripts，只出现在产物里的进 assets。

## 三、准：理解模型的脾气，话才说得对

模型不缺知识，缺**注意力的引导**。三招对三个脾气：

| 脾气 | 症状 | 对策 |
|---|---|---|
| 注意力需要引导 | 泛泛说废话 | **用问题牵着走**：写「该问的问题」，不写「该找的答案」 |
| 默认模式改不掉 | 每次都犯同一错（写 UI 就紫蓝渐变、CTA 上 "Learn More"） | **禁令清单**：把不要的逐条点名，当反面教材 |
| 压力下走捷径 | 改改试试、原地打转 | **铁律 + Red Flag**：斩钉截铁的禁令放开头，再列症状清单让模型自己踩刹车 |

**问题引导示例**：
❌ 检查代码是否违反单一职责原则
✅ 问自己：这个模块有几个不同的修改理由？超过一个，就可能违反

**铁律 + Red Flag 示例**（systematic-debugging）：
> NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST（没查清根因之前，禁止动手修）
> Red Flags（回退到第一步）：
> - "I think the problem might be..."（在猜，不是在分析）
> - 没搞清根因就动手改
> - 修好了，却说不清为什么好了

**写法**：先想清模型用它时最可能犯的那个错，把防它的规则用斩钉截铁的措辞放开头；再列这个错发作时的典型症状，让模型能自己识别、踩刹车。

**引导式提问（打开思路）**：确定型 skill（PRD / 技术方案等）面对的用户（产品方/使用方）思路常狭窄、想不到很多点。skill 不能只当"问答机"——用户说啥写啥，要当"思路放大器"：
- 用户说"想做一个应用" → 引导问：有没有竞品/参考应用？参考应用有哪些功能？这个功能你要不要？它的上游/下游是谁？
- 用「问题 + 给 2~3 个选择项 + 例子」把思路打开，让用户想到更多，把需求/方案考虑完整；
- 用户说的可能是错的 → 专家视角主动判断，发现不合理处主动纠正/补充，不照单全收。

## 四、稳：把流程本身立稳

长流程最常见的病 = 丢步骤、包办决策、做完没标准。四件套：

1. **工作流清单**：让模型边执行边打勾，关键步骤标
   - `⚠️ REQUIRED` = 绝不能跳过
   - `⛔ BLOCKING` = 不完成不许往下走
2. **确认节点（Gate）**：生成 / 修改这类有后果的操作，在决策点强制停下来问用户
   - **确认点逐条列清单（全仓通用铁律）**：凡需用户拍板的点（选型/边界/假设/范围/阈值…），一律**逐条编号列成清单、一次性呈现**给用户确认——不混成一段话、不自己拍板、不漏项；用户确认后逐条记结论，未确认不推进。
3. **交付前检查清单（Pre-Delivery Checklist）**：定义「怎么算做完」，每条具体到可检查
   - ❌ 确保可访问性好
   - ✅ 所有图片都有 alt text；所有表单输入都有 label
4. **优先级分级**：分析类 skill 给 P0-P3 定级，让模型知道什么该重点说、什么可轻描淡写

**参数系统（可选，提升使用频率）**：用 `$ARGUMENTS` 收参 + frontmatter `argument-hint` 提示，支持只跑局部：
`/slide-deck content.md --outline-only`（只出大纲）/ `--regenerate 3`（只重做第 3 页）/ `--quick`（跳过确认）

## 五、简洁不落俗

AI 写的 skill 天然臃肿、满是套话。做完后做**减法**，问「哪些可以去掉」，而不是「哪些可以加」。

**逐条点名要删的 AI 味**：
- 空洞承诺性措辞：`确保高质量` `力求完美` `极大地提升` `无缝` `赋能` `很好地`——无法检查的形容词一律删；
- 套话开场 / 收尾 / 过渡：`首先…其次…最后` `值得注意的是` `综上所述` `不难发现` `下面我们来`；
- 冗余引导语：`需要说明的是` `这里要强调的是` `正如前面提到的`；
- 空泛强调副词堆叠：`非常` `极其` `充分` `全面` 连用；
- emoji 滥用、加粗泛滥、为表格而表格（无信息量的堆砌）。

**简洁判据**：一句话能说清不用三句；删掉不承载信息的词；优先动词短语，少写「进行 XX 操作」。

**禁止口语化直接入 skill（硬标准）**：用户提问题/想法时往往口语化（如「感觉不太对」「这个有点那个」「反正就是…」），这类原话**禁止原样写进 skill**；必须先提炼成简明、准确、可操作的专业表述再落笔。skill 全程「简明扼要、不啰嗦」——这是硬标准，不是可选。

## 六、心法注入（内容层方法论）

以上五节管「skill 文档本身怎么写」（形式层）。还有一个内容层的问题：**skill 应该让 Agent 执行什么方法论**——做减法、决策规划分离、review 独立性、验收标准前置、派活四件套、苏格拉底反问、自动化兜底三套。

这部分判据见 `assets/vibe-principles-mapping.md`（心法映射表），优化时按 skill 所属类别对照注入，不在此重复。
