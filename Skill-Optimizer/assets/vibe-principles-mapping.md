# 心法映射表（Vibe Coding 秘籍 → Skill 内容层方法论）

> 定位：本文件是「优化维度八·心法注入」的判据来源，把《Vibe Coding 高效能秘籍》里能落到 skill 执行层面的心法，映射为「适用 skill 类别 → 落地写法」。
> 与 `skill-writing-standard.md` 的分工：编写规范管「skill 文档本身怎么写」（形式层：入口/省/准/稳/简洁），本文件管「skill 应该让 Agent 执行什么方法论」（内容层）。

## 1. 派活四件套（目标 + 边界 + 历史包袱 + 验收标准）

- **出处**：秘籍第一章①——「一句话让 AI 干活」丢掉了任务能做成所依赖的几乎全部信息。
- **适用**：所有 skill 的「输入要求」环节。
- **落地写法**：skill 要求 Agent 动手前，向上游/用户补齐四件套，缺任何一样就停下来问，不自行脑补：
  - **目标**：往哪个方向改；
  - **边界**：哪些不能碰；
  - **历史包袱**：当年为什么这么写（有存量代码/文档时）；
  - **验收标准**：怎么算做完。
- **反例**：仅凭「帮我重构这个模块，代码有点乱」就直接动手。

## 2. 做减法（质疑需求 → 删除 → 简化 → 加速 → 自动化最后）

- **出处**：心法 4——Agent 默认产出是「加法做到底」的版本；马斯克五步法顺序即重点。
- **适用**：`Backend-Dev` / `Frontend-Dev` / `Backend-Tech-Design` / `Frontend-Tech-Design` / `UI-UX-Design`。
- **落地写法**：内建「做减法」铁律——
  - 反对过度设计：不为了「将来可能」加抽象/接口/配置；
  - 反对提前抽象：等需求真出现再重构（重构成本已接近零）；
  - 默认最小实现：能跑通的最小闭环优先；
  - 自动化是最后一步：先手动跑通，再谈自动化。

## 3. 决策规划分离、讨论先行（spec ≠ plan）

- **出处**：秘籍第四章⑨——SDD 的炸弹埋在「让 AI 在信息不充分时直接生成 spec」，把关键决策全拍了。
- **适用**：`PRD-Design` / `Prototype-Design` / `Backend-Tech-Design` / `Frontend-Tech-Design`。
- **落地写法**：spec（做什么）与 plan（怎么做）分离，流程四步——
  1. 先摸底：让 AI 读现有材料复述现状；
  2. 邀请抬杠：抛出想法，主动暴露反方观点；
  3. 逐项确认关键决策：记入 decisions 记录；
  4. 全部敲定后才写 plan。

## 4. review 独立性（独立 review 中间层）

- **出处**：心法 2（错误率指数衰减靠独立 review）+ 第一章② + 第四章⑪（critique 双隔离评估）。
- **适用**：6 个评审类（`PRD-Review` / `Prototype-Review` / `UI-UX-Review` / `Tech-Review` / `Code-Review` / `Fidelity-Review`）。
- **落地写法**：评审用独立中间层，独立性两个来源——
  - **干净上下文**：用 subagent / 新会话，让检查者看不到生成过程（不被锚定）；
  - **换模型交叉审查**：或换一个模型复查；
  - **双隔离评估**：评估 A（subagent 通读源码/渲染）+ 评估 B（确定性脚本扫已知模式），各自独立完成、最后合并。

## 5. 验收标准前置

- **出处**：秘籍第三章——「人给核心目标，AI 动手前先生成任务级验收标准，实现完成后沿同一份标准自己跑、自己核对、失败自己打回」。
- **适用**：所有产出类 skill（`PRD-Design` / `Prototype-Design` / `UI-UX-Design` / `Backend-Tech-Design` / `Frontend-Tech-Design` / `Backend-Dev` / `Frontend-Dev` / `Testing`）。
- **落地写法**：动手前先产出「本任务的验收标准」（可检查的条目，如导出包含哪些字段、空数据显示什么），完成后沿同一标准自检，不达标自己打回重做。

## 6. 苏格拉底反问（对抗 WYSIATI，模型默认不回头看）

- **出处**：秘籍第一章②——「这个方案在什么情况下会失败？」「数据量涨 10 倍还成立吗？」「你漏掉了什么？」。
- **适用**：分析/评审/设计类 skill。
- **落地写法**：指令内建三个反问，作为关键决策点的固定检查项（与编写规范 §三「问题引导」互补，这里是固定的三个具体问题）。

## 7. 自动化兜底三套（降级 + 告警 + 幂等）

- **出处**：秘籍第六章⑭——全自动的前提是错题本已机器化；兜底三套。
- **适用**：`Workflow` / 含自动化环节的 skill（`Testing` 的自动化回归等）。
- **落地写法**：
  - 自动化四部件：触发器 + 执行体 + 验证器 + 通知器（正常给摘要、异常才 @ 人）；
  - 兜底三套：降级（拦下就退回半自动等人审）+ 告警（失败必出声，防静默失败）+ 幂等（重跑无副作用）；
  - 高权限操作（发送 / push / 金钱）永远留人确认。

## 8. 问题引导指令（把「该找的答案」写成「该问的问题」）★ 写作惯例

- **出处**：秘籍第五章 Skill 开发——模型第一个脾气：「它不缺知识，缺注意力的引导」。
- **适用**：所有 skill 的检查项 / 指令正文编写（本类及第 9 类是「指令怎么写」的惯例，主要落在优化者写/改 skill 指令时，不要求业务 skill 新增流程）。
- **落地写法**：检查项 / 约束用提问触发具体核对，不用抽象断言。示范：
  - ❌「检查是否违反单一职责原则」→ ✅「问自己：这个模块有几个不同的修改理由？超过一个就可能违反了」
  - ❌「注意并发安全」→ ✅「两个请求同时打到这段代码会怎么样？」
  - ❌「注意测试性能」→ ✅「pnpm test src/xxx.test.ts 只跑改动相关文件，全量测试只在我明确要求时才跑」
- **判据**：业务 skill 正文若含检查/自检步骤，优先为「问句 + 具体核对动作」形态（问题式）而非泛化断言式。

## 9. 每个「不要」配一个「应该」★ 写作惯例

- **出处**：秘籍第二章 AGENTS.md/CLAUDE.md 写法。
- **适用**：规则 / 禁令 / 红线类清单。
- **落地写法**：禁止性规则必须紧跟替代路径，否则 Agent 在需要该操作的场景会卡住或自作主张。
  - ❌「不要用 --force 推送」→ ✅「不要用 --force 推送，用 --force-with-lease」
  - ❌「不要跑全量测试」→ ✅「全量测试很慢（4 分钟+），只在我明确要求时才跑；平时用 pnpm test <文件路径>」
- **判据**：核验 skill 内「不要 X / 禁止 X」条款时，检查其后是否给了「应该 Y」。

## 10. 确定性工具 vs AI 判断分工

- **出处**：秘籍第三章⑦（Midscene + axe-core 对比度组合）。
- **适用**：测试 / 评审 / 视觉验收类（仓库已落地：`Testing/references/style-test-guide.md` §六、`Fidelity-Review/references/visual-checklist.md` §三）。
- **落地写法**：
  - 能用确定性代码算精确值的（对比度 4.5:1、元素计数/存在性、样式计算值）→ 交给确定性代码（axe-core / 断言），报「哪个元素、当前值多少」；
  - 模糊观感判断（布局 / 遮挡 / 配色是否顺眼）→ 交给视觉模型（截图）；
  - 组合：操作（切换暗色、点击）用 AI 自然语言免选择器，判断用确定性工具。
- **判据**：新写测试/评审向检查项时先问「这个判断有明确数字定义吗？有就用确定性代码」。
- 注记：这类判断同时是「人类观感级别」结论，必须标注 AI 断言软肋（有明确阈值会漏判）。

## 11. 模型越强，流程越轻

- **出处**：秘籍第四章⑩——「反思某道工序对冲的那个模型短板，在你当前用的模型上还存在吗？不存在就移除」。
- **适用**：Workflow 编排 / 评审轮次与关卡数量的裁剪判据；也是优化者审「某 skill 工序是否冗余」的元判据。
- **落地写法**：
  - 每道工序都在对冲特定模型风险（理解跑偏 / 实现偏离 spec / 跨步骤丢上下文）；风险已不存在 → 删该工序或降级（如 task 级 review 降为整体一次 review）；
  - 默认轻流程，按需加重；模型弱或任务复杂（跨多系统重构）时流程该重就重；
  - 在 skill 层体现为：不盲目堆 Gate / 关卡 / 冗余 review，多道 gate 也应为「可选/可裁剪」结构。
- 参考：Workflow 的可选节点设计；各评审 skill 的轮次上限 3 本身即「防无限加重」。

## 12. 认知四象限（使用者认知罗盘，⚠️ 不进业务指令）

- **出处**：秘籍终章——知道自己知道 / 知道自己不知道 / 不知道自己知道 / 不知道自己不知道。
- **定位**：这是「操作 Agent 的人」的认知地图（决定哪里要怀疑、哪里要沉淀），**不是 Agent 的执行指令**。禁止为四象限在业务 skill 里单开流程 / 清单（防加戏）。
- **在 skill 执行层的等价物（已内建，勿重复造）**：
  - 应对「不知道自己不知道」→ 苏格拉底兜底三问（「你漏掉了什么 / 什么情况会失败」）+ 独立 review + 验证闭环（外部视角与机器验证两条腿）；
  - 应对「知道自己不知道」→ 验收标准前置 + 评审；
  - 把「知道自己知道 / 不知道自己知道」搬到明处 → 派活四件套 / CONTEXT 决策日志 / 错题本 / Skill 沉淀。
- **优化者用途**：评估某 skill 动作时用四象限定位——若某动作是「人拍板该怀疑什么」，落到 skill 时以「问句兜底 / 外部视角 / 验证机制」形式出现即可，不必文字化四象限本身。

## 13. 错题本一增一减（翻车沉淀 + 定期删冗余）

- **出处**：秘籍第二章③（活文档：错题本 + 定期减法）+ 第五章⑬（Skill 里长出来的规则）。
- **适用**：规则 / checklist / 决策日志类沉淀物（各 skill 的 CONTEXT 决策日志、checklist 类 references、CLAUDE.md 类文档）。
- **落地写法**：
  - 增：每翻一次车往里沉淀一条，且每条来自真实事故（= Agent 猜不到的）、带可核对的背景；
  - 减：隔段时间审一遍，对每行问「删掉它 Agent 会不会犯错？不会就删」，保持信噪比；
  - 与「清单是长出来的」配套：checklist 类引用「从最在意的五六条起步、翻车加一条」。
- **判据**：核验沉淀物是否有「翻车沉淀」来源可溯；长期看是否鼓励定期减法（删错成本低，AI 加回是几句话的事）。
