## 一、角色定位（Who We Are）

- **Skill 人设**：Skill 运维 + 迭代器（Skill Ops / Iterator），负责让本仓库各 Skill 长期贴合用户需求；
- **核心目标**：把 skill 运行中暴露的问题沉淀为 skill 本身的改进——**记录、挖掘、优化**三位一体，长期迭代；
- **铁律（Domain Boundary）**：本 skill **不参与任何业务交付**——不写 PRD、不画原型、不做方案、不写代码、不做测试，只优化 skill 本身。某次交付物的质量问题归评审闭环管，本 skill 管「每一次都犯的方法论问题」。

## 二、术语表（Glossary）

| 术语 | 英文/Key | 权威定义 | 易混淆概念排除 |
|---|---|---|---|
| 问题池 | issue/ | 仓库根目录 `issue/`，所有 skill 运行问题的唯一事实源，按 `<skill名称>/<日期目录>/<问题文件>` 组织 | ❌ 不是评审任务清单（那是某次交付物的评审闭环载体）；❌ 不是 CONTEXT.md 的 Open Questions（那是设计期问题） |
| 问题 | Issue | 一条记录在 issue 池里的优化点，含标题/来源/等级/标签/现象/期望vs实际/修复方向/优化状态等字段 | ❌ 不是评审发现的问题（评审改的是那次交付物，Issue 改的是 skill 本身） |
| 埋点 | Instrumentation | 各 skill 执行收尾时自查上报问题的机制（**主记录通道**），规则见 `references/instrumentation-guide.md` | ❌ 不是元技能后台监听（skill 无法常驻，「监听」由埋点实现） |
| 兜底记录 | Fallback Recording | 元技能保留的补记入口：用户喊「记个问题/复盘」时由元技能直接写 issue，补埋点漏记 | ❌ 不是主通道（主通道是埋点） |
| 挖掘 | Mining | 从聊天记录（`chats/` 目录或粘贴文本）提取优化点的模式，按 signal-checklist 扫四类信号 | ❌ 不是复盘本次会话（那属兜底记录） |
| 信号 | Signal | 聊天记录里可识别的优化线索，四类：负面/正面/返工/触发痕迹 | ❌ 不是问题本身（信号需聚合提炼才成为问题） |
| 沉淀 | Precipitate | 优化完成的落点动作：issue 状态改「已沉淀」，强制填沉淀目标 + 沉淀位置 | ❌ 不是「已解决」（已解决无从验证是否真变成了 skill 改进） |
| 标准 | Standard | 本 skill 的固定执行依据，共六份：四份模式标准（issue-template 记录 / signal-checklist 挖掘 / optimize-checklist 优化 / self-audit-checklist 体检）+ 一份编写规范（skill-writing-standard，优化维度二~六判据来源）+ 一份心法映射（vibe-principles-mapping，优化维度八判据来源） | ❌ 不是参考资料（标准是必须逐项走的强约束） |
| 标准可迭代 | Standard Iterability | 标准本身也是被优化对象：标准有问题记到 `issue/Skill-Optimizer/`，优化时先修标准再用 | ❌ 不是随意改标准（同样走 issue + 决策日志留痕） |
| 全方位优化 | Full-spectrum Optimization | 优化模式的八维度核验：问题修复/入口·触发精准/省·上下文体积/准·指令写法/稳·流程稳定/简洁不落俗/术语一致/心法注入 | ❌ 不只是修 issue（还有体积、指令、流程、文风、心法等非 issue 驱动维度） |
| 编写规范 | Writing Standard | `assets/skill-writing-standard.md`，一个 Skill 该怎么写的通用底座（入口/省/准/稳/简洁不落俗），是 optimize-checklist 维度二~六的判据来源 | ❌ 不是模式标准（4 份模式标准各对应一个模式的执行 checklist；编写规范是通用知识底座） |
| 简洁不落俗 | Concise & Unclichéd | 反 AI 味套话的写作要求：删空洞承诺性措辞（「确保高质量」类）、套话开场/收尾/过渡、冗余引导语、emoji/加粗/表格堆砌；一句话能说清不写三句 | ❌ 不是「省」（省管结构体积，简洁不落俗管行文表达） |
| 性能体积 | Performance & Size | skill 文件过大/冗余/token 超载导致的执行性能问题；硬红线 SKILL.md ≤ 500 行，超限下沉 references；其余手段：精简/scripts 封装/assets 不加载/压缩描述 | ❌ 不是业务代码性能（那是 Testing / Code-Review 管的） |
| 自我指涉 | Self-reference | 元技能自身也进 issue 池可自优化；优化顺序永远是先己后人 | ❌ 不是只优化别人 |
| 正面参考 | Positive Reference | 用户明确认可、值得沉淀的做法，作为优化方法借鉴 | 与「反面参考」成对，好做法坏做法都有案例可依 |
| 反面参考 | Negative Reference | 用户明确否定的做法，作为坏案例避免再犯 | ❌ 不是待修问题（它是已确认的坏案例记录） |
| 自洽体检 | Self-audit / Consistency Audit | 模式④：把目标 skill 当产品查 bug，按 self-audit-checklist 六维核验（术语一致 / 逻辑闭环 / 文句质量 / 声明-流程一致 / 跨位置同步 / 简洁不落俗），产出问题清单交用户逐条裁决 | ❌ 不是优化（只出清单不改，改动逐条经批准）；❌ 不是 issue（issue 记运行中已暴露的问题，体检查存量文档缺陷） |
| 沉淀约定 | Precipitate Convention | 全局强约束（2026-09-05 用户口径），两层：① **粒度**——「沉淀某问题到 skill」= 沉淀该问题所属**类别**的问题（类别级通用判据/检查项/防复发规则），具体问题仅作该类**案例**佐证，不作主体；② **落点**——先沉淀到源仓库 `D:\project\agent-project\tenger-skills\`（skill 文件改动 = SKILL.md / references / CONTEXT.md / assets 对应 skill；问题记录 = `issue/` 池，仅存源仓库），skill 文件改动再**同步到 CodeBuddy 副本** `C:\Users\15136\.codebuddy\skills\` 同名文件，两处内容一致 | ❌ 不是单点问题直接写死（那是案例附注）；❌ 不是只改 CodeBuddy 副本（源仓库才是事实源） |
