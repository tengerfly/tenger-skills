# Workflow —— 全流程开发编排 Skill

> **状态**：✅ 定稿
> **定位**：只调度、记账、守门，不产出业务文档。
> **核心原则**：一条链，任意起点，逐步推进，随时可停。

## 一、这是什么

把 14 个专业 Skill 串成一条链，并支持**从任意节点起跑**的编排 Skill。它以被开发项目根目录下的 `.spec/PIPELINE.md` 为唯一状态源，负责：确定起点、按序调度子 skill、开工前做前置产物检查、收尾回填状态并输出交接摘要、评审未通过时自动回退重跑。

14 个子 skill 原本只靠 `.spec/` 目录约定做隐式衔接，本 Skill 补上三层：

| 层 | 载体 | 解决什么 |
|---|---|---|
| 编排层 | `SKILL.md` | 谁先谁后、调用谁、怎么回退 |
| 状态层 | `.spec/PIPELINE.md` | 走到哪了、产物在哪、能不能续跑 |
| 交接契约 | PIPELINE「交接记录」 | 上游给了什么、下游该读什么、留了什么坑 |

## 二、核心模型

```
① 竞品分析 → ② PRD 设计 → ③ PRD 评审 → ④ 原型设计 → ⑤ 原型评审 → ⑥ UI/UX 设计 → ⑦ UI/UX 评审
→ ⑧ 后端技术方案 → ⑨ 前端技术方案 → ⑩ 技术方案评审 → ⑪ 后端开发 → ⑫ 前端开发 → ⑬ 代码评审 → ⑭ 测试
       ▲              ▲              ▲               ▲                                          ▲
      起             起             起              起                                         起
      点             点             点              点                                         点
```

**每个节点都可以作为起点**。三个参数：

| 参数 | 怎么定 | 默认 |
|---|---|---|
| **起点** | 用户点名，或从 `.spec/` 已有产物推断 | ① 竞品分析（0-1 全流程） |
| **终点** | 用户点名；不点名 = 只跑起点这一个节点 | 起点节点本身 |
| **跳过** | 用户随时说「跳过 XX」 | 无 |

**推进节奏**：每完成一个节点 → 回填 PIPELINE → 输出交接摘要 → **停下等用户决定**（继续 / 跳过 / 重做 / 就到这）。

## 三、节点速查表

| # | 节点 | 调用 Skill | 前置（缺失阻塞） | 产出 |
|---|------|-----------|----------------|------|
| ① | 竞品分析 | Competitive-Analysis | 用户想法 | `Competitive-Analysis/.output/<主题>竞品分析/` |
| ② | PRD 设计 | PRD-Design | 用户想法 | `.spec/PRD/V1/` |
| ③ | PRD 评审 | PRD-Review ⇄ PRD-Design | `.spec/PRD/V1/` | `.spec/需求评审/` |
| ④ | 原型设计 | Prototype-Design | `.spec/PRD/V1/` | `.spec/原型/`（含布局清单） |
| ⑤ | 原型评审 | Prototype-Review ⇄ ④/② | `.spec/PRD/V1/` + `.spec/原型/` | `.spec/原型评审/` |
| ⑥ | UI/UX 设计 | UI-UX-Design | PRD + 布局清单 + 低保真原型 | `.spec/设计稿/` |
| ⑦ | UI/UX 评审 | UI-UX-Review ⇄ ⑥/④/② | PRD + 布局清单 + `.spec/设计稿/` | `.spec/设计评审/` |
| ⑧ | 后端技术方案 | Backend-Tech-Design | PRD | `.spec/TDD/V1/` |
| ⑨ | 前端技术方案 | Frontend-Tech-Design | PRD + TDD | `.spec/FTDD/V1/` |
| ⑩ | 技术方案评审 | Tech-Review ⇄ ⑧/⑨ | TDD 或 FTDD + PRD | `.spec/技术方案评审/` |
| ⑪ | 后端开发 | Backend-Dev | TDD | 后端代码 + `PROJECT.md` + `PLAN.md` |
| ⑫ | 前端开发 | Frontend-Dev | FTDD | 前端代码 + `PROJECT.md` |
| ⑬ | 代码评审 | Code-Review ⇄ ⑪/⑫ | 后端代码 或 前端代码 | `.spec/代码评审/` |
| ⑭ | 测试 | Testing | 可运行代码 + PRD | `.spec/测试/` |

**串行硬约束**：`⑧ → ⑨`（FTDD 依赖 TDD 接口契约）、`⑪ → ⑫`（前端按后端真实契约对接），不可并行。

> 环境前置由子 skill 自行检测：浏览器工具对 ⑤⑦⑨⑫⑭ 为硬依赖、⑧⑩ 为软检测；⑥ UI/UX 设计为 Superdesign 底座三件套硬依赖（CLI / 授权 / SOP）。

## 四、典型用法

| 用户说 | 起点 | 跑什么 |
|-------|------|-------|
| 「从零开发 XX」 | ① | 一路到 ⑭ |
| 「只做竞品分析」 | ① | 只跑 ① |
| 「根据我的 PRD 生成原型」 | ④ | 只跑 ④，跑完停 |
| 「评审原型」 | ⑤ | 只跑 ⑤，跑完停 |
| 「生成设计稿」 | ⑥ | 只跑 ⑥，跑完停 |
| 「评审设计稿」 | ⑦ | 只跑 ⑦，跑完停 |
| 「我有 PRD 了，走后续开发」 | ④ | ④ → ⑤ → … → ⑭ |
| 「按这个方案写代码」 | ⑪ | ⑪ → ⑫ |
| 「评审这份代码」 | ⑬ | 只跑 ⑬ |
| 「测试这个项目」 | ⑭ | 只跑 ⑭ |

> 起点未点名时，按 `.spec/` 已有产物自动推断，**推断后必须经用户确认**。设计稿（⑥）为可选节点，用户明确不需要时标记 `已跳过`（⑦ UI/UX 评审随之跳过）。

## 五、目录结构

```
Workflow/
├── SKILL.md                        # 主指令：核心模型 + 节点速查表 + 起点推断 + 调度规程 + 评审回退 + 铁律
├── README.md                       # 本文档
├── CONTEXT.md                      # 术语与决策日志
└── assets/
    └── pipeline-template.md        # .spec/PIPELINE.md 状态文件模板
```

被开发项目侧：

```
<项目根目录>/
└── .spec/
    ├── PIPELINE.md                 # ★ 流程状态（本 Skill 唯一产出，跨会话续跑锚点）
    ├── PRD/V1/
    ├── 原型/
    ├── 原型评审/                   # ★ 原型评审产物（汇总报告、任务清单、维度评审）
    ├── 设计稿/                     # ★ UI/UX 设计稿产物（README、定稿 HTML、设计规范副本、截图）
    ├── 设计评审/                   # ★ UI/UX 设计稿评审产物（汇总报告、任务清单、维度评审、截图）
    ├── TDD/V1/
    ├── FTDD/V1/
    ├── 需求评审/
    ├── 技术方案评审/
    ├── 代码评审/
    └── 测试/
```

## 六、评审回退

仅 ③ ⑤ ⑦ ⑩ ⑬ 适用。评审 Skill「只审不改、不设门禁」，**是否放行由本编排 Skill 判定**：

```
评审完成 → 任务清单（待确认）→ 用户裁决 → 已确认 = 0 → 放行
                                          → 已确认 > 0 → 回退修改方（轮次上限 3）
```

| 评审节点 | 修改方 |
|---------|-------|
| ③ PRD 评审 | `PRD-Design` |
| ⑤ 原型评审 | `Prototype-Design`（原型缺陷） / `PRD-Design`（需求冲突） |
| ⑨ 技术方案评审 | `Backend-Tech-Design` / `Frontend-Tech-Design`（按归因，双方则先后端后前端） |
| ⑫ 代码评审 | `Backend-Dev` / `Frontend-Dev`（按归因，双方则先后端后前端） |

> 评审节点与 ⑥ 均**可跳过**：用户说「跳过代码评审，直接测试」即从 ⑪ 跳到 ⑬；用户说「跳过原型评审，直接做方案」即从 ④ 跳到 ⑦；用户说「跳过设计稿，直接做技术方案」即从 ⑤ 跳到 ⑦。

## 七、铁律

1. 编排器不产出业务文档，只写 `PIPELINE.md`；
2. 状态以落盘为准，不靠对话记忆；
3. 每节点完成必须停下等用户决定（用户说「一路做到 X」除外）；
4. 前置缺失就阻塞，不硬推；
5. 评审未清零不放行，回退超 3 轮交回用户；
6. 串行处不许并行（⑧→⑨、⑪→⑫）；
7. 子 skill 内部规程优先，编排器不越权代答（含 ⑥ 的 Superdesign 成本红线：变体数量与花钱动作由用户裁决）；
8. 子 skill 永远可独立调用，本 Skill 只是可选串联方式。
