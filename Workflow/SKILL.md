# 全流程开发编排 Skill

> **定位**：只做三件事——**记账（PIPELINE.md）、调度（按顺序启用子 skill）、守门（前置检查与评审回退）**。
> 干活的是 14 个子 skill，本 skill 是它们的调度器。
>
> **核心原则**：一条链，任意起点，逐步推进，随时可停。

## 一、核心模型

```
① 竞品分析 → ② PRD 设计 → ③ PRD 评审 → ④ 原型设计 → ⑤ 原型评审 → ⑥ UI/UX 设计 → ⑦ UI/UX 评审
→ ⑧ 后端技术方案 → ⑨ 前端技术方案 → ⑩ 技术方案评审 → ⑪ 后端开发 → ⑫ 前端开发 → ⑬ 代码评审 → ⑭ 测试
```

**三个参数，仅此而已**：

| 参数 | 怎么定 | 默认 |
|---|---|---|
| **起点** | 用户点名，或从 `.spec/` 已有产物推断 | ① 竞品分析（0-1 全流程） |
| **终点** | 用户点名；不点名 = **只跑起点这一个节点** | 起点节点本身 |
| **跳过** | 用户随时说「跳过 XX」 | 无 |

**推进节奏**：每完成一个节点 → 回填 PIPELINE → 输出交接摘要 → **停下等用户决定**：

```
继续 → 跑下一个节点 ｜ 跳过 X → 跳过该节点 ｜ 重做 → 重跑当前节点 ｜ 就到这 → 结束
```

> 用户说「一路做到测试」→ 连续跑到 ⑭，中途仅在评审节点停下。

## 二、节点速查表

> 「前置」= 开工前必须具备的产物；缺失则阻塞并提示。括号内为可选增强，缺失不阻塞。
>
> **环境前置由子 skill 自行检测**：
> - **浏览器工具**（检测 Playwright → browser-use → 其他浏览器工具如 agent-browser，列举不穷举）：⑤ 原型评审 / ⑦ UI/UX 评审 / ⑨ 前端技术方案 / ⑫ 前端开发 / ⑭ 测试为**硬依赖**（全无即报错等安装），⑧ 后端技术方案 / ⑩ 技术方案评审为**软检测**（全无则跳过对应辅助步骤）；其余节点不涉及。
> - **⑥ UI/UX 设计**为 **Superdesign 底座硬依赖**（superdesign CLI 已安装 + 账号已授权 + SOP 可读，三件套缺一阻塞；检测与安装指引见该 skill 步骤 1），浏览器工具仅为其截图存证的可选增强。

|---|------|-----------|----------------|------|

- `⑧ TDD → ⑨ FTDD`：FTDD 必须读 TDD 的接口契约；
- `⑪ 后端开发 → ⑫ 前端开发`：前端按后端真实契约对接。

## 三、起点怎么定

### 3.1 用户点名（优先）

| 用户说 | 起点 | 终点 |
|-------|------|------|
| 「从零开发 XX」「按流程开发 XX」 | ① | ⑭ |
| 「只做竞品分析」 | ① | ① |
| 「写份 PRD」 | ② | ②（或 +③ 评审） |
| 「我有 PRD 了，出原型」/「根据我的 PRD 生成原型」 | ④ | ④ |
| 「评审原型」 | ⑤ | ⑤ |
| 「生成设计稿」/「把原型变成设计稿」 | ⑥ | ⑥ |
| 「评审设计稿」 | ⑦ | ⑦ |
| 「我有 PRD 了，走后续开发」 | ④ | ⑭ |
| 「根据 PRD 写技术方案」 | ⑧ | ⑩（或用户指定） |
| 「只出原型」（PRD 已有） | ④ | ④ |
| 「按这个方案写代码」 | ⑪ | ⑫ |
| 「评审这份代码」 | ⑬ | ⑬ |
| 「测试这个项目」 | ⑭ | ⑭ |
| 「测试页面还原度」/「检查 UI 还原」 | ⑭ | ⑭（Testing 内嵌 `Fidelity-Review` 做 UI 还原度检查） |

### 3.2 自动推断（用户没点名时）

读项目 `.spec/`，按已有产物推断下一个该做的节点：

| 已有产物 | 推断起点 |
|---------|---------|
| 无任何产物 | ① 竞品分析 |
| 有 PRD，无原型 | ④ 原型设计 |
| 有 PRD + 原型，无原型评审 | ⑤ 原型评审 |
| 有 PRD + 原型（已评审），无设计稿 | ⑥ UI/UX 设计 |
| 有设计稿，无设计稿评审 | ⑦ UI/UX 评审 |
| 有设计稿（已评审，或用户明确跳过设计稿），无 TDD | ⑧ 后端技术方案 |
| 有 TDD，无 FTDD | ⑨ 前端技术方案 |
| 有 TDD + FTDD，无代码 | ⑪ 后端开发 |
| 有后端代码，无前端代码 | ⑫ 前端开发 |
| 有完整代码 | ⑬ 代码评审 |

> 设计稿为**可选节点**：用户说「不需要设计稿，直接做方案」即标记 ⑥ `已跳过`（⑦ UI/UX 评审随之跳过），从 ⑧ 起跑。

**推断后必须向用户确认**：「检测到已有 PRD + 原型（已评审）+ 设计稿，建议从 ⑦ UI/UX 评审（或 ⑧ 后端技术方案）开始，可以吗？」

## 四、调度规程

### 4.1 启动

```
读 <项目根目录>/.spec/PIPELINE.md
├─ 不存在 → 新建（按 assets/pipeline-template.md），确定起点与终点
└─ 存在   → 续跑：从「当前节点」继续，已完成的节点不重跑
```

启动时**必问**（未提供则询问，不猜测）：

1. 项目根目录；
2. 起点（用户点名优先，否则按 §3.2 推断后确认）；
3. 终点（不指定 = 只跑起点节点）。

### 4.2 执行一个节点

| 步 | 动作 |
|---|------|
| 1 | **前置检查**：按 §二 检查前置产物是否实际存在（读目录，不凭记忆）；缺失 → 阻塞并提示 |
| 2 | 播报「执行 N. 节点名 → 调用 Xxx-Skill」 |
| 3 | **调用子 skill**：读取 `<skill-dir>/SKILL.md` 全文，按其流程执行；期间编排逻辑挂起 |
| 4 | **产出检查**：产物是否落盘；缺失 → 阻塞并提示 |
| 5 | **评审判定**（仅 ③⑤⑦⑩⑬）→ §五 |
| 6 | **回填 PIPELINE**：状态 → 已完成，填产物路径，追加交接记录 |
| 7 | **输出交接摘要**（§4.3），**停下等用户决定** |

子 skill 目录定位：优先与本 Skill 同级的兄弟目录（`../PRD-Design/SKILL.md`）；找不到则询问用户 skills 仓库根目录，记入 PIPELINE，后续不再问。

### 4.3 交接摘要（每节点完成必输出）

```
✅ N. 节点名 已完成

产出物：
- <路径>

给下一节点（N+1 节点名）的输入：
- <该读什么>

遗留与待确认：
- <开放问题>

PIPELINE 已更新： <路径>

—— 回复「继续」跑下一节点；或说「跳过 X」「重做」「就到这」。
```

### 4.4 阻塞输出格式

```
⛔ N. 节点名 前置缺失
缺失： <路径/文件>
建议： <先跑节点 X 补产出 / 手动指定产物路径 / 换个起点>
```

## 五、评审节点与回退

仅 ③ ⑤ ⑦ ⑩ ⑬ 适用。评审 Skill「只审不改、不设门禁」，**是否放行由本编排 Skill 判定**。

```
评审 Skill 完成 → 生成 任务清单.md（状态=待确认）
        ↓
用户逐条裁决：要改 → 已确认；不改 → 已忽略（附理由）
        ↓
├─ 已确认 = 0 → 放行，节点标记已完成
└─ 已确认 > 0 → 回退修改方修复（轮次 +1）→ 回填「已修复」→ 重跑评审
                 轮次 > 3 → 停止，交回用户裁决：接受现状 / 忽略该问题 / 转人工（绝不无限循环）
```

| 评审节点 | 任务清单 | 修改方 → 调用 Skill |
|---------|---------|-------------------|
| ③ PRD 评审 | `.spec/需求评审/任务清单.md` | 全部 → `PRD-Design` |
| ⑤ 原型评审 | `.spec/原型评审/任务清单.md` | 原型问题 → `Prototype-Design`；PRD 定义冲突 → `PRD-Design` |
| ⑦ UI/UX 评审 | `.spec/设计评审/任务清单.md` | 设计稿问题 → `UI-UX-Design`；布局冲突 → `Prototype-Design`；PRD 定义冲突 → `PRD-Design` |
| ⑩ 技术方案评审 | `.spec/技术方案评审/任务清单.md` | 后端 → `Backend-Tech-Design`；前端 → `Frontend-Tech-Design`；双方 → 先后端后前端 |
| ⑬ 代码评审 | `.spec/代码评审/任务清单.md` | 后端 → `Backend-Dev`；前端 → `Frontend-Dev`；双方 → **先后端后前端** |

> 修改方 Skill 内部已含「评审任务清单检测」与「回填」步骤，编排器**只指定入口，不重复实现**。
>
> **评审节点与 ⑥⑦ 均可跳过**：用户说「跳过代码评审，直接测试」即从 ⑫ 跳到 ⑭；用户说「跳过原型评审，直接做方案」即从 ④ 跳到 ⑧；用户说「跳过 UI/UX 评审，直接做方案」即从 ⑥ 跳到 ⑧；用户说「跳过设计稿，直接做技术方案」即从 ⑤ 跳到 ⑧。

## 六、PIPELINE.md

- **路径**：被开发项目根目录 `.spec/PIPELINE.md`
- **模板**：`assets/pipeline-template.md`
- **唯一写入方**：本 Skill；子 skill 只读不写
- **作用**：跨会话续跑的唯一依据

只记录**本次路径涉及的节点**，不写死全部节点。核心三段：

1. **本次路径**：起点、终点、计划节点序列、跳过节点；
2. **进度**：每个涉及节点的状态与产物路径；
3. **交接记录**：每节点完成追加一条。

## 七、铁律（强制）

1. **编排器不产出业务文档**——只写 `.spec/PIPELINE.md`，需求/原型/设计稿/方案/代码/测试报告一律由子 skill 产出。
2. **状态以落盘为准**——判断进度只读 PIPELINE.md，不靠对话记忆；每节点完成即时回填。
3. **每节点完成必须停下等用户决定**——不得自动往下跑（用户明确说「一路做到 X」除外）。
4. **前置缺失就阻塞，不硬推**——不许「先跑着，回头补」。
5. **评审未清零不放行**，回退轮次超 3 交回用户。
6. **串行处不许并行**——`⑧→⑨`、`⑪→⑫` 严格串行。
7. **子 skill 内部规程优先**——其内部 Gate、必问项、提交门禁（含 ⑥ 的 Superdesign 成本红线：变体数量与花钱动作由用户裁决）照常执行，编排器不越权代答。
8. **子 skill 永远可独立调用**——本 Skill 只是可选的串联方式，不改变任何子 skill 的原有行为。

## 八、常见错误对照表

| 常见错误 | 纠正方式 |
|---------|---------|
| 编排器自己动手写了 PRD / 方案 / 设计稿 / 代码 | 只调度，不代劳 |
| 凭对话记忆判断进度，没读 PIPELINE.md | 每次启动先读 PIPELINE.md |
| 节点做完自动往下跑 | 停下等用户决定（除非用户说一路做完） |
| 用户只点名一个节点，却跑了整条链 | 终点未指定 = 只跑起点节点 |
| 前置缺失时自己造占位文件继续跑 | 阻塞并提示，由用户决定补跑还是换起点 |
| 让 TDD 与 FTDD、或前后端开发并行 | 两处硬串行，不并行 |
| 评审出 P0 但用户「以后再说」，编排器放行 | 未清零不放行；用户坚持则标「已忽略」并附理由 |
| 回退无限循环 | 轮次上限 3，超限交回用户 |
| 子 skill 目录找不到就猜路径 | 按 §4.2 询问用户，不猜测 |
| 起点没确认就开始跑 | 自动推断的起点必须经用户确认 |
| ⑥ 生成设计稿时擅自加变体/多轮生成 | 子 skill 成本红线优先：额度是用户的，花钱动作等用户裁决 |
