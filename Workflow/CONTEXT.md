## 一、角色定位（Who We Are）

- **Skill 人设**：技术项目经理（Technical PM / Delivery Lead），负责把 14 个专业 Skill 按要求串起来推进，不亲自产出任何交付物；
- **核心目标**：让用户「说一句话就能从任意节点起跑，并随时决定要不要继续」；
- **铁律（Domain Boundary）**：本 Skill **只做调度、记账、守门**——不写 PRD、不画原型、不做技术方案、不写代码、不做测试报告。所有交付物一律由子 skill 产出。

## 二、术语表（Glossary）

| 术语 | 英文/Key | 权威定义 | 易混淆概念排除 |
|---|---|---|---|
| 节点 | Node | 链上的一个执行单元，一一对应一个专业 Skill（如「④ 原型设计」= `Prototype-Design`，「⑥ UI/UX 设计」= `UI-UX-Design`，「⑦ UI/UX 评审」= `UI-UX-Review`）。14 个节点按默认顺序排列成链 | ❌ 不是「阶段（Stage）」——「阶段」隐含必须按顺序走完全量；节点可任意作为起点 |
| 链 | Chain | 14 个节点的默认排列顺序：竞品分析 → PRD 设计 → PRD 评审 → 原型设计 → 原型评审 → UI/UX 设计 → UI/UX 评审 → 后端技术方案 → 前端技术方案 → 技术方案评审 → 后端开发 → 前端开发 → 代码评审 → 测试 | ❌ 不是「流水线（Pipeline）」——流水线隐含单向不可跳过；链上任意节点可跳过 |
| 起点 | Entry Node | 本次执行的第一个节点。由用户点名，或从 `.spec/` 已有产物自动推断（**推断后必须经用户确认**） | ❌ 不是「流程的开始」——不是每次都从 ① 开始 |
| 终点 | End Node | 本次执行的最后一个节点。**用户不指定 = 只跑起点这一个节点**，跑完停下 | ❌ 不是「默认跑到 ⑬ 测试」 |
| 路径 | Path | 本次实际要跑的节点序列（起点 → 终点的链上区间，扣除跳过节点） | ❌ 不是固定的 13 段流程模板 |
| 跳过 | Skip | 用户决定不做某个节点。PIPELINE 中标记 `已跳过` 并写原因 | ❌ 不是「裁剪（Trim）」——裁剪预设了「全量是默认、跳过是例外」，本模型下跳过是一等公民 |
| 前置 | Prerequisite | 某节点开工前必须具备的产物，实际读目录校验；缺失即阻塞并提示 | ❌ 不是「软依赖」——本模型不做硬/软依赖分级，前置未满足一律阻塞；可选增强项只是「有则用」，不构成依赖 |
| 交接记录 | Handoff Record | 每完成一个节点在 PIPELINE 追加一条，含产出物 / 给下游的输入 / 遗留待确认 / 用户决定。是节点间唯一交接契约 | ❌ 不是口头交接；❌ 不是评审任务清单（那是评审→修复闭环的载体） |
| 回退 | Rollback | 评审节点（③⑤⑦⑩⑬）任务清单中 `已确认` > 0 时，回退到修改方 Skill 修复，再重跑评审。轮次上限 3 | ❌ 不是「重做」——重做是重跑当前节点，回退是回到上游节点 |
| 子 skill | Sub-skill | 被本 Skill 调度的 14 个专业 Skill。始终可独立调用，不经编排层 | ❌ 不是「子流程」——它们是完整独立的 Skill，本 Skill 不改变其行为 |
