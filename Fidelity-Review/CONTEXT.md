## 一、角色定位（Who We Are）

- **Skill 人设**：资深前端 UI 验收专家（UI Fidelity Reviewer）；
- **核心目标**：把「前端实现页面」对照「UI 设计稿（双通道基准）」做逐页还原度评审——视觉还原（布局/层级/颜色/字号/间距等）+ 交互还原（可点性/反馈/方式一致）+ 超长文案健壮性专项，输出分级问题清单（每条含截图、成因、修改建议）；
- **职责边界（Domain Boundary）**：只审不改；只评「实现页 vs 设计稿」的还原度。**不评**业务逻辑正确性（归 Testing）、接口契约/架构（归 Code-Review）；**不评**设计稿本身质量（归 UI-UX-Review / UI-UX-Design）；不参与开发（Frontend-Dev）。设计稿自身缺陷 → 修改方为 UI-UX-Design。

## 二、术语表（Glossary）

| 术语 | 英文/Key | 权威定义 | 易混淆概念排除 |
|---|---|---|---|
| 页面还原度评审 | Fidelity Review | 对照 UI 设计稿逐页评审前端实现页面的「设计长什么样、实现变没变样」，输出视觉+交互+超长文案三大评审面的分级问题清单 | ❌ 不是「设计稿评审」（UI-UX-Review：审 UI-UX-Design 产物本身）；❌ 不是「代码评审」（Code-Review：逻辑/代码层） |
| 还原度 | Fidelity | 实现页对设计稿的忠实程度；与 Frontend-Dev 的 `fidelity-guide.md` 同词系 | ❌ 不是「还原基线」（那是 Frontend-Dev 开发时对原型/设计稿的承诺；本 skill 是第三方独立验收） |
| UI 设计稿 | Design Mockup | 视觉基准（应然）：UI-UX-Design 产出的 `.spec/设计稿/` 高保真 HTML + design-system，或用户指定的外部设计稿 | ❌ 不是原型（`.spec/原型/`，低保真，仅作交互存在性辅助）；❌ 不是实现页（实然） |
| 双通道基准 | Dual-Channel Baseline | 通道 A = `.spec/设计稿/`（含 design-system token，可机械比对）；通道 B = 用户指定外部设计稿（Figma 导出/PNG/README，目测比对） | ❌ 不是「任选其一」——A 存在则优 A，B 仅在 A 缺失时启用 |
| 视觉还原 | Visual Fidelity | 实现页与设计稿在页面设计/布局/层级/颜色/字号/间距/圆角阴影/图标图片/三态上的一致程度 | ❌ 不是「交互还原」（可点性/反馈）；两者分开走查 |
| 交互还原 | Interaction Fidelity | 实现页可点元素能点、点击反馈正确、交互方式与设计稿一致、普适交互（Tab/弹层/表单校验）正常 | ❌ 不含业务逻辑正确性（点了后端成功与否归 Testing/Code-Review） |
| 超长文案专项 | Overflow Probe | 用真实业务文案 + 极端长文案替换动态文本位，验证实现页是否溢出/遮挡/换行错乱/布局被挤崩（设计稿短文案好排版、实现页长文案崩 = 问题） | ❌ 不是「文案一致性」（核对写没写对）；是「文案变长后样式崩不崩」 |
| 截图必证 | Screenshot Evidence | 一切样式/视觉/溢出问题必须配浏览器截图（实现页截图，必要时与设计稿并排对照），存 `screenshots/` | ❌ 不是「可选增强」——硬性产出 |
| 还原度报告 | Fidelity Report | `.spec/页面还原评审/页面还原度评审报告.md`：分三大评审面逐页问题清单，每条含出处/现象/期望 vs 实际/成因/严重度/修改建议/建议修改方 | ❌ 不是任务清单（报告是分析；清单是任务收口） |
| 评审任务清单 | Review Issue List | `.spec/页面还原评审/任务清单.md`，单一事实源，状态 待确认→已确认→已修复/已忽略 | ❌ 只在独立模式产出；Testing 场景不建 |
| 轻量问题清单 | Mini Issue List | Testing 调用本 skill 时就地输出的问题清单（编号/页面/现象/严重度/截图/建议），供 Testing 汇总 | ❌ 不是任务清单（无状态机、无修改方闭环） |

| D-03 | 2026-09-05 | 职责边界：**独立专项能力**——Code-Review 只管逻辑/代码层不碰页面样式；本 skill 专吃「前端实现页 vs 设计稿」的视觉+交互还原；**Testing 内部会调用本 skill** 做 UI 还原度检查 | 用户明确：Code-Review 是逻辑/代码层；Testing 中做还原度是其一部分，独立出来是为了「有设计稿和页面即可单独触发」（用户裁决） | ✅ 已确认 |
| D-04 | 2026-09-05 | 评审范围 = **视觉还原 + 交互还原**。交互还原取**全量 + 普适项**：除设计稿驱动的交互（可点性/反馈/跳转链路）外，还查 Tab 切换/弹层抽屉开关/表单校验反馈等常见 UI 交互 | 用户补充：除样式外还要处理交互问题（设计稿按钮可点、实现页点不动、交互方式变了都算）；范围贴近「页面好不好用」（用户裁决选交互全量+普适项） | ✅ 已确认 |
| D-05 | 2026-09-05 | 特色专项 = **超长文案健壮性**：设计稿短文案好排版，实现页接真实/长文案崩（溢出/遮挡/换行错乱/布局挤崩）= 问题，必配截图 + 给修改建议 | 用户点名典型场景：一行文字设计稿是好的、实际文案多导致样式错乱 | ✅ 已确认 |
| D-06 | 2026-09-05 | 交付形态 = **双模式**：①独立调用：只审不改，产出 `.spec/页面还原评审/` 报告 + 分级清单 + 截图 + **任务清单交 Frontend-Dev**（沿用仓库评审闭环，设计稿缺陷回 UI-UX-Design）；②被 Testing 调用：作为其 UI 还原度检查环节**就地输出轻量问题清单**供 Testing 汇总，不另建任务清单 | 用户裁决选双模式：既要独立闭环可验收，又要能被 Testing 内嵌不冲突 | ✅ 已确认 |
