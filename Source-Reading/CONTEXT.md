# Source-Reading 设计上下文

## 为什么造（2026-09-18）

用户学习大型开源仓库（react / vue3 级）时缺一个「翻译器」：源码能看但抓不住主线，网上教程要么太啰嗦要么图文两张皮。需要一个 skill：给定 GitHub 仓库 → 产出「流程图 + 通俗易懂的关键点讲解」，帮助快速建立心智模型。

## 用户原始诉求（逐轮澄清，全部落进 SKILL.md §一）

1. 根据GitHub 仓库源码生成学习材料：流程图 + 关键点实现逻辑
2. 大仓库（react/vue3 级）拆分成多章节生成
3. （澄清①）不是「简介」——是**实现的关键点以通俗易懂的语言描述，不啰嗦**
4. （澄清②）**逻辑清晰**是快速学习的命根子：章节=阅读顺序、每章一条主线、图文一一对应
5. （澄清③）**前置知识铺垫**：用到用户可能不懂的概念先给简介+权威链接再进正题；链接必须核实，**错误的宁可不给**（误导比缺失更糟）

## 关键决策

| 决策 | 理由 |
|---|---|
| 流程图用 mermaid | GitHub/VSCode 原生渲染、纯文本可版本化，与本仓 README 一致 |
| 大仓「先出章节规划确认再动笔」 | 对齐 Prototype-Design 布局清单的确认习惯；避免 10 章写完方向不对 |
| 拆章按子系统/核心流程，不按目录 | 学的是逻辑不是文件夹；「调度+协调+提交」塞一章必炸 |
| 每章固定骨架（位置→前置→问题→图→关键点→衔接） | 骨架固定才能保证「逻辑动线唯一」，读者不迷路 |
| 关键点 = 锚点 + 干什么(≤2句) + 为什么(≤2句) | 通俗+不啰嗦的可执行化；「为什么这么设计」是学习源码的核心价值 |
| 链接宁缺毋错 | 用户明确强调：错误链接误导学习，拿不准给「权威站点+搜索词」 |
| 源码克隆到工作区外临时目录 | 只读不写铁律；绝不污染在研项目 |
| 规模三档（小单文档/中3~5章/大5~10章） | 防小题大做，也防大仓硬塞一篇 |

## 与既有 skill 的关系

- **OSS-Radar**：边界分工——本 skill 帮用户「学会」；OSS-Radar 借「优秀实践」反哺自有 skill。学习过程中若发现可借鉴实践，报 OSS-Radar 任务清单，不自己改。
- **Competitive-Analysis**：产品/商业层调研归它，本 skill 只管工程实现理解。
- **Skill-Optimizer**：本 skill 自身问题走 `issue/Source-Reading/` 埋点。

## 待观察点（首跑后回填）

- 规模分档阈值（2万/10万行）是否符合实际手感
- 单章 300 行上限是否太紧/太松
- 锚点抽查比例（每章 ≥2）是否足以兜住漂移
