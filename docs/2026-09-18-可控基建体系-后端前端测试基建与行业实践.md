# 可控基建体系：后端/前端/测试基建清单 · 语言无关设计 · 行业实践 · RSI 之辨

> **日期**：2026-09-18（同日补全测试基建清单）
> **来源**：ZCode 会话整理
> **主题**：从「AI coding 产物可控」出发，讨论后端基建清单 → 行业对应实践 → 语言无关的基建体系设计 → RSI 与 Harness 之辨 → 前端基建清单 → 测试基建清单 → 大模型厂家基建动态

## 一、后端基建清单（八大类）

### 1. 流量入口层
- **API 网关**：统一入口、路由转发、鉴权前置（Nginx、Kong、APISIX、Spring Cloud Gateway）
- **负载均衡**：Nginx、LVS、云 SLB
- **限流 / 熔断 / 降级**：Sentinel、Hystrix、Resilience4j

### 2. 服务治理
- **服务注册与发现**：Nacos、Consul、Eureka、ZooKeeper
- **配置中心**：Nacos、Apollo、Consul（配置动态下发、热更新）
- **服务间通信**：gRPC、Dubbo、Feign
- **分布式事务**：Seata、本地消息表、TCC/SAGA

### 3. 数据存储层
- **关系型数据库**：MySQL、PostgreSQL（读写分离、分库分表）
- **缓存**：Redis、本地缓存（Caffeine）、多级缓存
- **搜索引擎**：Elasticsearch、MeiliSearch
- **对象存储 / 文件服务**：MinIO、OSS、S3
- **OLAP / 数仓**：ClickHouse、Doris
- **时序数据库**：InfluxDB、Prometheus TSDB

### 4. 异步与任务
- **消息队列**：Kafka、RabbitMQ、RocketMQ、Redis Stream（削峰、解耦、异步）
- **定时任务 / 调度**：XXL-Job、Quartz、Elastic-Job、BullMQ
- **延迟任务**：订单超时关闭等（延迟队列、时间轮）
- **工作流引擎**：Temporal、Camunda（审批流、流程编排）

### 5. 可观测性
- **日志系统**：采集、聚合、检索（Logback/Pino → ELK / Loki）
- **指标监控与告警**：Prometheus + Grafana、云监控
- **链路追踪**：SkyWalking、Jaeger、OpenTelemetry
- **健康检查与探活**：/health 接口、K8s 探针

### 6. 安全与合规
- **认证授权**：登录态、SSO、JWT/OAuth2/RBAC（Keycloak、Casbin）
- **数据安全**：加密存储、脱敏、传输 HTTPS
- **幂等与防重**：防重复提交、防重放
- **审计日志**：操作留痕
- **内容安全**：敏感词过滤、风控

### 7. 通用业务组件
- **分布式锁**：Redis/Redisson、ZooKeeper
- **全局唯一 ID**：雪花算法、号段模式（发号器）
- **通知服务**：短信、邮件、站内信、App 推送（统一封装多渠道）
- **Excel 导入导出**、PDF 生成、水印

### 8. 研发效能与交付
- **CI/CD**：Jenkins、GitLab CI、GitHub Actions
- **容器化与编排**：Docker、Kubernetes
- **API 文档**：Swagger/OpenAPI 自动生成
- **灰度发布 / 蓝绿部署**、压测（JMeter、k6、wrk）

**中小项目优先级**：数据库 + 缓存 + 日志 + 统一响应/异常处理 + 认证授权 + 消息队列 + 定时任务 + 监控告警；网关、配置中心、链路追踪等上规模再加。

## 二、核心方法论：让 AI coding 产物可控的三层保障

**背景**：先搭好基建，AI coding 遇到基建场景就直接用基建，不同的 AI 写同样的业务，最后写出来的代码可控。变的只是业务逻辑本身，业务逻辑再按固定流程写。

**结论**：可控性的来源不是「有基建」，而是「AI 被强制使用基建」。需要三层保障：

### 第一层：基建本体（两种形态）
- **代码形态（SDK/共享包）**：AI 写业务时直接 import——统一响应体、错误码、异常处理、日志 SDK（带 traceId/脱敏）、鉴权装饰器、幂等组件、分布式锁封装、发号器、Excel、通知服务
- **环境形态（独立服务/中间件）**：AI 不写它但要用它的规范——MQ、调度平台、Redis、ES、对象存储、日志平台、监控告警
- **关键设计原则：基建 API 要「防呆」**——AI 容易用对、难用错。日志不暴露原生 Logger 而是暴露 `bizLogger.orderEvent()`；响应只有一个 `ok()/fail()`。**API 面越窄，AI 自由发挥空间越小。**

### 第二层：AI 约束文档（最容易被忽略）
基建写完了 AI 不知道或知道了不用，需要 AGENTS.md/CLAUDE.md 写**场景 → 组件映射表 + 禁止事项**：

```markdown
## 技术决策一律使用基建，禁止自造
- 需要日志 → 用 @app/logger 的 bizLogger，禁止直接 console.log / new Logger
- 需要异步/解耦 → 用 @app/mq 的 publish()，禁止自己写 setTimeout 轮询
- 需要定时任务 → 在调度平台注册，禁止用 setInterval/cron 库裸写
- 需要锁 → redisLock(key, fn)，禁止基于数据库的 DIY 锁
- 需要返回值 → 统一用 ResponseUtil.ok/fail，禁止自定义响应结构
```

### 第三层：机器强制（兜底）
纯靠提示词不是 100% 可控，CI 加机器检查：
- ESLint 自定义规则：禁 console.log、禁直接 import 原生库
- Code Review 清单 + CI 卡点
- **即使换一个没读过文档的 AI，产物也被物理约束收敛到基建上**

**反驳「AI 变强就不需要基建」的论据**：
1. AI 越强，失控越快——无约束 AI 把「能跑但风格各异」的技术债产出速度放大 10 倍
2. 功能实现是一次性的，维护是终身的——可维护性 = 变更时受影响范围小 + 接手时理解面窄，基建收敛正是这两个指标的实现
3. 没有公司因为「招的都是高级工程师」就取消框架、规范和 code review
4. 模型会换代，基建会留下——可控性存在于你的仓库里，而不是模型里

**案例库三补强**：
- **兜底规则**：遇到案例库未覆盖场景，禁止自行发明，先复用最接近模式并在注释中标注待确认
- **反例库**：每个基建组件配一条「禁止写法」（AI 会混用训练数据里的其他风格）
- **案例库版本化**：基建 API 升级时案例库必须同步更新，作为发布流程固定环节

## 三、行业对应实践（2026）

「个人实践」已成体系化方法论，每层都有对应物：

| 你的做法 | 行业叫法 | 代表 |
|---------|---------|------|
| 基建收敛 | Platform Engineering / Golden Path / Paved Road | Netflix paved road、Spotify golden path、Backstage；2026 趋势：IDP 成为「企业级 AI 网关」 |
| skill 案例库 | Agent Skills（开放标准）+ AGENTS.md | Anthropic SKILL.md 规范；AGENTS.md 已有 60k+ 开源项目采用 |
| 业务按固定流程写 | Spec-Driven Development | GitHub Spec Kit、AWS Kiro（需求→设计→任务→AI 实现，AI 不做技术决策） |
| 机器兜底 | Repository Guardrails / 架构即代码 | ESLint `no-restricted-imports`、ts-arch/ArchUnit、CI 卡点 |

**机器兜底层的关键洞察**：约束要写在仓库和 CI 里而不是提示词里；lint 报错 agent 自己能读到并自我修正，所以机器检查不只是「拦截」，还是「反馈回路」。

**行业有、方案里还缺的两块**：
- **Evals（约定回归测试）**：把历史「标准 PR」做成 golden tasks，案例库改版后跑一遍验证 AI 产物是否仍合规——给 skill 体系本身做回归测试
- **MCP（把基建暴露为工具）**：把发号器、脚手架、部署封装成 MCP 工具，AI 只能通过工具调用使用基建，物理上没有自由发挥的入口

## 四、语言无关的基建体系设计（个人 NestJS / 公司 Java）

**核心原则：清单抽象到「能力」层，实现做成可插拔的「档案（Profile）」层。** 行业先例：SLF4J 之于日志、JDBC 之于数据库、OTel API 之于可观测性。

### 三层结构

```
┌─────────────────────────────────────────────┐
│  能力层（语言无关，核心资产，只写一份）         │
│  能力清单 + 场景映射 + 契约 + 禁止事项          │
│  全程不出现任何库名、框架名                     │
├─────────────────────────────────────────────┤
│  档案层（每个环境一份薄映射，可插拔）           │
│  profiles/personal-nestjs.md                 │
│  profiles/company-java.md                    │
├─────────────────────────────────────────────┤
│  实现层（基建本体）                            │
│  个人：NestJS SDK + 中间件                    │
│  公司：内部 starter / 平台服务 / 中间件         │
└─────────────────────────────────────────────┘
```

### 能力卡片写法（成败关键）

❌ 语言绑定的写法：定时任务用 BullMQ 的 Worker，延迟用 delayed job

✅ 能力卡片的写法（描述语义和验收标准，与语言无关）：

```markdown
## 能力：定时任务
- 触发场景：周期性业务（对账、结算、数据同步）、延迟动作（超时关单）
- 契约：任务必须幂等；多实例部署不允许重复执行；失败要有重试与告警；
       业务逻辑写在独立处理函数中，不允许把业务散落在调度配置里
- 禁止：业务代码内自建轮询/setInterval；绕过调度平台直接 cron
- 实现：见 profile 的「定时任务」条目
```

### 「公司优先、个人兜底」决策链（skill 固定开工动作）

```markdown
## 基建选择决策链（每个任务开工时执行）
1. 读取当前仓库，盘点已有基建：
   - 看 AGENTS.md / README / 依赖清单（pom.xml、build.gradle、package.json）
   - 识别已有能力：日志门面？MQ 客户端？调度平台接入？统一响应封装？
2. 仓库已有某能力的基建 → 必须用公司的，映射表用 company profile
3. 仓库没有、但个人基建覆盖 → 问用户：引入个人基建还是用公司推荐？
4. 都没有 → 按 skill 默认选型生成，并在方案文档中标注为待评审决策
```

### 语言无关的边界：两级案例
- **语义级案例**（语言无关，只有一份）：流程 + 契约 + 伪代码——skill 主体
- **语言级案例**（每个 profile 一份薄样例）：同一场景 NestJS/Java 各写一遍——代码风格 few-shot
- AI 工作流：语义案例定流程 → 档案表定组件 → 语言案例定风格

### 落地四件套
1. `infra-capabilities.md` —— 能力清单（语言无关核心资产）
2. `profiles/*.md` —— 每环境一份映射表（约 50 行）
3. skill 决策规则 —— 基建盘点优先级链
4. 每环境的语言级案例目录

**隐藏福利**：沉淀的是方法论不是代码——个人 NestJS 封装的坑以「契约经验」形式迁移到公司 Java 环境，跨语言可复用。

## 五、RSI 与 Harness 之辨

**「RSI 取代 Harness」混淆了两个问题**：RSI 优化的是模型能力（能不能写好代码），体系解决的是收敛（无数个都写好的方案里选哪一个）。能力再强也不会自动产生收敛——你的基建/案例库/固定流程本质是一台「收敛器」，把无限解空间压到一个解。

**即使 RSI 成立，三样东西替代不了**：
1. **事实性约束**：公司用什么基建、哪些数据要脱敏——是事实和既有承诺，只能被「告知」，告知这个动作就是 harness
2. **评价标准**：自我改进需要目标函数——能力卡片（契约+验收标准）就是目标函数；没有 harness 的 RSI 是没有损失函数的优化
3. **多主体协作**：真实工程是多个 AI 会话 + 人类 + 已有代码库的协作，多个独立实例产出一致结果按定义需要共享协议

**诚实的分层——harness 里会过时的与升值的**：
- 贬值：HOW 层散文规则（函数不超 50 行、命名方式）——模型变强后价值趋零
- 升值：WHAT/WHY 层契约（延迟任务必须幂等、错误码编排、公司基建映射）——模型永远无法从预训练推出，只能显式供给
- 行动：继续加重契约和机器检查比重，少写风格类说教

**时间尺度**：模型六个月一代，RSI 是模型层事件；能力清单、profile、契约库在项目层/公司层，不随模型换代贬值。**强 AI 时代，代码变成一次性商品，契约、评测、基建映射才是仓库里真正的资产**。拥有目标函数的人就是技术方向的所有者。

## 六、初衷：可维护的代码运行系统

**目标不是「AI 写出可控的代码」，而是「持续变更的能力」**——代码是某个周末的快照，系统是让快照三年内还能被安全修改的机制。AI 写码速度×10 而理解能力没留在团队 = 没人敢动的黑箱 = 负债不是资产。

四条由此推导的设计决策：

1. **把「人能不能看懂」设为验收标准**——「新人测试」：任何新会话或新同事，能在半天内理解任意模块并安全地改它。命名表达业务语义、模块有入口文档、变更可在不动其他模块下完成。
2. **AI 产出必须包含「给人看」的部分**——代码 + 模块说明 + 关键决策理由（ADR）。ADR 是当时的你留给未来的你的信。
3. **业务层宁可直白，不要聪明**——AI 爱在业务代码里展示技巧（三层泛型、微妙重载、三行压缩）。模型的智慧是临时状态，仓库的可读性是永久状态，宁可牺牲前者保后者。
4. **所有事统一于此**——基建收敛=人只需理解一套技术事实；固定流程=一种代码叙事；能力卡片=读规格即可判断代码对错；机器兜底=标准不依赖某人记得。

**宪法序言（建议写进 skill 第一屏）**：

> 代码的读者是人，AI 只是作者之一。一切规则服务于：系统永远可被新人理解、可被安全修改。

**裁决标准**：让系统更可懂的规则留下，只是让生成更爽的丢掉。

## 七、前端基建清单（十二类）

### 1. 工程化底座
脚手架/项目模板（统一新项目起点）、Monorepo（pnpm workspace + Turborepo/Nx）、构建体系（Vite/Webpack 配置收敛）、多环境配置

### 2. 代码质量与规范
ESLint + Stylelint + Prettier 三件套（AI 兜底也靠它）、TypeScript 严格模式、路径别名、husky + lint-staged + commitlint、测试（Vitest 单测 + Testing Library 组件测试 + Playwright E2E）

### 3. UI 组件与设计系统（前端重头）
组件库二次封装（业务组件 ≠ 原子组件）、Design Tokens（颜色/间距/字号/圆角统一变量，暗黑主题靠它）、图标/字体/栅格统一供给、设计规范文档（也是给 AI 看的基建）

### 4. 网络与数据层
请求封装（axios 实例统一拦截器/错误处理/重试/取消/loading）、接口契约对齐（OpenAPI → TS 类型自动生成，与后端单一事实源联动）、状态管理（客户端 Zustand/Pinia 与服务端 TanStack Query/SWR 分离）、Mock 体系（MSW）

### 5. 路由与页面骨架
路由守卫、懒加载、权限路由生成；布局系统（菜单、面包屑、多标签）

### 6. 权限与安全
token 存取/无感刷新/SSO 对接、按钮级/路由级/数据级权限、XSS 防护、水印、脱敏

### 7. 性能
代码分割、图片优化（懒加载/CDN/WebP）、虚拟列表、防抖节流工具库、Web Vitals 采集

### 8. 前端可观测性（前端特有）
错误监控（Sentry + sourceMap 还原）、埋点体系（PV/UV、点击流、曝光统一上报 SDK）、白屏检测、慢接口上报

### 9. 通用业务组件
文件上传（分片/断点续传）、Excel 导入导出、富文本/Markdown 编辑器、图表封装、打印、水印

### 10. 构建部署
CI/CD 前端流水线、静态资源 CDN 与缓存策略（hash 指纹）、微前端（qiankun/Module Federation，多团队才需要）、灰度发布 / Feature Flag

### 11. 国际化与多主题
i18n 方案（vue-i18n/next-intl）、RTL、时区货币

### 12. AI 时代新增（最重要）
AGENTS.md/CLAUDE.md 项目级 AI 指令、组件使用文档 + 页面模板库（AI 的 few-shot 案例库）、设计规范结构化版本（design-system.md，AI 还原设计稿有据可依）

**中小项目优先级**：工程化底座 + 请求封装 + 组件库二次封装 + 权限 + 错误监控。

## 八、测试基建清单（十大类）

> 测试基建与前后端基建同层：能力写成语言无关的能力卡片，实现落进 profile；AI 遇到测试场景直接用基建，不自选框架、不自造数据、不留无证据的「已测」。

### 1. 测试策略与流程
- **测试金字塔与配比**：单测为主、集成为辅、E2E 冒烟——配比写进项目规范，AI 不得自选
- **测试先行**：TDD/FTDD 文档先行出用例再写实现（与现有 skill 链路一致）
- **验收标准结构化**：Gherkin 单源，PRD → 测试矩阵可追溯
- **缺陷分级与回归集**：P0/P1 分级冻结、修复必加回归用例

### 2. 单元测试
- **框架**：Vitest/Jest（TS/JS）、JUnit + Mockito（Java）、pytest（Python）
- **覆盖率门禁**：行/分支阈值卡 CI（如 ≥80%）；禁止无断言凑数测试
- **Mock/Stub 规范**：只 mock 边界（网络/时间/随机/外部服务），不 mock 被测单元内部
- **测试数据构造**：factory + faker；禁止复制生产数据、禁止用例间共享可变数据

### 3. 组件与 UI 测试
- **组件测试**：Testing Library——按角色/文本查询，测行为不测实现细节
- **组件工作台**：Storybook（组件隔离开发、状态存档、视觉对照）
- **视觉回归**：Playwright 截图比对 / Chromatic（设计稿还原的机器校验，与 Fidelity-Review 联动）

### 4. E2E 与浏览器自动化
- **框架**：Playwright 优先（跨浏览器、trace、并行），Cypress 备选
- **选择器策略**：角色 / testid 优先，禁脆弱 XPath 与位置式 CSS 定位
- **网络拦截**：MSW（组件层）、Playwright route（E2E 层）——后端未就绪时前端可测
- **AI 走查**：browser-use 全状态 + 全点击覆盖、截图存证（Testing skill 既有 SOP）

### 5. 接口与契约测试
- **接口测试**：Supertest（内联集成）、Postman + Newman（集合化回归）
- **契约测试**：OpenAPI schema 校验（TS 类型自动生成 ↔ 后端单一事实源）；跨服务用 Pact
- **Mock 服务**：Prism（OpenAPI 直接起 mock）、MSW

### 6. 性能与压测
- **接口压测**：k6（脚本化、可进 CI）、JMeter（GUI 场景）、wrk（快速基线）
- **前端性能**：Lighthouse CI、Web Vitals 采集（LCP/INP/CLS 预算）
- **慢接口治理**：P95 时延预算 + 慢接口清单（Testing skill 既有产出）

### 7. 测试环境与数据
- **一键环境**：docker-compose 起 DB/Redis/MQ，本地 = CI
- **真实依赖集成**：Testcontainers（不 mock 数据库语义）
- **数据隔离**：每用例独立 seed，事务回滚或库级隔离
- **环境安全**：禁连生产、禁真实短信/支付通道（一律沙箱）

### 8. CI 集成与质量门禁
- **PR 门禁**：单测 + lint + build 必跑，红即禁合
- **覆盖率卡点**：降阈值需显式豁免并留记录
- **测试报告**：Allure / 内建 reporter——失败可定位到用例与截图
- **flaky 治理**：重试上限 + 失败分类（flaky / blocked / product），flaky 用例限期修或隔离出主集

### 9. 缺陷知识与回归资产
- **反模式池**：bug-patterns（失败模式 → 修复模式关联）
- **失败案例库**：failure case 存证（现象 / 根因 / 修复 / 回归用例）
- **golden tasks**：历史标准任务做回归——skill / 组件库改版后重跑（Evals 的种子）

### 10. AI 时代新增（最重要）
- **验收标准机器可读**：结构化 AC → 测试矩阵自动生成，AI 不自由解读「验收通过」
- **AI 测试产出也有门禁**：AI 跑的测试必须留证据（命令、结果、截图），无证据视为未测
- **Evals 回归**：换模型 / 换 skill 版本后跑 golden tasks，比对行为一致性而非源码一致性
- **测试能力卡**：测试基建同样写成能力卡片（场景 + 契约 + 禁止 + 实现见 profile），与前后端基建同层管理

**中小项目优先级**：单测框架 + 覆盖率门禁 → E2E 冒烟集 → OpenAPI 契约校验 → docker-compose 测试环境 → CI 门禁；视觉回归、Pact、Testcontainers 上规模再加。
