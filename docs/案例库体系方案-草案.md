## 0. 顶层定位与整合原则

### 0.1 体系顶层定位（2026-09-16 用户明确）

> **终极目标：Skill 体系 = 核心资产；Agent = 可替换的执行引擎。**
> 换任何 agent，装上这套体系即可照常干活；长期维护对象是这套体系与其案例库经验。

由此推出三条设计约束（**一等约束，优先级高于任何单点优化**）：

1. **资产与引擎分离**：核心资产（流程 / 模式 / 案例 / 模板 / 判据 / 门禁）必须与 agent 解耦；agent 专有能力只能作「增强」，缺失时降级而非崩溃。
2. **资产自包含可迁移**：把体系搬到任意环境（新机器 / 新 agent / 新安装方式）后，所有引用仍可解析——不得依赖仓库外路径或某 agent 专有机制。
3. **质量不依赖引擎智能**：流程要写到「换一个平庸的执行引擎也能跑对」——判据可执行、交付有 Gate、完成有证据（与既有「形式匹配失败类型」「完成声明证据门禁」同源）。

> 详细设计见 **§9**（v3 新增）。

### 0.2 两份方案的关系与整合原则

OpenAI 方案与本仓库**不在同一层面**，直接对比会得出错误结论：

| 维度 | OpenAI 方案 | 本仓库现状 |
|---|---|---|
| 性质 | **目标态蓝图**（To-Be），从零设计的完整 OS | **存量系统**（As-Is），已实际运行多轮 |
| 范围 | 全生命周期（含编排、Eval、Golden Path、Registry、Dashboard、90 天计划） | 16 专业 skill + 编排 + 元技能，聚焦"能干活的流程" |
| 成熟度 | 设计态，未在真实项目验证 | 已验证（含 SOP 化先例、门禁闭环、双向沉淀） |

**存量已覆盖（不必重建）**：

| OpenAI 提出 | 本仓库对应物 |
|---|---|
| Orchestrator + Gate Based Orchestration + Rework Loop | `Workflow`（一条链/任意起点/门禁闭环/上限 3） |
| Quality Gate（5 段） | 各 skill 的 Gate + Pre-Delivery Checklist + 完成声明证据门禁 |
| Progressive Disclosure（L0~L5） | 四级加载（L1 元数据 / L2 SKILL / L3 references / L4 scripts） |
| Knowledge Extraction + Postmortem | `issue/` 池 + `bug-patterns/` 池 + 评审闭环双向沉淀 |
| ADR（决策记录） | 各 skill `CONTEXT.md` 决策日志 D-xx（元层）+ 方案文档选型章节 |
| Pattern Library | **12 个 `references/case-library/`（本草案要升级的对象）** |
| Case / Evidence | 部分散落在 case-library 与 bug-patterns |
| Human-in-the-loop | 各 skill 的确认门（Gate 四类触发）+ P0/P1 冻结 |

**存量真正缺的（本草案要补的）**：Case 与 Pattern 未分离、无组合沉淀、无模式选择机制、无禁止自创规则、无去重规范、无决策置信度、无证据分级、无元数据过滤、无技术决策矩阵。

**整合原则**：**只吸收可映射到存量的补强，不照搬整体重构。**理由：① 用户既定原则「增量补强、不推翻现有框架」；② 归位原则——新内容先问归属，找不到归属说明结构缺一类，而不是把外部结构整体搬进来；③ 存量已验证有效，蓝图未经验证。

## 2. 体系设计

### 2.1 五类库的职责切分

拆分理由：用户举例的「前端模板」实际混装了两类东西（模板 vs 模式），照此细分后共五类。

| 库 | 解决什么 | 目录落点 | 消费方式 | 写入方 |
|---|---|---|---|---|
| **模式库** Pattern | 问题**怎么解**（通用知识） | `<skill>/references/case-library/` | 按需加载**参考** | 执行沉淀 + 池提炼 |
| **案例库** Case | 真实项目**怎么解的、结果如何**（实战证据） | 同上（独立文件或独立小节，见 §2.5） | 找同类证据 | 项目复盘 |
| **模板库** Template | 产出**是什么样** | `<skill>/assets/` | **复制 / 填充** | 人工封装 + 复盘固化 |
| **评审案例库** Known-Issues | **怎么查得准** | `<skill>/references/known-issue-patterns.md` | 评审时**对照** | 门禁闭环方向 B |
| **反模式池** Anti-Pattern | **什么不要再犯** | `bug-patterns/` + 各库 `anti-patterns` 段 | **提炼**进主流程 | Bug-Fix + 闭环方向 A |

> 判据：**"怎么做"→ 模式库；"谁做过、结果如何"→ 案例库；"产出什么"→ 模板库；"怎么查"→ 评审库；"别再做"→ 反模式池。**

### 2.2 三层职责

```
Agent
  └─ Skill（怎么工作 · 决定「何时加载哪份库」，主流程标注引用点）
       ├─ Library（怎么解决 + 产出什么）
       │    ├─ 模式库：问题 → 适用 → 不适用 → 解法 → 代价 → 证据
       │    ├─ 案例库：真实场景 → 选了哪些模式 → 结果数据 → 教训
       │    └─ 模板库：产物骨架 + REQUIRED 槽位
       └─ Decision / Evidence（为什么这么选 + 凭什么可信）
            ├─ 方案文档内：ADR 片段
            └─ 卡片内：决策置信度 + 假设 + 证据等级
```

### 2.3 模式库内部分区

**与编写规范的冲突与裁剪**：外部建议 `patterns/` 下分 `solution / anti / composite / production-cases / failure-cases` 目录；但本仓库编写规范 §二 已定「references **按领域组织**，不按类型」。

**v2 折中方案**（保留领域组织，吸收 OpenAI 的"分类必须显式"）：

```
<skill>/references/case-library/
├── 00-README.md            # 索引 + 规范（主流程唯一入口）
├── <领域 1>.md             # 如 reliability-patterns.md（限流/熔断/降级/幂等…）
├── <领域 2>.md             # 如 architecture-patterns.md
├── composite-patterns.md   # 复合模式（成熟组合方案）          ← v2 新增
├── anti-patterns.md        # 跨领域反模式（仅多条时建）        ← v2 明确
└── cases.md                # 实战案例（生产/失败/实验）        ← v2 新增，与模式分离
```

- **领域内反模式** → 写在该领域文件的「反模式」小节；
- **跨领域反模式**（多条且无单一领域归属）→ 建 `anti-patterns.md`；
- **复合模式** → 独立 `composite-patterns.md`（**v2 改判**：成熟组合本身是可复用资产，不应每次由模型现场组合）；
- **实战案例** → `cases.md`（或按项目建 `cases/<项目>.md`，条目多时再拆）；
- **单条模式仍留在领域文件内**，不按"一条一文件"拆（避免文件爆炸）。

### 2.4 解法模式卡 schema（Solution Pattern）

**格式：卡片头必填（Markdown 表格）+ YAML 元数据块可选。**

```markdown
### <模式名>（`<ID>`）

| 字段 | 值 |
|---|---|
| 场景 | 什么样的业务/量级下会遇到 |
| 适用边界 | 什么时候该用（**可判定谓词**，如 QPS ≥ 5000 且读写比 ≥ 10:1） |
| 不适用 | 什么时候别用（**反 AI 套用关键**：强一致性、命中率 < 20%…） |
| 代价与风险 | 引入了什么新问题（含失败模式：缓存穿透/击穿/雪崩） |
| 关联模式 | 见 §2.10 五类关系 |
| 证据等级 | L0 模型常识 / L1 一般经验 / L2 官方文档标准 / L3 自测实验 / L4 生产数据 |
| 决策置信度 | high / medium / low（+ 关键假设 + 未确定项） |
| 成熟度 | experimental / stable |
| 使用计数 | 被复用次数（用于体检"高频未升级"） |
| 上次验证 | YYYY-MM-DD |
| 状态 | 草稿 / 已收录 / 已升级为 SOP / 已废弃 |

**问题**：一句话说清要解决什么。
**解法**：核心做法（关键代码/配置/架构图）。
**反模式**：本领域内常见错误做法。
**出处**：链接（保可溯源）。
```

**决策置信度写法**（吸收 OpenAI §55）：

```yaml
decision:
  choice: cache-aside
  confidence: medium
  evidence_level: L3
  assumptions:
    - 读写比 > 10:1
    - 可接受最终一致
  uncertainty:
    - 峰值 QPS 未知
```

> 注：置信度**不是"模型觉得自己对"**，而是对证据与假设完整度的描述。

**可选 YAML 元数据块**（用于第一层筛选，见 §2.7）：

```yaml
---
id: backend.cache.cache-aside
category: [backend, caching]
tags: [redis, read-heavy]
problems: [high-read-load, database-pressure]
constraints: [eventual-consistency-acceptable]
related: [cache-penetration, cache-breakdown, distributed-lock]
status: 已收录
---
```

**ID 命名规范**（补 G1）：`<领域域>.<子域>.<模式名>`，全小写连字符。
例：`backend.cache.cache-aside`、`frontend.component.compound`、`prd.framework.rice`、`test.strategy.risk-based`。

### 2.5 实战案例卡 schema（Case，与 Pattern 分离）

**分离理由**（OpenAI §15）：Pattern = 通用知识（一般情况下怎么解）；Case = 实战证据（我在真实项目里怎么解、结果如何）。混在一起会导致"通用结论"与"单点事实"互相污染。

```markdown
### <案例名>（`<case-id>`，如 `ecommerce.hot-product-v1`）

| 字段 | 值 |
|---|---|
| 项目背景 | 业务、量级、约束 |
| 选用了哪些模式 | 引用模式 ID（组合关系） |
| 结果数据 | 可量化（QPS / P99 / 成本 / 人力） |
| 踩到的坑 | 未预料的问题与修复 |
| 教训 | 可迁移结论 |
| 类型 | 生产案例 / 失败案例 / 实验案例 |
| 出处 | 项目路径或链接 |

**最终决策**：…
**决策依据**：…
```

**四种卡片的分工**（吸收 OpenAI §82）：

| 卡片 | 回答 | 本仓库落点 |
|---|---|---|
| Solution Pattern | 一般情况下怎么解 | 各领域 `*-patterns.md` |
| Production Case | 真实项目怎么解、结果如何 | `cases.md`（生产） |
| Failure Case | 哪些做法失败了、为什么 | `cases.md`（失败）+ `bug-patterns/` |
| Experiment Case | 某个技术点实测结果 | `cases.md`（实验），**本仓库目前基本为空** |

### 2.6 模板库规范

模板分三种粒度（避免"模板"一词歧义）：

| 粒度 | 形态 | 例 | 消费方式 |
|---|---|---|---|
| **工程脚手架** | 可运行的项目骨架 | `Frontend-Dev/assets/frontend-template-react/` | 复制 → 改配置 → 起项目 |
| **文件/模块模板** | 单文件填充式 | `module-code-template.md` | 复制 → 填空 |
| **文档模板** | 骨架 + REQUIRED 槽位 | `overview-template.md` | 复制 → 逐槽填 |

**模板库索引（新增要求，补 G8）**：每个 skill 的 `assets/` 需具备索引（写入 skill README 或 `assets/00-README.md`），说明：有哪些模板（含粒度）／何时套用（对应主流程哪一步）／套用后必替换的槽位清单。

**模板维护闭环**：项目实践 → 复盘抽形态 → 封装/更新模板 → 下个项目套用 → 暴露问题 → 再修模板。
即用户说的「后续我只维护这套模板」——**模板 = 从做过的项目里抽出的最优形态**。

### 2.7 加载规则（"检索"的本地化）

本仓库无向量检索引擎，AI 靠**元数据过滤 + 索引导航 + 主流程引用点**，四层：

| 层 | 动作 |
|---|---|
| L0 | 主流程步骤写明"此时读 `<库>/00-README.md`" |
| L1 | 读 `00-README.md` → 按「何时读」列匹配当前场景 |
| L2 | **元数据先行过滤**：按 `category / tags / problems / constraints` 筛候选（**不扫全库**，控成本） |
| L3 | 仅加载命中的领域文件/卡片 |

三条硬要求：
1. **主流程引用点必标**（判据：下次不读这篇参考，是否就会照旧做错？是 → 必须进主流程）；
2. **「何时读」必写可判定谓词**（不写"需要时读"这类空话）；
3. **单层加载**（references 只嵌套一层）。

### 2.8 模式选择机制（v2 新增，补 G10）

**不要让 AI 直接给方案。**必须走候选-过滤-决策链条：

```
候选集合 → 兼容性过滤 → 约束过滤 → 风险过滤 → 证据检查 → 权衡分析 → 决策
```

输出格式：

```yaml
selection:
  selected: [backend.cache.cache-aside]
  alternatives: [backend.cache.write-through, backend.read-replica]
  reasons: [read-heavy, eventual-consistency-acceptable]
  rejected: [write-through]
  rejection_reasons: [unnecessary-write-path-complexity]
```

落点：方案类 skill（Backend/Frontend-Tech-Design）的选型步骤 + 方案文档记录。

### 2.9 禁止自创模式（v2 新增铁律，补 G11）

```
先搜已有模式 → 找到就复用
  → 不满足则组合已有模式
    → 仍不满足才提新模式候选
      → 人工确认后才入库存档
```

**不设此规则会发生什么**（真实风险）：

```
cache_strategy_v1 / cache_strategy_v2 / advanced_cache_strategy
smart_cache_strategy / hybrid_cache_strategy …
```

体系随之失控。

### 2.10 组合规则（v2 升级，补 G6）

关系五类（吸收 OpenAI §54）：

| 关系 | 含义 |
|---|---|
| `requires` | 前置依赖（没它不行） |
| `enhances` | 互补增强 |
| `conflicts` | 互斥（不可同用） |
| `replaces` | 替代关系 |
| `commonly-composed-with` | 常见组合搭配 |

**组合必须逐项过收敛证明**（沿用 `socratic-grilling`：失败场景 / 涨 10 倍 / 漏项 + 用户认可），未过不得写入方案。
**禁止清单式堆砌**：一次引入 ≥3 个新模式时，逐个说明"不做会怎样"，说不清就砍。

### 2.11 反过度工程化总规则（v2 新增）

> **复杂度必须由问题证明，而不是由技术偏好证明。**

低 QPS / 简单业务 / 单体应用 → 不主动引入 Kafka、K8s、微服务、分库分表、分布式事务、复杂缓存体系（除非有明确约束支持）。

这与本仓库既有"做减法铁律 + 量级不达阈值不引入（`decision-rules.md` §八）"同源，v2 将其**显式写成跨 skill 总规则**。

### 2.12 技术决策矩阵（v2 新增）

对重要选型维护对比矩阵（吸收 OpenAI §53）。示例：

| 维度 | Redis | Local Cache | CDN | Read Replica |
|---|---|---|---|---|
| 一致性 | 弱 | 最弱 | 弱 | 强 |
| 延迟 | 低 | 最低 | 最低 | 中 |
| 规模 | 高 | 单机 | 极高 | 中 |
| 运维成本 | 中 | 低 | 低 | 低 |
| 失败模式 | 依赖可用性 | 进程级失效 | 回源 | 主从延迟 |

落点：方案类 skill 的选型章节（替换"Redis 永远是答案"式默认）。

### 2.13 ADR 与证据的归属（本地化，不建独立 ADR 库）

| 承载处 | 内容 |
|---|---|
| 方案文档内（TDD/FTDD 选型章节） | ADR 片段：Context / Options / Decision / Rationale / Consequences |
| 卡片内 | 决策置信度 + 假设 + 不确定项 + 证据等级 |

**证据等级**（吸收 OpenAI §16）：`L0 模型常识 / L1 一般工程经验 / L2 官方文档·标准 / L3 自测实验·Benchmark / L4 生产环境数据`。
高风险决策**必须**用 ≥L2 证据；L0/L1 不得作为方案依据。

不建独立 ADR 库的理由：避免同一决策三处记录（归位原则：同一件事不说三遍）。

### 2.14 与现有两个池的关系

| 池 | 记什么 | 消费方 | 与案例库关系 |
|---|---|---|---|
| `issue/` | **skill 自身**方法论问题 | Skill-Optimizer 模式③ | 无关 |
| `bug-patterns/` | **代码/方案层面**的真实错误模式 | 方案/开发 skill（经提炼） | 原始卡留池溯源；提炼后的可执行规则进反模式 |

判据：**问题出在「skill 怎么干活」→ `issue/`；出在「写出的方案/代码有哪类坑」→ `bug-patterns/`；提炼后的通用解法 → 模式库。**

## 5. 维护机制

### 5.1 四个写入通道

| 通道 | 触发 | 写入方 |
|---|---|---|
| ① 执行中沉淀 | skill 跑完发现通用解法 | 该 skill 收尾 |
| ② 评审闭环双向沉淀 | 门禁闭环放行后（P0 必沉） | A 产出方防复发 / B 评审方检出方法 |
| ③ 池提炼 | Skill-Optimizer 模式③-附加 | 从 `bug-patterns/` 提炼成可执行规则 |
| ④ 用户直投 | 用户丢资料/经验 | 用户 → 落库 |

### 5.2 生命周期状态机（与成熟度正交，v2 设计）

```
草稿 ──(其他项目复用 ≥2 次)──> 已收录 ──("不读就会照旧做错")──> 已升级为 SOP
                                  └──(被新方案取代)──> 已废弃（保留卡片、标注替代者，不删）
```

**与 OpenAI 六态的映射**（v2 不照搬的理由）：OpenAI 把"成熟度"与"生命周期"混在一条链上（Draft→Experimental→Validated→Stable→Deprecated→Retired）。v2 拆为**两个正交维度**，更准确：

| OpenAI 态 | v2 表达 |
|---|---|
| Draft | 状态=草稿 |
| Experimental / Validated | 状态=已收录，成熟度=experimental |
| Stable | 状态=已收录/已升级为 SOP，成熟度=stable |
| Deprecated / Retired | 状态=已废弃 |

### 5.3 属性化记录（替代主观评分，v2 升级）

不写"9.5 分"这类主观分数，改记工程属性：

| 属性 | 取值 |
|---|---|
| status | 草稿 / 已收录 / 已升级为 SOP / 已废弃 |
| maturity | experimental / stable |
| evidence_level | L0~L4 |
| usage_count | 被复用次数 |
| last_validated | 上次验证日期 |
| known_limitations | 已知局限 |

### 5.4 知识去重（v2 新增）

库大到一定规模必然出现同义条目：

```
cache-aside / cache-aside-best-practice / redis-cache-aside
hot-data-cache / read-cache-strategy
```

规范：每条模式**必须**声明 `canonical`（规范名）与 `aliases`（别名）；同义条目合并，旧名保留为 alias 并标 `deprecated_by`。
落点：T1 §去重 + T9 体检项。

### 5.5 定期体检（挂 Skill-Optimizer 模式④）

| # | 体检项 |
|---|---|
| 1 | **孤儿条目**：卡片存在但主流程/索引无引用点 |
| 2 | **出处失效**：链接不可达 |
| 3 | **重复条目**：违反 canonical 规范 |
| 4 | **高频未升级**：usage_count ≥3 却仍为「草稿/已收录」→ 应升级 |
| 5 | **字段缺填**：缺「不适用 / 代价 / 证据等级 / 状态」 |
| 6 | **证据不匹配**：标 L3/L4 却无实测数据 |
| 7 | **过期未验证**：`last_validated` 超期（默认 12 个月） |

### 5.6 挂接点

- 规范 T1；模板 T2~T7；体检清单 T9；

## 9. 可移植性与资产自包含设计（v3 新增）

> 服务 §0.1 的一等约束：**换 agent / 换机器后，体系必须照常工作。**

### 9.1 三层模型

| 层 | 内容 | 可移植性要求 |
|---|---|---|
| **核心资产** | SKILL.md 正文（流程 / 铁律 / 判据）、`references/`（模式·案例·知识）、`assets/`（模板）、`shared/`（公共约定）、案例库全部条目 | **必须 100% 可迁移**：纯 Markdown / 文本，无 agent 专有语法 |
| **适配层** | 触发声明（frontmatter）、加载方式、工具映射、安装路径、记忆机制、并行 / 子 agent | **每个 agent 适配一次**；改动只允许发生在适配层，**不得倒灌核心资产** |
| **引擎** | Agent 本身（Claude Code / CodeBuddy / OpenCode / …） | 可替换，不产生依赖 |

| **P2** | **两个数据池（`issue/`、`bug-patterns/`）在源仓库根，不外发** | 同上 | 埋点写入无处可写；评审闭环沉淀无处可落 |
| **P3** | **安装路径硬编码** | Skill-Optimizer SKILL.md：`C:\Users\15136\.zcode\skills\` / `C:\Users\15136\.codebuddy\skills\` | 换机器（用户名不同）后同步指令失效 |
| **P4** | **兼容性只是静态声明，无适配机制** | 18 个 SKILL.md 均写 `compatibility: Claude Code / Agent SDK / OpenCode`，但无触发/加载/工具的差异说明 | 声明"兼容"却无章可循：不同触发或加载模型的 agent 上行为不可预期 |

### 9.3 补齐设计

#### (1) 可移植包（Distribution Bundle）

把"体系"定义为一个**自包含目录树**，而非"一堆散落的 skill 目录"：

```
tenger-skills/                 ← 可移植包根（整个目录可整体搬迁）
├── <各 skill 目录>
├── shared/                    ← 必须随包分发（修复 P1）
├── issue/                     ← 空骨架随包分发（修复 P2）
├── bug-patterns/              ← 空骨架随包分发（修复 P2）
└── INSTALL.md                 ← 安装 / 迁移说明（修复 P3）
```

- **P1**：`shared/` 纳入分发范围，安装时随体系一起落地。
- **P2**：两个池只分发**空骨架 + 规则 README**（不含历史数据）；历史数据由用户按需迁移。
- **P3**：安装文档不写死用户名 / 盘符，改用占位符（如 `<AGENT_SKILLS_DIR>`）+ 解析规则。

#### (2) 引用解析规则（消除路径歧义）

| 引用写法 | 解析规则 |
|---|---|
| `shared/xxx.md` | 相对**体系根**（可移植包根）解析 |
| `references/yyy.md`、`assets/zzz.md` | 相对**本 skill 目录**解析 |
| `.spec/`、`.codebuddy/memory/` | 相对**被开发项目根**解析 |

**要求**：每个 skill 的 SKILL.md 开头统一声明**三层根**（体系根 / skill 根 / 项目根），任何路径引用不得跨层混用。现状已有「仓库根 `shared/xxx.md`」写法，需统一为上述口径并补根声明（修复 Q11）。

#### (3) Agent 能力矩阵与降级策略

| 能力 | 用途 | 缺失时的降级（**不得崩溃**） |
|---|---|---|
| 读 frontmatter 触发 | 自动触发 skill | 手动点名 skill |
| 按需加载文件（渐进披露） | 省上下文 | 一次性读入（成本上升，流程不变） |
| **文件读写** | 全部流程 | **硬依赖，无降级** |
| 终端执行 | 跑测试 / 构建 / lint | 降级：产出命令清单交用户执行 |
| 浏览器 | 截图 / 核验 / 还原度审查 | 沿用既有两级策略（硬依赖 skill 报错等安装；软检测 skill 跳过） |
| 子 agent / 并行 | 三角色并行评审、并行还原度审查 | 串行执行（结论口径不变） |
| 记忆机制 | 跨会话上下文 | 不依赖：记忆是增益，非必需 |
| skill 调用工具（如 `use_skill`） | 主 agent 调子 skill | 降级：正文写「按 X skill 执行」，由主 agent 顺序执行 |

> **总原则**：核心流程只依赖「**文件读写 + LLM 推理**」这两项任何 agent 都具备的能力；其余全部是增强项，缺失即降级。

#### (4) 安装 / 迁移清单（`INSTALL.md` 必含）

1. 包内目录 → 目标位置的映射（用占位符，不写死路径）；
2. 必装项（skills + `shared/`）与可选项（池骨架、`chats/`）；
3. 迁移后自检：引用是否可解析 / 池是否可写 / 浏览器能力检测结果；
4. **不同 agent 的适配差异表**（触发方式、加载方式、工具名映射、安装目录）。

### 9.4 与既有约定的兼容

- **不推翻「信息单一归属」**：`shared/` 仍只存一份，靠"随包分发"而非"内联到各 skill"实现自包含（避免多处重复）。
- **不影响 §2 的库设计**：本章只解决"搬迁后引用不断"，与模式库 / 模板库的内部结构无关。
- **与既有浏览器两级策略同源**：该策略已是"能力检测 + 降级"的雏形，本章只是把它上升为全局原则并覆盖其余能力。
