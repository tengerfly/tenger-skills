# 用例编写指南：三段式 + 状态注入 + Mock 边界

> 解决「少流程、状态跑不到」：可达性靠 setup 注入，全面性靠状态机枚举，真实性靠 mock 边界。

## 一、三段式结构（强制）

每条用例 = `setup（注入前置状态）→ act（操作）→ assert（断言）`：

```yaml
id: TC-ORDER-014
模块: 订单管理
状态: 已支付·3天未发货            # 必须对应状态机节点（或页面清单条目）
关联AC: AC-M02-003
优先级: P0
setup:                            # ← 状态注入替代 UI 遍历
  - seed: order.create(status=paid, paidAt=now()-3d)   # API/DB 造数
  - mock: sms.send -> ok                                # 外部依赖 mock
  - intercept: GET /api/inventory/* -> 500              # 异常态拦截（按需）
act:
  - aiAct: 打开「我的订单」第 1 条订单详情
assert:
  - aiAssert: 显示「催促发货」按钮且可点击
  - expect: url 匹配 /orders/\d+
  - network: 全部响应 200、console 无 error
coverage: [order.paid, order.paid→reminded]             # 回填，覆盖率计算依据
```

模板见 [../assets/case-template.md](../assets/case-template.md)。

## 二、状态注入手法（setup 怎么写）

| 手法 | 适用 | 示例 |
|---|---|---|
| API 造数 | 有创建/配置接口（首选，最不易腐化） | `POST /api/test/seed-order` |
| DB 种子 | 造数接口覆盖不到的深层状态 | SQL/ORM 脚本插入订单+支付记录 |
| storageState | 登录态/权限复用 | 先登一次存 `storageState.json`，后续用例免登录 |
| 路由拦截 | 异常态/外部依赖 | `page.route('**/api/pay', 500)` |
| 时钟 mock | 过期类状态 | `page.clock.set()`：token 过期、优惠券过期 |

**原则**：浏览器只负责「到达状态后，页面表现对不对」；不要用 20 步 UI 操作去构造一个状态——又慢又 flaky 还到不了。

## 三、Mock 边界铁律（真实优先，mock 兜底）

| 类别 | 策略 | 例子 |
|---|---|---|
| **AI 服务（项目核心能力）** | **真实优先**：项目已接真实 LLM → 必须打真实链路；仅接口不通/无 key/超预算时降级 mock 并在报告声明 | LLM 生成剧本/摘要/题目 |
| 已配置测试凭证的第三方 | **真实优先**（用测试账号/沙箱环境） | 沙箱支付、测试号短信 |
| 会产生真实世界副作用的第三方 | **Mock**（无沙箱时） | 真实扣款、给真实用户发短信/邮件 |
| 异常/极端态 | **Mock/路由拦截** | 接口 500、超时、弱网、并发冲突 |
| 前置业务状态 | **注入真实数据**（不 mock 逻辑） | API/DB 造「已支付订单」 |
| 被测系统业务逻辑 | **绝不 mock** | mock 即失去测试意义 |

**降级规则**：先探测真实可用性（健康检查/一次最小真实调用）；不可用才降级 mock；每一次降级必须：① 在用例 `setup` 里显式标注 `provider: mock（降级原因）`；② 汇总进报告「覆盖边界声明」（哪些 AI 路径是 mock 跑的）；③ 修复项登记「真实链路未验证」。禁止默认全 mock 图省事——那等于核心功能零覆盖。

- mock 尽量按 OpenAPI 契约生成（与真实接口同源，防 mock 漂移）；
- 每条用例的 mock 必须写在 `setup` 里显式声明，禁止隐藏在公共代码里偷偷 mock；
- 报告中列出本条用例 mock 了什么——评审者需要知道哪些路径没被真实覆盖。

## 四、用例从哪来（生成顺序）

1. **状态机枚举**（主力）：读 PRD 状态机 → 列出全部状态 × 全部合法迁移 → 每个迁移至少一条用例；无状态机时按页面清单 × 三态展开，并登记基准缺失风险；
2. **AC 对照**：每条验收标准至少一条用例反标它；
3. **全点击补充**：每页可交互元素盘点，未覆盖的元素补用例或标原因；
4. **L3 探索转化**：探索发现的稳定缺陷固化为正式用例。

## 五、优先级与数量控制

| 优先级 | 定义 | 数量预期 |
|---|---|---|
| P0 | 核心链路主状态迁移 | 少而精，回归必跑 |
| P1 | 主要功能/次迁移/主要页面三态 | 主体 |
| P2 | 次要样式/文案/边缘迁移 | 可选跑 |

反冰淇淋反模式：E2E 用例不是越多越好——每条都要维护 mock 和种子；关键链路用 E2E，其余靠 L0/L1 兜底。

## 六、用例质量自检（写完每条过一遍）

- [ ] 状态字段对应状态机真实节点（不是「随便看看」）
- [ ] setup 能机器执行（命令/脚本可跑，不是人肉步骤）
- [ ] assert 有明确判据（预期有来源：AC/设计稿/契约，非臆断）
- [ ] mock 全部显式声明且不碰被测系统逻辑
- [ ] coverage 字段已填（否则覆盖率算不准）
- [ ] 失败时可复现（setup 可重置到初始态，用例间无顺序依赖）
