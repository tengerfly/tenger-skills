# 项目计划：企业级 AI 自动化测试系统（Auto-Test）

> 版本：v0.1（基于 2026-09-18 竞品调研，详见 `.spec/AI自动化测试竞品分析/AI自动化测试竞品分析报告.md`）
> 状态：待评审 → 评审通过后进入正式需求（PRD）与技术方案阶段

---

## 0. 一句话定位

**一个「AI 验收测试编排 Agent」**：AI 写完代码说「写好了」之后，由它自动跑分层测试、收集带证据的缺陷报告、生成修复任务喂回编码 AI、修复后自动回归，循环到全绿——把「人肉验收 AI 代码」这个环节自动化掉。

它**不重复造轮子**：浏览器操作复用 Playwright/Midscene/browser-use，代码修复复用 ZCode/Claude Code/Cline，沙箱复用 Docker/E2B。我们自研的只有**编排、证据规范和闭环状态机**——这正是调研发现的市场空白。

---

## 1. 为什么做：问题与数据

你的痛点不是个例，是被量化的行业现状：

| 证据 | 数据 | 来源 |
|---|---|---|
| AI 代码缺陷密度 | AI 编写 PR 平均 10.83 个问题 vs 人工 6.45（约 1.7 倍） | CodeRabbit《AI vs Human Code Report》2025-12 |
| 开发者信任下滑 | 对 AI 工具准确性信任度 43%→33%；66% 最不满「几乎对但不完全对」 | Stack Overflow 2025 开发者调查 |
| AI 评审噪音 | 「CI 的 AI 评审总能找出点什么」→ 开发者学会忽略告警 | Hacker News 一线讨论 |
| AI 自查偏判 | 带修复历史的 agent 反复查同类问题、漏检新问题 | autonomous-qa-loop 项目 README |

**结论**：人工验收是 AI 开发工作流的最大瓶颈之一；且反馈必须是「分级、可复现、带证据」的，否则会被像 AI 评审噪音一样忽略——这是本系统设计的核心约束。

## 2. 调研结论：赛道格局与我们的位置

```
┌─────────────────────────────────────────────────────────────┐
│  闭环编排层（测试→报告→修复任务→回归）  ← ★ 空白，我们做这里     │
│  先例：web-eval-agent(1238★,已停运) webqa-agent(233★)        │
├──────────────────────────┬──────────────────────────────────┤
│  测试执行层（成熟，复用）   │  代码修复层（成熟，复用）            │
│  browser-use   115,077★  │  OpenHands      88,399★          │
│  playwright-mcp 37,235★  │  cline(SDK形态)  68,662★          │
│  stagehand     24,330★   │  aider          49,035★           │
│  midscene      14,939★   │  SWE-agent      20,351★           │
├──────────────────────────┴──────────────────────────────────┤
│  沙箱层（复用）：Docker Compose 起步 / E2B 13,868★             │
└─────────────────────────────────────────────────────────────┘
```

三个关键判断（依据见竞品报告第 5/6/10 节）：

1. **执行器是红海，编排闭环是空白**。midscene/shortest 只做「跑测试」，SWE-agent/OpenHands 只做「改代码」，中间「测完→出证据报告→转修复任务→回归验证」没人做全。最接近的 web-eval-agent 已停运——教训是：闭环要做**主体**，不能做某个 IDE 的附属插件。
2. **纯 AI 测试的最大诟病是不稳定（flaky）**。对策已明确：确定性层打底 + AI 层只做机器做不了的事（视觉验收、探索）。
3. **赛道淘汰极快**（Magnitude/Hercules/ZeroStep 仓库均已 404）。所以架构上执行器必须**可插拔**，不绑死任何一家。

## 3. 四个核心产品决策【设计假设，待你确认】

| # | 决策 | 选择 | 理由 |
|---|---|---|---|
| D1 | 做什么 | **薄编排层 CLI**（后期可长成服务/平台），不自研浏览器驱动 | 执行器已 115k★ 级成熟；我们的价值在闭环逻辑 |
| D2 | 怎么测 | **分层测试金字塔**：确定性门禁打底 + AI 验收在上 | 纯 AI 测试 flaky 是全体竞品共同差评；L0 秒级拦截 80% 低级问题（编译错/类型错/lint/单测挂），AI token 只花在刀刃上 |
| D3 | 怎么修 | 缺陷报告 → **结构化修复任务 MD** → 投喂你现有的编码 AI（ZCode/Claude Code headless）→ 全量回归 | 修复器复用；「任务格式」是闭环的关键资产 |
| D4 | 做成什么形态 | **引擎（确定性程序）为主体 + MCP 接口对外 + 薄 Skill 做 ZCode 入口；Agent 只做内部组件** | 编排/状态/调度必须是确定性代码（Skill 做不到、全 Agent 化必然 flaky）；MCP 让任何编码 AI 都能调用（web-eval-agent 验证过的正确部分）；Skill 贴合现有 ZCode 工作流，见 3.1 |

### 3.1 形态决策详解：为什么不是纯 Agent / 纯 Skill / 纯 MCP

| 形态 | 本质 | 在本系统中的角色 | 承担不了什么 |
|---|---|---|---|
| Skill | 教 agent 做事的方法论（提示词 + 脚本） | ZCode 内的**调用入口**与闭环纪律（fresh-agent 规则、何时触发测试、如何消化修复任务卡） | 持久状态（用例库/报告历史/趋势）；独立调度（CI、定时任务里没人跟它对话） |
| MCP server | 标准化工具接口 | 引擎的**标准对外接口**：任何编码 AI（ZCode/Claude Code/Cursor/Cline）都能一行调用 `run` / `get_report`，实现「AI 写完自己调测试、自己修」 | 只是接口，背后必须有引擎；做成纯 MCP = 又做成别人的附属插件（web-eval-agent 停运的教训） |
| Agent | 自主 LLM 循环程序 | **内部组件**：L3 探索性测试（browser-use）、修复执行（headless 编码 agent） | 整个系统全 agent 化 = 编排不确定、状态困在上下文窗口、CI 难集成、成本失控——正是纯 AI 派竞品被差评的根源 |
| **引擎（主体）** | 确定性 TypeScript 程序 | 分层调度、门禁短路、循环状态机、证据库、报告聚合、CI 集成 | 判断力（交给 LLM）和浏览器操作（交给执行器），这两样恰恰是复用品 |

三者协同的日常形态：
1. 你在 ZCode 里说「测试一下」→ Skill 引导编码 agent 调 MCP 工具 `auto-test run`；
2. 引擎在 Docker 沙箱跑 L0→L2，返回证据报告 + 修复任务卡；
3. 编码 agent 消化任务卡修代码 → 再调 `auto-test run --regress` → 全绿；
4. CI / 每日定时任务里，引擎直接以 CLI 运行，全程不需要任何 agent 在场（L3 巡检除外）。

### 3.2 与现有 ZCode Testing Skill 的关系（2026-09-18 对比，SKILL.md 实读）

Testing Skill 已覆盖（会话内形态）：代码层闭环检查（typecheck/lint/单测/build/e2e + hooks）、midscenejs 视觉断言（aiAssert/aiQuery）、Playwright 网络监听与慢接口清单（>1000/3000/5000ms 阈值体系）、P0/P1/P2 分级 + 截图/复现步骤/「证据先于声明」纪律、问题文档转 Bug-Fix 承接修复。

引擎补的结构性缺口（7 条）：

| 缺口 | Testing Skill 现状 | auto-test 引擎 |
|---|---|---|
| 无人值守 | 只能在会话内、人工触发 | CI / hook / 定时 / 修复循环第 N 轮自动执行 |
| 用例资产 | 每次现场生成用例文档，两遍覆盖路径可能不同 | 固化为可重复执行的回归套件 |
| 历史与趋势 | 无状态（「禁沿用上次结果」） | run 历史：通过率 / flake 率 / 耗时 / 成本 / 修复轮次 |
| 修复闭环 | 文档转交 Bug-Fix，回归靠人再触发 | 任务卡→headless 编码 AI→自动回归→轮次状态机 |
| 成本结构 | 每轮完整 agent 会话 | 分层短路，LLM 只花在 L2/L3 |
| 沙箱隔离 | 本机 dev server 直跑 | Docker 隔离，多项目并行互不干扰 |
| 可用范围 | 有会话的宿主（ZCode 等） | MCP 接任意编码 AI / CI |
| L3 探索 | 无（全状态+全点击为穷举法） | browser-use 自由探索找 bug |

**关系定位：不替代，分工 + 继承。** 人盯着的深度验收继续用 Testing Skill；无人值守的高频回归与修复循环用引擎。引擎的 L2 用例生成与薄 Skill 入口直接继承 Testing Skill 的方法论资产（全状态 / 全点击 / 三态必测 / 覆盖边界声明 / 阈值体系）。

## 4. 总体架构

```
                    ┌──────────────────────────────────────────┐
                    │            Auto-Test 编排器 (CLI)          │
                    │   用例管理 / 调度 / 门禁 / 证据聚合 / 状态机   │
                    └───────┬──────────────────────────┬───────┘
                            │                          │
              ┌─────────────▼─────────────┐  ┌─────────▼──────────────┐
              │      被测系统 (沙箱)        │  │      修复循环控制器       │
              │  Docker Compose:          │  │  缺陷报告→修复任务生成     │
              │  app + db + mock 依赖      │  │  →编码AI headless执行    │
              └─────────────┬─────────────┘  │  →fresh-agent 回归      │
                            │                │  →轮次上限/人工升级       │
              ┌─────────────▼─────────────┐  └─────────▲──────────────┘
              │        分层测试引擎          │            │
              │  L0 确定性门禁 (秒-分钟)     │  ┌─────────┴──────────────┐
              │  L1 API/契约测试 (分钟)      │  │   证据库 / 报告中心       │
              │  L2 AI 视觉E2E验收 (分钟)    │  │  截图/视频/console/网络   │
              │  L3 探索性Agent (按需)       │  │  HTML报告+缺陷清单        │
              └───────────────────────────┘  └────────────────────────┘
```

### 4.1 分层测试策略（D2 详解）

| 层 | 内容 | 工具 | AI 参与 | 失败处理 |
|---|---|---|---|---|
| **L0 确定性门禁** | install、build、tsc、eslint、单元测试 | 传统 CI 工具链 | 无 | 直接阻断，秒级反馈 |
| **L1 契约/API** | 接口冒烟、OpenAPI 契约校验、关键路径 curl 级断言 | 脚本 + AI 生成用例后固化 | 生成时 | 阻断，附请求/响应证据 |
| **L2 AI 视觉验收** | 按「验收标准」逐条跑真实浏览器流程 | **Playwright + Midscene**（视觉定位免 selector） | 执行+判断 | 分级：阻断/警告/建议 |
| **L3 探索性测试** | 无预设脚本自由探索找 bug、监控 console/网络错误 | **browser-use / playwright-mcp** | 全程 | 只出报告不阻断 |

规则：**L0 挂了不跑 L1，L1 挂了不跑 L2**（省 token、快速失败）；L3 默认手动触发或每日定时。

### 4.2 缺陷报告与修复任务规范（D3 详解，闭环的核心资产）

每条缺陷 = 一份机器可读、AI 可执行的「修复任务卡」：

```markdown
## BUG-2026-09-18-003 [阻断] 登录后未跳转工作台
- 复现步骤: 1. 打开 /login 2. 输入 demo/demo 3. 点击「登录」
- 期望: 跳转 /dashboard   实际: 停留在 /login，无报错提示
- 证据: screenshot.png | video.mp4 | console.log(3 errors) | network.har
- 定位线索: 改动 diff 涉及 src/auth/LoginForm.tsx；console 报错指向 handleSuccess 未触发
- 验收标准: 按上述步骤执行后 URL 变为 /dashboard（回归时机器判读）
```

### 4.3 防自欺设计（来自 autonomous-qa-loop 方法论）

- **fresh-agent 回归**：每轮回归用全新无历史的测试 Agent，只喂「原始验收标准 + 产物」，不喂上一轮的怀疑点和结论；
- **全量回归**：修复后重跑整个套件，不是只跑上次失败的用例（防「改 A 坏 B」震荡）；
- **确定性优先**：L0/L1 的失败任何 AI 判断都不能覆盖；
- **轮次上限**：修复循环最多 N 轮（默认 3），超限停下升级人工，防止无限震荡烧 token。

### 4.4 全流程覆盖：状态注入与 Mock 数据策略（解决「少流程、状态跑不到」）

**问题定义**：纯浏览器遍历存在状态可达性瓶颈——① 大量状态无法从 UI 构造（「已支付 3 天未发货」「账号被封禁」）；② 外部依赖（支付回调/短信/三方推送）在测试环境触发不了；③ LLM 遍历偏主流程且不确定，漏检是静默的。

**解法三件套**：

1. **用例三段式（状态注入替代 UI 遍历）**——每条用例 = `setup → act → assert`，前置状态用 API 造数 / DB 种子 / localStorage 注入直接构造，浏览器只断言「该状态下页面表现是否正确」：

```yaml
id: TC-ORDER-014
状态: 已支付·3天未发货            # 对应 PRD 状态机节点
setup:
  - seed: order.create(status=paid, paidAt=now()-3d)   # API/DB 注入前置状态
  - mock: sms.send -> ok                               # 外部依赖 mock
  - intercept: GET /api/inventory/* -> 500              # 异常态拦截（按需）
act:
  - aiAct: 打开「我的订单」第 1 条订单详情
assert:
  - aiAssert: 显示「催促发货」按钮且可点击
  - network: 响应 200、无 console 报错
coverage: [order.paid, order.paid→reminded]             # 回填状态机覆盖
```

2. **状态机驱动用例生成 + 覆盖率门禁**——从 PRD 状态机（现有 Testing Skill 已强制 PRD 含状态机图，资产现成）机器枚举**全部状态 × 全部迁移**生成用例清单；报告强制给出状态覆盖率 / 迁移覆盖率 / 元素点击率，**不达标不算跑完**。「少流程」从 agent 自觉变成可计算数字。

3. **Mock 基建进沙箱**——Docker Compose 增加 mock-server 容器（按 OpenAPI 契约生成，如 Prism/WireMock，防 mock 与真实接口漂移）；Playwright 路由拦截模拟异常态（500/超时/弱网）；时钟 mock 处理过期类状态（token/优惠券）；外部回调可编程触发（模拟支付成功推送）。

**Mock 边界（铁律）**：mock 外部依赖与异常态；前置业务状态用**注入真实数据**（不 mock 逻辑）；被测系统自身业务逻辑**绝不 mock**。

| 类别 | 策略 | 例子 |
|---|---|---|
| 外部第三方依赖 | Mock（测试环境不可控） | 支付网关、短信、OAuth、物流 |
| 异常/极端态 | Mock/路由拦截 | 接口 500、超时、弱网、token 过期 |
| 前置业务状态 | 注入真实数据 | API/DB 造「已支付订单」，UI 只断言 |
| 被测系统业务逻辑 | 绝不 mock | mock 即失去测试意义 |

## 5. 技术选型清单【设计假设，M0 实测后可调整】

| 组件 | 选型 | 备注 |
|---|---|---|
| 编排器语言 | **TypeScript / Node** | 与 Playwright/Midscene/stagehand 同生态 |
| 浏览器底座 | Playwright | 行业标准 |

| 用例格式 | Markdown/YAML（验收标准即用例） | shortest 验证的形态，人能读 AI 能跑 |
| LLM | 走 Midscene/编码 AI 各自配置 | 编排器不直接依赖特定模型 |

## 6. 里程碑路线图（每个都有明确验收标准）

### M0 · 最小闭环验证（约 1 周）——先证明这条路走得通
- 挑一个你现有的 AI 开发 Web 项目（或 demo 应用）
- 手写 3–5 条自然语言验收用例，用 Playwright + Midscene 跑通
- 产出一份含截图/console/网络错误的 HTML 报告
- 人工把报告转述给编码 AI 修复，修完重跑，确认「发现→修复→回归通过」完整走通一轮
- **验收**：一轮真实的 发现问题→AI修复→回归变绿 闭环记录
- **同时校准**：flake 率、单轮 token 成本、耗时（这组数据决定后面怎么投入）

### M1 · 测试编排器 CLI（2–3 周）
- `auto-test init / run / report` 三条命令
- Markdown 用例管理 + 验收标准结构化（**三段式：setup 注入 / act 操作 / assert 断言**）
- **状态注入与 Mock 基建**：API 造数与 DB 种子脚本、mock-server 容器（OpenAPI 契约生成）、Playwright 路由拦截、storageState 复用登录态、时钟 mock
- **状态机用例生成器**：读 PRD 状态机枚举全部状态×迁移生成用例清单；报告含状态/迁移/元素点击覆盖率（不达标不算跑完）
- L0→L1→L2 调度（分层短路，快速失败）
- 统一 HTML 证据报告（截图/视频/console/网络聚合）
- 缺陷 → 修复任务卡自动生成（4.2 的格式）
- **验收**：一条命令对目标项目跑完 L0–L2，输出统一报告 + 覆盖率 + 可直接投喂 AI 的任务清单

### M2 · 自动修复闭环（2–3 周）
- 修复任务卡自动投喂编码 AI headless（ZCode/Claude Code CLI）
- 修复后自动全量回归 + fresh-agent 轮换
- 循环状态机：全绿通过 / 轮次上限升级人工
- 对外暴露 **MCP server**（`run` / `get_report` 工具）+ 薄 **ZCode Skill** 入口：任何编码 AI 可直接调用并自主进入修复循环
- **验收**：从「代码提交」到「全绿报告」无人工干预跑通（或仅在超限时人工介入）

### M3 · 沙箱化与企业级（3–4 周）
- Docker Compose 一键起被测环境（app + db + mock）
- 用例并行执行、历史结果存储与趋势（flake 率、通过率、耗时、成本）
- 多项目配置隔离；CI / Git hook 触发（commit 后自动 L0，PR 后自动全量）
- **验收**：新项目接入 ≤ 30 分钟配置；任意历史报告可追溯

### M4 · 探索性测试 Agent（可选，按 M0–M3 数据决定）
- browser-use / playwright-mcp 集成 L3 自由探索
- 每日定时「巡检」模式，新缺陷自动建卡
- 远期：computer-use 扩展桌面端应用测试

## 7. 风险清单与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| LLM 测试不稳定（flake） | 高 | 分层短路 + AI 结果分级（阻断/警告/建议）+ 失败重试一次 + flake 率监控进入 M3 趋势 |
| 修复循环震荡（改 A 坏 B） | 高 | 全量回归 + 轮次上限 3 轮 + 超限人工升级 |
| 「AI 测 AI」互相糊弄 | 中 | fresh-agent 轮换 + 确定性层终审权 |
| token 成本失控 | 中 | 分层触发（L0 过才跑 L2）+ 用例去重 + stagehand 式动作固化（后期） |
| 执行器项目停更（赛道墓场多） | 中 | 执行器抽象接口可插拔，L2 换执行器不动用例 |
| Mock 边界失控 → 假数据全通过 | 中 | Mock 边界铁律（只 mock 外部依赖/异常态）；mock 按 OpenAPI 契约同源生成并随契约测试校验 |
| 非 Web 项目不适用 | 低 | 明确 v1 边界=Web 全栈；L0/L1 层与项目类型无关，天然通用 |
