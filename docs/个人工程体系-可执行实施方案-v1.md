# 个人工程体系（PEOS）可执行实施方案 v1.0

> **Personal Engineering Operating System**
>
> 目标：把“无论使用什么模型，都能持续交付可维护、可验证、可观测、可回滚的软件”从工程思想落成一套可以每天执行、可以检查、可以复盘、可以持续进化的工程体系。
>
> 版本：v1.0
>
> 日期：2026-09-20
>
> 当前实施分支：`refactor/workflow-system-v2`
>
> 适用项目：个人 OPC、公司项目、客户项目、新项目、旧项目接管、功能迭代、Bug 修复、应用重构、发布运维和持续优化。

---

## 0. 先定义最终结果

这套体系最终不是“很多 Skill 的集合”，而是一个**可被个人调用的工程团队**：

```text
用户/业务想法
  → 产品澄清
  → 竞品与问题研究
  → 产品边界和 MVP
  → PRD
  → 原型与 UI/UX
  → 技术方案
  → 组件与知识复用
  → 开发
  → 代码审查
  → 测试
  → 发布
  → 日志/监控/用户行为
  → 问题分诊
  → 迭代 / 修复 / 重构 / 优化
  → 再次发布
  → 定期巡检
  → 经验、组件、Skill 和基线沉淀
```

最终能力必须满足：

1. 不依赖某个模型；
2. 不依赖个人临时记忆；
3. 不把模糊想法直接当成确定需求；
4. 不允许未经验证的代码进入发布；
5. 不允许发现线上问题后只修当前现象、不防止复发；
6. 不允许公司和客户私有资产未经授权进入个人公共资产；
7. 不允许项目只在开发阶段有流程、上线后失去反馈；
8. 不允许流程产出大量文档却无法驱动实际开发；
9. 所有关键结论都有证据、状态、负责人和下一步；
10. 任意模型替换后，仍然按照同一套输入、输出、Gate 和质量标准执行。

## 1. 核心工程思想的可执行化

### 1.1 思想到机制的映射

| 工程思想 | 必须落成的机制 | 验证方式 |
|---|---|---|
| 模型不是核心竞争力 | 统一 Skill Contract、状态机、产物契约、确定性脚本 | 更换模型后重复执行同一场景 |
| AI 不能自由发挥 | 需求澄清、证据标签、决策记录、Gate、用户确认 | 抽查是否存在无依据假设 |
| 代码不能成为屎山 | 项目结构、代码规则、Code Review、复杂度/重复检查、巡检 | 代码审查和定期巡检 |
| 代码必须自己能看懂 | 统一命名、模块边界、错误处理、日志、测试和 ADR | 人工阅读关键链路 |
| 交付要稳定 | 测试分层、回归、发布验证、回滚路径 | 发布前后验证 |
| 线上问题要反哺 | web-monitor、server-log、server-monitor、Signal Triage | 错误可关联到版本和 commit |
| 经验要复用 | skills-knowledge、Pattern、Adapter、Composite、Registry | 下次任务命中复用资产 |
| 项目要持续变好 | Quality-Inspection、Post-Release-Review、Skill-Optimizer | 巡检趋势和重复问题下降 |

### 1.2 质量恒定的真实含义

质量恒定不等于每一次生成的代码完全相同，而是指：

```text
模型生成结果可以不同
但进入下一个阶段的最低质量标准不能不同
```

任何模型输出必须经过：

```text
Skill Contract
→ 证据检查
→ 结构/类型/lint 检查
→ 测试
→ Code Review
→ 发布验证
→ 运行观测
```

模型没有权力绕过：

- 产品确认；
- 技术方案确认；
- 组件决策；
- 测试 Gate；
- 发布 Gate；
- 生产操作授权。

## 2. 总体架构

### 2.1 六层架构

```text
L1 调度与治理层
   tenger-skills / Workflow / State Machine / Gate / Contract

L2 知识与资产层
   skills-knowledge / Pattern / Composite / Adapter / Profile / Registry

L3 产品与工程交付层
   PRD / UI / DEV / Testing

L4 发布层
   Release Plan / Deployment / Verification / Rollback

L5 运行观测层
   web-monitor / server-log / server-monitor

L6 反馈与进化层
   Signal Triage / Incident / Defect / Optimize / Inspection / Skill Evolution
```

### 2.2 仓库边界

当前只修改：

```text
D:\project\agent-project\tenger-skills
```

外部基础设施项目只作为集成对象，后续需要单独授权后再修改：

```text
D:\project\agent-project\web-monitor
D:\project\agent-project\server-log
D:\project\agent-project\server-monitor
D:\project\agent-project\skills-knowledge
```

边界规则：

- `tenger-skills`：流程、Skill、状态机、契约、模板、校验器；
- `skills-knowledge`：组件、能力卡、Pattern、Composite、Adapter、平台 Profile；
- `web-monitor`：前端错误、性能、用户行为和回放信号；
- `server-log`：结构化服务日志、请求上下文和关联 ID；
- `server-monitor`：主机/服务指标、心跳、拨测和告警；
- 项目仓库：项目专属代码、项目专属基线、项目专属决策和私有数据。

### 2.3 三种资产隔离

| 资产类型 | 允许沉淀位置 | 是否跨项目复用 |
|---|---|---|
| 通用方法、模板、规则 | `tenger-skills` | 可以 |
| 去敏 Pattern、组件能力和适配器 | `skills-knowledge` | 可以，需审核 |
| 公司/客户源代码、数据、业务规则 | 对方项目仓库 | 不得未经授权复制 |
| 私有凭证、Token、生产数据 | 密钥/受控系统 | 永不写入公共 Skill |
| 项目运行数据 | 项目或受控观测系统 | 只沉淀去敏统计和结论 |

## 3. 工作流总状态机

### 3.1 生命周期模式

每个任务进入系统时必须先归类为以下一种模式：

| 模式 | 含义 | 是否默认改变外部行为 | 入口 |
|---|---|---:|---|
| `CREATE` | 新产品、新应用、新平台 | 是 | `Idea-Intake` |
| `CHANGE` | 新功能、规则变更、体验升级 | 是，按批准范围 | `Change-Intake` |
| `DEFECT` | 已批准行为被破坏的 Bug | 否 | `Defect-Triage` |
| `REFACTOR` | 内部治理、技术债、架构整理 | 默认否 | `Project-Onboarding` |
| `INCIDENT` | 正在影响生产的高影响事故 | 临时允许 | `Incident-Response` |
| `OPTIMIZE` | 由数据、性能、成本或行为驱动的优化 | 按批准范围 | `Product-Analytics` |

如果用户只说“改一下”“优化一下”“重构一下”，不能直接猜测模式，必须输出：

```text
候选模式 + 当前证据 + 未知问题 + 需要用户确认的差异
```

### 3.2 工作流阶段状态

```text
REQUESTED
→ INTAKE_COMPLETE
→ DISCOVERY_IN_PROGRESS
→ BASELINE_READY
→ DESIGN_IN_PROGRESS
→ DESIGN_REVIEW
→ IMPLEMENTATION_PLANNED
→ IMPLEMENTATION_IN_PROGRESS
→ CODE_REVIEW
→ TESTING_IN_PROGRESS
→ TESTING_PASSED
→ RELEASE_PLANNED
→ RELEASED
→ OBSERVING
→ REVIEWED
→ CLOSED
```

失败或发现上游问题时必须回退：

```text
任何阶段
→ BLOCKED
→ 回退到最早受影响阶段
```

例如：

- 开发中发现需求边界不清：回到 PRD；
- 测试中发现接口契约不一致：回到技术设计；
- 上线后发现是业务规则错误：转 `CHANGE`，不能当普通 Bug 修；
- 重构中发现必须改变用户行为：转 `CHANGE`；
- 生产事故：先进入 `INCIDENT`，恢复后再转 `DEFECT` 或 `REFACTOR`。

### 3.3 Gate 结果

所有 Gate 只能有三种结果：

```text
PASS        可以进入下一阶段
CONDITIONAL 有明确例外、风险和责任人，可以受控继续
BLOCKED     禁止进入下一阶段
```

`CONDITIONAL` 不能等于“先做再说”，必须登记：

- 例外内容；
- 风险；
- 责任人；
- 截止时间；
- 补证动作；
- 是否允许发布。

## 4. 项目工作区标准结构

每个项目必须拥有以下工程元数据目录：

```text
project-root/
├── src/                         # 项目源代码
├── test/                        # 测试代码
├── docs/                        # 对外或项目文档
├── .spec/
│   ├── WORKFLOW.yaml            # 当前工作流状态
│   ├── manifest.yaml            # 产物登记和追踪关系
│   ├── PROJECT.yaml             # 项目基本信息和平台 Profile
│   ├── baseline/
│   │   ├── project-profile.yaml
│   │   ├── architecture-map.md
│   │   ├── behavior-baseline.md
│   │   ├── api-and-data-inventory.md
│   │   ├── test-baseline.md
│   │   ├── observability-baseline.md
│   │   ├── release-baseline.md
│   │   └── unknowns-and-risks.md
│   ├── decisions/               # 决策记录和 ADR
│   ├── traceability/            # 需求-设计-代码-测试-发布追踪
│   ├── tasks/                   # 当前任务、缺陷和行动项
│   ├── signals/                 # 运行信号归一化结果
│   ├── inspections/             # 周期巡检
│   ├── releases/                # 发布计划、验证和回滚记录
│   └── reports/                 # 阶段报告
├── PROJECT.md                   # 人类可读项目入口
├── PLAN.md                     # 当前阶段计划
└── README.md
```

不得把以下内容放进项目公共文档或仓库：

- Token、密码、私钥；
- 真实客户数据；
- 未授权生产日志原文；
- 未脱敏用户身份信息；
- 公司/客户内部私有资料。

## 6. 人与 AI 的职责边界

### 6.1 AI 可以自动做的事情

在用户已授权范围内，AI 可以：

- 读取项目和文档；
- 分析代码结构；
- 运行安全的本地检查；
- 生成分析报告、计划、测试、代码草稿；
- 根据既有组件库推荐复用方案；
- 执行非生产环境的测试和构建；
- 生成问题清单和修复建议；
- 在明确边界内修改项目文件；
- 提交可审查的变更摘要。

### 6.2 必须由人确认的事情

以下事项必须明确停下来等待确认：

- 产品定位、目标用户和 MVP 范围；
- 竞品取舍和商业模式；
- 破坏兼容性的 API/数据变化；
- 是否改变旧项目外部行为；
- 数据迁移和数据删除；
- 生产环境操作；
- 发布和回滚；
- 安全/隐私/合规例外；
- 使用公司/客户私有资产沉淀为公共资产；
- 将 `CONDITIONAL` Gate 变成正式放行。

### 6.3 禁止事项

- 不得因为用户只说一句话就直接开始写代码；
- 不得没有基线就直接重构旧项目；
- 不得没有复现证据就声称 Bug 已修复；
- 不得只运行单元测试就宣称发布安全；
- 不得只接服务器日志就宣称应用可观测；
- 不得把“测试没报错”当成“需求正确”；
- 不得未通过 Gate 自动部署；
- 不得把项目私有知识直接写入个人公共知识库。

## 7. 六类场景的标准执行方式

## 7.1 新项目 `CREATE`

### 入口

用户提出想法、产品方向或一句模糊需求。

### 执行步骤

1. `Idea-Intake`：记录原始想法，不补写成完整需求；
2. `Product-Discovery`：追问用户、场景、痛点、替代方案和成功标准；
3. `Competitive-Analysis`：研究竞品、相邻产品、用户已有解决方式；
4. `Product-Definition`：明确目标用户、核心问题、价值主张和非目标；
5. `Application-Blueprint`：规划应用全链路、模块、角色和主要流程；
6. `Feature-Decision`：把功能分成必须做、应该做、可以做、暂不做；
7. `PRD-Design`：写 PRD、业务规则、异常和验收条件；
8. `PRD-Review`：用户审核，未通过不得进入 UI；
9. `Prototype-Design`：绘制完整关键路径原型；
10. `Prototype-Review`：用户审核交互；
11. `UX-Architecture` / `Design-System` / `Component-Mapping`：形成 UI/UX 基线；
12. `Technical-Discovery`：识别约束、依赖、风险和可观测要求；
13. `Component-Decision`：先查 `skills-knowledge`，再决定复用、组合、扩展或新建；
14. `Backend-Tech-Design` / `Frontend-Tech-Design` / `Observability-Design`；
15. `Implementation-Planning`：拆成可独立验证的小切片；
16. `Backend-Dev` / `Frontend-Dev`；
17. `Code-Review`；
18. `Testing-Workflow`；
19. `Release-Workflow`；
20. `Operations-Workflow`；
21. `Post-Release-Review` 和 `Quality-Inspection`。

### 新项目完成条件

- 用户知道做什么、不做什么；
- PRD、原型、UI、技术方案和代码可以相互追踪；
- 关键流程有测试和监控；
- 发布有回滚和观察窗口；
- 没有将假设隐藏成事实。

## 7.2 旧项目接管

必须先执行 `project-onboarding`，禁止直接进入开发。

### 盘点顺序

1. 工作区和分支快照；
2. 运行时、包管理器、入口和构建命令；
3. 架构和依赖地图；
4. 关键用户旅程和服务主链；
5. API、数据、迁移和外部依赖；
6. 测试现状；
7. 日志、监控、告警和版本关联；
8. 发布、灰度和回滚；
9. 未知项和风险；
10. 选择后续 `CHANGE` / `DEFECT` / `REFACTOR`。

### 接管完成条件

- 有基线，而不是只有目录介绍；
- 每个未知项都有风险和补证动作；
- 知道项目如何运行、如何测试、如何发布和如何回滚；
- 知道线上错误如何定位到版本和请求；
- 旧行为和正确需求已经分开记录。

## 7.3 功能迭代 `CHANGE`

1. `Change-Intake`：描述变化目标、原因、用户和预期结果；
2. 读取当前基线；
3. `Impact-Analysis`：分析产品、UI、接口、数据、权限、测试、发布和监控影响；
4. 判断是否需要回到 PRD、UI 或技术设计；
5. 形成变更决策和范围；
6. 更新受影响产物；
7. 设计、开发、测试、发布；
8. 发布后比较变更前后指标；
9. 把未达预期的结果转为下一条 `CHANGE` 或 `OPTIMIZE`。

## 7.4 Bug 修复 `DEFECT`

1. `Defect-Triage` 收集版本、环境、用户、时间、复现步骤和证据；
2. 区分：代码缺陷、需求错误、环境问题、数据问题、监控误报；
3. 建立最小复现；
4. 定位根因，不只修表象；
5. 先补失败测试；
6. `Bug-Fix` 只实施最小修复；
7. 执行回归和相关非功能测试；
8. 发布后观察是否复发；
9. 有通用预防价值时沉淀到 `bug-patterns/`。

## 7.5 应用重构 `REFACTOR`

1. `Project-Onboarding` 建立行为基线；
2. `Refactor-Planning` 明确重构目标；
3. 规定不可改变的 API、数据、用户流程和性能底线；
4. 建立 characterization tests、contract tests 和 smoke tests；
5. 设计兼容层、迁移顺序和回滚点；
6. 小切片改造；
7. 每个切片单独测试和审查；
8. 对比重构前后构建时间、错误率、P95、资源消耗、测试稳定性和可维护性；
9. 如果必须改变业务语义，立即转为 `CHANGE`；
10. 发布后通过 `Quality-Inspection` 验证重构没有引入回归。

## 7.6 生产事故 `INCIDENT`

1. `Runtime-Signal-Triage` 确认影响范围和严重级别；
2. `Incident-Response` 先止损：降级、关闭开关、回滚或隔离；
3. 记录时间线、动作、证据和影响；
4. 恢复后验证关键链路；
5. 形成根因和永久修复任务；
6. 转 `DEFECT`、`REFACTOR` 或 `CHANGE`；
7. 补测试、监控、告警和运行手册；
8. 复盘并沉淀反例。

## 7.7 运行优化 `OPTIMIZE`

1. `Product-Analytics` 分析产品指标、行为、性能、成本或错误趋势；
2. `Optimization-Planning` 建立当前基线、预期收益和保护指标；
3. 明确实验或变更范围；
4. 先设计验证方式再实施；
5. 发布后对比前后数据；
6. 收益不足时关闭、回滚或继续迭代；
7. 不把“感觉更快”当成性能结论。

## 8. PRD-Workflow 的具体执行标准

PRD 阶段必须解决的问题不是“把用户的话写长”，而是：

```text
用户真正要解决什么问题？
谁遇到这个问题？
现在如何解决？
为什么现有方案不够？
我们真正应该做什么？
哪些功能不应该做？
完整使用链路是什么？
失败、异常、权限、数据和边界是什么？

```

每个 PRD 必须包含：

1. 原始想法；
2. 用户和场景；
3. 问题定义；
4. 竞品与替代方案；
5. 功能对比矩阵；
6. 产品取舍；
7. 目标和非目标；
8. 角色和权限；
9. 核心流程；
10. 异常流程；
11. 数据和业务规则；
12. 关键页面和状态；
13. MVP 范围；
14. 后续版本候选；
15. 业务验收标准；
16. 未决问题和用户确认项；
17. 风险和降级方案；
18. 可观测性要求；
19. 版本基线。

PRD 阶段 Gate：

```text
PRD_READY
```

必须满足：

- 产品目标和非目标清楚；
- 竞品功能已经转化为取舍，而不是简单抄功能；
- 关键流程有终态；
- 异常、权限、空数据、重复操作、中断和失败都有处理；
- 所有设计假设有标记；
- 用户已经确认关键范围。

## 9. UI-Workflow 的具体执行标准

8. 响应式和平台差异；

## 10. DEV-Workflow 的具体执行标准

### 10.1 技术方案前先做三件事

1. 读取项目基线；
2. 搜索 `skills-knowledge` 可复用能力；
3. 研究相关开源项目、官方文档和已有实现。

### 10.2 组件决策链

必须按以下顺序：

```text
已有项目组件
→ skills-knowledge 能力卡
→ 已有 Composite 组合
→ Adapter 适配
→ 扩展已有组件
→ 最后才新建
```

任何新建组件必须写清：

- 为什么现有组件不能用；
- 评估过哪些组件；
- 兼容性问题；
- API 和使用方式；
- 测试策略；
- 是否需要沉淀为通用资产。

### 10.3 开发切片标准

一个开发切片必须：

- 目标明确；
- 修改范围明确；
- 可以独立构建；
- 可以独立测试；
- 有回滚方式；
- 不混入无关重构；
- 完成后可以由别人理解。

禁止：

- 同一个切片同时改产品规则、架构、命名和格式；
- 一次生成几千行没有验证的代码；
- 在没有测试的情况下大面积替换模块；
- 用“之后再补测试”作为默认策略。

### 10.4 代码质量最低标准

- 一个模块只承担清楚的主要职责；
- 业务规则集中且可定位；
- 错误处理不能被吞掉；
- 外部输入必须校验；
- 重要副作用必须显式；
- 日志必须包含必要关联上下文并脱敏；
- 关键行为必须有测试；
- 复杂度上升必须说明原因；
- 依赖新增必须有决策记录；
- 不得产生无法解释的重复实现。

### 10.5 Code Review 固定维度

每次代码审查都检查：

1. 需求是否实现；
2. 是否超出批准范围；
3. 模块职责；
4. 数据和状态变化；
5. 错误处理；
6. 安全和权限；
7. 性能和资源；
8. 日志、指标和追踪；
9. 测试和回归；
10. 依赖和兼容性；
11. 可读性和命名；
12. 是否存在 AI 味代码；
13. 是否需要更新知识库或 Pattern。

## 11. Testing-Workflow 的具体执行标准

测试不是最后“跑一下”，而是从 PRD 和技术方案开始建立追踪关系。

### 测试分层

```text
L0 静态检查：格式、类型、lint、依赖
L1 单元测试：纯逻辑和边界
L2 契约测试：API、事件、数据协议
L3 集成测试：模块、数据库、外部依赖
L4 E2E：关键用户旅程
L5 探索性测试：未预先覆盖的异常组合
L6 非功能测试：性能、安全、兼容性、无障碍、稳定性
L7 发布后验证：健康检查、主链冒烟、指标观察
```

### 测试追踪

```text
REQ-xxx
  → DESIGN-xxx
  → CODE-xxx
  → TEST-xxx
  → RELEASE-xxx
  → SIGNAL-xxx
```

### 通过标准

- P0/P1 测试失败不得进入下一阶段；
- 新 Bug 必须先补能失败的测试或最小复现；
- 修复后必须执行目标回归和相关回归；
- 不能以覆盖率数字替代关键路径覆盖；
- 不稳定测试必须单独记录，不得静默忽略；
- 生产事故修复必须包含发布后观察。

## 13. 三个基础设施项目的接入方案

### 13.1 统一信号模型

三个项目最终都要能够映射到统一信号：

```yaml
signalId: "SIG-20260920-0001"
source: web-monitor | server-log | server-monitor | user-feedback | test
signalType: error | performance | availability | security | behavior | resource
severity: P0 | P1 | P2 | P3
occurredAt: "2026-09-20T00:00:00+08:00"
environment: production | staging | development
appVersion: ""
commit: ""
traceId: ""
reqId: ""
sessionId: ""
userRef: "anonymous-or-hashed"
service: ""
route: ""
summary: ""
evidenceRefs: []
status: NEW | TRIAGED | ROUTED | RESOLVED | VERIFIED | CLOSED
```

### 13.2 `web-monitor`

负责提供：

- 前端异常；
- 页面加载和性能；
- 用户关键行为；
- 页面和会话上下文；
- `appVersion`、环境和可选 `traceId`；
- SourceMap 解析结果；
- 前端错误和服务端请求关联。

### 13.3 `server-log`

负责提供：

- 结构化日志；
- `reqId`、`traceId`、`userId` 的上下文；
- 请求开始、结束、异常和耗时；
- 脱敏；
- NestJS 或其他后端框架集成；
- 多目的地传输。

### 13.4 `server-monitor`

负责提供：

- CPU、内存、磁盘、网络；
- Agent 心跳；
- 服务可用性；
- 拨测；
- 断线缓冲；
- 指数退避；
- 告警和通知；
- 状态页或事件记录。

### 13.5 统一关联要求

至少可以实现：

```text
用户操作
→ sessionId
→ web-monitor 错误
→ traceId
→ server-log 请求日志
→ reqId
→ 服务异常
→ appVersion / commit
→ server-monitor 主机和服务指标
```

如果不能关联，必须登记为可观测性缺口，不能假装已经形成闭环。

## 14. Quality-Inspection 定期巡检制度

### 14.1 四种巡检频率

| 频率 | 检查内容 | 触发方式 |
|---|---|---|
| 每次变更 | 类型、lint、测试、构建、代码审查 | PR/任务完成前 |
| 每次发布后 | 错误率、关键旅程、日志、性能、告警 | 发布后观察窗口 |
| 每周 | 测试健康、重复错误、依赖、未关闭问题 | 定时执行 |
| 每月/每季度 | 架构漂移、技术债、组件复用、Skill 有效性 | 人工发起或定时 |

实际频率可以按项目风险调整，但不能完全取消巡检。

### 14.2 巡检输出

每次巡检都生成：

```text
.spec/inspection/YYYY-MM-DD/
├── inspection-report.md
├── gate-results.yaml
├── findings.md
├── trend.md
└── evidence-index.md
```

### 14.3 巡检发现分类

- 代码行为错误：`DEFECT`；
- 产品规则要变：`CHANGE`；
- 内部结构退化：`REFACTOR`；
- 指标/成本/性能机会：`OPTIMIZE`；
- 正在影响生产：`INCIDENT`；
- 流程或 Skill 自身问题：`Skill-Optimizer`。

### 14.4 巡检不能做什么

- 不自动升级所有依赖；
- 不自动大面积格式化；
- 不自动重构；
- 不自动关闭告警；
- 不自动修复生产代码；
- 不把风格偏好直接当 P0；
- 不使用“AI 味”作为没有证据的主观结论。

## 15. 模型无关执行协议

### 15.1 每次调用模型前提供的上下文

模型只能收到与当前任务相关的最小上下文：

```text
任务模式
当前阶段
目标
输入产物
约束
不可改变的边界
允许修改的目录
必须输出的产物
完成 Gate
失败回退路径
```

不允许把整个项目和所有历史信息无差别塞给模型。

### 15.2 每次模型输出后执行的检查

```text
1. 输出结构是否符合 Skill Contract
2. 是否回答了当前任务而不是自由扩展
3. 是否把假设当事实
4. 是否缺少证据
5. 是否超出修改范围
6. 是否生成未要求的代码/文件
7. 是否通过确定性检查
8. 是否需要人工确认
9. 是否登记状态和产物
10. 是否可以被下游消费
```

### 15.3 更换模型时的验收

模型切换后必须使用同一组黄金场景：

1. 模糊想法新建 Web + 后端；
2. 接管陌生旧项目；
3. 已有项目功能迭代；
4. Bug 修复；
5. 行为保持型重构；
6. 发布后监控发现错误；
7. 定期巡检发现架构漂移。

对比：

- 是否正确归类模式；
- 是否主动发现未知；
- 是否遵守 Gate；
- 是否少做无依据假设；
- 是否生成完整产物；
- 是否通过测试；
- 是否出现 AI 味代码；
- 是否遗漏监控、日志、回滚和安全；
- 是否修改了不允许修改的内容。

## 16. 质量评价指标

- 发布后复发率；

- 平均修复时间。

- 类型检查失败数；
- lint 失败数；
- 测试不稳定率；
- 重复代码趋势；
- 复杂度趋势；
- 超大文件数量；
- 未处理异常数量；
- 依赖风险数量；
- 未关联日志的关键错误数量；

- 组件复用率；
- 重复问题下降率；
- Skill 触发准确率；

## 20. 何时算这套体系真正完成

不是创建了 63 个目录就算完成，而是满足以下验收：

### 产品层

- 可以从一句模糊想法推导完整产品链路；
- 可以通过竞品研究帮助用户明确取舍；
- 可以让用户和 AI 对“做什么”达成一致；
- 可以支持新建、迭代、Bug、重构和优化。

### 工程层

- Web 和后端可以稳定交付；
- 组件优先从知识库复用；
- 代码结构人和 AI 都能看懂；
- 代码不是依赖某个模型的临时产物；
- 每次变更都有测试和回滚思路。

### 运行层

- 前端、后端、服务器信号可以关联；
- 错误可以定位到版本、commit 和请求；
- 修复之后可以验证是否复发；
- 发布后数据可以驱动下一轮工程任务。

### 进化层

- 重复问题能够沉淀为 Pattern；
- 组件可以跨项目复用；
- Skill 会根据真实项目反馈优化；
- 定期巡检可以发现质量退化；
- 更换模型不会导致质量标准变化。

### 个人能力层

最终形成：

```text
个人
+ 一套可以执行的工程体系
+ 一套可复用的知识和组件资产
+ 一套真实运行反馈闭环
+ 一套持续巡检和进化机制
= 可独立承担复杂软件项目的个人工程团队
```
