# 工程体系使用手册

> 核对日期：2026-09-21。适用对象：使用 tenger-skills 推进项目的你，以及代你执行任务的 Agent。
> 先记住：**给项目、说目标、划范围、定终点；看阶段摘要，确认关键决策。** 不需要背下所有 Skill。
> 想了解体系为什么这样设计，读 [当前项目介绍与目标对齐说明书](当前项目介绍与目标对齐说明书.md)。

## 1. 一分钟上手

日常直接聊天即可，不需要填写流程字段或背 Skill 顺序。例如：

```text
项目在 [路径]。做个可运行 Demo，只验证 [核心思路]，不用部署。
```

```text
给现有列表增加 [筛选项]，沿用现有交互和技术栈，只改相关代码，改完验证。
```

```text
用 AI 自写优化 [页面]，不改布局和文案，不使用 Superdesign。
```

AI 应自行判断最短足够路径，只简述范围、复用基线和验收终点。涉及关键业务分歧、范围/预算扩大、付费、外部仓或生产操作才请求确认。没有明确要求发布，就不自动发布；“修好它”默认包含针对性验证，不是做完入口阶段就停下来等你说“继续”。

需要更清晰交接时，可以补充这些信息（不是每次必填表）：

```text
体系仓库：[tenger-skills 路径；执行方尚不知道时提供]
目标项目：[路径]
目标与验收点：[什么结果算完成]
允许/禁止：[修改范围、不允许的动作]
已有材料：[相关文件；没有就说没有]
时间/成本预算：[可选]
本次终点：[可选；默认目标实现并验证，不含发布]
```

### 1.1 AI 自动选择执行强度

| 强度 | 典型任务 | 你会得到什么 |
|---|---|---|
| 轻量 | 实验 Demo、低风险小需求/小 Bug、局部设计 | 直接执行必要 Skill，保留验收点、改动和验证摘要；不要求整套 PRD/FTDD/Envelope |
| 标准 | 常规跨模块迭代、正式领域交接 | 更新受影响需求/设计，复用已有基线，相关评审与回归 |
| 完整 | 大型新项目、跨系统改造、高风险任务 | 完整追踪及所需安全、验证与发布控制；仍不越过用户终点 |

小任务涉及权限、资金、迁移、不可逆删除或生产操作时会升级对应控制，不按代码行数决定。轻量结果不等于正式 Gate 通过，不修改正式批准状态；已有相关阻塞也不能绕过。Superdesign A 路径保持原流程，自写 B 才采用本次裁剪。

规则入口：仓库根 `shared/execution-profiles.md`。这是 Agent 执行规则，不是自动调度器，不承诺固定时间或 token 节省比例。

### 1.2 PRD 不必每次通读

已有 PRD 的速查表/模块文档就是需求 Wiki 的基础：先固定已确认版本，再按 REQ/AC 找原文，补齐相关权限/状态/跨模块依赖。任务摘要记录来源路径和内容指纹，续做/交接时核对是否变化；只有变更影响的上下文才刷新。索引只是导航，不能独立修改或替代原文。无 PRD 的小 Demo 只需明确目标与验收点。

规则入口：仓库根 `shared/requirements-context.md`；无需额外部署 Wiki 或向量数据库。

> 下文 `.spec/` 全套状态、Envelope、注册与审批操作是**标准/完整及正式交接**的使用说明，不是所有轻量任务的前置。轻量暂停/跨会话时只需把同一任务摘要保存到已有记录（没有才新建 `.spec/tasks/<task-id>.md`）。专业视觉验收仍需真实浏览器；源码检查不等于视觉通过。

**你只需要优先掌握三个入口：**

| 你想做的事 | 优先入口 |
|---|---|
| 做项目、改项目、不知道从哪里开始 | `workflow`，由它判断生命周期和阶段 |
| 已明确只要某一项专业工作 | 点名对应 Skill，例如 `prd-review`；仍核对前置、范围和授权 |
| 改进这套工程体系本身 | `skill-optimizer`；偏好/行为进化用 `skill-evolver` |

当前体系（包括本次轻量路由与 B 自写调整）仍待真实项目试跑与独立验收。可以在明确授权、受控范围内试用，但不要把本地校验通过当成全体系正式验收或生产授权。

### 1.3 试跑时的问题记录

出错后不等收尾：执行方在下一安全节点把已观察事实写入现有报告/任务卡/轻量摘要，并维护项目 `.spec/问题日志.md` 索引。根因未知仍记事实；恢复和交付前回读未决项。已修复不等于复核通过。无问题不建空台账，也不为记录错误补整套正式文档。

发现疑似 Skill 缺陷但未获跨仓授权时，先在项目标待反馈。你可以说「综合分析这个项目的问题日志，给出需要反哺的规则」；明确授权后才修改体系源仓或同步安装副本。原始问题一事一源，索引和经验规则只引用，不复制多份。

规则入口：`shared/problem-recording.md`。这是 Agent 规程，不是后台自动捕获服务；写失败会明确报告未落盘，不能保证宿主突然退出也不会丢失尚未保存的信息。真实试跑验收案例见 `docs/task-scope-regression.md`。

## 2. 先把两类仓库分清楚

```text
tenger-skills/                  工作方法、公共规则、注册表和校验器
  Workflow/SKILL.md             总入口
  shared/                      共同契约和模板
  governance/                  Skill/流程/状态/产物/知识依赖登记
  scripts/                     验证工具

你的业务项目/                  真正被开发的对象
  .spec/                       这个项目的产物、状态、证据和决策
  src/ 等                      这个项目的代码

skills-knowledge/              外部可复用工程资产库（另一个仓库）
```

- 为业务项目生成的 PRD、评审和测试记录，写到**业务项目**，不要全堆进 tenger-skills。
- tenger-skills 自己也有 `.spec/`，那是这套体系自身的治理和研究资料，不是其他项目的进度表。
- 本仓 `skill-knowledge/`（单数）只是引用层；外部 `skills-knowledge`（复数）才是资产本体。
- Git 路径是 `Workflow/`；当前 Windows 本地可能显示 `WorkFlow/`，不要误建两个目录。

## 3. 第一次使用：准备什么

### 3.1 让执行方能读到完整依赖

最简单的方式是明确给出**体系仓库绝对路径和目标项目绝对路径**，让执行方从源仓读取入口与引用。

不能假定把一个 `SKILL.md` 复制出去就能独立运行：它还会读取公共契约、注册表、references 和 assets。若使用宿主的已安装副本，应确认：

- 读到的是本次更新后的版本，不是旧副本；
- 公共契约、注册表与资源路径都可解析；
- 没有让不同来源的副本和旧记忆互相覆盖。

本仓没有一个通用于所有宿主的“一键安装所有 Skill”脚本。本手册不假定安装已完成，不执行个人目录同步，也不建议用镜像删除命令覆盖安装目录。

### 3.2 检查能力，不只检查文件

| 工作 | 必须确认的能力 |
|---|---|
| 仓库校验 | Python 3.10+；Windows PowerShell 5 或 PowerShell 7；固定依赖 PyYAML 6.0.3 |
| 代码实现和测试 | 目标项目自身的包管理器、构建命令、测试环境；不是安装 Python 就够了 |
| 原型/UI/前端真实验收 | 可用浏览器工具、可启动页面、可保存截图证据 |
| OSS 研究 | 能取得可靠源码/官方资料与版本锚点；无可靠证据时标 OPEN |
| 工程资产复用 | 外部知识库位置可读，索引与版本可核对 |
| 发布和运行闭环 | 环境、真实授权、回滚方案、日志/监控可用且已脱敏 |

`auto-test` 分层执行：L0/L1 不以浏览器为统一前置；L2 浏览器流程/视觉验收需要真实浏览器。无法执行的层必须列出，不能把局部通过说成全量通过。

UI 出稿以当前 `UI/UI-UX-Design/SKILL.md` 为准，支持云端/AI 自写路径；不要再按历史流水线“没有云端额度一律阻塞”的旧描述操作。付费仍需确认。

### 3.3 初始化并验证体系仓库

以下在 Windows PowerShell 执行。将 `$SkillsRoot` 改成你的实际位置。

```powershell
$SkillsRoot = 'D:\project\agent-project\tenger-skills'
Set-Location -LiteralPath $SkillsRoot

# 首次使用：创建本仓 .venv、安装固定依赖并执行校验；可能需要联网安装依赖。
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\bootstrap.ps1

# 日常全量校验：已包含回归测试。显式传路径，避免本次发现的默认参数问题。
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\validate.ps1 -ProjectRoot $SkillsRoot

# 可选：只调试回归测试，不等价于全量体系校验。
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\run-tests.ps1
```

本次实测：**显式 ProjectRoot 的全量校验退出 0，36 个测试通过**；外部知识库未配置，输出降级警告。bootstrap 的既有成功记录见系统验证报告，本次未重复安装依赖。

**已知启动限制**：本次环境中直接 `-File .\scripts\validate.ps1` 不带 ProjectRoot 会在默认参数求值时出现 PSScriptRoot 为空的错误。上面显式传路径的命令已验证可用；本次未修改脚本。

这些命令校验的是**工程体系仓库**。不能把 `validate.ps1 -ProjectRoot` 随意指向普通业务仓库并认为它会自动运行那个项目的业务测试。

### 3.4 外部知识库：可选依赖不等于可以伪造检索

有真实知识库时，按实际位置设置，仅影响当前终端及子进程：

```powershell
$env:SKILLS_KNOWLEDGE_ROOT = 'D:\project\agent-project\skills-knowledge'
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\validate.ps1 -ProjectRoot $SkillsRoot -StrictKnowledge
```

至少需要知识库内存在 `asset-library/registry.yaml` 和 `组件总清单.md`。不要创建空文件骗过检查。

- 不配置：默认 `warn-and-degrade`，不是完整外部知识验证。
- StrictKnowledge：缺失依赖应失败。
- 某项实现必须依赖外部资产而无法取得时，仍要停止该项或由你确认可接受的替代方案；全仓校验的降级策略不是业务任务免责条款。
- 本次没有运行连接真实知识库的严格验收，不声称外部库已验证。

## 4. 日常使用：你做决策，执行方维护过程

### 你负责什么

1. 说清要达成什么、不做什么、做到哪里停。
2. 确认产品定位、MVP、关键业务规则与重要技术取舍。
3. 裁决评审问题是否成立；确认风险例外、付费、生产和跨仓操作。
4. 看最终证据，判断交付是否满足你的目标。

### 执行方负责什么

- 检查分支、未提交变更、既有基线和真实可用环境，不覆盖你的工作。
- 按任务风险选择执行强度和所需 Skill，不把模型自己的推断当作用户已确认需求。
- 轻量任务维护同一份范围、验收和验证摘要；标准/完整及正式交接维护 manifest、workflow、traceability、决策和证据引用。
- 由对应专业 Skill 产出，由评审/测试提供可复核证据。
- 失败时给出责任人、缺什么、如何解除阻塞，不无限重试或假放行。

这里的分工是工作规程，不代表仓库有后台服务自动替执行方完成所有记录。

### 正式流程：每阶段看这一张摘要

以下为摘要格式示意，不是本项目的真实通过记录：

```text
项目 / 本次执行批次：……
本次目标与终点：……
当前阶段 / 使用 Skill：……
已完成：……
产物与版本：实际路径/manifest ID
验证：实际命令与退出码、报告/截图路径
Gate：PASS / CONDITIONAL / BLOCKED
允许下游：true / false
遗留问题与未测范围：……
需要你决定：……
下一步 / 责任人：……
```

轻量任务只需报告「改了什么、依据与验收点、实际验证结果、未测项和下一步」，不填写正式 Gate 或 manifest 字段。

你可以直接说：“只给我结果摘要和待决问题，细节按需落盘，需要时我再看。”

## 5. 常用场景：直接照着说

### 5.1 从零做产品

```text
项目是 [路径]，我想给 [目标用户] 解决 [问题]。
使用 workflow，先做项目基线、想法登记和产品发现。
这次只做到形成可讨论的问题和假设，不直接写完整 PRD，更不要写代码。
把证据、假设和需要我确认的内容分开。
```

之后按产品发现 → 竞品研究 → 定义 → 蓝图 → 功能决策 → PRD/评审 → 原型/评审推进。你确认了后续范围，才继续。

### 5.2 已经有 PRD，想直接做原型或开发

```text
项目 [路径]，已有 PRD 在 [路径]，本次希望做到 [原型评审/测试]。
先验证这些产物是否有效、已批准、覆盖本次范围。
能复用的不要重做；缺失或失效的列明，不能假定以前聊天确认过就算通过。
给我最短的合规路径，不要自动部署。
```

有效产物不代表所有后续前置已满足：从 PRD 到代码仍需按项目形态核对原型、方案、接口等。

### 5.3 老项目加一个功能

```text
项目 [路径]，增加 [功能]，现有 [行为/接口/数据] 不允许被破坏。
先核对影响范围：低风险局部需求直接实现并做针对性验证，不补整套接管文档。
复杂跨模块变更再走标准 CHANGE，补齐必要基线，只重做受影响阶段和评审/回归。
不改 [禁止目录/模块]，不升级无关依赖，不上线。
```

不要为小功能重写整个产品，也不要因为“改动小”跳过受影响行为的测试。

### 5.4 修 Bug / 处理事故

```text
项目 [路径]，当前现象 [描述]，期望行为 [依据]。
复现步骤/日志/版本：[材料路径或记录]。
先判断风险；局部低风险问题直接定位并交给所需开发 Skill 修复/验证，
不机械加完整 intake；复杂缺陷或生产信号才进入 defect-triage/事故流程。
根因证据不足不要直接猜改；本次允许 [范围]，结束于回归验证。
若判定为生产事故，先给止损选项；生产操作须我单独授权。
```

Bug-Fix 负责定位和委托闭环；实际改码交给对应开发，深度回归交给测试。止损成功不等于永久修复完成。

### 5.5 只评审 / 只验收

```text
只评审 [产物路径]，基准是 [PRD/原型/设计稿路径]。
使用 [prd-review / tech-review / code-review / fidelity-review]。
只审不改，给带证据、严重级别、修复判据和责任人的问题清单。
待我确认后，再安排对应产出方修改。
```

真实运行验收用 `auto-test`，要求报告已测、未测、残余风险及新证据。`testing` 是备用，不是另一个默认必跑整套流程。

### 5.6 重构 / 性能或成本优化

```text
项目 [路径]，要改善 [结构/性能/成本]。
先建立当前基线，明确不可改变的外部行为和保护指标。
结构重构走 REFACTOR；指标优化走 OPTIMIZE。
先交方案、收益验证方式和回退路径，等我确认再实施。
```

若提出新行为，不要藏在“重构”名义下，应显式登记需求变化。

### 5.7 准备发布

```text
项目 [路径]，版本 [commit/tag]，目标环境 [环境]。
先用 release-planning 核对评审、测试、变更范围、回滚和观察指标。
这次只出发布计划，不执行部署。
等我明确批准具体版本、环境、动作和窗口后再执行。
```

发布后还要 `release-verification` 和观察/复盘。不要用“部署命令退出 0”替代业务健康验收。

### 5.8 体系越用越乱，或希望它记住偏好

```text
本次对象是 tenger-skills，不是业务项目。
请 skill-optimizer 根据 [问题池/会话/失败轨迹] 诊断 [具体问题]。
区分项目偶发问题、通用流程问题和用户偏好；无证据不泛化。
先给增量改进建议、落点、验证和回滚方式，不先大规模重构。
若用 skill-evolver 提炼偏好，请把沉淀内容完整展示给我，确认后再执行。
```

当前 `skill-evolver` 默认标准档是逐条确认后执行，不是默认自动自我改写。

## 6. 怎样继续、暂停、跳过和恢复

### 继续

“继续到 [明确终点]，沿用已确认范围；遇到新范围、授权或关键决策问题停下。”

### 暂停

“停在当前安全边界，记录已完成、未完成、改动、证据和下一步，不再进入下游。”

### 跳过

“我希望跳过 [阶段]，先核对已有产物是否等价覆盖，说明缺口与风险。”

这不是无条件绕过 Gate 的口令。缺少必要证据不能标 PASS，P0 不能靠风险接受放行。

### 换会话/换执行 Agent

```text
继续项目 [路径]，不要靠上次聊天记忆推断进度。
先读项目 .spec/manifest.yaml、workflow.yaml、traceability.yaml，
以及当前任务的决策、Gate 和证据文件。
核对代码版本与上次记录是否一致；失效证据不能复用。
先告诉我：上次停在哪、现在是否仍可继续、下一动作是什么。
这次只做到 [终点]。
```

旧项目仅有 `.spec/PIPELINE.md` 或 `.spec/WORKFLOW.yaml` 时，先只读取历史信息，再经核对迁入现行记录；不要同时维护两套“当前进度”。

## 7. Gate 和评审闭环：为什么有时系统会停下来

| Gate | 含义 | 你该做什么 |
|---|---|---|
| PASS | 必需输入、产物、证据、批准及验收完整，本次无残余 P0/P1 | 根据约定终点决定继续或停止；不自动等于允许生产发布 |
| CONDITIONAL | 授权责任人明确接受了残余风险；只有 allowDownstream=true 才可继续 | 看风险、责任人、截止时间、补救措施和批准范围 |
| BLOCKED | 必需输入/授权/证据缺失，或有不能放行的问题 | 要求说明缺什么、谁处理、达到什么条件才解除 |

- P0：关键链路不可用、不安全等，任何残留都阻塞。
- P1：重要边界、契约或可验证性问题，未解决不能 PASS。
- P2/P3：非关键问题可记录风险、责任人和后续动作，不自动单独阻塞。
- `PRD_APPROVED`、`TEST_PASSED` 是阶段状态；不是额外 Gate 值。

### 标准评审闭环

```text
产出 → 评审 → 冻结本轮问题清单 → 用户/授权人裁决
→ 对应产出方修复 → 核对修复证据 → 复核 → 记录 Gate
```

同一问题批次最多三轮修复复核；没有自动第四轮，也没有“三轮满了强制放行”。残余 P0 必须 BLOCKED；残余 P1 只能走完整授权例外或继续阻塞。

例外记录必须有：`exceptionId`、`risk`、`owner`、`dueAt`、`remediation`、`allowDownstream`、`approvalRef`。一句“先这样吧”不能自动转为任意范围永久豁免。

评审复核聚焦已确认清单，新增问题单独登记；测试修复后的回归仍按测试规程覆盖受影响行为/全量回归，不能误解成只重跑一个失败点即可交付。

权威规则：[Gate](../shared/gate-policy.md)、[防死循环](../shared/anti-deadloop.md)。

## 8. 文件在哪里：日常先找这三份

以下为业务项目的常用布局示意，未必每次任务都有所有目录：

```text
目标项目/.spec/
  manifest.yaml         交付物索引
  workflow.yaml         当前阶段、Gate、阻塞原因、下一步
  traceability.yaml     需求/产物/实现/测试/发布/信号之间的关联
  tasks/                task-envelope 的实际任务实例
  decisions/            真实决策与例外批准
  gates/                Gate 记录
  evidence/             验证材料（也可能归档在各领域产物目录）
  authorization.yaml    任务预检使用的审批人/可批准动作配置
  PRD/                  常用产品规格目录
  原型/、设计稿/         结构与视觉产物
  需求评审/、代码评审/等  评审报告和问题清单
  auto-test/            用例库、报告、任务卡、截图/日志等
```

这不是让你手工创建一堆空目录。执行方应按实际任务产生文件并登记真实路径；模板中的占位符不是合法授权和有效证据。

项目的评审问题留在项目里；可复用 Bug 模式才进入本仓 `bug-patterns/`，Skill 方法问题进入 `issue/`。沉淀前要去敏、判断复用价值并确认资产归属，不把客户代码直接搬回个人库。

## 9. 进阶：任务范围单和状态转换预检

普通使用者可先跳过本节；需要解释为什么转换被拒绝时再读。

### 9.1 两个不同的检查时点

1. **开始工作前**：确认项目、执行批次、输入、允许/禁止路径和真实授权，建立 task envelope 实例。
2. **完成工作后、写入完成状态前**：归档真实产物和本轮证据，绑定版本与摘要，执行只读 `task_preflight.py`。

预检要求完成证据，不是要求开工前先伪造“已经完成”。未产出的东西不得预先登记成已验收。

### 9.2 预检需要哪些实际材料

- 目标项目的 manifest、workflow、traceability；任务实例中的身份、生命周期、版本与当前状态一致。
- 合法的 transitionId/from/to/actor；不是编一个状态名。
- `.spec/authorization.yaml` 及 manifest 登记的真实 APPROVED 决策，审批范围和有效期匹配。
- `execute-task` 基础授权；部署还需 `deploy`；解除阻塞还需 `clear-block` 与解除证据。
- 本轮证据的 `executionId`、`revision`、`role`、`subjectRefs`、`subjectDigests`、`contentDigest`；摘要按文件原始字节 SHA-256。
- 任务输入/产物、允许路径、禁止路径、期望输出和验收条件完整。禁止路径优先。

执行方从 [任务模板](../shared/templates/task-envelope.yaml) 创建目标项目 `.spec/tasks/` 下实例，填真实信息。不要直接把模板占位值当可放行任务。

### 9.3 命令与成功含义

以下假设已创建实际任务文件；`$ProjectRoot` 和任务文件名须替换。不是复制后就必然通过的演示实例。

```powershell
$SkillsRoot = 'D:\project\agent-project\tenger-skills'
$ProjectRoot = 'D:\project\your-project'
& "$SkillsRoot\.venv\Scripts\python.exe" `
  "$SkillsRoot\scripts\task_preflight.py" `
  --project-root $ProjectRoot `
  --task-file '.spec/tasks/TASK-001.yaml'
```

- 退出 0：提出可用的只读转换计划；输出中 `stateChanged=false`、`skillExecuted=false`。
- 退出 1：读取 errors，按缺口修复；不能手工把 Gate 改成 PASS 糊过去。
- 工具不调用 Skill、不写状态、不部署；实际受控状态写入仍由流程执行方负责。
- 预检后任何输入、代码、批准或证据变化，都应重新核对并运行。
- YAML 与摘要只能验证一致性，不能证明签批人身份。生产级可信审批还需受保护的审查/签名或外部审计控制。

细节见 [验证工具链说明](validation-toolchain.md)。

## 10. 常见卡点与处理

| 现象 | 原因/正确处理 |
|---|---|
| 不知道该叫哪个 Skill | 叫 workflow，并给目标、范围、终点；不要先读完 45 个入口 |
| 文档越写越多但没推进 | 要求每份产物说明“哪个下游消费、解决哪个决策/验收问题”；按影响裁剪，不能拿文档数量当进度 |
| 仓库校验通过，系统仍 BLOCKED | 前者是结构/规则检查；后者仍等真实试跑和独立验收，不矛盾 |
| validate.ps1 报 PSScriptRoot 为空 | 用本手册显式 `-ProjectRoot $SkillsRoot` 的调用；不要把启动失败记成检查通过 |
| import yaml 失败或用了错 Python | 运行 bootstrap；优先用本仓 .venv；检查是否误设 TENGER_PYTHON |
| 缺浏览器却给出“页面验收通过” | 结论无效；补能力或明确未测边界，依赖真实渲染的阶段不可假通过 |
| “知识库未配置” WARNING | 明确降级；配真实路径后跑严格模式，不声称做过完整检索 |
| 有代码但没有批准基线 | 先接管并确认；现有行为只是事实，不自动成为正确需求 |
| 三轮修复后还有 P1 | 不强制 PASS；等待有效例外或重新明确范围和修复决策 |
| 换会话丢了上下文 | 从项目三份主记录、决策和证据恢复；核对版本，不靠旧聊天猜 |
| Agent 说“我已批准” | 建议不是用户批准；检查真实授权者、动作、范围和有效期 |
| 旧文档说用 PIPELINE、强制放行 | 这些是历史口径；以当前 shared 契约、注册表和 workflow.yaml 为准 |

## 11. 一次任务结束，检查这八件事

- [ ] 目标与实际结果对应，没有未批准的范围扩张。
- [ ] 产物路径与当前版本清楚，manifest 能找到。
- [ ] 本次真的执行了应有验证，有命令、退出码或其他可复核证据。
- [ ] 覆盖边界、未测项和残余风险写明。
- [ ] Gate 与 allowDownstream 合法，没有把未验收写成通过。
- [ ] 决策确实来自你或授权责任人，付费/生产/外部仓操作没有越权。
- [ ] 状态、下一动作和责任人已落盘，换会话可以继续。
- [ ] 有复用价值的问题说明沉淀落点；没有价值的不要硬造规则或新组件。

## 12. 本手册的边界

本次是**说明书整理与使用命令核验**，没有更改 Skill 行为、注册表、批准记录、系统 Gate 或生产环境。当前总 Gate 仍为 BLOCKED，等待真实项目试跑和独立验收。

后续维护本手册时，应核对当前 Skill、公共契约和脚本，不把本文变成与它们竞争的第二套运行规则。历史迁移指南与记忆只能解释背景，不能覆盖现行契约。
