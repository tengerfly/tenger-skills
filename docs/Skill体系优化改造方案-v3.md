## 0. 你对"质量可靠"的定义（我复述，这是全案的第一性原理）

> 强模型：说完需求，一次做到满意。
> 弱模型：只做到 60%，**skill 的审核机制发现哪里不对、告诉模型该怎么改**，模型改，再审，直到达标。
> 最终质量可靠，**与模型强弱无关**。

换成一句话：

**这套体系交付的不是"流程"，是"收敛保证"。**

流程（13 个节点、4 个评审域、3 轮上限）只是收敛的手段。手段失效时，加流程没有用——必须修**收敛机制**本身。

这句话同时定义了"模型无关"：质量不取决于模型第一次做得多好，只取决于
①**检查能不能查出问题** ②**问题能不能被描述成可执行的改法** ③**循环能不能停**。
三件事都不依赖模型能力，所以可以做到模型无关。

## 1. 证据：不收敛是实测的，不是猜的

### 1.1 两个项目，同一套 skill，差 4 倍以上

| 项目 | 周期 | 结果 |
|---|---|---|
| travel-agent（CREATE） | 10-09 → **10-11**（2 天） | 到 `CODE_REVIEW_IN_PROGRESS`，Gate PASS，389 单测 / e2e 47 / 覆盖 94.7% |
| knowledge-bases（CHANGE） | 10-09 → **10-15**（6 天+） | 仍停在 `TECH_DESIGN_IN_PROGRESS` / **BLOCKED** |

skill 集合完全相同。**所以慢的变量不是 skill 数量、不是装载面。**

### 1.2 评审轮次的演变（按 `knowledge-bases/.spec/` 实际的复核报告统计）

| 评审域 | 第 1 轮 | 第 2 轮 | 第 3 轮 | 判定 |
|---|---|---|---|---|
| 需求评审 | P0=5 P1=33 P2=39 | P0=0 P1=7 P2=11 | P0=0 P1=1 P2=0 | ✅ 收敛 |
| 原型评审 | P0=9 P1=30 P2=26 | P0=2 P1=4 P2=4 | **P0=7 P1=15 P2=93** | ❌ **爆炸** |
| 设计评审 · 批次 1 | P0=14 P1=12 P2=20 | P0=10 P1=14 P2=20 | — | ❌ 不收敛 |
| 设计评审 · 批次 2 | P0=3 P1=3 P2=4 | P0=3 P1=12 P2=7 | P0=2 P1=15 P2=28 | ❌ 变大 |
| 设计评审 · 批次 3 | P0=6 P1=8 P2=5 | P0=3 P1=3 P2=2 | P0=1 P1=2 P2=1 | ✅ 收敛 |

三个读数：

1. **同一域里，收敛与否分明**——需求评审和批次 3 好好收敛了，原型评审和批次 1/2 完全没收敛。说明这不是"评审太难"，是**某个条件在两个场景下不同**（见 §2）。
2. **P2 是爆炸源**：原型评审第 3 轮 P2=93。P2 本是"记录风险后可保留"，却被开了任务清单并追踪状态，实际按阻断项处理。
3. **第一轮 P0 数量从 3 到 14 不等**——同一套判据，不同轮次/批次给出的严重度差 4 倍。**严重度是模型现判的，不是标定的**，这直接违反你要的"模型无关"。

### 1.3 一个被低估的成本

knowledge-bases 在 `.spec/设计稿/_tools/` 里现场造了 `review_r3_scan.py`、`review_r3_scan.js`、`hook_review_notes.py`、`review-harness-r2.html`、`review-baseline.json`、`review-after.json`——**6 个对账工装，跑完就扔，下个项目重造。**
这正是"模板库"原本要解决的速度问题。模板弱化后，这个缺口必须由**体系自带工装**补上，否则只会更慢。

## 2. 不收敛的四个成因（逐条对得上证据）

### 成因 1 · 评审对象在被评审的同时被修改 → 每轮审的是不同的东西

原型评审第 2 轮 P0=2，第 3 轮 P0=7。同一对象不可能凭空多出 5 个 P0——**说明中间改过**。

你们其实已经有机制：`contentDigest` / `subjectDigests` + `gate-policy.md` §6.6 明写"摘要不符即视为被评审基线已不存在，本轮结论作废"。但**流程上没有强制冻结点**：设计稿改了，评审继续在原轮次上跑，于是每轮都在审一个新版本。

> 这是最致命的一条：**不冻结就永远不收敛**，因为达标线一直在动。

### 成因 2 · 每轮重新全量扫描，而不是只验上一轮

`shared/anti-deadloop.md` 写了"复核只验本轮已确认项，不无限新增"，但**没有执法者**。评审 skill 的职责写的是"找没闭环/四维独立复审"，模型自然按"再查一遍"执行 → 第 3 轮还能查出 93 个 P2。

### 成因 3 · 发现集没有边界，也不闭合

问题清单是**只增不减的台账**（`待确认 → 已确认/已忽略 → 已修复`），没有"本轮要关多少、关完就算过"的闭合定义。所以退出条件是"评审觉得没问题了"——一个模型判断，不可机械判定。

### 成因 4 · 严重度是模型现判的，没有标定

P0 从 3 到 14 波动，说明 P0/P1/P2 的边界由评审者的手感决定。**严重度不稳 → 轮次上限（3 轮）在不同域上含义完全不同 → 收敛保证不成立。**

> 这四条不是"执行不力"，是**机制缺件**。加规则不会好，只会让下一轮查得更细。

## 3. 目标架构：一条主链 + 三层检查 + 一个收敛器

### 3.1 一条主链：4 个交付物（不是 13 个节点）

| 交付物 | 内容 | 谁产出 |
|---|---|---|
| **D1 需求包** | PRD + 范围 + **可执行验收判据**（AC 逐条带判定方式） | product 包 |
| **D2 设计包** | 原型 + 设计稿 + design-system token | design 包 |
| **D3 方案包** | TDD/FTDD + 接口契约 + 测试方案 | build 包 |
| **D4 实现包** | 代码 + 测试 + 验收脚本的实跑记录 | build + verify 包 |

原来的 idea-intake / discovery / definition / blueprint / feature-decision / prd-design / prd-review **不是 7 个阶段，是 D1 内部的 7 个章节 + 1 次确认**。同理原型/设计稿评审不再各占一个节点，而是 D2 的检查集。

> 你已认可的 7 个包边界不变；变的是**包内从"节点链"变成"交付物 + 检查集"**。

### 3.2 三层检查：能用脚本判的绝不交给模型

| 层 | 性质 | 判据来源 | 成本 | 谁执行 |
|---|---|---|---|---|
| **L1 结构** | 可脚本 | 必需章节/字段/引用/digest/登记 | 秒级、零 token | `validate_core` 等 |
| **L2 契约** | 可脚本 | 接口/类型/枚举/页面↔原型↔token 对应 | 秒级 | 新增 check_* |
| **L3 语义** | 需判断 | 闭环/口径/还原度/可维护性 | 贵 | 评审 skill + rubric |

**关键约束：L3 只查 L1/L2 查不到的。** 现在大量 L3 工作（逐段对账、token 搬运、契约一致）本质上可脚本化，却交给了模型用自然语言做——这是"9 天"的主要成分之一。

### 3.3 一个收敛器（**本方案的核心新件**）

这是把"模型无关"变成事实的唯一办法。规格如下：

| 规则 | 内容 | 可机械核验 |
|---|---|---|
| **R1 冻结** | 每个交付物评审前打 `digest`；评审期间该文件只读。要改 → 结算为新版本，本轮结论作废并重开 | ✅ 现成 `subjectDigests` |
| **R2 闭合集** | 第 1 轮产出 `F1`（固定 ID 集合）；**第 2 轮起只验 F1，不新增** | ✅ 复核报告只能出现 F1 的 ID |
| **R3 新发现进队列** | 新问题进 backlog，**不阻断本轮**；只有 P0 或"F1 同类复发"可并入 F1 | ✅ 类型字段 |
| **R4 退出条件** | F1 全关 + L1/L2 全绿 = PASS。**不是"评审说没问题了"** | ✅ 全机器可判 |
| **R5 严重度标定** | P0/P1/P2 由**规则表**定义（附例），不由模型手感定义 | ✅ 规则表 + 抽查 |
| **R6 P2 预算** | 每轮新增 P2 上限（如 10）；超出必须给出"为什么是新类"否则丢弃 | ✅ 计数 |
| **R7 自主预算闸** | 自主跑：轮次 ≤3、总时长 ≤T、同交付物总发现 ≤N；到顶**停下出收敛报告**，不继续开新批次 | ✅ 计时/计数 |

**R7 尤其重要**，因为你说"都是让大模型自主跑的"。自主跑没有预算闸，就一定会跑到你不得不插手为止——本轮就是九天。

**收敛报告**只答三问：① 卡在哪个判据 ② 为什么三轮没关掉 ③ 需要你定什么（选项 + 影响）。**不再产出第四轮任务清单。**

### 3.4 修复指导（弱模型能不能达标，全靠这个）

finding 强制五字段，缺一个即不算有效发现：

```yaml
id: D2-F1-007
severity: P1              # 规则表定义，可机械复核
where: .spec/设计稿/graph.html:120-135
symptom: 状态词 12 种，design-system §1.2 只定义了 4 种
criterion: 出现的每个状态词都能在 §1.2 找到映射        # 可执行判据
fix: 在 §1.2 补齐映射表，或改稿面用已定义词；二选一
verify: 跑 checks/token-coverage.py，输出 0 missing
```

有 `criterion` + `verify` 的 finding，弱模型也能照着改到绿；没有的，就只能靠"再评一遍"。

## 4. 与你的三条不变量对齐

| 不变量 | 这个架构怎么满足 |
|---|---|
| **宿主无关** | 一切是"文件 + Python + 测试"。入口用项目根 `AGENTS.md` + `stages/*.yaml` 清单；不依赖宿主 skill 发现、不依赖 `skill-usage.json`、不依赖任何 hook。7 个包是可选的适配层，内容由清单生成，不另存一份。 |
| **模型无关** | L1/L2 是确定性脚本；L3 必须给 rubric + 反例；退出条件是"F1 全关 + L1/L2 全绿"，不含模型判断。强模型一轮过，弱模型多轮，**轮数由检查驱动，不由流程规定**。 |
| **模板弱化** | 不再维护大模板；改为**体系自带的小工装**（对账脚本、契约断言、token 覆盖检查）+ 判据。模板从"复制粘贴源"降级为"可选参考"。 |

**一个必须点明的取舍**：模板弱化会拿掉"速度"，工装化拿回"速度"。两者不能只做一半——只弱化模板不建工装，项目会更慢（knowledge-bases 的 6 个一次性脚本就是证据）。
