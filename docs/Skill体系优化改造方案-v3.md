## 0. 我理解的需求（**请先更正这一节**）

按优先级四件，外加一个隐含目标：

| # | 需求 | 我的复述 |
|---|---|---|
| 1 | 保证质量 | 流程按约定走，产出的代码不是没人看得懂的屎山。**不可谈判。** |
| 2 | 流程要快 | 近 50 个 skill 堆砌，每个任务都要背一大堆规则，慢。 |
| 3 | 按阶段加载 | 某一阶段只加载该阶段的 skill。 |
| 4 | 弱化"教 LLM" | 模型变强了，不需要手把手教怎么做。 |
| 5 | （隐含）自进化 | 已有可观测 + 评审体系，希望它驱动 Skill 自我改进。 |

**我的判断**：1 与 2/3/4 并不冲突，冲突发生在"用什么手段保证质量"上。

现在是用**文字**保证质量。文字的成本随规则条数线性上升（每次运行都要重读），收益随模型变强快速下降。所以需求 1 的解法不是"加更多规则"，而是"把能机械化的挪出文字"。这是本方案的主轴。

如果上面有任何一条理解偏了，先纠正它，后面的设计都建立在它之上。

## 1. 评审

三个直接结论：

1. **契约实际有三档**：`v1`（33 个）、`legacy-wrapper`（12 个）、`legacy-adapter`（5 个，走 `contractPath`，校验器不查必需章节）。所谓"统一契约"覆盖的是 40/45。
2. **重复量 56KB**：合同样板 49.9K + 问题记录块 9.8K（减去一份真身）≈ 全量 21%。删掉它们**一条规则都不用删**。
3. **规则存量 306 条**，且只增不减（见问题 2）。一个执行方在单次任务里要同时守住 306 条硬门禁中的一大截，实际做不到——**违规不是因为规则不够，是因为规则太多**。

### 1.2 单任务指令量（核心痛点量化）

|---|---|---|---|---|---|
| A 轻量：改一个前端页 | 20,744 | 24,329（**11 个**） | 12,714 | **61,075** | ~64k |
| B 轻量：贴日志修 bug | 13,301 | 19,285（7 个） | 12,714 | **48,588** | ~51k |
| C 标准：前后端各一模块迭代 | 89,406（8 节点） | 36,500（17 个） | 12,714 | **141,908** | ~149k |
| D 完整：从 0 做一个应用 | 151,604（20 节点） | 36,068（15 个） | 12,714 | **203,674** | ~213k |

**最刺眼的一行是 A 和 B：所谓"轻量档"，在文档上存在，在指令上不存在。**

- `frontend-dev` 一个正文点名 11 个 shared 契约。`shared/execution-profiles.md` 说"轻量不展开全量注册表"，但 skill 正文的 Preconditions 说"read skill-contract / gate-policy / anti-deadloop"——**两条规则在打架，执行方只会读，因为读更安全**。
- 所以"流程慢"不是节点多。是**每个节点都要重读一遍全量契约**。

### 1.3 六个结构性问题

#### 问题 1 · L1 的边界放错了层

你的 `skill-writing-standard.md` §二 已经有 L1–L4 渐进披露模型，方向是对的。但 L1 装的是**45 个原子节点的 description**。**L1 应该是"阶段"，不是"节点"。**

后果可以逐条对上现状：

- 45 条触发词互相覆盖（"评审"命中 5 个 skill，"检查/走查/审查"再命中一批）；
- 于是 `workflow/SKILL.md` 被迫写 205 行消歧规则（§2 入口判据、§3 路由表、§3.1 资源门禁、§4 闸门核对）；
- 于是每加一个 skill，编排器就要加一段"什么时候不用它"。

**这是架构问题在文档层的症状，改文档改不好。**

历史证据：过去 4 次提"按需加载"，全部只落到**写作规范**层（L1–L4 表、≤500 行红线、references 四条组织规则），**没有任何一次改变宿主实际能看到什么**。装载面没动，规范写得再细也不会生效。这解释了为什么"按需加载"提了 4 次、一次没落地。

#### 问题 2 · 增长有引擎，衰减没出口

规则的唯一增长路径是：评审发现问题 → 错误对照表加一行 → 状态写"已沉淀"。306 行就是这么来的。

对面没有任何机制：没有删除、没有合并、没有"这条已经能机器查了所以正文该删"。

《兼容策略》明确"旧 skill 不删"；17/45 是 wrapper/adapter。结果是**能力单增、入口单增、每次同步成本单增**。

这正是屎山的生成机制：**只追加、不归位**。`skill-writing-standard.md` §八"归位原则"把这件事讲得很透（"凌乱不是错别字，而是每轮都把新内容追加到最近的地方"），但**没有执法者**。

#### 问题 3 · 选择压力错位：你在优化"规则被写下来"，不是"缺陷变少"

| 环节 | 实测 | 含义 |
|---|---|---|
| 观测 | 102/102 事件来自 quality-inspection（运维节点），**业务节点 0** | 业务轨无数据 |
| 观测写入 | 靠 agent 手敲 `tsr node-start/end`，**无 hook**（instrumentation-guide 自认"执行规则，不是监听器"） | 不照做则归零 |
| 评审-结构层 | 45 条能跑、12 套 baseline 全绿 | 真在跑 |
| 评审-行为层 | 19/19 blocked；台账 360 行真跑 6 条（351 blocked） | 基本没跑 |
| 单条行为用例成本 | 32,357 / 58,691 / 106,325 token | 不可能常态跑 |
| 闭环 | `confirmations` 不存在，闭环率 N/A；候选卡 1 张未确认 | 人在环断开 |
| 进化 | 台账 4 条，**0 条走完全链**；跑通的 2 条都是"量具修自己" | 不是从用户信号进化 |

**"这条规则有用吗"这个问题，现在没有任何数据能回答。能回答的只有"这条规则写下来了吗"。**

而"写下来"是零成本动作、"有用"是高成本验证动作 —— 于是进化必然滑向堆文字。这不是执行不力，是**适应度函数写错了**。

#### 问题 4 · slim 闸门空转，根因不是数据不够

你规定"三读数不齐禁下结论"，于是永远缩不了。

但真正缺的不是样本量，是**检查器不产出 finding**。现在检查器只输出"红/绿 + mustContain 命中/未命中"，不输出：

- 哪条规则、在哪一行、命中了几次；
- 这个问题被采纳还是被忽略；
- 哪条规则跑了 N 次、一次没命中。

**没有 finding 就没有命中率，没有命中率就没有观察名单，没有观察名单就没有删除许可。**

修这一条链路，同时解锁三件事：精简名单 / 规则 TTL / 结局指标。**这是全案 ROI 最高的一处。**

#### 问题 5 · auto-test 双源漂移

| 位置 | 哈希 | 特征 |
|---|---|---|
| `D:\project\agent-project\auto-test\skills\auto-test\SKILL.md` | `82BE5358…` | 有 `version: 0.1.0`、`spec: agentskills.io`（**源**） |
| `tenger-skills/Test/auto-test/SKILL.md` | `934736634…` | 加了三层 legacy-wrapper 契约与独立调用段（**改写副本**） |

同一能力两份正文、没有单一事实源。这类漂移最终必然产生"改了一处、另一处还是旧的"——正是这套体系要防的那类事故。**阶段包里 `verify` 入口必须先解决这件事。**

#### 问题 6 · "教"的弱化，方向反了

你说教 LLM 做事的点可以弱化。但按你 `skill-writing-standard.md` §3.7 **自己**的区分，规则分两类：

| 类型 | 例 | 模型变强后的趋势 | 本方案处置 |
|---|---|---|---|
| **技术型 / 参考型** | 怎么写 React、动效曲线、命名规范、组件库用法、目录结构 | 确实越来越会，且**可以机械校验** | 弱化 → 转检查器 / 直接删 |
| **纪律型** | 测试先行、证据先于声明、只审不改、不离基线、不确定即问、禁静默 TODO | **越强越容易自信地走捷径**，重要性反而上升 | 不弱化 → 强化，且从散文变机器可判 |

**混在一起"弱化"，会正好削掉你现在最值钱的那部分。** 这是本方案要拦的第一个误操作。

### 1.4 该保留的（护城河，本方案一字不动）

- Gate 三值 + 例外七字段 + 三轮上限、无强制放行；
- Envelope + `task_preflight` 只读（`stateChanged`/`skillExecuted` 恒 false）；
- `contentDigest` / `subjectDigests`（防"改了正文没改台账"；实测字段检查漏 73% 漂移）；
- TSR `node-start`/`node-end` + `verify` 复算（防倒签、防"比字节更漂亮"的描述）；
- 证据七标签；单一事实源 + 权威序（shared > governance > SKILL.md > references > legacy）；
- 量具自验（新判据先证会红）；l2Triage 的"罚合规产物"豁免（这条是被真事故换来的）。

**这些是"保证质量"的真身，占系统价值的大头，且成本不随规则条数增长。全案不碰。**

## 2. 目标架构

### 2.1 一句话

**能力体量不动，可触发面收敛；判断留文字，机械进检查器；规则加 TTL。**

三件事分别对应三个问题：入口（问题 1）、文字成本（问题 2/6）、进化动力（问题 3/4）。

### 2.2 四层（复用你已有的 L1–L4 词汇，不造新词）

| 层 | 现状 | 目标 | 作用 |
|---|---|---|---|
| **L1 目录** | 45 条 description / 6,752 字符 | **9 条 / ≤1,800 字符** | 决定"要不要用" |
| **L2 阶段正文** | 每节点 6–20KB，各自重复契约 | 每阶段 4–6KB，只含本阶段契约 | 触发后常驻 |
| **L3 成员细则** | 45 份 SKILL.md 正文 | 原位下沉为 pack 成员 | 按步加载 |
| **L4 检查器** | 只校验流程（gate/artifact/trace） | 新增"产物检查器"（finding 级） | 不占上下文 |

关键变化只有一句：**L1 从"节点"变成"阶段"；L3 从"45 份平级 skill"变成"9 个包 45 个成员"。**

### 2.3 九个入口（推荐档）

| 入口 | 成员能力（原 skill） | 正文预算 | 必要性 |
|---|---|---|---|
| `workflow` | 编排、路由、门禁核对、失败回退 | 4K | 唯一总入口 |
| `product` | idea-intake / product-discovery / competitive-analysis / product-definition / application-blueprint / feature-decision / prd-design / prd-review | 6K | 需求域 |
| `design` | prototype-design / prototype-review / ui-ux-design / ui-ux-review / fidelity-review | 6K | 设计域 |
| `build` | backend-tech-design / frontend-tech-design / tech-review / backend-dev / frontend-dev / code-review | 6K | 构建域（最大） |
| `verify` | auto-test（**先解决双源**） | 4K | 验证域 |
| `ship` | release-planning / deployment-execution / release-verification / post-release-review / signal-collection / signal-triage / incident-response / quality-inspection | 5K | 发布运维域 |
| `meta` | skill-optimizer / skill-evolver / skill-lifecycle / oss-radar / source-reading / essence-distill | 5K | 元工作域 |
| `bug-fix` | 独立入口（日志驱动，真跨阶段） | 保留 | 用户张口就来的场景 |
| `onboarding` | 独立入口（接管旧项目/基线盘点） | 保留 | 跨阶段，且是 CREATE 的起点 |

补：`defect-triage` / `change-intake` / `impact-analysis` / `refactor-planning` / `optimization-planning` 的**路由判断**进 `workflow` 正文（它们本来就是"判一下走哪条"，不产出实质能力）；**能力体**留在对应 pack。

**为什么是 9，不是 7 也不是 12**：7 会把 `bug-fix`/`onboarding` 塞进包，跨阶段任务每次都要换包；12 会让"评审"类触发重新互相覆盖。9 是"跨阶段入口仍可直达 + 阶段内不再竞争"的最小集。

**为什么不是合并**：你历史文档已明确否决"合并/删减"路线（会丢能力，且 17/45 是 legacy 包袱）。本方案**不合并能力、不删规则**，只动"谁能被自动触发"。这正是过去 4 次"按需加载"失败的那一步——**没动装载面**。

### 2.4 规则四分类 J/M/R/D（全案核心机制）

| 类 | 含义 | 载体 | 判定 |
|---|---|---|---|
| **J 判断** | 只有人能定：何时问、要不要升级、范围怎么裁、设计稿能不能降级 | 正文（问题式 + 判据） | 写不成断言的 |
| **M 机械** | 可判真假 | 检查器 `check_*` + `ruleId` | 给产物能返回 finding |
| **R 参考** | 查得到 | references（按需） | 不需要在正文出现 |
| **D 纪律** | 压力下会犯 | 铁律 ≤8 条 | 有"会怎么犯"的具体借口 |

**新机制**：每条错误对照行必须标 J/M/R/D；**M 类必须给 `ruleId`**。没有 `ruleId` 的 M 类视为"未沉淀"，状态不许写"已沉淀"。

落地成本低：这只是把**已有的 L2 回流规则**（P0/P1 必须回流 ≥1 条用例）升一档——从"有断言"到"有可执行检查"。已有的 `relay.py`、`issueRef`、`mustContain` 全部复用，只加一个字段与一条校验。

举例（frontend-dev 的 48 行里）：

| 现规则 | 分类 | 去处 |
|---|---|---|
| 禁 `父级>标签` 通配选择器做样式出口 | M | stylelint 自定义规则 |
| 稿面 `@media` 断点随 token 搬 | M | token 对账脚本扩一项 |
| 组件库派生视觉值（Avatar 字号）须压回稿面 | M | Playwright computed-style 断言 |
| 禁 `calc(100vh - header)` 硬算 | M | lint / grep 规则 |
| 弹框内负 margin 通栏条 | M | 结构断言 |
| "还原度优先，不确定即问给选项" | J | 留正文 |
| "设计稿是唯一视觉基准，禁止自创" | D | 留铁律 |

### 2.5 结局指标（替代"规则存在性"作为适应度）

四项全部能从现有数据算，**不需要新埋点**：

| 指标 | 来源 | 现状 |
|---|---|---|
| 返工轮次 | TSR 的 `round`/`batch`（已有字段，未聚合） | 可立即算 |
| 缺陷复发率 | `tsr recurrence`（已有 6.9%，1 条 3 卡链） | 可立即算，需按 skill 分组 |
| 规则命中率 | **新增**：finding 的 `ruleId` 统计 | 依赖 W1 |
| 逃逸缺陷 | Gate `PASS` 之后才发现的 P0（issue 池反查） | 可立即算 |

可选第 5 项：净删除行数（对"屎山"最直接，但需项目侧配合，先不做）。

### 2.6 衰减与退役

1. **规则 TTL**：连续 N 次运行 0 命中、且无关联缺陷 → 降级到 references 或删。
2. **新增付费**：加一条 M 类必须同时给 `ruleId`；加一条 J 类必须说明"为什么既不能机械化也不是 D 类"。**净增需删/合并一条。**
3. **退役评审**：每季度一次，输入 = §2.5 四项 + 观察名单。

这条是全案最硬的一条，也是最容易被绕过的一条。建议先只对"新增规则"生效，不动存量（存量走 W1 逐条分类）。

## 3. 工作包

四个包，按"风险从低到高、收益从快到慢"排序。**W0 当天可做且零风险，W2 是主改造。**

### W0 · 去重与契约三档归一（0.5 天，零风险）

| 项 | 动作 | 收益 |
|---|---|---|
| 问题记录块 ×45 | 正文留 1 行引用 `shared/problem-recording.md` | −9.8K 字符 |
| Contract Compatibility Layer ×12 | 收敛为 `shared/legacy-skill-adapter.md` 一处，正文只留差异 | −49.9K 字符 |
| 5 个 legacy-adapter | 补 13 章节，或**显式**声明"仅此 5 个豁免"并写进 registry | 消除契约三档 |
| L2 回流块 ×11 | 引用 `governance/eval-spec.yaml` | −3K 字符 |

- **不动**：任何一条规则、任何一个 Gate、任何注册表语义。
- **验收**：总字符 264,644 → ≤205,000；`validate_core` 四子命令 + 12 套 eval 结构层**仍全绿**。
- **反向对照**：故意删掉一个引用目标，校验器必须红（证明"留引用"不是"留空话"）。
- **回滚**：单 commit，`git revert`。

### W1 · 规则分类 + 检查器（2–3 天，解锁一切）

| 项 | 动作 |
|---|---|
| 分类台账 | 新建 `governance/rule-taxonomy.yaml`：306 行逐条打 J/M/R/D |
| 首批检查器 | 20 条高 ROI M 类：契约一致性 8 / 前端样式 6 / 证据摘要 6 |
| 统一输出 | finding = `{ruleId, severity, file, line, message}` |
| 接 slim | `tsr slim` 改读 finding：0 命中进观察名单（现有闸门终于有输入） |
| 文档改写 | 对应正文行改成"跑 X，返回 finding 即违规" |

- **不动**：J/D 类一条不改。
- **验收**：每条新 `check_*` 必须有**反向对照**（把产物改坏必须红）；一条历史缺陷能被检查器复现。
- **风险**：机械化过头会把判断类误判成 M，产生假红、罚合规产物。**你们已经被这个坑伤过**（l2Triage 里 3 条 issue 因判据不可机械化而豁免）。因此 M 类判定强制"双侧证据交集"测试，交集为空就不许判 M。

## 5. 风险与不做的事

### 明确不做

1. **不合并 skill、不删规则**（历史已否决；会丢能力）。
2. **不推翻契约层**（Gate/Envelope/digest/TSR 是护城河）。
3. **不加大爆炸式重构**（删旧入口仍守 5 条件）。
4. **不把 J 类判断机械化**（假红比漏检更贵）。
5. **不为变绿改闸门**（红线）。
6. **不新增流程节点、不加第二个运行时 CLI**。

### 主要风险

| 风险 | 缓解 |
|---|---|
| 机械化过头 → 假红 → 罚合规产物 | M 类强制"双侧证据交集"；每条新检查带反向对照 |
