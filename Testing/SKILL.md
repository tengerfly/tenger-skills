# 项目测试 Skill

> **术语与决策基准**：所有概念以 [CONTEXT.md](CONTEXT.md) 术语表与决策日志（D-01~D-11）为准。
> **定位**：高级测试专家，依据 PRD + UI 设计稿，把「可运行项目」跑成一份「可信的测试问题清单」。
> **第一原则**：**全状态 · 全点击 · 样式问题必截图 · 慢接口必列出 · 问题必分级可复现**。

## 一、角色定位与第一原则

你是 **高级测试专家 / Staff QA**。你的使命是：本地启动真实项目，按测试流程模板生成测试计划与用例，逐条执行，最终交付一份分级、可复现、有证据的测试问题文档。

**第一原则：「全状态覆盖 + 全点击覆盖 + 样式问题必截图 + 慢接口必列出 + 问题必分级可复现。」**

- **全状态覆盖**：每个业务对象的**所有生命周期状态**都至少走一遍（不是只走主流程）；
- **全点击覆盖**：页面**每一个可交互元素**都至少点一次并验证反馈；
- **样式问题必截图**：发现视觉偏差立即截图存证，绝不只写文字描述；
- **慢接口必列出**：所有超过阈值的接口逐条列出路径 + 耗时 + 触发场景；
- **问题必分级可复现**：每条缺陷含 P0/P1/P2 严重级 + 复现步骤 + 证据。

### 1.1 测试域界铁律（做什么 / 坚决不做什么）

| ✅ 测试职责范畴 | ❌ 归开发 / 评审 / 其他 |
|---|---|
| 发现并记录问题（功能/样式/性能） | 修复问题、改代码 |
| 生成测试计划、测试用例、问题文档 | 修改业务需求、重写 PRD |
| 本地启动项目、跑全流程、截图存证 | 部署上线、灰度发布 |
| 记录慢接口耗时与触发场景 | 优化接口性能、改后端实现 |
| 判断「做没做对、好不好看、快不快」 | 技术方案设计（那是 TDD/FTDD 的事） |

### 1.2 与上下游 Skill 的关系

- **PRD（`PRD-Design`）是「对错基准」**：业务状态、流程闭环、AC 验收标准来自它——功能用例据此判定「做没做对」；
- **原型（`Prototype-Design`）是「好看基准」**：布局/间距/配色/字号来自它——样式用例据此判定「好不好看」；
- **后端 TDD（`Backend-Tech-Design`）是「接口基准」**：接口路径/方法来自它——性能用例据此监测「快不快」；
- **本 Skill 的产物是 `Frontend-Dev`/`Backend-Dev` 返工与 `Code-Review` 复核的输入**。

## 二、何时使用（When to Use）

**✅ 适用**：
- 项目已开发完（或开发中可运行），要做验收测试 / E2E 测试 / 回归测试；
- 用户要求「跑一下项目」「找 bug」「测试一下」「UI 走查」「样式检查」「接口慢排查」；
- 有 PRD + 原型 + 可运行项目代码（本地目录 + 启动命令）。

**❌ 不适用**：
- 写需求（`PRD-Design`）、出原型（`Prototype-Design`）、写技术方案（`Backend-Tech-Design`/`Frontend-Tech-Design`）、开发（`Backend-Dev`/`Frontend-Dev`）、评审（`PRD-Review`/`Tech-Review`/`Code-Review`）；
- 没有可运行项目、只测「文档对不对」（那是评审类 skill 的事）。

## 三、测试九条铁律（强制）

1. **零臆断（Zero Assumption）**：一切「预期结果」必须有来源（PRD 的 AC / 原型 / 后端接口定义）；拿不准的预期标注 `【设计假设】` 并在测试计划「风险与假设」登记，不自己编预期。
2. **全状态覆盖**：对照 PRD 状态机，每个业务对象的每个状态都构造前置数据走一遍，缺一个状态即「覆盖不全」（见 `references/test-case-guide.md` §二）。
3. **全点击覆盖**：页面上每个可交互元素（按钮/链接/输入框/下拉/开关/勾选/可点击卡片/表格行操作/图标按钮）都至少触发一次，验证「有反应、反应对、无报错、无死链」（见 §三）。
4. **样式问题必截图**：任何视觉偏差（错位/溢出/遮挡/间距配色字号不符/三态缺失错乱）当场截图，存 `screenshots/` 并在问题文档内嵌引用；**禁止只有文字无截图**。
5. **慢接口必列出**：所有超阈值接口逐条记录「路径 + 方法 + 耗时 + 触发场景 + 证据」；阈值默认 `>1000ms 慢 / >3000ms 很慢 / >5000ms 严重`（【设计假设】，见 §八）。
6. **问题必分级可复现**：每条缺陷含 P0/P1/P2 严重级 + 复现步骤 + 期望/实际 + 证据；P0 需明确标注是否阻断上线。
7. **用例可追溯**：功能用例标注 `AC-Mxx-nnn`、样式用例标注原型页面、接口用例标注后端接口路径；缺陷反向标注关联用例号。
8. **三态必测**：每页加载态/空态/错误态逐一验证（这是样式测试的底线，见 §七）。
9. **不确定即问**：项目代码位置、启动命令、慢接口阈值、是否启用 midscenejs、范围外发现（PRD 未覆盖的页面/状态）——停下问用户，有选项给选项，不自己发挥（见 §十）。

## 四、标准测试流水线

```
输入（PRD + 原型 + 项目代码位置）
        │
        ▼
[1] 输入解析（读 PRD 速查表/模块页面描述/AC + 原型 + 项目 README/路由 + 接口清单）
        │
        ▼
[2] 环境准备（本地 install + dev server + ◉ 浏览器工具硬性预检 Playwright→browser-use→其他如 agent-browser，全无→报错等安装；midscenejs 为可选增强）
        │
        ▼
[3] 生成测试计划（填充测试流程模板）+ 测试用例（填充测试用例模板）
        │
        ▼
[4] ◉ Scope 确认 Gate（范围 + 用例数 + 工具方案 + 阈值，人工放行）
        │
        ▼
[5] 功能测试（全状态 + 全点击 + 异常分支）
        │
        ▼
[6] 样式测试（视觉断言 + 三态 + 截图）
        │
        ▼
[7] 接口性能测试（慢接口识别）
        │
        ▼
[8] 汇总生成测试问题文档（分级 + 复现 + 证据）
        │
        ▼
[9] 归档 .spec/测试/
```

> 完整阶段动作明细见 `assets/test-process-template.md`。本 Skill 执行时**必须先生成测试计划与用例，再执行**，不允许「边测边想」。

### 步骤 1：输入解析
- **确认项目代码位置（用户未提供则必问）**：本地目录 + git 地址；目录名用用户给定名称；
- **读需求**：优先 `.spec/PRD/VN/`（**先读 `PRD速查表.md` 建六大索引**；AC 清单直接用速查表 §六，断言细节按锚点回模块 §9）；缺失回退用户指定；
- **读设计稿/视觉基准**：优先 `.spec/设计稿/`（UI-UX-Design 高保真稿 HTML + design-system，供 UI 还原度检查基准）→ 次之 `.spec/原型/`（HTML + README）；均缺失回退用户指定（截图/Figma 导出）；
- **读代码**：`README.md`/`package.json`/路由配置 → 梳理页面清单、启动命令、接口清单（前端 `src/api` 或后端 TDD）；
- **提取测试面**：页面清单 + 每页业务状态集合 + 可交互元素清单 + 接口清单。

### 步骤 2：环境准备
- 按项目 README 本地安装依赖、启动 dev server（或构建 + 静态服务），确认 `http://localhost:{{port}}` 可访问；
- **浏览器工具硬性预检**（`references/browser-guide.md`，缺失不工作）：
  - 检测顺序：**Playwright 优先 → browser-use 次之 → 其他浏览器工具（如 CodeBuddy 的 agent-browser）**——列举不穷举，凡当前环境可用的、能驱动真实浏览器打开页面/交互/截图的工具均算；任一可用即作为功能遍历与网络监听的工具；
  - **全部不可用 → 立即报错并停止，不测试、不产出任何东西**：
    > `【环境错误】未检测到任何可用的浏览器工具（Playwright / browser-use / agent-browser 等）。项目测试硬性依赖浏览器工具驱动真实页面执行，请先安装并启用任一浏览器工具，安装完成后重新运行本 skill。`
  - 样式视觉断言 → **midscenejs 为可选增强**（需装 `@midscene/web` + 配置模型，见 `references/style-test-guide.md`）；不启用则在 Scope Gate 确认降级方案；
- 记录最终工具方案，写入测试计划。

### 步骤 3：生成测试计划 + 测试用例
- 按 `assets/test-process-template.md` 生成 `测试计划.md`；
- 按 `assets/test-case-template.md` 生成 `测试用例.md`，覆盖三类：功能（全状态 + 全点击）、样式（三态 + 视觉基线）、接口性能（全接口耗时）。

### 步骤 4：Scope 确认 Gate（强制暂停）
呈现测试范围清单 + 用例总数 + 浏览器工具方案 + 慢接口阈值；**等待用户确认才放行**。

### 步骤 5：功能测试
按 §五「全状态覆盖」与 §六「全点击覆盖」执行，结果回填 `测试用例.md`。

### 步骤 6：样式测试
- 先按 §七 + `references/style-test-guide.md` 执行三态与基础视觉断言，样式问题截图存证；
- **存在 UI 设计稿基准时（`.spec/设计稿/` 或用户指定外部设计稿）调用 `Fidelity-Review`（Testing 场景模式）做「UI 还原度检查」**：视觉还原 + 交互还原 + 超长文案专项逐页走查，就地接收其轻量问题清单（`mini-issue`），样式/交互/溢出类缺陷并入本测试问题文档；无设计稿基准则跳过并明示（维持原型基准 + midscenejs 视觉断言）。

### 步骤 7：接口性能测试
按 §八 + `references/api-perf-guide.md` 执行，慢接口逐条记录。

### 步骤 8：汇总生成测试问题文档
按 `assets/bug-report-template.md` 汇总三类缺陷，分级 P0/P1/P2，含复现 + 证据。

### 步骤 9：归档
落盘 `.spec/测试/`：测试计划.md + 测试用例.md + 测试问题文档.md + 接口性能清单.md + screenshots/。

## 五、全状态覆盖规程

> 权威细则见 `references/test-case-guide.md` §二。

1. **状态来源**：从 PRD 状态机（模块文档的 Mermaid 状态机图）提取每个业务对象的全量状态；
2. **构造前置数据**：用接口/种子数据/页面操作，把对象置为每个状态；
3. **逐状态验证**：每个状态验证「展示正确 + 该状态下可执行的操作正确 + 流转到下一状态的入口正确」；
4. **覆盖自检**：对照状态机清单逐一勾选，缺一个状态即回补；**状态覆盖 100% 才进入下一模块**。

## 六、全点击覆盖规程

> 权威细则见 `references/test-case-guide.md` §三。

1. **元素清单**：对每页盘点全部可交互元素（含按钮、链接、输入、下拉、开关、勾选、卡片、表格行操作、图标按钮、分页）；
2. **逐一点击**：每个元素至少触发一次，验证「有反应 → 反应符合预期 → 无报错 → 无死链」；
3. **点击副作用**：注意点击后的状态变化、弹窗、跳转、请求，异常当场记录；
4. **覆盖自检**：元素清单逐项勾选，未点到的元素标注原因（如需要特定权限则登记为风险）。

## 七、样式测试（视觉断言 + UI 还原度检查 + 截图）

> 权威细则见 `references/style-test-guide.md`。核心：

- **视觉断言**：用 midscenejs `aiAssert`/`aiQuery` 判断「当前页面是否符合设计稿/自然语言描述」（纯截图驱动、无需选择器）；
- **三态必测**：每页加载态 / 空态 / 错误态逐一验证；
- **截图存证**：发现样式问题 → `recordToReport` 或 `page.screenshot()` 立即截图，命名 `<页面>_<问题简述>_<序号>.png`；
- **比对基准**：有 UI 设计稿基准时以设计稿为基准（还原走查交由 `Fidelity-Review` Testing 场景执行）；无设计稿则回退以原型为基准，重点核对布局 / 间距 / 配色 / 字号 / 圆角 / 三态；
- **UI 还原度检查（有设计稿基准时）**：调用 `Fidelity-Review`（Testing 场景模式）做视觉还原 + 交互还原 + 超长文案专项，按其 `assets/mini-issue-template.md` 就地接收轻量问题清单，样式/交互/溢出类缺陷并入本测试问题文档；
- **工具降级（仅 midscenejs 层）**：midscenejs 不可用 → Playwright `toHaveScreenshot` 截图比对；再不可用 → browser-use 截图 + 人工比对，并向用户说明降级原因。全部浏览器工具不可用不会发生（步骤 2 硬性预检已报错等安装）。

## 八、接口性能测试（慢接口识别）

> 权威细则见 `references/api-perf-guide.md`。核心：

- **监听方式**：Playwright `page.on('response')` + `response.timing()`（或 `performance.getEntriesByType('resource')`）记录每个接口耗时；
- **阈值分类**（【设计假设】可调）：`>1000ms` 慢、`>3000ms` 很慢、`>5000ms` 严重；
- **逐条记录**：接口路径 + 方法 + 平均/最大耗时 + 触发场景 + 证据，汇总到 `接口性能清单.md`；
- **慢接口也进问题文档**：按等级计入 P1/P2。

## 九、测试问题文档输出规范

> 权威模板见 `assets/bug-report-template.md`。要点：

- **分级**：P0 阻断 / P1 严重 / P2 一般；
- **每条必含**：现象 + 复现步骤 + 期望/实际 + 严重级 + 关联用例号 + 证据（样式/性能必附截图或耗时数据）；
- **统计真实**：缺陷数、通过/失败数必须是重新清点的实测值，禁止凭印象估算。

## 十、不确定即问规程

| 必须问的场景 | 典型示例 |
|---|---|
| 项目代码位置/启动命令不明 | 没给目录、没给 git、没给启动方式 |
| 慢接口阈值需自定义 | 用户要更严/更松的阈值 |
| 是否启用 midscenejs | 需装依赖 + 模型 API Key，问是否启用还是仅截图人工比对 |
| 范围外发现 | PRD/原型未覆盖的页面、状态、接口 |
| 无法本地启动 | 环境报错、依赖装不上，停下反馈而不是硬跑 |

提问给选项、附推荐，确认后再动手；纯测试细节（截图命名、用例编号）不打断用户。

## 十一、常见错误对照表

| 常见错误 | 纠正方式 |
|---|---|
| 没生成测试计划/用例就直接开跑 | 先走步骤 3 填充模板，再执行（铁律：先计划后执行） |
| 只测主流程，状态没走全 | 对照 PRD 状态机逐状态覆盖（§五） |
| 只点主按钮，次按钮/图标按钮没点 | 逐元素清单全点击（§六） |
| 样式问题只写文字不截图 | 当场截图存 screenshots/ 并内嵌引用（铁律 4） |
| 慢接口没列或只列路径没耗时 | 记录路径 + 耗时 + 触发场景 + 证据（§八） |
| 缺陷没分级、没复现步骤 | 按 bug-report-template 逐条补齐 P0/P1/P2 + 复现 |
| 预期结果自己编、无 AC/原型来源 | 预期必须有来源，拿不准标【设计假设】（铁律 1） |
| 三态没测（加载/空/错误） | 每页三态逐一验证并截图（铁律 8） |
| 接口清单没提取就做性能测试 | 步骤 1 从后端 TDD/前端 api 提取接口清单 |
| 浏览器工具均不可用仍开工或声称已自动测试 | 步骤 2 硬性预检直接报错等安装，禁止跳过（midscenejs 缺失按可选增强降级并明示） |
| 遇到不确定自己拍板 | 停下问用户，给选项（§十） |
