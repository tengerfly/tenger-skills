# PRD 检测 / 评审 Skill

> IRON LAW：**只审不改**——只指出哪里不通、为什么不通、建议往哪补；不替用户改写 PRD。
> 问题定位到原文，结论可追溯。

## 一、定位与铁律

**角色与层级（立场隔离）**：

| 层级 | 角色 | 立场（唯一标准） | 检查 | 不检查 |
|---|---|---|---|---|
| 一审 | 前端开发专家 | 能否照 PRD 独立写完前端 | 页面/入口、功能区块、交互闭环、状态覆盖、流程断点 | 数据库、接口、服务端逻辑、文案写法 |
| 一审 | 后端开发专家 | 能否照 PRD 独立完成服务端与数据设计 | 业务对象、数据规则、状态机闭环、异常边界、数据口径一致性 | 控件、视觉、测试用例、命名术语 |
| 一审 | 测试专家 | 能否照 PRD 直接写可执行测试 | 验收可测性、覆盖完整性、可追溯性、可量化性 | 实现方式、页面布局、文案表述 |
| 总审 | 产品专家（**兼调度者**） | 需求在**业务语义层**是否立得住、说得通、叫得统一、写得准 | 审查：目标与价值闭环、业务逻辑闭环、业务规则完整性、术语、文案、一致性与矛盾（+ 异常与业务兜底，按需）；调度：归并、定级校准、冲突裁决、归属指派、补漏 | 技术实现、数据建模细节、测试用例设计 |

- 一审三角色**并行且互不可见**；产品专家为**总审层 + 调度者**，在三角色完成后启动，输入 = PRD 原文 + 三份角色评审。
- **术语与文案的「正确性」由产品专家唯一认领**（含调度时从 FE / BE 归并的同类问题）；FE / BE / TE 只从自身视角判「有无 / 是否可开发 / 是否可测」，**不判写法对错**（口径见 `references/product-checklist.md`）。

**铁律**：

1. **只审不改**：不替用户改写 PRD；修改由 `PRD-Design` 经任务清单交接。
2. **定位到原文**：每条问题标出处（文件 / 章节 / 需求 / 原句）。
3. **零幻觉**：不编造 PRD 之外的问题；区分「PRD 缺失（该写没写）」与「超出 PRD 范畴（不该写，不是问题）」。
4. **视角隔离 + 独立上下文**：三角色各审各的，不交叉、不代劳；不参考生成过程。**产品专家为唯一例外**——可读三角色结论并做调度，但只标原编号 + 命中角色，不复述其结论充当新发现。
5. **不设门禁**：只出问题清单，不判 PRD 通过/不通过；是否修改由用户决策。
6. **成因必写**：写明为何不通（如状态机无终态、跨模块未注册、步骤流未到出口）；推不出标「成因未明」，禁臆造。
7. **问题直列 + 修改方向**：以清单表逐条列出（含原文引用、自足可读），不藏在段落里；每条必带**修改方向**（改哪个概念 / 哪句话、往哪改），只给方向不代写。

**适用范围**：适用「已写好的 PRD（路径或粘贴）做三角色会审 + 产品专家总审」；不适用写需求（PRD-Design）、改需求、竞品分析或技术方案等内容。

## 二、输入与前置

| 项 | 说明 |
|---|---|
| 输入 | PRD 目录（默认 `.spec/PRD/`）或粘贴内容；含 `PRD速查表.md` 时**先读建结构地图**（模块/页面/AC 定位），**仍须逐节通读原文** |
| 输出 | `.spec/需求评审/`：`前端评审.md` / `后端评审.md` / `测试评审.md` / `产品评审.md` + `评审汇总报告.md` + `任务清单.md` |

**评审基线唯一性检查（陈旧产物检测，⛔ 必做，在评审前完成）**：

扫描 PRD 目录是否存在**先前方向 / 半途废弃版本**的残留文档。判据（命中任一即疑）：① overview / 速查表与部分模块文档「所属需求」名称不同源；② 模块文档引用的总纲 / 章节 / 术语表不存在或指向另一套文档；③ REQ/AC/模块编号体系两套并存冲突；④ 文档状态 / 元数据指向多个需求名；⑤ 同一对象在两套文档中规则互斥且无仲裁。

命中即产出 P0 问题「**基线污染**」——出处 = 残留文件清单 + 冲突证据，修改方向 = 提请用户裁决**删除**或**归档隔离**；**未裁决前该 P0 持续阻断评审-修复循环退出**。禁止把残留旧档当有效基线混入评审。

**方向新旧判定以用户确认为唯一依据**：复述两套产物请用户指认并记录时间线，**禁止**凭完成度 / 数量 / 时间戳 / 自查报告推断；给出评审对象前先向用户复述「保留 / 排除」两栏文件清单确认。

## 三、主流程（8 步）

**1. 解析 PRD**：确认输入来源；按 §二 执行基线唯一性检查；识别需求背景、模块划分、各模块流程 / 状态 / 验收标准；记录评审基线（文档清单、模块清单、章节覆盖）。

**2. 三角色并行评审**：前端按 `references/frontend-checklist.md`、后端按 `references/backend-checklist.md`、测试按 `references/test-checklist.md` 逐条评审；另各自对照 `references/known-issue-patterns.md`（评审方案例库）过一遍，命中即入本角色清单。三角色在**独立上下文**（subagent / 新会话）中评审，互不可见结论，不参考生成过程，只认成品原文；条件允许可用不同模型交叉审查。

**3. 三份角色评审落盘**：按 `assets/role-review-template.md` 写 `前端评审.md` / `后端评审.md` / `测试评审.md` 至 `.spec/需求评审/`；问题**逐条直接列出**（含原文引用），自足可读。

**4. 产品专家总审（总审层 + 调度者）**：按 `references/product-checklist.md` 执行——先读三份角色评审（记命中区域与三角色均未覆盖的章节），再通读 PRD 原文独立复核；按 §4.2 出 `产品评审.md`。

**5. 汇总**：按 `assets/summary-template.md` 生成 `评审汇总报告.md`——以 `产品评审.md` 的调度结果为准合并四份清单（已归并不重复计入，定级以校准后为准）；标共性问题（多角色同时发现 = 系统性缺陷）与冲突项（以产品专家裁决为准）；按 P0/P1/P2 统计。

**6. 任务清单 + 用户确认**：按 `assets/issue-list-template.md` 生成 `.spec/需求评审/任务清单.md`——逐条落清单（状态 `待确认`）、每条附**修复判据**、逐条向用户确认（要改 → `已确认`；不改 → `已忽略` + 理由）；P0/P1 阻断（未清零不进入收尾归档；节点放行由编排侧判定），P2 不阻塞；复核只验本轮已确认清单，新发现降 P2 或经同意进下一轮；编号链 `FE/BE/TE/PM-xx` → `SUM-xx` → `REQ-xx`（见 `assets/issue-list-template.md` 实例化参数）。确认后交 `PRD-Design` 修改并回填状态。

**7. 双向沉淀判定**：放行后按 `../../shared/anti-deadloop.md` §五 判定（P0 双向必沉）——**A 防复发**：改产出方 skill `PRD-Design` 的防复发规则（记其 CONTEXT D-xx）；**B 检出力**：本 skill `references/known-issue-patterns.md` 按模板加一条（含「检出方法」）。改不了的落 `../../issue/PRD-Design/<日期>/`（来源=评审闭环，写明双向落点）。判定结果记入汇总报告「沉淀判定」节。

**8. 归档**：四份评审 + 汇总 + 任务清单全部落盘 `.spec/需求评审/` 后交付。**问题日志**：归档同时在项目 `.spec/问题日志.md` 台账追加一行索引（日期｜来源｜问题产物｜轮次｜状态｜反哺出口；格式见 skill 源仓库 `../../shared/templates/problem-log-template.md`）。

> 门禁闭环、防评审死循环三招（含轮次上限 3：满 3 轮未收敛 → 强制清 P0 后放行、残留 P1 记遗留）、分级与沉淀的定义见仓库根 `../../shared/anti-deadloop.md`，本 skill 只保留流程参数，不重复定义。

## 四、评审规范

**4.1 严重度分级（只标注，不设门禁）**——P0/P1/P2 定义与处理口径见 `../../shared/anti-deadloop.md` §三，下表为本域典型示例：

| 级别 | 含义 | 典型 |
|---|---|---|
| P0 致命 | 逻辑断头/无头、流程走不通、需求自相矛盾、缺失到无法开工 | 流程只有入口没有出口；核心对象无状态定义 |
| P1 重要 | 描述模糊歧义、状态/边界/异常未定义、数据口径不一致、验收不可测、规则冲突无仲裁、需求无目标承接（无源需求） | 「友好提示」「尽量快」；同一称谓在两个模块指不同对象 |
| P2 建议 | 表达可优化、术语不统一、非关键细节缺失 | 中英混用；章节序号不连续 |

**4.2 产品专家总审与调度**：

- **核心必查**（每次全查）：PM-1 目标与价值闭环 / PM-2 业务逻辑闭环 / PM-3 业务规则完整性 / PM-4 术语 / PM-5 文案 / PM-6 一致性与矛盾。
- **扩展档**（命中才查）：PM-7 异常与业务兜底，触发条件 = 涉及资金交易 / 审核审批 / 第三方对接 / 不可逆操作 / 存量数据之一；未触发在 `产品评审.md` §3 标「不适用（未触发）」。
- **调度五动作**（总审必做）：① **归并去重**——同一问题多角色命中则合并并标命中角色；② **定级校准**——同类问题三角色定级不一致则统一口径；③ **冲突裁决**——结论互斥时收敛并给建议方向；④ **归属指派**——纯术语 / 文案类收归 PM-4 / PM-5，技术类退回对应角色；⑤ **补漏扫描**——三角色均未覆盖的章节复核缺口。
- **术语判定基准**：PRD 内术语表 → PRD 内首次定义处 → 记「建议补充术语表」不判错；**不引入 PRD 之外的术语标准**。
- 三角色已编号的问题标**原编号 + 命中角色**，调度后不重复编号；调度动作与结果写入 `产品评审.md` §4「调度处理记录」。

## 五、常见错误对照表

| 常见错误 | 纠正方式 |
|---|---|
| 评审时改写 PRD | 只记问题，给建议方向，不动原文 |
| 三角色结论混写 | 分角色成文，汇总再合并 |
| 问题无出处、只说整体感觉 | 定位到文件 / 章节 / 原句 |
| 把越界内容当缺失 | 区分「缺失」与「越界」，分别标注 |
| 结论笼统 | 写清为什么不通 + 建议方向 |
| 只列现象无成因 | 补成因，可考才写、不臆造 |
| 产品专家复述三角色结论当新发现 | 标原编号 + 命中角色，不重复编号 |
| 产品专家照抄三角色问题不调度 | 走调度五动作，结果入 `产品评审.md` §4，不重复计数 |
| 只给判断不给修改方向 | 每条补修改方向（改哪个概念 / 哪句话、往哪改） |
| 把陈旧方向残留文档当有效基线直接混评 | §二 先做基线唯一性检查；发现残留列 P0 基线污染，提请用户裁决后再继续 |
