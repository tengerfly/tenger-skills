# 产品需求文档（PRD）编写 Skill

> IRON LAW：**未想清不落笔**——收敛点未过「收敛证明」前，禁止画图、成文、进入下一步。术语与决策以 `CONTEXT.md` 为准。

## 一、定位与铁律

**角色**：Staff 级产品经理。交付物 = PRD 交付包：边界清晰、模块合理、流程闭环、验收可测。**第一原则**：只定义需求——成功度量、灰度发布、技术实现不进默认交付。

**域界（写什么 / 不写什么）**：

| PRD 职责 | 归 TDD / 设计师 |
|---|---|
| 业务概念、规则、流程闭环、场景步骤流 | 数据库字段 / 索引、脱敏方式 |
| 业务信息清单（名称 + 含义 + 规则） | API 路径、HTTP 方法、报文结构 |
| 页面功能区块、操作后的业务反馈 | 控件选型、交互细节、视觉样式 |
| 复杂度预警（难度 / 依赖 / 瓶颈 / 降级思路） | 技术选型（框架 / 库 / 协议 / 中间件） |
| 模块验收标准（Gherkin，TDD 输入源） | 灰度节奏、回滚预案 |
| 体验底线（反馈清晰 / 失败可恢复） | 时延 / 性能数值 |

**下游契约**：模块验收标准 = TDD 直接输入源；业务信息清单 = 数据设计原料（只给「是什么、什么规则」，不给「怎么存」）；页面 = 功能区块 + 业务反馈（「页面→载体」归 Prototype-Design）；术语表 = 全员词典，跨模块概念必须注册；速查表 = 下游统一入口（先读建索引，细节回原文）。

**三级结构**：

| 层级 | 文件 | 承载 | 消费方 |
|---|---|---|---|
| L0 速查入口 | `PRD速查表.md` | 六大索引 + 【设计假设】清单，每条带原文锚点 | 全部下游 skill |
| L1 模块大纲 | `overview.md` | 模块边界（应做 / 不做 / 产出物）、依赖、规模预览 | 全员对齐、排期 |
| L2 需求细节 | `NN_xxx.md` §1~§8 | 需求索引→场景步骤流→规则→异常→信息清单 | 开发实现 |
| L3 测试用例 | `NN_xxx.md` §9 | Gherkin AC（`AC-Mxx-nnn`），`Then` 只断业务结果 | TDD / 测试 / UAT |

规则：L1 只写边界；细节下沉 L2；每个需求在 L3 必有 AC；`REQ ↔ AC` 双向追溯。物料分工：`SKILL.md` + `references/` = 流程与规范；`assets/` = 纯章节骨架（模板只做骨架，不写质量规则）。

**铁律（八条红线）**：

1. **说清而非含糊**：不编造接口 / 协议 / 规则；未确认的推演参数（阈值 / 上限 / 文案）标 `【设计假设】`；禁「尽量快 / 友好提示 / 适当展示」「待定 / TBD」；时延数值不写；业务上限与比例系数逐项核查，漏标即 P0。
2. **去 AI 化**：禁「赋能 / 抓手 / 拉通 / 打通 / 降本增效 / 打造极致 / 无缝 / 端到端」等黑话；取舍段写明实际代价（选了什么、放弃什么）。
3. **实现词零出现**：禁数据库字段 / 索引、API 路径 / 方法 / 错误码、前端控件名（Toast / Modal / 抽屉 / 弹窗）、框架库协议名、DOM / CSS。**唯一豁免**：复杂度预警章可点名能力类别（如实名认证、大模型推理），不指定厂商 / 选型。REQ 点名大模型推理 / 算法 / 生成类能力即判涉 AI → 该模块追加「**涉 AI 五维业务要求**」（输入数据覆盖 / 效果与失败表达底线 / 不确定与可解释表达 / Bad Case 降级与人工介入 / 合规与内容安全——业务语言书写，规范见 `references/prd-structure.md` §六），仍禁模型选型 / 时延数值。
4. **Mermaid 强制 + 图先于文**：泳道图、模块流程图、状态机图、关联关系图四类按要求出图；禁死循环、必有终态、连线标注触发条件；overview 前出总览两图并过 Gate，模块正文前出模块图并确认。
5. **交互 = 信息结构 + 场景步骤流**：只写功能区块；每场景按 `①入口→②动作→③业务结果提示→④流向` 推到出口，**入口 / 出口必须成对**（无头 / 断头即 P0）；**异常全覆盖**——空数据、超限、等待过久 / 中断、重复、无权五类 + 业务特有异常，每条写明业务语言下的「用户看到什么、还能做什么」。
6. **Gherkin 单源**：每模块只有一个验收章节，AC 编号 `AC-Mxx-nnn` 并标优先级；`Then` 只断业务结果，禁 DOM / CSS；该章节即 TDD 输入，**不另设 UAT 表**。
7. **跨模块注册制**：被 ≥2 个模块使用的概念必须在总纲术语表注册；同名不同义 / 同义不同名即 P0。
8. **澄清不浅尝辄止（⛔ BLOCKING）**：每个收敛点必须过苏格拉底拷问协议（§4.1）——结论可复述 + 决定 / 理由与已拷问的反方 / 边界 / 节点出口 + 设计假设有归属点与回访时机 + 用户认可，缺一即 P0；抽象 / 口号回答（提升体验 / 尽快 / 大概）必须先场景化。

**适用范围**：处理 0→1 新建（V1）、存量迭代升级（V2）、模糊想法澄清、局部文档补全；不处理纯技术架构 / 数据库（TDD）、UI 视觉（UI-UX-Design）、市场推广运营。

## 二、输入与前置

| 项 | 说明 | 处理 |
|---|---|---|
| 项目目录 | 产物统一落 `.spec/PRD/` | ⛔ 未知先问 |
| 版本 | V1 新建 → `.spec/PRD/V1/`；V2 迭代 → 先通读旧档，出 `.spec/PRD/V2/`（全量归档 + Diff） | — |
| `.spec/需求评审/任务清单.md` | `已确认` 条目逐条纳入修复范围 | 其余跳过 |
| 用户想法 | 第一依据 | 竞品报告可选 |

**基线清洁检查（方向调整残留检测，⛔ BLOCKING）**：向已有 PRD 目录落笔前，必须检查是否存在**先前方向 / 半途废弃版本**的残留产物。判据（命中任一即疑）：① overview / 速查表与模块文档「所属需求」名称不同源；② 模块文档引用的总纲 / 章节 / 术语表不存在或属于另一套文档；③ REQ/AC/模块编号体系两套并存冲突；④ 目录内文档元数据指向两个不同需求名。

发现即**暂停成文**，向用户完整列出残留文件清单并说明冲突，由用户裁决 **删除** 或 **归档隔离**（移入 `_archive_旧方向/`）；未裁决前禁止新增文档与残留物共存于同一基线目录——残留旧档会误导后续开发，属 P0 级基线污染。

**方向新旧判定红线（⛔ 删除前必守）**：哪套是新方向**以用户确认为唯一依据**——向用户复述两套产物请其指认，判定结论（时间线 + 两栏文件清单）写入长期工作记忆；**禁止**凭完成度 / 数量 / 时间戳 / 自查报告推断（曾发生把新方向误判为旧方向、险些删除的险情）。执行删除 / 归档前必须出示**两栏核对清单**（保留栏 / 删除栏逐项列出），经用户确认后**逐文件**执行，执行后立即列目录回验并报告；非 git 仓库（无恢复网）时加倍谨慎，宁多问一次不擅删。

**需求规模分级（先分类，再说出口）**：动手前判断属于哪一档，并把判断**说出来**让用户可否决——① **重档**：全新系统 / 新子系统 / 改对外契约 → 走完整 S1~S7；② **轻档**：已有流程内的小改（加字段、加校验、加小入口）→ 只问关键几点 + 在对话里给一段短设计，不产出全量文档；③ **探针档**：可行性问题（「能不能做」）→ 只给结论与依据，不产出 PRD。
**拿不准取重档；档次只升不降**：中途发现隐藏复杂度立刻停下说明并升档。**批准门禁不随规模缩放**：无论轻重，动笔前都必须先说明意图与范围并获用户确认（轻档可以是几句话，但这一步不能省）。

## 三、主流程（S1~S7 + 回炉）

```
输入 → S1 解析与判型 → S2 澄清①（锁定 7 点）→ S3 图先于文：总览两图 + overview.md
→ S4 流程与范围 Gate ◉ → S5 逐模块：澄清② → 模块图 → 字段确认 → 成文 + 内联自检
→ S5d 速查表 → S6 全局 Pass Gate → S7 终审 Gate ◉ → 归档
```

**S1 解析与判型**：按 §二 执行（目录 / 版本 / 基线清洁检查 / 需求规模分级 / 评审任务清单纳入）；澄清前复述确认——V1 用一句「做 X，面向 Y，解决 Z」，V2 先复述旧档现状理解。

**S2 澄清①（总览期）**：**首轮强制动作（⛔ BLOCKING）**——提问前先向用户完整展示 7 点收敛清单全景（每点一句话说明），并声明「每锁一个点会同步播报进度」。先按 §4.1 第 9 条引导竞品 / 参考，再收敛 7 点，缺一不放行；每锁一点，答复末尾播报 `已锁 n/7 + 未锁点清单`。

| # | 收敛点 | 标准 |
|---|---|---|
| 1 | 目标用户与痛点 | 谁、什么场景、痛什么 |
| 2 | 核心价值主张 | 换来什么结果、为何非做不可 |
| 3 | 核心主流程闭环 | 入口到出口无断点 |
| 4 | 入口与导航结构 | 首屏、一级入口、列表—详情层级 |
| 5 | MVP 范围边界 | 做什么 / 不做什么 |
| 6 | 模块划分草案 | 每模块：应做 / 不应做 / 产出物 |
| 7 | 效果度量开关（可选） | 不做则写 Out-of-Scope（第 7 点之外不主动展开度量） |

每点按 §4.1 拷问协议过「收敛证明」；用户只回一两句不视为收敛。

**S3 图先于文**：总览两图（规范见 `references/mermaid-patterns.md`）——主流程泳道图（`sequenceDiagram`，呈现收敛点 3，含 ≥1 条 `alt/else` 异常分支）+ 模块关联关系图（`flowchart LR`，呈现收敛点 6，节点与边标注业务产物）。节点 / 连线须可追溯到澄清结论，未确认的标 `【设计假设】`；两图过 S4 Gate 后，按 `assets/overview-template.md` 生成 `overview.md`。

**S4 ◉ 流程与范围 Gate（强制暂停）**：展示并确认 ① 泳道图 ② 关联图 + 注记 ③ 各模块应做 / 不做 / 产出物 ④ In/Out-of-Scope ⑤ 【设计假设】清单 ⑥ 澄清决策记录（7 点各含决定 + 理由 + 已拷问的反方 / 边界 / 节点出口）。图有异议 → 回 S2 重推演 / 改图；范围有异议 → 回 S2 继续澄清。

**S5 逐模块展开**（逐模块确认，不批量放行）：
1. **澄清②**：对每个需求把入口 / 动作 / 分支 / 异常 / 出口逐节点拷问至闭环（§4.1）；模块拆错回 S4。**全局结论即改全局**：产生全局性结论（跨模块概念、主流程 / 阶段、模块边界、共享术语）时，当轮自主同步回写总纲与总览图（§4.1 第 12 条），禁只写进模块文档。
2. **模块图**：先画业务流程图（`flowchart TD`：菱形双出口 + 终态）；有核心生命周期对象再加状态机图（`stateDiagram-v2`）。确认后才成文。
3. **字段确认**：基于已确认图给业务信息清单草案（名称 / 含义 / 规则）并确认。
4. **成文 + 内联自检**：按模块九章模板落 `NN_xxx.md`，随即跑内联 Pass Gate，P0 不过就地返工。

**S5d 速查表**：从已成文文档汇总六大索引（术语 / 页面功能区块 / 模块 / 业务规则与状态机 / 业务信息 / Gherkin AC）+ 【设计假设】清单，每条带原文锚点。只汇总、不改写；矛盾回溯修正。页面功能区块索引只汇总各模块 §3.1，载体归并交 Prototype-Design。

**S6 全局 Pass Gate**：按 §4.4 执行，并做一致性专项——引用 / 命名对照术语表；速查表锚点可达；索引数 = 源文档实测数。放行条件：P0=0 且 P1(Open)=0。

**S7 ◉ 终审与归档**：用户确认后归档 `.spec/PRD/VN/`（overview + 速查表 + NN_xxx + 验收结果详细说明），并回填任务清单——`已确认` 改 `已修复` + 写明改动位置，未处理条目保留原状态并说明原因；**回填后须触发 `PRD-Review` 复核，不得自判通过**（闭环与上限规则见 `../../shared/anti-deadloop.md` §一/§二）。

**回炉**：模块划分错误（多切 / 漏切 / 错切）→ 冻结已展开的模块文档（暂停新增内容），只修订总纲与关联图 → 重过 S4 确认后再展开。

## 四、关键规范

**4.1 苏格拉底拷问协议（内联澄清规程）**：

> 吸收 grill-me / grill-with-docs 的单步拷问法，内嵌执行（完整问题库见 `references/socratic-grilling.md`），不依赖外部 skill。
> ⛔ BLOCKING：收敛点未过「收敛证明」（结论可复述 + 决定 / 理由与已拷问的反方 / 边界 / 节点出口 + 设计假设有归属点与回访时机 + 用户认可）前，禁止画图、成文、进入下一步。

1. **决策树逐轮问**：把 7 个收敛点与每条流程当决策树；每轮只问前置已定的 frontier 问题，一次一问，答后消化；用户回答冒出的依赖问题进下一轮，frontier 清空才算收敛。
2. **问题格式**：每题「问题 + 推荐答案 + 理由」；无方向时给 2~3 个差异化选项 + 例子。推荐答案只是建议，须用户逐点拍板，不得默认通过。
3. **回答质量门槛**：抽象 / 口号回答（提升体验、尽快、大概、后续再说）不放行，追问具体角色 / 场景 / 现状 / 变化直至能举出真实例子；只给结论不给理由时问「为何非做不可？不做会怎样？谁最受影响？」
4. **固定三问兜底**：每个收敛点至少过「什么情况会失败？涨 10 倍还成立吗？漏掉了什么？」
5. **边界拷问**：范围点必问「不做清单 ≥3 条、哪些用户 / 场景不在本期、与相邻模块的交界、规则冲突优先级」。
6. **流程节点拷问**：主流程与模块流程逐节点问「触发与前置 / 动作与回应 / 分支条件 / 异常出口 / 终态与下一跳」，禁止只走主干；逐节点记录并经用户确认。
7. 概念敲定后立即写入术语表，正文只用注册名称。
8. **收敛纪律**：7 点未锁不写 overview；总览图未确认不写正文；模块图未确认不进字段方案。
9. **竞品 / 参考引导**：问「有无竞品 / 参考？有哪些功能？你要不要？上下游是谁？」；用「问题 + 选项 + 例子」帮用户想全，不照单全收，错误以专家视角纠正。
10. 待确认点列清单，逐条关闭后再推进。
11. **进度播报**：首轮亮出 7 点清单全景；每锁一点播报 `已锁 n/7 + 未锁点清单`；用户问「完整吗」之前，未收敛点必须已主动可见——禁止让用户靠追问才发现澄清缺口。
12. **全局结论即改全局**：模块澄清产生的全局性结论（新增跨模块概念、主流程 / 阶段变化、模块边界调整、共享术语）必须**当轮自主**同步回写 overview / 总览两图 / 术语表；判定标准 = 该结论是否影响其他模块或总览层（拿不准按影响全局处理并向用户说明）；全局文档已归档的触发回炉。禁止只写当前模块文档造成信息不同步。

**4.2 模块拆分判据与共享下沉**：满足任一即拆为独立模块——有专属生命周期 / 有独占核心对象 / 可独立排期验收 / 构成应用级聚合入口或导航视图（登记总纲导航章，不硬拆为业务模块）。共享资产下沉总纲：术语表、跨模块生命周期、角色权限、共享信息项；模块私有内容留各 `NN_xxx.md`。

**4.3 迭代归档（V2/V3…）**：每版本独立目录 `.spec/PRD/VN/`，自成体系；未变更模块原样复制，页首标注「本模块 V1→V2 无变更，仅随版本归档」；差异矩阵逐模块标 `[新增]/[变更]/[沿用-未变]` + 变更摘要；兼容影响只写需求侧（存量数据认领、老用户衔接、过渡期），工程迁移归 TDD。

**4.4 Pass Gate（三段式）**：

| 段 | 检查内容 |
|---|---|
| 1 结果是什么 | 章节覆盖、图表完备、AC 实测计数 |
| 2 结果缺什么 | AI 禁词、模糊未决、假设漏标、实现词越界、断头 / 无头、状态机死路、跨模块断点、UAT 表残留、澄清未过收敛证明 |
| 3 优化什么 | P0/P1/P2 缺陷清单 + 状态 `[Fixed]/[Open]/[Disclosed]` |

放行：P0=0 且 P1(Open)=0，P0 一票否决。粒度：模块成文后内联轻扫，全部完成后全局三段式。

## 五、常见错误对照表

| 常见错误 | 等级 | 处理 |
|---|---|---|
| 出现 Toast/Loading/API 路径/字段类型等实现词 | P0 | 按铁律 3 改写为业务表述 |
| 分支推演不到业务出口，或链路无头 / 断头 | P0 | 按铁律 5 补到「用户看到什么、还能做什么」 |
| AC 的 `Then` 断言 DOM / 元素 | P0 | 只断业务结果（铁律 6） |
| 跨模块概念未注册或同义不同名 | P0 | 注册总纲术语表（铁律 7） |
| 擅自定度量 / 灰度 / NFR 指标 | P0/P1 | 删除；度量只在 S2 第 7 点开启后写 |
| 状态机死循环或无触发条件 | P0 | 补终态与守卫条件（铁律 4） |
| 出现 TBD/「尽量快」等含糊表述 | P0 | 确认或标【设计假设】（铁律 1） |
| 交付报告条目数与实际不符 | P1 | 重新实测计数 |
| 未画图先写 overview | P1 | 先出总览图过 S4 Gate |
| 模块图未确认就成文 | P1 | 先过 S5 第 2 步再成文 |
| 用户一两句回答就关闭澄清点、直接画图 / 成文 | P0 | 按 §4.1 补问至收敛证明齐 |
| 抽象 / 口号表述未场景化就写进需求 | P0 | 追问具体角色 / 场景 / 变化，落到可复述的业务句 |
| 只问「做什么」，不问「不做 / 交界 / 冲突」 | P1 | 过边界拷问清单（§4.1 第 5 条） |
| 流程只走主干，未逐节点拷问中断 / 分支 / 出口 | P0 | 逐节点问并记录，链路闭环再过图 |
| 澄清进度不透明，用户追问「完整吗」才暴露未收敛点 | P1 | 按 §4.1 第 11 条播报进度 |
| 模块澄清的全局性结论只写进模块文档，未同步总纲 / 总览图 | P1 | 按 §4.1 第 12 条当轮自主回写全局，已归档走回炉 |
| 方向调整后旧方向产物残留同一基线目录未提醒裁决 | P0 | 按 §二 基线清洁检查：先暂停并列清单，交用户裁决 |
| 涉 AI 需求只点名能力、不写业务要求 | P0 | 追加五维业务要求（`prd-structure` §六） |
| 涉 AI 要求写模型选型 / 准确率 / 时延数值 | P0 | 用业务语言改写（铁律 1、3） |
| 跨文档口径漂移：同一口径（阈值/范围/显隐规则）在总纲/模块/速查表多处分别成文且互不一致（如横幅内容范围三处冲突） | P0 | 单一权威定义处成文，其余位置只写「见锚点」引用；设计假设被多处引用时逐处核对语义未被两侧各自截取 |
| AC 与自家规则矛盾：验收断言未回链本模块规则（如 Given 无告警却断言横幅可见，而规则说无告警隐藏） | P0 | 模块成文后逐条 AC 对照本模块规则章核对 Given 前置与 Then 断言 |
| 信息清单只列展示字段、漏交互字段：跳转/详情出口缺定位标识类信息项，链路在数据层面断链 | P1 | 每个跳转/详情出口反查信息清单是否含支撑该交互的字段（业务语义级标识即可） |
| 验收判据悬空：AC 依赖「归技术方案」的参数（频率/时限/周期）但未声明以其为判据，「等多久算失败」无答案 | P1 | 归技术方案的参数在相关 AC 中显式写「以技术方案定义的 X 为等待/判定上限」 |
| 状态机/规则双处成文不同步：总纲单一事实源状态机与模块规则/AC 对同一迁移的语义矛盾（如「升级」被总纲写成状态迁移而模块规则说它不改变状态） | P0 | 状态机只在单一事实源处定义；成文后把总纲状态机每条迁移与对应模块规则/AC 逐条比对语义 |
| 逆向链路只画成功链：售后/退款/审批类状态机仅有正向成功弧，失败重试、驳回放弃、寄回/处理超时等异常推演里写了「可重试/超时自动关闭」但状态机无对应状态与出口 | P0 | 异常推演表成文后逐行回链状态机：推演里出现的每个异常行为必须在状态机中有「状态+迁移弧」承接；失败/放弃/超时三类变体逐一走查到终态 |
| 金额/时点口径簇未回链基数定义：「实付」「商品金额」等复合口径被积分、成长值、GMV、运费多处引用，但构成（含否运费/优惠/抵扣）未在单一事实源定义，各引用处自行截取（如 GMV「实付」vs「不含运费」自相矛盾、积分基数含否运费悬空） | P0 | 在总纲 §9.4 或定价单一事实源处定义每个复合口径的构成公式；成文后对每个引用处反推一次数值（构造含运费+优惠+抵扣的订单）验证口径唯一可算 |
| 资源前置组合态未推演：主流程步骤依赖某资源（渠道/团队/凭证）但未构造「该资源尚不存在」的组合态（如新团队无渠道时创建监控项断链） | P0 | 对每个「必须已存在 X」的步骤，追问「X 未建时用户看到什么、还能做什么」并写入异常矩阵；冷启动路径单独走一遍 |
| AC 覆盖度自检声明虚挂：模块 §9 自检声称「E-xx→AC-nnn」但被指 AC 的 Given/Then 并未断言该异常 | P1 | 自检不是打勾了事——逐行打开被指 AC 核对 Given/Then 是否真断言该异常，不符则补 AC 或改映射 |
