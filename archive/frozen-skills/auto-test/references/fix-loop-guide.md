# 修复闭环指南（发现 → 修复 → 回归）

> 本 skill 的灵魂。测试不闭环 = 报告写完就死。

## 一、修复任务卡（缺陷的唯一交付形态）

每条 P0-P2 缺陷一张卡（模板见 [../assets/bug-card-template.md](../assets/bug-card-template.md)），要求**机器可读、AI 可执行**：
- 复现步骤精确到「可直接照做」；
- 证据齐全（截图/console/网络/相关 diff 线索）；
- 附「回归验收标准」——回归时机器判读的断言，写卡时就要想好；
- 定位线索给方向不给结论（防止把测试 agent 的猜测当成事实带偏修复 agent）。

## 二、投喂与执行

引擎模式：任务卡投喂编码 agent headless（CLI/SDK）。
会话模式：同会话的编码 agent 直接消化任务卡，但必须**先读卡再改码**，修完声明「已按 BUG-xxx 修复，请回归」。

两种模式共同纪律：
- 修复 agent 只拿任务卡 + 必要上下文，**不拿测试过程**（防被测试方的推测带偏）；
- 禁止修复 agent 顺手改用例库——用例改了回归就失去意义；认为用例错 → 在任务卡回复争议，由测试方裁决。

## 三、fresh-agent 回归（防「AI 测 AI」）

**为什么**：带着上轮上下文的 agent 会反复检查已知问题、漏检新问题（偏见自证）。

**规则**：
1. 回归执行者不携带上轮任何怀疑点/结论/修复意见；
2. 回归输入只有三样：原始验收标准（PRD AC）+ 用例库 + 当前代码；
3. **全量回归**：重跑整套用例，不是只跑上次失败的——「改 A 坏 B」只能靠全量发现；
4. 每轮产生全新证据（新截图/新日志），禁止引用上轮。

## 四、轮次状态机

```
R(0) 首轮测试 ──全绿──▶ 交付
  │ 有缺陷
  ▼
修复(1) ──全量回归 R(1)──┬─全绿─▶ 交付
  ▲                      │有缺陷
  │                      ▼
  └────── 修复(2) ── R(2) ──┬─全绿─▶ 交付
                           │有缺陷
                           ▼
                      修复(3) ── R(3) ──┬─全绿─▶ 交付
                           ▲            │仍有缺陷
                           └──超限────▶ 升级人工
                                        输出震荡分析
```

- 上限 3 轮（默认，可配）：防无限震荡烧 token；
- 升级人工时输出**震荡分析**：哪几个缺陷在互相打架、共同根因猜测、建议的人工决策点；
- 连续两轮出现**完全相同**的失败 → 提前终止（修复未生效，检查任务卡是否被理解错）。

## 五、闭环健康度自检（每轮收尾）

- [ ] 每条缺陷有卡、每张卡有回归验收标准？
- [ ] 回归是全量且 fresh 的？
- [ ] 用例库本轮零改动（或改动有裁决记录）？
- [ ] 轮次计数与历史在 `报告/` 里可追溯？
- [ ] 最终报告能回答「哪轮修了什么、现在还剩什么」？
