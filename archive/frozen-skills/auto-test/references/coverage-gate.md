# 覆盖率门禁（「少流程」的机器判读）

> 目的：把「跑没跑全」从 agent 自觉变成可计算数字。不达标 = 没跑完，禁出「通过」结论。

## 一、三个覆盖率指标

| 指标 | 计算方式 | 门禁阈值（起步值，可调） |
|---|---|---|
| **状态覆盖率** | 已验证状态数 ÷ 状态机状态总数 | ≥ 90% |
| **迁移覆盖率** | 已验证迁移数 ÷ 状态机合法迁移总数 | ≥ 80% |
| **元素点击率** | 已触发交互元素 ÷ 逐页盘点总数 | ≥ 90%（未点到的必须标原因） |

- 数据来源：每条用例的 `coverage` 字段（case-authoring-guide §一）+ 用例执行结论（Pass/Fail/Blocked）；
- Blocked（前置不成立/环境问题）不计入已验证；
- 无状态机基准时：只算元素点击率，并登记「无状态机基准，状态覆盖不可计算」风险。

## 二、覆盖率 ratchet（只升不降）

- 每轮报告记录三项指标；**新一轮不得低于上一轮**（防止修 bug 顺手删用例）；
- 下降 = 门禁失败，无论功能是否全绿。

## 三、门禁判定顺序

1. L0/L1 全绿？（否则整体 Fail，看分层短路）
2. P0 = 0？
3. 三项覆盖率达标且不低于上轮？
4. 覆盖边界声明已写？
- Complete evidence and acceptance checks -> `PASS`; missing evidence, residual P0, or unsafe handoff -> `BLOCKED`; authorized residual risk -> `CONDITIONAL` with the complete exception record.

## 四、缺口处理

覆盖率不达标时，缺口清单进报告：
- 哪些状态/迁移/元素没覆盖、为什么（不可达？时间不够？缺 mock？）；
- 不可达的状态 → 反推产品问题（「这个状态从任何入口都到不了」本身可能就是 bug）；
- 缺 mock 导致的 → 补 mock 方案后补用例，不允许「先跳过」静默通过。
