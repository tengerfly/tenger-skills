# Fact-Check 设计上下文

## 为什么造（2026-09-18）

用户两个真实痛点：

1. **方案坑时间**：AI 给的方案 A 是错的，用户辨别不了，套用后费了大半天才发现错误
2. **知识坑脑子**：AI 给的知识点是错的，用户当真记住了，长期记忆着错误内容

诉求：在「照做/记忆」之前给 AI 结果加一道核验关。

## 关键决策

| 决策 | 理由 |
|---|---|
| 拆原子断言逐条判定，不给综合可信度评分 | AI 最常见的错误是「半真半假」，整体打分会掩护错误细节；用户真正关心的也只是承重断言 |
| 证据层级 L1 实验 > L2 官方文档 > L3 源码 > L4 多独立源 | 可执行行为是唯一金标准；文档要防版本错位；博客互抄不算独立证据 |
| 四值判定（含 ⚠️ 条件成立 / ❓ 未证实）而非二值真假 | AI 错误大多是「条件性正确被说成普适」，二值表达不了；❓ 防「查不到就默认对」 |
| 反证搜索必做 | 只找正证天然偏确认偏误；`gotcha / deprecated / breaking change` 类搜索最能逮版本错位 |
| 明确写死「再问一遍 AI」不算证据 | 同一模型自我确认会自信地重复甚至编新理由，给用户虚假安心感 |
| 承重断言优先 | 核验资源有限，先验「错了最贵」的几条，不平均用力 |
| 只核验不重写替代方案 | 防越界成「再生成一个 AI 方案」——那只是把待核验对象换了一个 |
| 铁律与 `../../shared/evidence-before-claims.md` 呼应 | 那条管自己做的完成声明，这条管核验别人的断言，同一证据哲学的两个面；不重复定义 |
| 查无证据 = ❓ + 原因，禁止编造核验（红线，用户 2026-09-18 追加） | 确实不知道、网络也搜不到时，唯一合法输出是「未证实 + 说明原因」；为完成核验而编造证据（假链接/假引文/假实验输出/假多源一致）等于给错误盖「已验证」章，比不核验更坑；❓ 是合法结论不是失败 |
| 源码导读类产物核验路径：L3 = 锚点「行号+内容」双匹配，发现锚点不精确/内容级错误 → 回写修正原产物并记录修正清单 | 「行存在」≠验对；react/vue3/七仓批量三轮实测各抓到锚点漂移与内容级 ❌（2d47900 + 3069744） |
| **核验上下文隔离（D-01 · 2026-10-19）**：若核验对象是本会话 / 同一 Agent 的产出或结论（含其自查结论），按 `../../shared/review-context-isolation.md` 派发 fresh 核验子代理（或交新会话；均无 ⇒ BLOCKED）；核验外部公开事实不强制隔离。SKILL 流程起始加参照说明 + 资源清单引用该契约 | 用户 2026-10-19 要求评审/核验判断必须在隔离上下文——同一 Agent 自验自己的结论等于确认偏误（`issue/Skill-Optimizer/2026-10-19/01`） |

## 与现有 skill 的关系

- 链外独立 skill，不占主链 14 节点（同 Fidelity-Review / Bug-Fix / OSS-Radar / Source-Reading）
- 承重断言被证伪后的替代方案重写 → Backend/Frontend-Tech-Design；已写代码的验收 → auto-test
- 收尾的 AI 错误模式沉淀与 Bug-Fix 同池（`../../bug-patterns/`）
