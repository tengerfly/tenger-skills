# 验收标准编写规范（Gherkin AC Guide v2）

> **v2 变革**：废除「Gherkin 用例集 + UAT Checklist」双轨制，每模块只有**唯一权威验收章节（§9）**。
> 这一份验收标准同时服务三方：开发据此先写测试用例（TDD 输入源）、测试逐条自动化转化、产品上线前人工走查逐条 Pass/Fail。

---

## 一、单源验收的三方契约

```
            ┌────────────────────────────┐
            │  §9 验收标准 (AC-Mxx-nnn)   │
            │  Given-When-Then 场景集     │
            └─────────────┬──────────────┘
      ┌───────────────────┼───────────────────┐
      ▼                   ▼                   ▼
 开发：TDD 先写     测试：1:1 转自动化用例    产品：UAT 人工走查
 测试用例的输入源    （Scenario 即骨架）      （逐条判定通过与否）
```

- 编号即追溯锚点：场景步骤流 ↔ 异常矩阵 ↔ AC 三者双向标注编号；
- 出现独立 UAT 表、或两套清单并存 → 判 P0（双源漂移，评测实证教训）。

---

## 二、编号与优先级规范

| 元素 | 规范 | 示例 |
|---|---|---|
| 场景编号 | `AC-Mxx-nnn`：模块两位序号 + 三位流水号，连续无跳号 | `AC-M03-001` |
| 优先级 | 置于场景标题内【P0/P1/P2】：P0 主链路与高危异常；P1 次高频；P2 低频 | `Scenario: AC-M03-002【P0】xxx` |
| Feature 头 | 一句话角色/愿望/价值 | `Feature: 售后退款` |

---

## 三、语法要点与中文习惯

- `Given` 业务前置状态（谁、处于什么业务局面），不写页面加载细节；
- `When` 用户的具体业务动作，承接步骤流语言；
- `Then / And` 断言**业务结果**：可见反馈文案、对象状态变化、数据结果、流向哪一环；
- 中文语体统一用「应」表达期望断言。

## 四、覆盖矩阵与写法示范

每个模块的 AC 必须覆盖四类：

### 1. 正向主链路
```gherkin
  Scenario: AC-M04-001【P0】提交合规退款申请后进入审核
    Given 已登录用户持有一笔已完成订单
    When 发起退款并填写原因"商品质量问题"、上传凭证后确认提交
    Then 页面出现提示"退款申请已提交"
    And 该订单生成一条状态为"审核中"的售后单
    And 订单详情中出现该售后记录及当前进度
```

### 2. 边界值
```gherkin
  Scenario Outline: AC-M04-005 退款金额边界
    Given 订单实付金额为 <order_amount>
    When 填写退款金额 <refund_amount> 并提交
    Then 系统受理结果为 <result>

    Examples:
      | order_amount | refund_amount | result              |
      | 10000        | 10000         | 受理成功             |
      | 10000        | 10001         | 拦截并提示超出可退上限 |
      | 10000        | 0             | 拦截并提示金额需大于零 |
```

### 3. 异常拦截
```gherkin
  Scenario: AC-M04-007【P1】提交时申请已被他人处理
    Given 该订单在另一端已被同意全额退款
    When 再次提交同单退款申请
    Then 请求被拦截且页面提示"该订单已有处理中的退款"，无新增记录
```

### 4. 重复操作
```gherkin
  Scenario: AC-M04-008【P1】短时间重复提交只受理一次
    Given 填写齐备并已成功提交一次
    When 在极短时间内再次触发同一提交
    Then 仅存在一笔审核中的售后单
    And 用户被告知无需重复提交
```

## 五、断言写法对照表（禁 DOM / 工程断言）

| ❌ 禁止写法 | 判定 | ✅ 改为业务断言 |
|---|---|---|
| `Then 按钮变为 Loading 态并置灰防重点击` | 控件实现词 | `Then 仅存在一笔受理记录，重复动作被明确告知无需重复提交` |
| `Then 弹出 Toast 居中停留 2s` | 控件实现词 | `Then 出现提示文案"验证码发送频繁，请稍后再试"` |
| `Then 调用 POST /api/refund 成功` | API 实现词 | `Then 生成一条状态为"审核中"的售后单` |
| `Then 返回错误码 COUPON_USED` | 错误码实现词 | `Then 提示"优惠券已被使用"，订单金额刷新为原价` |
| `Then 每个 token 渲染间隔 ≤100ms`（原 PERF-07 方向） | DOM/工程断言 | 流畅度不写数值（时延归技术层），AC 只断言结果完整呈现 |
| `Then P95 ≤200ms / FCP ≤1.2s` | 工程指标 | 归技术层（NFR），PRD 不出现 |

## 六、追溯与统计纪律

1. 步骤流每个场景 ≥1 条 AC；异常矩阵每行 ≥1 条 AC；
2. 场景/异常行标注对应 AC 编号，AC 标注来源场景号；
3. 验收报告中 AC 总数 = 重新清点实测值（禁止凭印象估算）；
4. `Given` 中出现的数据量词（如"3 件商品"）要与业务规则章一致。
