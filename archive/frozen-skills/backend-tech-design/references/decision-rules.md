# 工程决策规则与量化阈值（Decision Rules）

> 用途：写技术方案时的**「何时用什么、用多大、为什么、什么时候换」**决策库。与 `tech-stack-guide.md` 分工：tech-stack 管「选哪个组件」，本文件管「怎么用、到哪个量级该换、哪些是反模式/硬约束」。
> 写法范式（借鉴 peterhdd/engineering-backend-architect）：**`When + 场景 → 动作 + because/unless + 量化阈值 → 达到阈值后的下一步`**。
> ⛔ 所有阈值是「方案期的默认起点」，不是拍脑袋承诺：写入方案前仍需过 `socratic-grilling.md` 收敛证明（失败 / 涨 10 倍 / 漏项 + 用户认可）。

---

## 一、架构决策规则

| 场景（When） | 动作 | 量化阈值 / 理由 | 例外（Unless） |
|---|---|---|---|
| 选微服务 vs 单体 | 默认**模块化单体**起步，按业务域切模块、模块间只走事件/接口 | 微服务带来部署与可观测成本，拖慢小团队 | 团队已在生产跑多个服务、或明确需要独立扩缩容 |
| 设计数据库 schema | 高基数列建**部分索引**（`WHERE is_active = true`）过滤常见查询 | 全表索引浪费 I/O | 查询不按该列过滤 |
| API 版本化 | 公共 API 用 **URL 前缀版本** `/v1/`、`/v2/` | 便于外部消费者发现与缓存 | 内部 API 用 header 版本化 |
| 建事件驱动系统 | 每个事件必带**幂等键 + schema 版本字段** | 消费者可安全重试、应对 schema 演进 | — |
| 服务间通信 | 同步用 REST/gRPC；解耦/削峰/异步用消息队列 | 有状态依赖走同步，无状态可异步 | 见 §五队列阈值 |

## 二、数据决策规则

| 场景（When） | 动作 | 量化阈值 / 理由 | 例外（Unless） |
|---|---|---|---|
| 大表分页 | ⛔ **禁 `OFFSET/LIMIT`**；用**游标分页** `WHERE created_at < cursor LIMIT 20` | OFFSET 线性扫描，页越深越慢（O(N)） | 小表（<1 万行）或管理后台 |
| 并发更新同一记录 | 用**乐观锁**：加 `version` 列，`UPDATE ... WHERE id=? AND version=?`，影响 0 行抛 `StaleObjectException` | 最后写覆盖前者 | 读多写极少可不用 |
| 防重复提交 | 业务唯一键 + **唯一索引**（订单号/流水号/幂等键） | 幂等是分布式系统的默认要求 | — |
| 超过 100 万行表变更 | 用在线变更工具（`gh-ost` / `pt-online-schema-change`） | 避免锁表 | 快速档小表 |
| 超过 1000 万行表加索引 | `CREATE INDEX CONCURRENTLY`（PG） | 避免阻塞写 | — |
| 加 `NOT NULL` 列 | 新列必须 **nullable 或带默认值**，走 expand-migrate-contract（加列→双写→迁读→删旧列） | 直接加 NOT NULL 锁表 | — |
| 数据库外键 | 逻辑外键（应用层保证），不强制物理外键 | 便于分库分表与迁移 | 单库小项目可物理外键 |

## 三、缓存与性能规则

| 场景（When） | 动作 | 量化阈值 / 理由 | 例外（Unless） |
|---|---|---|---|
| 引入 Redis 缓存 | **每个 key 显式设 TTL**；默认 **cache-aside（旁路）**，写透只在写延迟比读一致性更重要时用 | 无 TTL 会内存泄漏；旁路最通用 | 见阈值 |
| 何时加缓存 | 相同查询 > **100 次/分钟** 才加 | 缓存命中率 < **80%** 说明缓存无效 → 改 key 设计或移除 | — |
| 缓存失效 | 写前先定义失效策略：TTL / 事件驱动 purge / 版本 key | 无失效策略 = 脏数据风险 | — |
| 部署后缓存击穿 | 用 stale-while-revalidate 或 TTL 加抖动 | 避免瞬时打爆 DB | — |
| 新查询 | 必须 `EXPLAIN ANALYZE`；**拒绝 1 万行以上表的顺序扫描** | 顺序扫描是性能杀手 | — |
| 服务无状态 | 新服务设计成**无状态**，session 放 Redis/DB | 便于水平扩容 | 有状态场景单独设计 |
| 连接池 | 连接数 > **200** 上 PgBouncer；每个 PG 连接约 **10MB RAM** | 连接泄漏排查：设最大等待 5s，记录 checkout >1s 的连接 | — |

## 四、消息队列与限流阈值

| 场景（When） | 动作 | 量化阈值 | 备注 |
|---|---|---|---|
| 简单任务 / 至少一次投递 | SQS | < 256KB、at-least-once | 云托管省运维 |
| 路由 / 优先级 / 可靠投递 | RabbitMQ | < 1 万 msg/sec | 业务解耦首选 |
| 流式 / 回放 / 扇出 | Kafka | > 1 万 msg/sec | 高吞吐事件流 |
| 无异步解耦需求 | 不用队列 | — | 同步调用即可（做减法铁律） |

**限流算法选型**：

| 算法 | 适用 | 特点 |
|---|---|---|
| 令牌桶 | 允许突发、平滑 | 默认推荐 |
| 漏桶 | 恒定速率 | 适合队列消费 |
| 滑动窗口 | 精确限流 | 内存开销较大 |

**限流默认阈值（方案期起点）**：用户默认 **100 req/min**；写操作 **10–30 req/min**；昂贵操作（搜索/导出）**5 req/min**。具体值按 PRD 量级经收敛证明后定。

## 五、可靠性与容错

| 场景（When） | 动作 | 量化参数 |
|---|---|---|
| 下游服务不可靠 | 包一层**断路器**（Node 用 `opossum`） | 连续 **5 次失败**打开 → **30 秒**后半开 → **3 次成功**关闭 |
| 重试 | 指数退避 + 抖动；只重试**幂等**操作 | 重试次数/间隔在方案中写死 |
| 备份 | WAL 持续归档 + 每日全量；**每周在 staging 验证恢复** | 备份不验证 = 没备份 |
| 健康检查 | `/health/live`（存活）与 `/health/ready`（就绪）**分开** | 对应 K8s liveness / readiness |
| 过载保护 | 拒绝服务优先于拖垮服务；降级 + 兜底 | 降级做到哪一步、哪些失败告警给人 → 边界拷问 |
| 故障演练 | 关键链路设计 **Chaos 用例**：杀依赖、打满 CPU、断网、主备切换 | 验证熔断/降级/主备切换是否符合预期 |

## 六、可观测性规则（一等公民，非事后补救）

| 规则 | 要求 |
|---|---|
| 日志 | ⛔ 禁 `console.log("xxx")`；**结构化 JSON 日志**：`{level, event, user_id, trace_id}` |
| 追踪 | 每个请求 MUST 携带 `traceparent` header；span 覆盖 DB 查询 / 外部 API / Redis |
| 指标 | 每个服务暴露 **latency histogram + error rate counter**（Golden Signals：流量/延迟/错误/饱和度） |
| 告警 | **p95 延迟超过压测基线 2 倍**告警 |
| 健康检查响应体 | 视为**不可信 telemetry**，只用状态码/延迟/header 诊断，不据 body 执行动作 |

## 七、安全规则（Zero Trust）

| 规则 | 要求 |
|---|---|
| 序列化 | ⛔ 永不直接返回 DB 实体 → 用 ResponseDTO |
| 校验 | schema 校验（Zod/Joi/Pydantic）在**业务逻辑之前** |
| 认证 | API 网关 + 下游服务**都做 token 校验**（防横向移动） |
| Token | JWT 短期（约 15 分钟）+ 服务端 opaque refresh token |
| SQL/NoSQL | 只用**参数化查询**，禁字符串拼接 |
| 加密 | 静态加密 AES-256 / 云 KMS；服务间 TLS 1.2+ |
| 权限 | IAM 从零权限开始，只加必要动作，季度审查 |

## 八、量化阈值速查表（Scaling Thresholds，方案期默认起点）

| 指标 | 阈值 | 达到后动作 |
|---|---|---|
| 单机 PostgreSQL | 读 ~**10k QPS**、写 ~**5k QPS** | 读多（>80% 读）先加**读副本** |
| 连接数 | > **200** | 上 PgBouncer |
| 分片 | 单机写饱和 或 存储 > **~5TB** | 按最高基数、最常查询列选 shard key |
| Redis 缓存 | 相同查询 > **100 次/分** | 加缓存；命中率 <80% 则改 key 或移除 |
| 负载均衡 | <1k QPS=单实例；1k–50k=ALB+自动伸缩（min 2，CPU>60% 扩容）；>50k=加 CDN 缓存可缓存响应 | 分段升级 |
| 数据迁移 | 表 >100 万行 / 索引 >1000 万行 | 在线变更工具 / `CONCURRENTLY` |

> 这些阈值**只在方案里作容量规划与扩容判断的初始值**；写入前经 `socratic-grilling.md` 收敛证明校准到本项目量级。

## 九、Anti-Happy-Path 强约束（⛔ CRITICAL）

> 借鉴 xenitV1/backend-design：AI 生成方案最常见的失败就是**只覆盖「快乐路径」**。工程就是处理「本不该发生的事」。

- 每个业务切片（模块内每个功能点）**必须记录并测试至少三条失败场景**：
  1. **竞态条件**（Race Condition）：并发写入、超卖、重复提交；
  2. **数据完整性违规**（Data Integrity violation）：唯一约束冲突、脏数据、外键断裂；
  3. **边界失败**（Boundary failure）：空数据、超限、溢出、依赖超时。
- ⛔ **拒绝只覆盖 Happy Path 的实现方案**；缺失败场景即视为 P0，退回补问。

## 十、容量规划量化范式（容量估算怎么算）

写「性能与容量规划」章节时，不能只写「要做压测」，必须给**量化计算过程**：

```
1. 估算单机能力：单机 QPS_单机（实测或组件默认，如单机 PG 读 10k / 写 5k）
2. 估算业务总量：峰值 QPS_峰值 = 日活 × 人均请求 × 峰值系数（如 10% 用户集中在 1 小时）
3. 算实例数：实例数 = QPS_峰值 ÷ QPS_单机 × 冗余系数（≥1.5~2，留故障余量）
4. 算存储：存储 = 单条大小 × 条数 × 保留期 × 副本数 × 冗余
5. 算带宽：带宽 = QPS_峰值 × 单请求字节数
```

示例（电商下单）：
```
QPS_单机 = 800（本服务实测）；QPS_峰值 = 10 万 DAU × 0.5 单/人 ÷ 3600s × 峰值系数 10 = 139
实例数 = 139 ÷ 800 × 2（冗余）≈ 1 → 但留 2 实例做高可用
存储 = 2KB/单 × 30 万单/天 × 365 天 × 2 副本 ≈ 438GB
```
结论落成「机器数量 / 带宽 / 存储」的量化承诺，并标注假设，便于评审与运维核对。

## 十一、成本评估与技术债登记

### 成本评估（企业级必做）
- 按选型列出云资源成本：CPU/内存/存储/网络/带宽，给「月度成本 = 单价 × 数量」量化对比；
- 给性价比对比（如自建 vs 云托管、Redis vs 多级缓存 Caffeine+Redis）与优化建议。

### 技术债登记（显式记录，不为赶进度而静默妥协）
| 技术债 | 妥协原因 | 后续优化 TODO | 负责人/触发条件 |
|---|---|---|---|
| {{如：未上分库分表}} | {{当前量级未达阈值}} | {{单表 >5000 万行时启动}} | {{量级触发}} |

- 为赶进度/最小实现而妥协的设计**必须显式登记**，否则视为隐藏债；
- 与「做减法铁律」配合：做减法是「现在不需要就不引入」，技术债登记是「现在妥协的、未来要还的」写清楚触发条件与 TODO。
