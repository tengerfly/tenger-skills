# 案例库（Case Library）索引与使用说明

> 定位：技术方案写作时**按需加载**的参考素材——「这个问题别人怎么解、怎么选型、怎么扛量」。不是必读，是查证与借鉴用的。
> 来源：大厂技术博客、开源 awesome 列表、同类 Skill（peterhdd / xenitV1 等），已精编浓缩，非原文搬运。完整资源清单见用户提供的《后端技术方案-Skill-案例库资源清单.md》。

## 一、目录

| 文件 | 内容 | 何时读 |
|---|---|---|
| `architecture-patterns.md` | Clean / Hexagonal / DDD / CQRS / Modular Monolith 模式解剖 | 服务拆分、架构风格选型时 |
| `system-design-cases.md` | 经典系统设计题（短链 / 秒杀 / 消息推送） | 做高并发/容量规划时 |
| `reliability-patterns.md` | 限流 / 熔断 / 降级 / Outbox / 幂等 / 分布式锁 | 写非功能设计、可靠性章节时 |
| `real-cases.md` | 大厂真实架构案例索引（Netflix / Uber / 阿里 / 美团等） | 找同类业务架构参考时 |
| `agent-templates.md` | Agent/LLM 后端项目模板（NestJS + Vercel AI SDK 等）+ 套用必补清单 | 用 Node.js 写 AI/Agent 后端、定 LLM 接入选型时 |

## 二、统一案例字段（每条案例遵循）

> 场景 → 技术挑战 → 选型决策 → 架构图/目录树 → 关键代码/配置 → 反模式 → 出处链接。

写进方案的案例必须是「决策可复现」的：说清**在什么场景、面临什么挑战、为什么这么选、踩过什么坑**，而不是只贴架构图。

## 三、使用原则

1. **借鉴决策，不照搬架构**：每个案例的选型理由要能回溯到「业务场景 + 量级」，与本项目量级对齐后才采纳。
2. **凡采纳必过收敛证明**：案例里的选型/阈值是参考起点，写入方案前仍走 `socratic-grilling.md`（失败 / 涨 10 倍 / 漏项 + 用户认可）。
3. **出处留链**：方案里引用案例结论时保留出处，便于评审溯源。
4. **不因「案例里有」就引入重型组件**：仍遵守做减法铁律，量级不达阈值不引入（阈值见 `decision-rules.md` §八）。
