# 创建与接管：只建立目标 Skill 的最小有效基线

## 澄清到足够开始

围绕真实任务问：要重复完成什么、输入/输出是什么、怎样算成功、哪些事不做、谁使用、有无工具或权限限制。用户只有一个例子时帮助补正常、异常和不该触发的邻近场景；不要求完整 PRD，不先套整个工程体系。

一句话职责可区分后再选名称（小写字母、数字、连字符，目录名与 name 相同）。描述写清能力和适用请求，不堆触发词，不承诺不存在的工具。多个独立职责应拆开；同一目标的维护阶段可由本入口按模式调度。

## 新建

1. 用 [目标 Skill 模板](../assets/skill-template.md) 起草，替换所有模板变量。只创建确实需要的 references/assets/scripts；常识不写成长篇教科书，长的条件流程放引用文件，入口注明何时读。
2. 在独立维护目录用 [上下文模板](../assets/context-template.md) 写清源码、用户范围、记录位置。源码与维护数据目录不可相互嵌套，也不可放入本工具包，以免复制时夹带隐私。
3. 用 [用例模板](../assets/cases-template.md) 建立任务相关的正常、边界、应拒绝/不触发场景，含可观察期望。初始例子只是起点，迭代时添加未用于改规则的场景，避免只适应一条示例。
4. 保留模板内的**使用反馈**小节，让以后执行目标 Skill 的助手在下一安全节点记录异常，而不需要先装本维护包。用户不希望记录时尊重其选择并说明缺少可追溯反馈的影响。默认仅保存脱敏最小事实，不保存整段聊天。
5. 做结构检查；有执行能力时在临时目录真实试跑目标任务，保存输入/输出与判定。不能试跑则交付“初稿/行为待验证”，不宣称已稳定可用。

## 接管已有 Skill

- 先读入口及所需引用，不重建目录、不覆盖用户未提交改动；确认真正可写源码，不改安装缓存。
- 记录当前版本（Git 提交加工作区差异，或文件副本与哈希），保留原有触发范围、可用工具和能力。
- 复用已有问题详情及编号；context.md 指向旧记录即可，不批量迁移或重写历史。
- 先补基线用例，反馈钩子缺失时提出窄范围植入方案，经用户确认后再加。不能在“只读接管”阶段直接加文件或修改规则。
- 观察到源码引用外部绝对路径/其他 Skill 时列为可移植性问题，交用户确定保留依赖说明还是抽离；不悄悄替换原能力。

## 初始交付

交付入口路径、用途/边界、记录落点、已验证与未验证场景、下一次如何提出反馈。无需创建空 issue，不因没有问题就编造改进需求。
