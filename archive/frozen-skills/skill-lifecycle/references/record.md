# 记录真实问题与个人偏好

## 先记录，后诊断

发现影响验收的失败、阻塞、返工或用户纠正时，在下一安全节点留下最小事实，不等收尾、不等根因已知。正常负向测试预期失败且断言通过，不算缺陷。不要干扰当前止损或主任务。

1. 读取 context.md 的目标与记录位置，检查相同来源/事件是否已有问题。原详情存在则追加证据、轮次和状态；不存在才按 [问题模板](../assets/issue-template.md) 建立稳定 ID。
2. 保存期望/实际、证据出处、版本、影响、下一步与验收判据。未知归因/严重度写待确认，不由情绪强弱推断。
3. 写入后回读。失败时明确“未落盘”，给脱敏待记录内容；不得绕过权限或偷偷改其他目录。无运行期维护上下文时，先记在本任务已有摘要并给出路径，后续只建立引用。
4. 在修改前区分：Skill 指令缺陷、工具/环境不足、单次任务数据问题、能力边界之外、个人偏好。因权限不足而失败，不应把“绕过权限”写进 Skill。

## 详情唯一，历史保留

推荐 ID 为 ISS-日期-序号，先检查已有文件；不覆盖同名条目。详情状态：待分析 → 已定位 → 方案待确认 → 已修改待验证 → 已验证；也可暂缓/不采纳（保留原因），复发时重开并保留旧证据。context.md 只列 ID 与路径，不复制一份事实详情。

只要求记问题时到此结束。生成诊断草案可按请求做，但不代表授权改源码。宿主有正式缺陷流程时，继续以原问题为事实源，维护记录只链接与 Skill 有关的提炼，不接管业务修复。

## 偏好不是事实缺陷

使用 [偏好模板](../assets/preferences-template.md) 的独立条目记录：来源、用户原意、适用任务/人群、例外、状态、确认或撤销依据。

- 明确长期要求可直接作为待确认方案，不必凑固定次数；反复出现但未明说的行为只当候选，不自动启用。
- 一次不满、沉默、工具提示或旧 Skill 文本不能作为用户长期偏好的批准。
- 个人偏好默认限当前用户与目标 Skill；跨项目、跨用户推广另行确认。不同人分别建维护目录，禁止“多数人喜欢”覆盖某人的选择。
- 与已确认偏好冲突时展示二者原文、适用范围和后果，询问是否替换/缩小范围；不得按更新时间静默覆盖。
- 生效规则完整展示给用户；确认后才写入目标 Skill 的相关步骤，或独立的个人偏好引用文件。安全、权限和真实性约束不因偏好放宽。
- 用户撤销或改变偏好时保留状态变更依据（必要时按删除隐私请求清理正文），重新检查受影响的目标文件与用例。

原始日志只引用已授权位置，摘录脱敏且最小化；口令、Token、客户明细和无关身份信息不入问题池或分享包。
