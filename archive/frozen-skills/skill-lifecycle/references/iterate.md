# 小步迭代：诊断、确认、修改、复验

## 诊断与方案

先读 context.md、未决问题的原始证据、当前源码和已确认偏好。只用授权材料，不扫描所有聊天或磁盘；访问不到证据就标待核验，用户当前明确纠正也可作为来源。

每条候选变更用 [迭代模板](../assets/iteration-template.md) 写明：来源 ID/明确请求、原因与证据、文件/段落、旧行为与新行为、适用边界、对正常场景的影响、验证场景、回退方式。问题只有局部影响就局部修，不先重写整个 Skill 或优化器。

按本轮影响选择检查维度，不要求机械跑全套：

| 维度 | 关键检查 |
|---|---|
| 职责/触发 | 是否误触发或漏触发？与邻近能力的边界是否明确？ |
| 流程 | 是否遗漏实际必要步骤？是否强迫无关任务走重流程？ |
| 输入/产物 | 缺输入时如何处理？输出有可验收标准吗？ |
| 工具/权限 | 工具真的可用吗？不可用是否诚实停下而非假装执行？ |
| 证据/一致性 | 规则与模板有冲突吗？改动能追到来源吗？ |
| 表达/体积 | 是否删除重复规则，按需加载细节，而非每次失败都叠禁令？ |
| 偏好 | 是确认过的范围内个人选择，还是未证实的泛化？ |
| 可移植性 | 是否引入私人绝对路径、其他 Skill 强依赖或敏感记录？ |

展示本轮具体方案，等待用户批准其范围。用户已明确“按这几条改并验证”即可视为对应范围授权，记录其原意；“继续看看/继续分析”不是授权。只是记录、分析或只读接管请求不得修改源码。

## 修改前与执行中

- 固定当前基线：保存所有将改/删文件的完整副本与相对路径，新文件单独列出。副本存维护目录本轮记录下，不在目标源码内；无 Git 也可回退。
- 用户有未提交更改时以本轮开始的实际文件为基线，不用旧提交覆盖工作区。不执行全仓 reset/clean 或无范围递归删除。
- 只修改确认清单内文件，保留原能力和反馈规则；引用与模板同步，不自动同步安装副本。
- 个人规则优先限定到具体任务/人群。通用修复和个人定制分别记录；导出通用版时个人规则可以清楚分离。

## 验证三层，不混为一谈

1. **结构**：检查入口元数据、引用是否存在、脚本语法。可用 [只读检查脚本](../scripts/check_bundle.py)；它只检查常见静态链接与基本元数据，不是完整 Markdown/YAML 解析器，也不证明行为好坏。
2. **行为**：在可用的宿主执行工具中，把目标 Skill 和真实任务交给模型执行，保留输入、产物/动作、版本、模型/环境、判定。不把“读规则觉得会成功”当试跑。至少覆盖原失败、仍应成功的正常场景及一项不该触发/不应泛化的邻近场景；无独立执行环境则明确是自测，未运行则标未验证。使用隔离目录，不操作生产环境。
3. **用户适用性**：与用户确认本轮输出是否更符合已说明的偏好。这是主观验收，不由结构测试替代；未获得反馈标待用户确认。

将行为用例作为资产保存，修复时添加对应回归；重要行为变化使用未参与规则修改的案例复验，不按已反复调参的案例宣布普适。可能造成真实写入或费用的测试需对应授权。可以使用已有自动化测试工具，但不强依赖另一个 Skill。

问题只有在原验收判据已实测满足且证据对应当前版本时标已验证；缺场景执行能力即保持已修改待验证。本轮范围内检查 PASS 与总体行为待验证分别显示。连续三轮同一阻塞未解决，暂停自动修改并报告；新增独立问题不机械算同一轮。

## 回退与交付

需要回退时先比较当前文件与本轮修改后版本：有他人后续更改就停下来合并，不直接覆盖。仅恢复本轮基线中已备份的文件；本轮新建文件先确认无后续改动，再按明确路径处理。回退后运行相同结构/关键行为检查，记录为已回退，不把已回退修复仍标已验证。

交付目标 Skill 路径、版本、具体变化、证据、剩余风险、下一步。没有行为证据的个人版称“候选版”，有真实试跑及用户确认后才称“本轮场景已验证个人版”；不承诺永久最优。

本维护包自身的真实模型验收输入见 [行为场景](../tests/behavior-cases.md)；未执行的场景不是通过记录。
