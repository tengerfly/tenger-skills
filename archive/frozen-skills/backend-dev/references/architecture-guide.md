# 微服务架构与模块化规范

> 用途：后端代码「怎么分层、怎么拆服务、怎么组织 Monorepo」的权威规范。冲突时以本规范为准，`assets/` 模板只是骨架。

## 一、总体结构

```
Monorepo（前后端同仓库）
├── 服务内：四层分层，依赖单向向下
└── 服务间：微服务边界，只走对外接口
```

微服务不放弃分层；服务内部必须清洁可维护。

## 二、服务内四层

```
Controller → Service → Repository / DAO → Entity / Model
```

| 层 | 做什么 | 不做什么 |
|---|---|---|
| Controller | 路由/消息处理、参数校验、鉴权、调 Service、统一响应 | 业务逻辑、循环处理、SQL、直接碰 Repository |
| Service | 核心流程、业务规则、事务/跨服务编排 | 传输层解析、SQL、直接操作 DB |
| Repository/DAO | 增删改查、条件查询、分页、数据映射 | 业务规则、状态流转判断 |
| Entity/Model | 与表结构一一对应的纯数据载体 | 任何业务逻辑 |

判错口诀：接口层出现业务 if = 越界；业务层出现 `SELECT`/`prisma.` = 越界；数据层出现业务 if = 越界；实体出现含逻辑方法 = 越界。

### 接口解耦

- Service 面向接口编程：依赖抽象，不依赖具体实现——便于单测 mock 与替换实现。
- NestJS：`@Injectable()` + interface/抽象类 + 构造器 DI；仓储定义 interface，Service 注入 interface。

## 三、服务间边界

### 拆分

- TDD 模块清单是候选边界，默认一模块一服务。
- 合并/拆分由业务耦合度决定：强耦合合并，弱耦合拆开。
- 不确定用选项确认（一拆一 / 合并 N 个服务 / 先单体后拆）。

### 通信铁律

| 禁止 | 正确 |
|---|---|
| 跨服务直连对方数据库 | 表归属明确，访问走对外接口 |
| 跨服务 import 对方 Repository/Entity | 只走 HTTP/gRPC/NATS/队列 |
| 服务间循环依赖 | 抽 libs/shared 或事件解耦 |
| 共享库写操作 | 一表一主，其它服务只读或走接口 |

### 交互方式

| 方式 | 适用 | 落地 |
|---|---|---|
| HTTP（网关） | 对外统一入口 | Gateway 路由到服务 |
| gRPC | 同步强契约 | @nestjs/microservices + proto |
| NATS/Kafka | 异步、事件驱动、最终一致 | 消息队列（按 TDD 选型） |
| 共享数据 | 读多写少 | 共享表/缓存（注明归属） |

每个服务上下游依赖必须与 TDD 模块方案及总文档关联图一致。

## 四、Monorepo 组织

```
repo/
├── apps/
│   ├── web/                    # 前端
│   └── server/
│       ├── gateway/            # HTTP 入口
│       ├── <service-a>/
│       └── <service-b>/
├── libs/shared/                # DTO/枚举/常量/契约/工具
├── package.json
├── pnpm-workspace.yaml
├── tsconfig.base.json
└── .env.example
```

### libs/shared（契约单一事实源）

| 内容 | 说明 |
|---|---|
| DTO | 前后端共用请求/响应类型，禁各写一份 |
| 枚举/常量 | 状态值、错误码分段、业务枚举 |
| 服务间契约 | proto / 消息事件结构 |
| 通用工具 | 无业务语义纯函数 |

共享包只放无业务归属的通用物；业务逻辑留在各自服务。

### 多人协作

- 服务边界清晰 → 并行互不冲突。
- 约定先行：目录、命名、契约、错误码分段在动手前统一。
- 共享包小步提交；契约变更先对齐文档再改代码。

## 五、服务内模块化

- 服务内按业务域分包（如 user-service 内 auth/profile），对应 TDD 模块细分。
- 通用能力（鉴权/日志/错误/响应/配置/中间件）下沉 common/shared。
- 模块间只经对外 Service 接口交互，禁循环依赖。

## 六、数据模型落地

- TDD 每张表逐字段映射 Entity：字段名/类型/可空/默认/约束/索引/注释一致。
- 约定照搬 TDD：金额整数分；时间 DATETIME/时间戳；枚举 TINYINT+注释；软删 `deleted_at`；逻辑外键。
- 实体纯净，规则在 Service。
- 每表归属唯一服务（写入方唯一），跨服务走接口。
- 建表用 migration（Prisma/TypeORM/SQL），可重复、可版本管理；禁手工改库。

## 七、事务与边界

- 事务边界在 Service；Repository 不做事务控制。
- 跨服务：单库本地事务；跨服务/跨库按 TDD 走最终一致 + 补偿（队列 + 重试 + 幂等），不硬造分布式事务。
- 幂等写操作：唯一索引/幂等键/状态机兜底，落成代码而非注释。

## 八、架构自检清单

- [ ] 四层齐全、依赖只向下、无跨层？
- [ ] Controller 无业务逻辑？
- [ ] Service 面向接口，无 SQL？
- [ ] Repository 无业务判断？
- [ ] Entity 纯数据？
- [ ] 服务拆分对齐 TDD，边界清晰？
- [ ] 无跨服务直连库/import 内部实现/循环依赖？
- [ ] 共享 DTO/枚举下沉 libs/shared？
- [ ] Entity 与表一致、表归属明确、迁移可重复？
- [ ] 事务边界在 Service、跨服务一致性按 TDD、幂等落成代码？
