# 开发类 skill 公共约定（Backend-Dev / Frontend-Dev）

> 两 Dev skill 的共用规则收口于此；各 skill 正文保留端差异（必问清单、技术栈、分层/组件规范），公共规则引用本文件。

## 零、任务裁剪与需求上下文

先读 `shared/execution-profiles.md` 与 `shared/requirements-context.md`。低风险独立任务可用局部实现计划替代完整 TDD/FTDD，用同一任务摘要替代新建 PROJECT/PLAN；先盘点相关代码/接口/测试即可，不套脚手架、不强制知识库沉淀或逐功能点提交。现有接口、架构与已批准需求必须遵守。新架构或风险边界变化则升级，不能借轻量直接改权限/数据迁移。

按实际影响执行检查和测试；缺少浏览器时可交付已实现但待视觉验证的代码，不宣称视觉通过。专业视觉验收的硬依赖不变。下面完整开发产物与提交节奏用于标准/完整流程，提交还须符合用户与工作区规则。

## 零之二、并行 teammate 模式（受限执行方）

当 Lead 把开发拆给多个并行 agent、且 **PROJECT.md/PLAN 与 git 提交权由 Lead 独占**时，执行方按以下替代口径运行（2026-10-18 knowledge-bases 实测，避免执行方在「无法提交/无法改 PLAN」上停等或违规）：

- 功能点边界 = 共享任务卡的 task 描述；进度 = 任务卡状态 + 给 Lead 的交付报告；
- 门禁 = 每个模块的验证命令与真实输出（测试通过数 / typecheck / lint），不要求本 agent 执行 commitlint/自动提交；
- 交付必须报「新增/修改文件清单 + 测试证据 + 装配需求 + 契约缺口」，由 Lead 统一提交并回写 PLAN/PROJECT；
- 不得因无提交权跳过测试或伪造通过；发现需改中央装配文件时报告 Lead，不越界。

## 一、项目现状基线（既有工程开工前置）

有代码而无 PROJECT.md/PLAN.md 时：先盘点目录/技术栈/依赖/规范/git，沉淀「项目现状基线」入 PROJECT.md；严格按现状开发——不套默认模板、不擅自换栈重构、不擅自分服务/换目录结构；存量问题登记，不在本次扩散修复。

## 二、澄清协议（统一模板）

- 给 2~4 选项并标推荐 + 理由；一次只问一个关键问题；多个拍板点可列编号清单一次呈现、逐条确认；结论留痕（注释 why / PROJECT.md 关键决策）。
- TDD/FTDD 已写死或默认已明确的直接采用，不重问；非关键细节先用默认并留痕。

```
【确认】{{一句话问题}}
影响：{{不确认的后果}}
选项：A（推荐：理由）/ B / C（或暂不实现标 TODO 登记风险）
```

## 三、通用错误行（两 Dev「常见错误对照表」公共部分）

| 错误 | 纠正 |
|---|---|
| 既有工程不盘点套默认模板 | 按现状基线 |
| 开发中再选型/换选型 | 选型定稿，开发期零决策 |
| 擅自拍板 | 澄清协议给选项 |
| 传参无注释 | 逐个写作用与约束 |
| 攒一批才提交 | 一功能点一 commit |
| 提交前不校验 | lint/commitlint 门禁全过 |
| 完成不更新 PROJECT/PLAN | 同步更新 |
| 续做不读进度 | 先读 PROJECT.md + PLAN.md |

（端专属错误行保留在各自 SKILL.md；公共行引用本表，不重复维护。）

## 四、源码写入通道与写后校验（多 agent 并行时 REQUIRED）

- 源码编辑只用 `read` / `edit` / `write`（或 IDE 专用工具）；**禁止**用 PowerShell `Get-Content -Raw | Set-Content`、shell heredoc 等文本管线改 UTF-8 源码——编码/换行回写会把全角中文写坏，实测一次损坏整个文件且只能重建。
- 用脚本/模板生成含正则、反斜杠或模板字符串的源码后，**立即**做两项校验：① 扫描控制字符（`\x00`–`\x08` 等）并跑编译/类型检查；② 正则优先用 `new RegExp(...)` / `includes` 等低转义写法，少用字面量转义。模板字符串的二次转义曾把 `\b` 写成退格符，导致整文件语法错误、两轮测试假失败。
- 写后回读关键片段，确认落盘内容与预期一致（证据先于声明）。
