# 问题记录、恢复与反哺

适用于全部 Skill 的直接调用和编排调用，包括轻量任务。统一的是记录出口，不新增状态机、后台监听器或完整建档前置。此规则优先于旧的「只在收尾记录」「不确定不记」及无条件跨仓沉淀要求；不改变领域执行、设计分支或正式 Gate。

## 1. 触发与持久化

- 已观察到的报错、验证失败、阻塞、用户纠正或复核新问题，在**下一安全节点**写入已授权的持久记录，不等正常交付。先止损的事故不因填表延误；信息脱敏后再写。
- 记录事实不要求先确认根因或可复用性。未知根因、严重度和归属标「待确认」；负面反馈引用原意，不直接认定为产品缺陷或通用偏好。
- 不把预期负向测试（预期失败且断言通过）和无影响的探索尝试都当问题；影响验收、导致阻塞/返工或需后续动作的失败才建条目。
- 正常收尾补处理结果与证据；中止/换会话前保存已知事实。恢复及最终交付前读取当前任务的问题记录、核对未决项和版本，不仅依靠聊天记忆。
- 写入后回读确认成功。无权限或写入失败时，不绕过权限：明确报告「未落盘」，提供脱敏的待记录内容与目标位置，保留下一步。不能承诺捕获尚未被观察到的宿主崩溃或强制终止。

## 2. 详情与索引（一事一源）

| 情况 | 详情唯一来源 | 可发现入口 |
|---|---|---|
| 已有评审清单、测试任务卡、缺陷报告 | 沿用该文件和原问题 ID | 项目 `.spec/问题日志.md` 引用源路径 + ID/锚点 |
| 轻量任务或尚无问题报告 | 已有任务摘要；没有才用 `.spec/tasks/<task-id>.md` 的问题小节 | 只要产生需追踪问题，追加/更新项目问题索引，不建全套 manifest/Envelope |
| 在本体系仓核查 Skill 自身问题 | 源仓 `issue/<Skill目录名>/<日期>/<序号>-<标题>.md` | `issue/` 本身；不再重复建项目问题详情 |
| 业务项目发现疑似 Skill 问题但未获跨仓授权 | 业务项目原问题文件，标「待反馈」 | 项目问题索引；获授权后建立溯源引用，不复制第二份原始详情 |

确认项目根和 Skill 源仓根后解析路径，不把当前目录、安装缓存或两层 `../` 默认当源仓。源仓问题目录复用已有叶目录名（如 `PRD-Design`、`auto-test`），新 Skill 沿用目录名；不要另建 `issue/PRD/prd-design` 分叉。写源仓、外部知识库、安装副本均须在本次授权范围内；未授权只留本地待反馈，不自动同步或部署。

稳定标识沿用 REQ 评审编号、BUG/DEF ID；无编号用 `<task-id>-ISS-01`。创建前查源路径 + ID；同一事件补证据/轮次/状态，不新建重复条目。相同报错但版本、范围或成因不同不强行合并；复发时重开原问题并保留历史，或新建关联条目。

项目索引使用 `shared/templates/problem-log-template.md`。旧台账无需全文迁移，新行加 ID/锚点即可；状态以详情为准，索引只是镜像。多问题共用报告时允许一行批次索引，但须列 ID 范围/锚点，全部复核后才将整批标闭环。无问题不制造空 issue。

## 3. 最小事实记录

可以写在现有清单、任务卡或摘要中，不强制独立文件：

```text
问题 ID / 发现时间 / 当前状态：
任务 / Skill / 步骤 / 项目与相关版本：
期望与实际：引用验收依据或用户纠正；根因未知就写未知
证据：脱敏命令、退出码、复现步骤、文件/日志/截图位置（按实际可得）
影响与严重度：P0/P1/P2/P3 或待确认；Skill 问题池仍用其 P0/P1/P2 口径
责任方 / 下一动作 / 修复判据：未确定则写待分诊及负责分诊的执行方
处理与复核：改动、复核人/Skill、实际结果与版本、未验证项
反哺：无 / 待分析 / 待授权反馈 / 已关联目标路径与条目
```

保留原始事实，更新处理历史，不用新结论覆盖失败证据。Token、密码、个人/客户数据不入池；敏感证据只引用授权位置。

## 4. 修复、复核与协作

「已修复」不等于「已验证/已闭环」。按原修复判据复测并记录当前版本证据后才能闭环；未复现、未执行或证据陈旧均保留未决。正式评审由原评审方/授权复核方确认，不自销评审问题；轻量自测可由执行方完成，但明确自测，不冒充独立复核。正式 Gate 仍遵循 `gate-policy.md` 和 `anti-deadloop.md`，记录问题不构成执行、解除阻塞或发布授权。

- **auto-test**：报告/任务卡是详情源；记录下一安全节点可得的失败；汇总时更新项目索引，复测后同步状态。P3 若只在报告中仍可用报告锚点索引。
- **Code-Review + Fidelity-Review**：协作任务以 Code-Review 合并清单为最终详情源，Code-Review 负责唯一索引；独立 Fidelity-Review 自己登记。交接前各自保留已观察证据，主方中断时保留临时引用并标待合并；恢复合并后将引用转向主清单，保留旧 ID 映射，不复制成两件问题。
- **defect-triage**：使用 `.spec/defects/<id>.md` 并同步索引；转事故/需求变更时保留原 ID 与路由目标，不能因分诊完成把实际缺陷标为修复闭环。

## 5. 从记录到反哺

先修项目，再按用户要求或里程碑复盘。Skill-Optimizer 读取明确授权的项目索引及其详情、源仓 `issue/`、偏好信号；不能只看索引摘要，也不能默认扫描全部磁盘或外部仓。

区分项目个例、流程缺陷、可复用代码模式和稳定偏好。只有事实与适用范围支持时才提炼；结果分别链接到对应 Skill/评审案例库、`bug-patterns/` 或 `evolution/`。不因一次失败自动改全局规则。同一来源可有产出方防复发和评审方检出规则两个落点，但原问题只有一个，两个落点均回链。

反哺记录包括来源、改动位置、验证证据、适用边界及回退方式；无授权则留待反馈。已落盘不等于已优化，已优化不等于真实项目行为已验收。此文件由执行 Agent 遵循，不是自动日志服务。
