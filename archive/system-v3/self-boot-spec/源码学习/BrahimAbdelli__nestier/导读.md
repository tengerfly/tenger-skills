> 定位：**七仓收官**。前六个项目教你权限/会话/MQ/微服务，这一个教最后一块拼图——**大型项目怎么组织代码**。它是一个 NestJS 11 的生产级脚手架：商品/分类/用户三模块 + 泛型基类 + 六边形架构 + 全套工程化。

## 00 · 总览

**前置知识 · 六边形架构（端口与适配器）**：传统三层架构（Controller→Service→DAO）里，业务逻辑依赖数据库——数据库是中心。六边形架构把它倒过来：**业务（domain）在中心，数据库/Web/邮件都是围绕它的「适配器」**；domain 定义「端口」（接口），外层实现「适配器」。好处：换数据库不改业务，业务逻辑可脱离框架测试。

**模块总图**（一次「查高价商品」请求的穿层之旅）：

```mermaid
flowchart LR
  subgraph presentation 表现层
    C["ProductController<br/>+DTO Mapper"]
  end
  subgraph application 应用层
    UC["FindExpensiveProductsUseCase<br/>(用例)"]
  end
  subgraph domain 领域层(中心)
    P["Product 值对象<br/>+ Repository 接口"]
  end
  subgraph infrastructure 基础设施层
    R["TypeOrmProductRepository<br/>+ ProductEntity + Mapper"]
  end
  C -->|"调用"| UC -->|"依赖接口"| P
  R -.->|"实现接口(依赖倒置)"| P
```

**怎么跑起来**：配 `.env`（DB/MailJet/auth secret）→ `npm run start:dev`；`docker-compose.yaml` 与 SonarQube 配置齐备。

**学习动线**：章1 六边形（必读）→ 章2 泛型基类 → 章3 认证与用户 → 章4 生产栈 → 章5 七仓收官。

## 01 · 精读：六边形架构与依赖倒置

**本章在全局的位置**：本仓的灵魂。看懂「接口在中心、实现在外圈、DI 负责缝合」这一件事，架构课就毕业了。

**核心问题**：`UseCase` 想查数据库，却「不认识」TypeORM——这怎么可能？数据到底怎么查的？

**主线讲解**（跟着一份代码的诞生顺序走）：

1. **领域层先定义端口**（`src/modules/product/domain/repositories/product.repository.interface.ts:4-7`）：`interface ProductRepositoryInterface extends BaseRepository<Product>`，外加两个业务方法声明。注意 Product 是从 `value-objects/product` 导入的**领域对象**，不是 TypeORM 实体——**领域层的世界里没有数据库**。
2. **接口配一个 DI 令牌**（`src/modules/product/domain/repositories/product.repository.ts:3`）：`export const PRODUCT_REPOSITORY = 'ProductRepository'`——领域层不只是定义接口，还给了它一个「认标签不认人」的容器令牌。
3. **基础设施层实现端口**（`src/modules/product/infrastructure/adapters/repositories/typeorm-product.repository.ts:11-15`）：`class TypeOrmProductRepository ... implements ProductRepositoryInterface`——真正的 TypeORM 查询都在这（`:25-33`），且查询条件永远带 `isDeleted: false`（软删过滤，`:29,39`）。**依赖方向：infra → domain**（import 接口），domain 对 infra 一无所知——这就是「依赖倒置」四个字的代码形态。
4. **用例只依赖令牌**（`src/modules/product/application/use-cases/find-expensive-products.use-case.ts:7`）：`@Inject(PRODUCT_REPOSITORY) private readonly productRepository`——构造器声明「给我任何实现了 ProductRepository 的东西」。一个用例一件事（查高价商品），薄到一行 `execute`。
5. **模块装配缝合**（`src/modules/product/product.module.ts:47-56`）：`{ provide: PRODUCT_REPOSITORY, useFactory: (...) => new TypeOrmProductRepository(repo, mapper, logger) }`——容器里「ProductRepository 令牌 = TypeORM 实现」的绑定在这里完成。**想换 MongoDB？新写一个适配器，只改这一处绑定**。`:57-59` 同样手法绑定 Mapper 接口。
6. **表现层收尾**（`src/modules/product/presentation/controllers/product.controller.ts:22-28,46-48`）：控制器继承泛型 `BaseController<Product, ProductDto, ...>`，业务方法里调完用例后 `productDtoMapper.domainsToDtos(products)`——**领域对象不许直接出网**，DTO 映射器把关。
7. **对照之前读过的所有项目**：RuoYi/mall/GVA 都是「Controller→Service→Mapper 直捅数据库」的**分层架构**；Nestier 是**六边形**——每多一层间接就多一点样板代码，换来的是业务可测试、存储可替换。小项目用前者，长生命周期项目用后者，这个判断力比模式本身值钱。

**收束**：依赖倒置 = 领域定义接口 + 外层实现 + DI 缝合。下一章看它怎么把这套结构的样板代码压缩到可维护。

## 02 · 泛型基类层：把样板代码压到一次

**本章在全局的位置**：六边形的代价是每模块四层文件很多——Nestier 用 `base` 模块的**泛型基类**把这个代价砍掉一大半（README 宣称的 Generic Repository Pattern）。

**关键点讲解**：

1. **base 模块也是四层**（`src/modules/base/`）：`domain/repositories/base.repository.ts`（泛型仓储接口）、`infrastructure/adapters/repositories/orm-base.repository.ts`（TypeORM 泛型实现）、`application/services/base.service.ts`（泛型服务）、`presentation/controllers/base.controller.ts`（泛型控制器）——**六个项目里第一次见「控制器也有抽象基类」**。
2. **业务模块白捡全套 CRUD**（`product.controller.ts:22-28`）：泛型参数一填（领域类/DTO/创建/更新/响应 DTO），增删改查、分页、搜素的接口全有了，自己只写差异化端点（如 `/expensive`）。
3. **软删除内建**（`src/modules/base/application/services/base.service.ts:82-90`）：`softDelete` 改 `isDeleted` 标记；创建时默认 `isDeleted = false`（`:48`）——RuoYi 章5 讲的「逻辑删除」，在这里是基类行为，业务模块**想不遵守都难**。
4. **分页内建**（`base.service.ts:39-40`）：`findAndCount(criteria)` 返回 `[数据, 总数]`，`FindAndCountCriteria` 统一承载分页/筛选参数（`domain/ports/find-and-count.criteria.ts`）——分页参数的类型化契约。
5. **三层 Mapper 体系**：DTO↔Domain（presentation/mappers）与 Entity↔Domain（infrastructure/adapters/mappers）各自独立，用 @automapper 的 profile 机制声明映射——**每层边界都有翻译官**，六边形成立的前提就是对象不越层裸奔。

**收束**：泛型基类 = 「结构收税一次，业务终身免税」。下一章看用户模块的认证与端口/适配器的又一个例子。

## 03 · 认证与用户模块：中间件、端口与预留的 RBAC

**本章在全局的位置**：Nest 官方推荐 Guard 做认证，Nestier 选了**中间件 + 模块级路由声明**——另一种合法姿势，且展示了端口/适配器在「发邮件」上的应用。

**关键点讲解**：

1. **认证中间件**（`src/modules/user/infrastructure/middleware/authentication.middleware.ts:20-39`）：取 `authorization` 头剥 Bearer → `jwt.verify(token, this.authConfig.secret)`（secret 走配置服务，`:17`）→ 解出的 `id/username/email/roles` 挂上 `req.user`。和 GVA 的 JWT 中间件同构——**Express 中间件思想在 Nest 里的直接延续**。
2. **认证的路由级声明**（`src/modules/product/product.module.ts:66-75`）：在**业务模块自己的 configure** 里 `consumer.apply(AuthMiddleware).exclude({path:'api/products/search'}).forRoutes(...)`——哪些接口要登录、哪个免登录，写在模块内部而不是全局配置。**模块自治**：把 user 模块拿掉，其他模块的认证声明也一并消失，依赖关系诚实。
3. **邮件是端口+适配器**（`src/modules/user/domain/ports/email.interface.ts` + `infrastructure/adapters/email/user-email.adapter.ts`）：领域层声明「我会发邮件」，基础设施用 MailJet 实现（依赖 `node-mailjet`）——六边形不只管数据库，**一切外部服务都是适配器**。配套的 `send-password-reset-email.use-case` 展示了用例层怎么消费端口。
4. **登录用 bcrypt**（`src/modules/user/application/services/user.service.ts:69-77`）：按邮箱查人 + bcrypt 比对——四项目同款，不再展开。
5. **⚠️ 诚实的发现：roles 是预留字段**：JWT claims 里带了 roles（`authentication.middleware.ts:32`）、实体和 DTO 里也有 roles——但全仓 grep **没有任何守卫/中间件消费 roles 做接口鉴权**（命中全是定义与展示）。README 说 JWT Authentication 没说 RBAC——**脚手架宣传什么给什么，没实现的不吹**，但你自己接手时要心里有数：RBAC 要自己补（rbac-test 的双守卫方案直接可搬）。

**收束**：认证中间件 + 模块级声明 + 端口/适配器——又是一套可直接抄的组合。下一章清点生产栈。

## 04 · 生产栈与工程化：一个脚手架的自我修养

**依赖清单解读**（`package.json`，都是为「上生产」准备的）：

| 类别 | 依赖 | 干什么 |
|---|---|---|
| 框架 | @nestjs/* 11.x | 当前最新大版本（2025-2026），比 recipe 的 7.x 新四代 |
| 对象映射 | @automapper/{core,classes,nestjs} | 三层 Mapper 的引擎 |
| 安全 | helmet、express-rate-limit、compression | 安全响应头、接口限流、响应压缩——**Web 生产三件套**，之前的 Java 项目里分别对应各种 Filter/拦截器 |
| 认证 | jsonwebtoken、bcrypt | 同款老朋友 |
| 缓存 | @nestjs/cache-manager、cache-manager | 缓存基建就位（⚠️ 使用面未逐查） |
| 邮件 | @nestjs-modules/mailer、node-mailjet、handlebars | 模板邮件（templates/ 目录放 handlebars 模板） |
| 数据 | @nestjs/typeorm、mongodb | TypeORM 主力 + mongo 客户端 |
| 日志 | winston、logform | 结构化日志 |

**工程化配套**：`jest.config.js` + `jest-e2e.config.js`（单测与 E2E 分离，每模块自带 test/ 目录与 mock）、`sonar-project.properties`（SonarQube 代码质量门禁）、`Dockerfile` + `docker-compose.yaml`、`AppInitializer.initializeApp`（`src/main.ts:10`——把管道/Swagger/全局配置的装配从 main 里抽出去，启动文件只留生命周期）。

**收束**：脚手架的价值不在功能多，在「团队不用做决定」——安全、日志、测试、质量门禁全替你定了默认值。

## 05 · 收束：七仓全景与三条架构思维

**七仓地图**（这批导读的最终索引）：

| 仓 | 一句话 | 读它收获什么 |
|---|---|---|
| RuoYi-Vue | 权限管理事实标准 | RBAC 三层、数据权限、表规范 |
| mall | 电商复杂度教科书 | MQ 延迟任务、库存模型、订单快照、存储选型 |
| mall-swarm | 微服务化样本 | 拆分得失、网关、认证中心、Feign |
| gin-vue-admin | Go 视角 | Casbin 标准件、GORM 迁移、泛型基类 |
| nestjs-recipe | Nest 最小完整样本 | Nest 标准件全家桶 |
| nestjs-course-code | Nest 食谱 120 道 | 按特性查阅（AOP/RBAC/双token/MQ/微服务） |
| **Nestier** | **架构组织范本** | **六边形、依赖倒置、泛型基类、模块自治** |

**三条架构思维**（收官沉淀）：

1. **依赖方向比分层更重要**：三层架构和六边形的区别不在层数，在「谁依赖谁」。让业务定义接口、让技术实现接口，业务才能长期存活。判断题：换掉数据库要改业务代码吗？要，就是依赖没倒置。
2. **样板代码要「收税一次」**：泛型基类、代码生成器、脚手架都在做同一件事——把结构性重复消灭在基建层，让团队的每一行代码都是业务差异。
3. **模块自治是微服务的前置练习**：Nestier 的模块内声明路由与依赖（连认证都模块自持）、Nest course 的 microservice 案例——平时把模块边界划清楚，真到要拆微服务时只是「把模块换成服务」，mall→mall-swarm 的成本差异就是明证。

**七仓读毕，你的后端进阶闭环**：写接口（起点）→ 横切与权限（RuoYi/GVA）→ 业务复杂度与 MQ（mall）→ 分布式（mall-swarm）→ Nest 标准件（recipe/course）→ 架构组织（Nestier）。下一步建议：挑一个你自己的项目，把 RuoYi 的表规范 + Nestier 的模块边界 + recipe 的配置校验三件事先落地——进阶不在读多少，在改多少。

**上手建议**：跑起来后做两个实验：① 把 `product.module.ts:47-56` 的工厂换成一个内存假实现（返回写死数据），接口照常工作——亲测依赖倒置；② 删掉 `exclude` 那行（`product.module.ts:71`），体验 `/search` 从免登录变要登录——理解模块级路由声明的粒度。
