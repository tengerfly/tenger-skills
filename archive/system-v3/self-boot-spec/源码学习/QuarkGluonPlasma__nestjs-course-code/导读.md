## 01 · 精读：Nest 的 AOP 机制（aop-test）

**本章在全局的位置**：Nest 进阶的「任督二脉」——搞懂中间件/守卫/拦截器/管道/异常过滤器**各站在请求生命周期的哪个位置**，框架就再无黑魔法。

**前置知识**：AOP（面向切面）：业务逻辑不动，横切逻辑（日志、鉴权、异常处理）挂到统一的位置上。Nest 的五种横切件就是五个预留插槽。

**关键点讲解**：

1. **一个控制器同时挂四种件**（`aop-test/src/app.controller.ts:8-25`）：类上 `@UsePipes(ValidatePipe)`、方法上 `@UseGuards(LoginGuard)`，还有（注释掉的）`@UseInterceptors(TimeInterceptor)`——装饰器即可插拔开关，全局/控制器/方法三级都可挂。
2. **五个文件各司其职**：`log.middleware.ts`（最外层，Express 级）、`login.guard.ts`（守卫：进不进得来）、`time.interceptor.ts`（拦截器：请求/响应两段包夹）、`validate.pipe.ts`（管道：参数对不对）、`test.filter.ts`（异常过滤器：出错怎么回）。执行顺序 = 中间件 → 守卫 → 拦截器前段 → 管道 → **handler** → 拦截器后段 →（异常时）过滤器。**这张顺序表请背下来**——debug「为什么我的守卫没拦住」这类问题全靠它。
3. **对照你已见过的**：GVA 的 JWT+Casbin 中间件 = 这里守卫的职责；mall 的 GlobalExceptionHandler = 这里过滤器；RuoYi 的切面日志 = 这里拦截器。**Nest 是把 Java/Go 世界散落的横切件收编成了五个正式编制**。

## 02 · 精读：认证与权限（rbac-test + 双 token）

**本章在全局的位置**：RuoYi/mall/GVA 的权限你已见实物，这里补上**纯 Nest 的实现**——你会发现思路一样，零件不同。

**核心问题**：不用 Casbin 不用 Spring Security，Nest 从零实现 RBAC 要多少代码？答案是：两个守卫 + 一个装饰器。

**关键点讲解**：

1. **权限标记 = 元数据装饰器**（`rbac-test/src/custom-decorator.ts:3-5`）：`RequireLogin = () => SetMetadata('require-login', true)`、`RequirePermission = (...permissions) => SetMetadata('require-permission', permissions)`——接口上标 `@RequirePermission('ccc_xxx')` 就完成了权限声明，**声明与判定分离**。
2. **LoginGuard：验身份**（`rbac-test/src/login.guard.ts:31-53`）：`Reflector.getAllAndOverride('require-login', [类, 方法])` 读元数据（没标就放行）→ 取 `authorization` 头 → `jwtService.verify` → 把解出的 user 挂到 `request.user`（`:52`）。顺带学一手：`:8-15` 用 `declare module 'express'` 给 Request 做类型扩展——TS 模块扩充的教科书用法。
3. **PermissionGuard：验权限**（`rbac-test/src/permission.guard.ts:25-47`）：拿 `request.user.roles` → 查库展开每个角色的 permissions → reduce 拍平 → 与元数据里声明的所需权限逐项对账，缺一个就 401。`getAllAndOverride` 支持类级+方法级两级声明（`:34-37`，方法优先）。
4. **数据模型三层**（`rbac-test/src/user/entities/`）：User ↔ Role ↔ Permission 两个多对多——和 RuoYi 的 用户/角色/菜单、mall 的 管理员/角色/资源**同构**。三套语言、同一个 RBAC。
5. **双 token 方案**（`access_token_and_refresh_token/src/user/user.controller.ts:13-33`）：登录同时签发**短效 access_token + 长效 refresh_token**；`:37-62` 的 `/refresh` 接口校验 refresh_token 后**两个都重新签发**——access 过期就用 refresh 换新，只有两个都失效才要求重新登录。这是你在 RuoYi（Redis 滑动续期）和 GVA（缓冲期响应头续期）之外看到的**第三种续期流派：双 token 无状态续期**——不需要服务端存储，靠两种有效期错峰。
6. **同主题扩展案例**：`redis-session-test`（传统 session 方案对照）、`single-token-refresh`（单 token 续期）、`email-login-backend`（邮箱登录）、`qrcode-login`（扫码登录）、`acl-test`（ACL 与 RBAC 的差异）。

## 04 · 精读：通信与异步（MQ/微服务/定时/缓存）

**本章在全局的位置**：这组补齐 Nest 的「服务间与服务内异步」——mall 里的 RabbitMQ 和 mall-swarm 里的微服务，在 Nest 世界的对应物全在这。

**关键点讲解**：

1. **RabbitMQ 先玩原生**（`rabbitmq-test/src/`）：这组案例故意**不用 Nest 封装**，用原生 amqplib 演示四种交换机——`direct.js`+`direct-consumer1/2.js`（精确路由）、`fanout.js`（广播）、`topic.js`（模式匹配）、`headers.js`（头匹配）。对照 mall 的延迟关单（direct + 死信）：**先懂底层交换机，再看任何封装都不虚**。
2. **Nest 微服务雏形**（`microservice-test-user/src/main.ts:6-9`）：`NestFactory.createMicroservice<MicroserviceOptions>({ transport: Transport.TCP })` 把一个 Nest 应用变成 TCP 微服务；调用方（`microservice-test-main/src/app.controller.ts:15,22`）注入 `ClientProxy` 然后 `userClient.send('sum', numArr)`——**消息模式的方法调用**。对照 mall-swarm 的 Feign：Feign 是 HTTP 同步调用，Nest 微服务默认是消息式的 request-response。这是「微服务通信」的两种流派，都见过实物了。
3. **运行时动态定时任务**（`schedule-task/src/app.module.ts:23-33`）：`SchedulerRegistry` 可以在**运行中**遍历、删除、重建 cron 任务（`getCronJobs`/`deleteCronJob`）——对照 RuoYi 的 quartz 动态任务管理（界面改 cron 即时生效），Nest 这套就是它的地基。
4. **缓存拦截器**（`cache-manager-test/src/app.controller.ts:37` + `app.module.ts:10`）：`CacheModule.register` 接 Redis，`@UseInterceptors(MyCacheInterceptor)` 给接口加缓存——Nest 版的「注解式缓存」。自定义 `MyCacheInterceptor` 可以改 TTL/Key 策略。
5. **同主题扩展**：`chat-room-backend`（WebSocket 网关）、`sse-test`（SSE 推送）、`event-emitter-test`（进程内事件总线——单体里的「发布订阅」，比 MQ 轻一个量级）。
