## 1. 先复述你的目标

**我的理解：你想把自己的产品判断、架构经验、开发规范、交付经验和踩坑教训，变成一支可以反复调用、由你掌控的 AI 工程团队。它不只把代码写出来，还要把事情想清楚、把质量验明白、把软件交付出去、把运行问题收回来，让下一次做得更快、更稳，而且代码和整个过程你能看懂、能接管。**

这个复述来自原始设计与已记录决策，不是本次替你新增目标：

## 2. 这个仓库到底是什么

**tenger-skills 是 PEOS（个人工程体系）的流程与治理仓库，不是业务应用，也不是已经实现的无人值守调度平台。**

目前可以把它理解为三部分：

1. **工作说明与专业方法**：各个 `SKILL.md` 告诉执行 Agent 什么时候做、怎么做、交什么、何时停。
2. **共同规则和工作登记表**：约束跨阶段交接、授权、证据、状态和质量底线。
3. **可执行检查工具**：Python/PowerShell 检查规则和记录的一致性；任务预检只提出可否转换状态的只读计划。

实际工作仍由具备相应工具能力的 Agent 或人员执行。注册了发布 Skill，不代表仓库已经接好了部署平台；注册了运行 Workflow，不代表监控已自动安装到项目。

### 当前规模（2026-10-18 仓库快照）

- Skill 注册表：**45 个本地 Skill + 1 个外部知识库引用**。
- Workflow 注册表：**1 个总流程 + 7 个领域流程**。
- 状态注册表：6 种生命周期、68 个状态、126 条转换。
- 这些是内部规模，不是你需要背的使用步骤；45 个 Skill 不会每个任务都执行。
- 7 个领域 Workflow 是注册表中的组织关系，**不是 7 套独立可运行的工作流引擎**；产品域另有实际的 `prd-workflow` Skill。

依据：[Skill 注册表](../governance/skill-registry.yaml)、[Workflow 注册表](../governance/workflow-registry.yaml)、[状态注册表](../governance/state-registry.yaml)。

## 3. 六个层次：谁管什么

| 层次 | 主要位置/模块 | 做什么 | 不做什么 |
|---|---|---|---|
| 调度与治理 | `workflow/`、`shared/`、`governance/`、`scripts/` | 分流、记账、守门、校验、规定交接方式 | 不代替专业 Skill 交业务产物；不凭规则文件自授权限 |
| 知识与资产 | 本地 `skill-knowledge/` 引用层；外部 `skills-knowledge` | 检索/复用能力、Pattern、组合方案、适配器和模板 | 本仓引用层不复制外部资产明细或组件本体 |
| 产品与交付 | `PRD/`、`UI/`、`DEV/`、`Test/` | 把需求变成经验证的设计和代码 | 不擅自新增功能、重选技术或跳过验收 |
| 发布 | `Other/` 中 3 个发布 Skill | 计划、经授权部署、部署后验证 | 测试通过不等于允许动生产 |
| 运行观测 | 外部监控/日志仓库；信号采集 Skill | 接收错误、性能、日志、指标、行为信号 | 不代表外部系统已接入；缺数据不能伪造“运行正常” |
| 反馈与进化 | 分诊、复盘、巡检、Optimizer/Evolver 和问题池 | 当前项目修好、未来项目少犯同类错误 | 不未经授权修改外部仓库或无限自动改写规则 |

外部集成分工：`web-monitor` 面向前端错误、性能和行为；`server-log` 面向结构化服务日志与请求关联；`server-monitor` 面向主机/服务指标、心跳、拨测和告警。本次只核对本仓集成约定，没有验收这些外部仓库。

> 名称提示：Git 中编排目录的准确拼写是 `workflow/`；当前 Windows 磁盘可能显示 `WorkFlow/`。这是同一入口。跨平台引用应按 Git 路径，不另外建一份。

## 4. 整体流程：一个交付环 + 一个学习环

### 4.1 新项目的完整交付路径

下面是人读的流程概览，不是状态机的全部边；具体转换以注册表、产物有效性和授权为准。

```text
你的想法/请求
  → 入口分类 + 项目基线
  → 产品发现、研究、定义、范围决策
  → PRD ⇄ PRD 评审
  → 结构原型 ⇄ 原型评审
  → UI 设计稿 ⇄ UI 评审（按项目需要）
  → OSS 同域研究 + 可复用资产检索
  → 后端技术方案 ⇄ 技术评审
  → 前端技术方案 ⇄ 技术评审（按项目形态）
  → 开发 ⇄ 代码评审（前端另核验设计还原）
  → 分层测试 ⇄ 修复与回归
  → 发布计划 → 明确授权 → 部署 → 发布验证
  → 运行观察 → 发布复盘 → 完成或下一次任务
```

- `⇄` 表示产出、评审、裁决、修复、复核组成闭环，不是看到文件就进入下一步。
- 技术方案保留“写一个、审一个”；前后端实施是否可并行，要先核对依赖与授权范围，不默认并行。
- 无视觉设计需求的任务不必强加 UI 出稿；但既然约定了设计还原验收，就不能缺基准还声称通过。
- 已有产物可复用，前提是 manifest、证据、批准记录和 Gate 能证明覆盖本次范围。聊天里说“以前做过”不够。
- 没指定终点，默认只完成当前入口阶段后停下；“做到测试”不包含生产发布。

### 4.2 产品域为什么拆成十步

```text
想法登记 → 产品发现 → 竞品研究 → 产品定义 → 应用蓝图
→ 功能决策 → PRD 编写 → PRD 评审 → 原型制作 → 原型评审
```

拆分是在防止“AI 接到一句想法就编一份看似完整的 PRD”：

- 产品发现：这是谁的问题？问题有证据吗？
- 竞品研究：别人如何解决？证据和适用边界是什么？
- 产品定义：我们服务谁、提供什么价值、不做什么？
- 应用蓝图：用户旅程、业务对象、状态、权限和异常如何闭环？
- 功能决策：MVP 到底做哪些，哪些明确不做？
- PRD：把已确认的决策变成能开发、能测试的规格。

研究可以给建议，不能替你批准定位和范围。这十步是职责分解，不意味着每个小变更都新增十份长文档。

### 4.3 其他五种任务怎么走

| 模式 | 人话含义 | 典型路径 |
|---|---|---|
| CHANGE | 已有项目加/改功能 | 请求登记 → 影响分析 → 重做受影响的产品/设计/方案 → 开发评审 → 测试 → 按需发布与观察 |
| DEFECT | 已批准行为没有正确实现 | 分诊 → Bug-Fix 定位与修复委托 → 必要方案/开发 → 评审回归 → 按需发布 |
| REFACTOR | 默认不改变外部行为，改内部结构 | 基线/特征测试 → 重构计划 → 方案 → 实施评审 → 回归 → 按需发布 |
| INCIDENT | 线上高影响问题 | 信号分诊 → 经授权止损与恢复 → 验证恢复 → 永久修复任务 → 回归、发布、复盘 |
| OPTIMIZE | 性能、成本、体验或体系质量改进 | 可信基线/数据 → 影响与收益分析 → 优化或实验方案 → 实施验证 → 比较结果 |

发布和运行阶段只在本次明确范围内推进。事故移交需建立相应执行记录，不把原任务的生命周期偷偷改掉。

### 4.4 学习环：两种问题入口，不能只修当前项目

```text
入口 A：设计/代码评审、测试发现的问题
入口 B：运行日志、监控、用户行为、发布复盘发现的问题
                       ↓
          先修项目问题，并保存证据
                       ↓
        判断能否提炼为通用规则/资产/偏好
          ├─ 方法与流程问题 → issue/
          ├─ 可复用 Bug 模式 → bug-patterns/
          ├─ 偏好与进化信号 → evolution/
          └─ 可复用工程资产 → 外部 skills-knowledge（经授权）
                       ↓
         Skill-Optimizer / Skill-Evolver
                       ↓
       产出方增加预防规则 + 评审方增加检出方法
                       ↓
          验证改动、留痕、下一项目复用
```

仓库有这些能力入口和记录目录，不等于已经积累了成熟偏好模型。当前进化台账及已查看的偏好文件仍是骨架；不能宣称“系统已经自动学会你的习惯”。

## 5. 全部模块速查：45 个本地 Skill，各自干什么

下列使用 canonical ID；真实目录、历史别名以 Skill 注册表为准。输出是人读摘要，准确文件位置和契约看对应 Skill。

### 5.1 总控、入口和巡检（7 个）

| Skill | 职责与典型结果 |
|---|---|
| workflow | 选择路径、限定起终点、登记状态与交接、执行 Gate；不包办专业产物 |
| project-onboarding | 盘清运行方式、代码结构、测试、发布、日志监控和缺口，形成工程基线；不把旧行为自动当正确需求 |
| change-intake | 将自然语言请求登记为任务，明确模式、范围、责任人与未知项 |
| impact-analysis | 判断功能/接口/数据/权限/测试/发布/运行影响，决定哪些阶段要重做 |
| defect-triage | 区分真 Bug、需求变化、环境问题和事故，给出证据与路由 |
| refactor-planning | 定义行为不变边界、特征测试、迁移批次和回退方案 |
| quality-inspection | 定期或按需检查维护性、测试、依赖、架构漂移和运行质量，输出问题与下一任务，不自动改码 |

### 5.2 产品域（9 个，不含上表路由与下表原型）

| Skill | 职责与典型结果 |
|---|---|
| prd-workflow | 产品域编排，串起十阶段，处理缺输入和回退，不替代各原子 Skill |
| idea-intake | 想法、目标、未知项、证据边界的登记 |
| product-discovery | 用户/问题/场景与替代方案的发现简报 |
| competitive-analysis | 有来源、有日期、有适用边界的竞品与市场研究 |
| product-definition | 待确认的用户定位、价值、非目标和成功指标 |
| application-blueprint | 用户旅程、业务流程、对象、状态、权限和异常闭环 |
| feature-decision | MVP、优先级、依赖、成本风险、排除项及决策记录 |
| prd-design | v2 产品规格原子 Skill：把已批准内容写成可开发、可验收的 PRD（旧名 PRD-Design 为兼容别名） |
| prd-review | 独立只读评审：按审查对象加载四份 checklist，查完整性/一致性/可测性，输出问题清单；只审不改 |

### 5.3 原型和 UI（5 个）

| Skill | 职责与典型结果 |
|---|---|
| prototype-design | 从批准 PRD 生成结构原型与布局清单；虽放在 UI 目录，属于产品域主流程 |
| prototype-review | 检查页面覆盖、状态、文案、交互与异常闭环 |
| ui-ux-design | 依据原型和设计规范制作视觉设计稿；现行 Skill 支持 Superdesign/AI 自写两条路径，付费先确认 |
| ui-ux-review | 检查结构不越界、字段一致、视觉规范和真实渲染质量 |
| fidelity-review | 将实际前端与设计稿比对视觉、交互及长文案健壮性，可独立或协同代码评审/测试 |

**原型 = 结构基线；设计稿 = 视觉基准。** 不能拿原型代替已有设计稿证明视觉还原。浏览器缺失时，不能用读 HTML 代替真实截图验收。

### 5.4 方案、实现和代码评审（6 个）

| Skill | 职责与典型结果 |
|---|---|
| backend-tech-design | 后端架构、模型、接口、约束与实现计划，产出 TDD（此处指技术设计文档） |
| frontend-tech-design | 前端页面、组件、状态、接口契约和技术选型，产出 FTDD |
| tech-review | 方案对需求、前后端契约、状态及数据流的独立评审 |
| backend-dev | 按批准方案与资产决策实现后端，交运行、测试和变更证据 |
| frontend-dev | 按 PRD、FTDD、原型与设计稿实现前端，核对接口及真实页面 |
| code-review | 代码质量、需求承接、接口、复用、风险检查；前端合并还原度问题清单 |

### 5.5 测试与修复（2 个）

| Skill | 职责与典型结果 |
|---|---|
| auto-test | 唯一测试入口：分层验收、可重复用例、证据、缺陷任务卡、修复后新证据回归及覆盖边界声明 |
| bug-fix | 证据驱动的根因定位、修复计划与委托闭环；不取代开发 Skill 改码，也不取代测试做深度验收 |

`Testing` 自 2026-09-22 退出活跃入口，旧名称映射 auto-test；历史方法与资源保留在 `Test/Testing/ARCHIVED.md`，不再执行备用测试流程。

### 5.6 发布（3 个）

| Skill | 职责与典型结果 |
|---|---|
| release-planning | 汇总版本、范围、发布步骤、回滚条件、观察指标和审批要求 |
| deployment-execution | 只按批准计划和环境范围执行部署，保存执行结果 |
| release-verification | 验证健康、关键旅程、遥测与版本，给继续/暂停/回滚建议；建议不是授权 |

### 5.7 运行与复盘（6 个）

| Skill | 职责与典型结果 |
|---|---|
| signal-collection | 采集并脱敏运行信号，关联版本、commit、请求/trace/session 等标识 |
| signal-triage | 对信号去重、定级，分到事故、缺陷、变更或优化 |
| incident-response | 经授权止损恢复、记录时间线、验证恢复，不把临时止损当永久修复 |
| product-analytics | 按产品目标和行为数据判断效果，区分有效结论与证据不足 |
| optimization-planning | 给出优化基线、收益目标、保护指标、实验和验证计划 |
| post-release-review | 比较上线前假设与上线后结果，形成后续行动和关闭依据 |

### 5.8 研究、学习与体系改进（7 个，含独立分享包）

| Skill | 职责与典型结果 |
|---|---|
| oss-radar | 技术方案前同域开源研究，也可研究体系改进情报；记录版本、证据、采用/借鉴/不采用边界 |
| fact-check | 将待采纳结论拆成断言并核验，不把 AI 回答直接当事实 |
| source-reading | 源码流程图和关键实现导读，帮助你真正看懂源码，不修改被学习源码 |
| essence-distill | 将学习材料提炼为可追溯、带原文锚点与适用边界的精华 |
| skill-optimizer | 问题池管理、记录/挖掘/优化/体检的调度与标准管理 |
| skill-lifecycle | `Skill/` 中可独立复制的创建、反馈记录、确认后个性化迭代包；不接管原工程流程 |
| skill-evolver | 从真实轨迹提炼信号和偏好，诊断并提出改进；默认逐条确认后执行、留台账可回滚 |

## 6. 支撑目录不是多余模块：各有一个明确职责

| 位置 | 用途 | 你什么时候看 |
|---|---|---|
| shared/ | Gate、防死循环、产物、生命周期、证据、浏览器、OSS 等共同契约与模板 | 遇到规则冲突或要改跨域行为时 |
| governance/skill-registry.yaml | Skill 身份、路径、别名、角色 | 找准确 Skill 入口时 |
| governance/workflow-registry.yaml | 总流程与领域成员关系 | 看流程分工时 |
| governance/state-registry.yaml | 合法状态转换、执行者、证据和失败路线 | 解释为什么不能进入下一阶段时 |
| governance/artifact-registry.yaml | 产物类型与约束 | 登记和消费产物时 |
| governance/knowledge-registry.yaml | 外部知识库依赖及缺失策略 | 判断是否降级、能否证明资产检索时 |
| governance/schemas/ | 描述型 YAML 结构约定，跨文件语义由 Python 实现 | 维护校验器时；不是直接可用的 JSON Schema |
| scripts/ | 初始化环境、回归测试、体系校验、只读任务预检 | 验证仓库或状态转换时 |
| .github/workflows/ | Windows/Linux CI 配置 | 维护持续验证时；有配置不等于远端已运行 |
| 项目仓库的 .spec/ | 当前项目产物、批准、证据、状态与追踪 | 日常看进度、交接、恢复时 |
| 本仓库的 .spec/ | 本体系自身治理记录以及历史研究产物 | 验收工程体系本身时，不存其他业务项目的状态 |
| issue/ | Skill 方法/流程问题池 | 优化工作方式时 |
| bug-patterns/ | 真实 Bug 的可复用错误模式 | 预防重复工程问题时 |
| evolution/ | 信号、偏好和进化台账 | 检查“学到了什么、为什么改”时 |
| chats/ | 会话材料约定与归档入口 | 有授权地回顾执行轨迹时 |
| docs/ | 人读说明、计划、研究 | 了解体系；不作为自动运行时加载入口 |
| .codebuddy/memory/ | 历史宿主记忆 | 仅作历史线索，旧规则不覆盖现行契约 |

每个 Skill 内部：`SKILL.md` 是执行入口，`README.md` 是人读导航，`CONTEXT.md` 是历史决策和待决项，`references/` 是按需细则，`assets/` 是模板/资源。不是每次都需要把所有文件加载一遍。

## 7. 你只需掌握的治理概念

| 名称 | 人话解释 |
|---|---|
| manifest | 交付物目录：是什么、在哪、谁产出、什么状态、依据是什么 |
| workflow | 当前进度表：在什么阶段、能不能继续、卡在哪、下一步谁做 |
| traceability | 关联账：需求对应什么实现、测试、版本和运行问题 |
| decision | 真实决策记录：谁在什么范围内批准了什么，而不是 AI 自己填一个 APPROVED |
| evidence | 本轮真实文件、命令、报告、截图、日志和摘要，说明为什么相信结论 |
| task envelope | 本次原子任务的范围单：项目、执行批次、版本、输入、授权、允许路径、期望输出和交接条件 |
| Gate | 放不放行：PASS / CONDITIONAL / BLOCKED，与阶段状态分开 |

正常使用时应由执行方整理这些记录，你主要确认目标、范围和决策，不需要手工维护所有 YAML。但这是**工作分工约定**，不是仓库已实现了自动记账服务。

## 9. 有没有偏离你的目标？逐项核对，而不是一句“完全没偏”

**判断：整体方向与原始目标一致；但“是否过重、哪些旧行为允许改变”仍需你裁决，且闭环效果尚未通过真实项目证明。**

| 设计变化/现状 | 对目标的帮助 | 需要你关注的偏移风险 |
|---|---|---|
| 从线性开发链扩到六种生命周期、发布和运行反馈 | 对齐从想法到上线后持续改进 | 不能让每个小任务都跑完整全链 |
| PRD 前拆出发现、定义、蓝图和功能决策 | 减少 AI 编需求、提前暴露取舍 | 有有效基线时应复用，不重复问答和造文档 |
| 增加 manifest、状态机、任务范围、授权与摘要 | 降低遗忘、假完成和错误交接 | 维护负担是否超过节约的返工，尚需试跑衡量 |
| 三轮后不再强制放行 | 保住质量底线和你的风险决定权 | 与历史“清 P0 后残留 P1 放行”不同，应明确接受这项变化 |
| 当前 Workflow 允许依赖满足后的前后端并行 | 可能提高效率 | 历史偏好强调串行“写一个审一个”；是否保留默认串行需你确认 |
| 外部知识库缺失时 warn-and-degrade | 避免完全离线时校验全部不可用 | 不能把降级通过说成已满足“先检索后实现/防重复造轮子”；必需资产缺失仍应阻塞相关任务 |
| 偏好与 Skill 进化机制 | 让工具越来越符合你的习惯 | 不应把少量反馈泛化为永久偏好，更不能未经确认重写规则 |
| 保留历史材料与兼容入口 | 防止经验丢失、一次性推翻旧体系 | 旧记忆/旧指南仍有冲突表述，使用者可能读错权威版本 |
| 把部署与监控纳入体系 | 对齐可回滚、可观测交付 | 只有流程定义，不能包装成完整接入和自动运维能力 |

### 建议由你确认的四项（本次未替你批准）

1. **目标不变**：核心成果是更稳、更可控、可复用的软件交付，而不是更多 Skill/文档。
2. **默认操作方式**：单入口、明确终点、阶段摘要；小任务按影响裁剪，不跳质量/授权底线。
3. **三轮后的行为**：不强制放行；P0 阻塞，残留 P1 只能由你或授权人明确接受风险后 CONDITIONAL。
4. **并行策略**：是否继续默认“串行写一个审一个”，只有你明确允许且依赖满足才并行；这是建议确认项，不是本文已修改的现行规则。

### 用什么证明“没有越做越偏”

下一步不建议继续扩模块，先用真实项目验证：

- 用一个熟悉项目的小功能走 CHANGE 路径：能否正确复用基线、范围不膨胀？
- 中断并换会话：能否只靠落盘资料恢复，而不让你重讲背景？
- 放入一个已知问题：能否被评审/测试检出，修复后用新证据复核？
- 遇到旧证据、缺授权、外部依赖缺失：能否如实停止或声明降级？
- 完成后：重复返工、你手工补上下文的次数、关键决策耗时是否下降？
- 经授权再覆盖发布和观测闭环；本地代码验证不能替代线上验证。

这才是你要的“工程体系有效”，而不是图画得完整或脚本全绿。
