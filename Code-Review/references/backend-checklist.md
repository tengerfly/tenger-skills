# 后端代码评审检查清单

> 用途：后端代码评审视角的逐条检查项。评审时**逐条对照执行**，命中一条记一条，标注 `文件:行` 与严重度。
> 立场：只审「后端代码能否对齐 TDD 接口 / 表结构且内部一致」，不评业务逻辑正确性。
> 用法：每组末尾的 `Ask` 是提问式引导——先问自己这个问题，答案即为命中判据。

## A. 接口契约（后端侧）

- [ ] A1 后端实现的接口路径 / 方法与 TDD「接口清单」一致（`GET /api/users`、`POST /api/users/:id`…）
- [ ] A2 每个接口的**入参个数**与 TDD 一致，无多余 / 缺失参数
- [ ] A3 入参类型与 TDD 一致（DTO 字段类型、可选 / 必填、`@IsOptional` / `@IsNotEmpty`）
- [ ] A4 出参字段与 TDD 一致（返回结构、字段名、嵌套结构）
- [ ] A5 错误码与 TDD「错误码分段」一致（1xxx 参数 / 2xxx 业务 / 3xxx 权限 / 5xxx 系统）
- [ ] A6 分页结构统一（`{ list, total }`），与 TDD / FTDD 一致
- [ ] A7 枚举值定义与 TDD 一致，且收敛在共享包 / 常量，不散落裸字符串
- [ ] A8 共享 DTO / 类型放 `libs/shared`，未在业务服务里重复定义一份

> Ask：这个接口的每个字段，后端定义与 TDD 是否逐一对应？有没有一端多、一端少？

## B. 可运行性（静态验证）

- [ ] B1 `pnpm install` 成功，依赖可解析
- [ ] B2 `tsc --noEmit`（或 `pnpm build`）无类型错误
- [ ] B3 `pnpm test` 全绿（跑不了 → 标注「未取证」，不写「通过」）
- [ ] B4 `pnpm lint` 通过（eslint / commitlint 门禁）

## C. 架构合规（四层分层 + 微服务边界）

- [ ] C1 Controller 只做路由 / 参数校验 / 调用 Service，不写业务逻辑、不碰 SQL
- [ ] C2 Service 只写业务逻辑与事务编排，不碰传输层、不写 SQL
- [ ] C3 Repository 是唯一出现 SQL / ORM 的层
- [ ] C4 Entity / Model 只做数据载体，不含业务逻辑
- [ ] C5 依赖单向向下：Controller → Service → Repository → Entity，无跨层调用、无反向依赖
- [ ] C6 服务间只通过对外接口通信，无跨服务直连数据库
- [ ] C7 无跨服务 import 对方内部实现（Repository / Entity）
- [ ] C8 无服务间循环依赖（必要时抽 `libs/shared` 或事件解耦）
- [ ] C9 服务边界与 TDD「模块边界」一致，表归属服务明确

> Ask：哪个层出现了不属于它的职责（Controller 里的 SQL、Service 里的 HTTP、Repository 里的业务判断）？

## D. 数据模型

- [ ] D1 Entity 字段与 TDD「表结构设计」逐字段一致（名称 / 类型 / 约束 / 索引 / 注释）
- [ ] D2 金额用整数（分），无浮点
- [ ] D3 时间 / 枚举 / 软删除 `deleted_at` 约定照搬 TDD
- [ ] D4 建表迁移脚本可重复执行、可版本管理（Prisma migrate / TypeORM migration / SQL）
- [ ] D5 无跨服务表访问（表归属唯一服务，跨服务走接口）

## E. 异常处理与统一响应

- [ ] E1 统一响应结构 `{ code, message, data }`，业务错误与系统错误分段
- [ ] E2 无空 catch 吞异常（异常要么处理、要么上抛）
- [ ] E3 错误信息对用户友好、对日志可追踪（trace_id）
- [ ] E4 入口层格式校验（class-validator + DTO）+ Service 层业务校验，双保险但不重复
- [ ] E5 异步错误有兜底（未处理的 Promise rejection / 事件回调异常不静默丢失）

> Ask：这个操作失败时，调用方知道出了什么事吗？日志里有足够上下文排查吗？

## F. 事务 / 幂等 / 并发与竞态

- [ ] F1 多步写操作有事务包裹，失败可回滚
- [ ] F2 关键写接口有幂等设计（幂等键 / 防重复提交）
- [ ] F3 并发场景（库存扣减、余额变更）有并发控制（乐观锁 / 悲观锁 / 原子操作）
- [ ] F4 关键技术点（事务 / 并发 / 缓存 / 幂等）实现与 TDD 方案一致
- [ ] F5 **Check-then-act / TOCTOU**：先查后写（余额校验→扣减、存在性检查→插入）必须原子化（唯一约束 / 条件更新 / 行锁），禁「查完再写」两段式
- [ ] F6 **乐观锁**：并发更新的记录带 `version` / `updated_at` 校验，更新语句包含版本条件，冲突有重试或明确失败
- [ ] F7 **分布式锁**：跨实例共享资源（定时任务、批处理）有锁，且锁有超时与持有者校验，不裸锁
- [ ] F8 **计数器原子性**：计数 / 库存用 `SET x = x + 1` 类原子更新，不用「读出来加一再写回」
- [ ] F9 **缓存一致性**：写操作有对应的失效 / 更新顺序，无「写库不删缓存」导致脏读；缓存击穿 / 雪崩有防护

> Ask：两个请求同时打到这段代码会发生什么？从检查到写入之间，状态可能被改掉吗？

## G. 代码质量

- [ ] G1 函数短小、单一职责，无巨型函数
- [ ] G2 命名自解释（业务语言），无 `a` / `b` / `tmp` / `data` 无意义名
- [ ] G3 无魔法值，状态 / 枚举 / 错误码一律常量 / 枚举定义
- [ ] G4 注释讲「为什么」（设计意图 / 业务规则 / 边界 / 取舍），不重复代码
- [ ] G5 方法有传参时，注释逐个写明参数作用与约束
- [ ] G6 配置外置（环境变量 / 配置文件），无硬编码连接串 / 密钥

> Ask：把这个函数名讲给别人，他能猜到里面做了什么吗？命名难，是不是抽象错了？

## H. 安全与数据

- [ ] H1 入口层有参数校验（格式 / 类型 / 必填）
- [ ] H2 敏感接口有鉴权，无未授权可访问的写接口
- [ ] H3 ORM / 参数化查询防 SQL 注入，无字符串拼接 SQL
- [ ] H4 敏感字段脱敏 / 不出参（密码 / 密钥 / 手机号掩码）
- [ ] H5 **SSRF**：用户可控 URL 发起外部请求时有域名白名单，禁直连内网地址
- [ ] H6 **路径穿越**：文件 / 路径参数先规范化再校验，禁 `../` 越权读写
- [ ] H7 **越权（IDOR）/ 多租户**：按资源归属校验（租户 / 属主维度），不信任客户端传来的 id / role / tenantId
- [ ] H8 **反序列化 / 原型污染**：不开不安全反序列化；合并用户对象时防 `__proto__` / 原型链污染
- [ ] H9 **加密与凭据**：密码用 bcrypt / argon2（禁 MD5 / SHA1 存密）；Token 校验签名、过期与签发方；密钥不入代码与日志
- [ ] H10 **资源耗尽**：正则防 ReDoS，循环 / 递归 / 缓冲有界，外部调用有限流与超时

> Ask：这个入参如果被恶意构造（超长 / 特殊字符 / 指向内网 URL / 他人 id），会发生什么？

## I. 测试闭环（不评业务覆盖）

- [ ] I1 测试先行（测试文件与实现同批次产出，非事后补）
- [ ] I2 测试标注 AC 编号（承接 TDD 测试用例）
- [ ] I3 `pnpm test` 可运行且全绿（不可运行 → 记 P1，标注未取证）

## J. 需求闭环（AC 承接）

- [ ] J1 TDD 接口清单中的每个接口都有后端实现（无漏做）
- [ ] J2 后端实现的每个接口都能追溯到 AC / TDD 需求（无凭空实现）
- [ ] J3 每个业务模块的 AC 有对应 Service / Controller 承接（结构性，不评对错）

## K. 性能与缓存

- [ ] K1 无 N+1：循环内单条查询 → 批量 / `IN` / join
- [ ] K2 热点路径无重复重开销：正则编译 / JSON 解析 / 加密运算不进循环
- [ ] K3 查询走索引、不无脑 `SELECT *`，大结果集强制分页
- [ ] K4 缓存有 TTL 与失效策略、键唯一，不把用户私有数据缓存到全局键
- [ ] K5 内存有界：集合 / 缓冲设上限，大文件流式处理，循环内不拼大字符串
- [ ] K6 外部调用有超时 / 重试 / 限流，不阻塞请求主链路

> Ask：数据量涨 10 倍 / 100 倍时这段还成立吗？能否批量化？这段结果可缓存吗、该缓存吗？

## L. 边界条件

- [ ] L1 `null` / `undefined`：可能为空的对象不做无保护链式取值
- [ ] L2 假值陷阱：`if (value)` 前确认 `0` / `""` / `false` 是否是合法值
- [ ] L3 空集合：`arr[0]`、首/末元素、`for...in` 前判长度，空集合有分支
- [ ] L4 数值边界：除零、超安全整数、负数、浮点用 epsilon 比较、分页 / 切片 off-by-one
- [ ] L5 字符串边界：空串、纯空白、超长文本、Unicode（emoji / 组合字符 / RTL）
- [ ] L6 分页边界：`page` / `pageSize` 越界与非法值、`total` 为 0、超大数据量下的行为

> Ask：这个值是 null / 0 / 空数组 / 负数 / 最大值时，分别会怎样？

## M. 删除候选与清理

> 目的：AI 写的代码常留死代码与无用依赖。本节判定「有没有该删的」，并区分能否安全删。

- [ ] M1 死代码：无引用 / 不可达 / 永不调用的函数、分支、导出
- [ ] M2 未用依赖：`package.json` 中无实际引用的包
- [ ] M3 关闭的 feature flag / 兼容旧版的残留分支
- [ ] M4 重复实现：同一能力存在两份实现（应合并为一处）
- [ ] M5 调试残留：注释掉的代码块、`console.log`、临时开关
- [ ] M6 清理计划：区分「**现在可安全删**」（无消费方、有测试覆盖）与「**需延后**」（有活跃消费方 / 需迁移）——后者按 `removal-plan-template.md` 出计划（前置条件 / 迁移步骤 / 验证与回滚）

> Ask：这段代码删掉会影响谁？有活跃消费方吗？删了怎么验证没事？
