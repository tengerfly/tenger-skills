# 前端代码评审检查清单

> 用途：前端代码评审视角的逐条检查项。评审时**逐条对照执行**，命中一条记一条，标注 `文件:行` 与严重度。
> 立场：只审「前端代码能否对齐 FTDD fetch / 原型且内部一致」，不评业务逻辑正确性。
> 用法：每组末尾的 `Ask` 是提问式引导——先问自己这个问题，答案即为命中判据。

## A. 接口契约（前端侧 fetch）

- [ ] A1 api 方法路径 / 方法与 FTDD「fetch 对接表」一致
- [ ] A2 每个 fetch 的**入参个数**与后端契约一致，无多传 / 漏传
- [ ] A3 入参类型与契约一致（字段名 / 类型 / 可选性）
- [ ] A4 出参消费字段与后端返回一致（后端返回的字段有消费，不消费孤儿字段）
- [ ] A5 错误码处理与后端契约一致（401 / 业务错误码分支）
- [ ] A6 分页结构消费与后端一致（`{ list, total }`）
- [ ] A7 枚举 / 状态值与后端一致，未在前端另写一套
- [ ] A8 共享类型 `import type` 引用（monorepo），未重复定义一份

> Ask：这个 fetch 的入参与后端契约逐字段对得上吗？后端返回的字段都用到了吗？

## B. 可运行性（静态验证）

- [ ] B1 `pnpm install` 成功，依赖可解析
- [ ] B2 `tsc --noEmit`（或 `pnpm build`）无类型错误
- [ ] B3 `pnpm test` 全绿（跑不了 → 标注「未取证」）
- [ ] B4 `pnpm lint` / `stylelint` 通过

## C. 架构合规（分层 + 组件抽离）

- [ ] C1 页面容器只做编排，不写复杂业务逻辑
- [ ] C2 业务逻辑下沉 hooks，组件只渲染与绑定
- [ ] C3 依赖单向：页面容器 → 组件 → hooks → api，无反向依赖
- [ ] C4 业务组件不直接 import 业务 api（数据流经 hooks → props）
- [ ] C5 同模块内 ≥2 处复用的 UI 已抽到 `features/<模块>/components/`
- [ ] C6 跨模块共用的组件已提升到 `src/components/`，无模块私有副本残留
- [ ] C7 无复制粘贴残留（同一段 UI / 逻辑无两份实现）
- [ ] C8 目录结构与 FTDD §6 一致

> Ask：这个组件里有几件事？超过一件，是否该拆组件或把逻辑下沉到 hooks？

## D. 还原（双基准：结构对原型、视觉对设计稿）

- [ ] D1 页面结构 / 布局骨架与**原型**一致（区块无缺失、无多余）
- [ ] D2 间距 / 配色 / 字号 / 圆角 / 阴影与**设计稿**一致（有设计稿时；原型不作视觉基准）
- [ ] D3 颜色 / 间距 / 字号收敛为设计 token（`variables`），无逐处写死色值；**有设计稿时 token 与 design-system §7 对账无缺项/错值**
- [ ] D4 交互与三态（加载 / 空 / 错误）齐全
- [ ] D5 还原度证据以「设计稿 ↔ 实现」并排截图为准（有设计稿时）；仅与原型比对视觉 = 未完成（详见 `Fidelity-Review`）

## E. hooks 数据流

- [ ] E1 数据获取 hook 返回 `{ data/list, loading, error, refetch }` 三态齐全
- [ ] E2 组件据此渲染三态，无缺空态 / 错误态 / 加载态
- [ ] E3 请求竞态有处理（取消 / 防抖 / 序列号）

> Ask：请求失败 / 返回慢 / 返回空时，界面分别长什么样？会不会显示上一次的数据？

## F. 异常 / 错误处理

- [ ] F1 请求失败有用户可见反馈，无静默失败
- [ ] F2 401 有统一处理（跳登录 / 刷新 token）
- [ ] F3 ErrorBoundary 兜底，无白屏
- [ ] F4 空态 / 错误态可恢复（重试 / 返回）

> Ask：这个操作失败时用户知道吗？他知道可以怎么办吗？

## G. 代码质量

- [ ] G1 组件 / 函数短小、单一职责（超 ~80 行即拆）
- [ ] G2 命名自解释（业务语言），无 `a` / `b` / `data` / `temp`
- [ ] G3 TypeScript 严格：props / state / 返回全量类型，禁 `any`、禁 `@ts-ignore`
- [ ] G4 无魔法值，枚举 / 状态 / 常量提取定义
- [ ] G5 注释简单易懂、讲「为什么」，一条注释一行；传参必注 `@param`
- [ ] G6 样式引用 CSS 变量，不写死

## H. 安全

- [ ] H1 用户输入渲染防 XSS（不 `dangerouslySetInnerHTML` 直接注入不可信内容）
- [ ] H2 token / 敏感信息不入 localStorage 明文（按 FTDD 约定）
- [ ] H3 环境变量管理（baseURL 等），无密钥硬编码进代码
- [ ] H4 越权前置收敛：按钮 / 路由 / 数据按权限渲染（前端不可信，但仍须收敛 UI，不靠前端隐藏当安全）
- [ ] H5 危险注入面：`JSON.parse` 后合并用户对象防 `__proto__` 污染；`postMessage` 校验来源；URL 参数/跳转地址防开放重定向

> Ask：把这里的 id 换成别人的 id，能看到别人的数据吗？这个跳转地址能被改成外站吗？

## I. 测试闭环（不评业务覆盖）

- [ ] I1 测试先行（`.test.tsx` 与实现同批次产出）
- [ ] I2 测试标注 `TC-Mxx-nnn` ↔ `AC-Mxx-nnn` 编号
- [ ] I3 `pnpm test` 可运行且全绿（不可运行 → 记 P1，标注未取证）

## J. 需求闭环（AC 承接）

- [ ] J1 FTDD 页面清单中的每个页面都有实现（无漏做）
- [ ] J2 实现的每个页面 / 模块都能追溯到 FTDD / 原型（无凭空实现）
- [ ] J3 每个页面关键交互有对应组件 / hooks 承接（结构性，不评对错）

## K. 性能与渲染

- [ ] K1 大列表有虚拟化 / 分页 / 懒加载，不一次性渲染上千条
- [ ] K2 列表 `key` 稳定唯一（可重排场景禁用数组下标作 key）
- [ ] K3 无重复渲染：`memo` / `useMemo` / `useCallback` 用在实测瓶颈处，不无脑包裹
- [ ] K4 重计算不进渲染路径；高频事件（滚动 / 输入 / resize）有防抖节流
- [ ] K5 路由级懒加载 + 大依赖按需引入（不整包 import）
- [ ] K6 图片 / 资源尺寸合理、懒加载，不阻塞首屏

> Ask：这个列表有 1000 条时会怎样？每次输入都会发请求吗？这段计算每个 render 都跑一次吗？

## L. 边界与长内容

- [ ] L1 空数组 / 空对象：列表空态、`arr[0]`、可选字段访问有保护
- [ ] L2 超长文本：标题 / 描述 / 用户名极端长时不溢出、不撑破布局（省略 / 换行约束）
- [ ] L3 数值边界：`0` / 负数 / 超大数 / 小数位的展示正确（金额千分位、百分比、计数）
- [ ] L4 空值渲染：`null` / `undefined` / 空串不渲染出 `NaN` / `undefined` 字样
- [ ] L5 时间与格式：日期时间按约定格式化，不直接展示 ISO 原始串

> Ask：这里的文案换成 3 倍长会怎样？数值为 0 / 负数 / null 时会显示成什么？

## M. 删除候选与清理

> 目的：AI 写的代码常留死组件与无用样式。本节判定「有没有该删的」，并区分能否安全删。

- [ ] M1 死组件 / 死 hooks / 死工具函数（无引用）
- [ ] M2 未用依赖与样式（`package.json` / 样式文件中无引用的类）
- [ ] M3 调试残留：注释掉的 JSX、`console.log`、`debugger`
- [ ] M4 重复组件：同能力两份实现（应合并到 `src/components/`）
- [ ] M5 清理计划：区分「**现在可安全删**」与「**需延后**」（有活跃页面使用 / 需迁移）——后者按 `removal-plan-template.md` 出计划

> Ask：这个组件 / 样式删掉会影响哪个页面？有页面还在用吗？
