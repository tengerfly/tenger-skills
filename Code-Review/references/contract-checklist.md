# 接口契约一致性检查清单（核心）

> 用途：本 Skill 的**核心专项**。逐接口做三方比对：**前端 fetch ↔ 后端实现 ↔ 共享类型**。
> 比对基准：TDD「接口清单」+ FTDD「fetch 对接表」+ `libs/shared` 类型定义。
> 命中项归因：前端调的接口后端没实现 → **后端**；后端字段前端没消费 → **前端**；两端字段不一致 → **双方**。

## 0. 比对方法

1. 从 TDD / 后端代码抽取**后端接口清单**（路径 + 方法 + 入参 + 出参）；
2. 从 FTDD / 前端代码抽取**前端 fetch 清单**（路径 + 方法 + 入参 + 出参）；
3. 逐接口三方比对，字段级核对（入参个数、字段名、类型、可选性、嵌套结构）。

## 1. 接口清单完整性

- [ ] 1.1 前端调的每个接口，后端都有对应实现（无"前端调了个不存在的接口"）
- [ ] 1.2 后端定义的每个接口，前端都有消费（或明确标注为对外预留）
- [ ] 1.3 接口总数前后端一致，无单边多出 / 缺失

## 2. 路径 / 方法一致（P0）

- [ ] 2.1 路径逐字符一致（`/api/users` ≠ `/api/user`、`/api/orders/:id` ≠ `/api/orders/{id}`）
- [ ] 2.2 HTTP 方法一致（`GET` vs `POST`、`PUT` vs `PATCH`）
- [ ] 2.3 路径参数 / 查询参数 / 请求体归属一致（参数放 URL 还是 body）

## 3. 入参个数与类型一致（P0，头号目标）

- [ ] 3.1 **入参个数一致**：后端接口入参 3 个，前端只传 2 个（或反之）= P0
- [ ] 3.2 参数名一致，**大小写敏感**（`orderNo` vs `order_id`、`userId` vs `uid`、`A` vs `a`）
- [ ] 3.3 参数类型一致（`number` vs `string`、`string` vs `array`）
- [ ] 3.4 必填 / 可选一致（后端 `@IsNotEmpty` 的前端有传，后端可空的前端不强制）
- [ ] 3.5 嵌套结构一致（`{ user: { id } }` vs `{ userId }`）

## 4. 出参字段一致（P0）

- [ ] 4.1 返回字段名一致，**大小写敏感**（后端返回 `orderNo`，前端按 `order_no` 或 `orderno` 取值 = 取不到）
- [ ] 4.2 返回字段类型一致（`number` vs `string`，前端直接 `toFixed` 会崩）
- [ ] 4.3 返回结构一致（`{ list, total }` vs `{ data: { list, count } }`）
- [ ] 4.4 后端返回的字段前端有消费，前端期待的字段后端有返回（无孤儿字段、无取空值）

## 5. 枚举 / 状态值一致（P0）

- [ ] 5.1 状态枚举值前后端一致（`"pending"` vs `"PENDING"`、`1/2/3` vs `"1"/"2"/"3"`）
- [ ] 5.2 枚举值收敛在共享包 / 常量，前后端引用同一份，未各写一套
- [ ] 5.3 前端对枚举的渲染映射（状态 → 标签）覆盖后端全部枚举值，无未处理状态

## 6. 分页 / 时间 / 金额格式一致（P1）

- [ ] 6.1 分页结构一致（统一 `{ list, total }`，页码 / 页大小参数名一致）
- [ ] 6.2 时间格式一致（`ISO8601` vs 时间戳 vs `YYYY-MM-DD HH:mm:ss`）
- [ ] 6.3 金额单位一致（后端整数分，前端按分渲染，不按元 / 浮点）
- [ ] 6.4 空值约定一致（`null` vs `undefined` vs `""`）

## 7. 错误码与错误处理一致（P1）

- [ ] 7.1 后端错误码分段（1xxx / 2xxx / 3xxx / 5xxx）前端有对应处理分支
- [ ] 7.2 前端对 `401` 有统一处理（跳登录 / 刷新）
- [ ] 7.3 业务错误码 → 前端提示文案的映射完整，无"错误码无人认领"

## 8. 共享类型单一来源（P0）

- [ ] 8.1 接口请求 / 响应类型定义在 `libs/shared`（或等价共享包），前端 `import type` 引用
- [ ] 8.2 前后端未各自重复定义同一份 DTO / 类型
- [ ] 8.3 共享类型被修改后，前后端是否同步更新（类型漂移 = 各写一份的前兆）

## 9. 鉴权 / 环境契约（P1）

- [ ] 9.1 token 传递方式一致（请求头字段名 `Authorization` / `X-Token` 前后端一致）
- [ ] 9.2 baseURL / 代理 / 环境变量一致（前端请求路径与后端挂载前缀对得上，无 `/api` 前缀缺失 / 重复）
- [ ] 9.3 跨域处理一致（CORS 配置与前端域名对得上）

## 10. 术语字段一致性（大小写 / 命名风格 / 同义词，P0）

> 用户明确要求：防止前端写 `A` 后端写 `a` 这类字段术语漂移导致的联调错误。

- [ ] 10.1 同一字段**大小写一致**：前端 `A` 后端 `a` = P0；`orderNo` vs `orderno` = P0
- [ ] 10.2 **命名风格统一**：驼峰 / 下划线 / 帕斯卡全项目唯一（如统一 `orderNo`，禁止混用 `order_no` / `OrderNo`）
- [ ] 10.3 **同义异名消除**：同一业务字段只用一词（`userId` vs `uid`、`total` vs `count`、`name` vs `title`，二选一且全链路统一）
- [ ] 10.4 **术语单一权威源**：字段名以 TDD 接口清单 / 共享类型为准，前后端统一 `import type` 引用，不各自造名
- [ ] 10.5 **状态 / 枚举词表唯一映射**：`已支付` ↔ `paid` 语义映射唯一，前端渲染与后端枚举一一对应
