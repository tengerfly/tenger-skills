# 代码评审 Skill

> **定位**：只审不改（P0 附「建议补丁」，仅写报告、不落盘源码）。找出后端/前端代码里"接口对不上、字段不一致、跑不起来、架构越界"的点，记录成文档，不替用户改代码。
> **术语**：TDD = 后端技术文档；FTDD = 前端技术文档；AC = PRD 模块验收标准编号（`AC-Mxx-nnn`）。

## 一、这是什么

本 Skill 是一个 **代码检测器**。它不改代码，只审代码：把 `Backend-Dev` 产出的后端代码与 `Frontend-Dev` 产出的前端代码，分别以 **后端代码评审** 与 **前端代码评审** 两个视角，对照 **PRD（AC）/ 原型 / TDD / FTDD** 逐一评审，并用 **接口契约一致性专项** 打通前后端，找出其中"接口对不上、字段不一致、无法运行、架构越界"的点，分视角记录，再汇总归档。

**一句话原则**：「审出问题，不改问题；契约对不上 = 头号目标；问题定位到 `文件:行`，结论可追溯到 AC / 接口。」

## 二、评审对象与输入基线

| 输入 | 角色 | 说明 |
|---|---|---|
| PRD（`AC-Mxx-nnn`） | 需求基线 | 判断代码"漏做 / 凭空"的锚点 |
| 原型 HTML | 还原基线 | 前端页面还原度基准 |
| 后端技术文档（TDD） | 设计基线 | 后端表结构 / 接口 / 模块边界 + 接口契约源 |
| 前端技术文档（FTDD） | 设计基线 | 前端页面 / 组件 / fetch 对接 + 契约源 |
| 后端代码 + 前端代码 + `libs/shared` | **被审对象** | 实际落地的代码工程 |

**优先读项目 `.spec/` 已有产出**（与 Backend-Dev / Frontend-Dev 同范式）：
- 后端代码：**项目目录**（Backend-Dev 产出，或实际工程目录）；
- 前端代码：`Frontend-Dev` 步骤 1 用户确认的目标目录；
- TDD：`.spec/TDD/VN/`；FTDD：`.spec/FTDD/VN/`；
- PRD：`.spec/PRD/VN/`（先读 `PRD速查表.md` 建索引，按锚点回原文）；原型：`.spec/原型/`；
- 缺失则回退到用户指定路径 / 粘贴内容。
- **代码与文档不在同一仓库 / 目录时**：以 **TDD「接口清单」+ FTDD「fetch 对接表」为契约中介**做三方比对，不要求代码与文档物理同仓。

## 三、两大评审视角 + 契约专项（立场隔离）

| 视角 | 唯一评审标准 | 关心什么 | 不关心什么 |
|---|---|---|---|
| **后端代码评审** | 后端代码能否对齐 TDD 接口 / 表结构且内部一致 | 接口实现、数据模型、四层分层、微服务边界、异常 / 事务 | 前端页面 / 组件 / 交互 |
| **前端代码评审** | 前端代码能否对齐 FTDD fetch / 原型且内部一致 | api 方法、hooks、组件抽离、还原度、三态 | 数据库、服务端实现 |
| **接口契约一致性专项** | 前后端接口与共享类型是否三方一致 | 路径 / 方法 / 入参个数与类型 / 出参字段 / 错误码 / 分页 / 枚举 | 业务逻辑正确性 |

> 契约专项的命中项**归因到后端 / 前端 / 双方**：前端调的接口后端没实现 → 归后端；后端定义的字段前端没消费 → 归前端；两端字段名不一致 → 归双方。

## 四、评审重点与域界（关键）

### 4.1 头号目标（P0 优先）

前后端**接口契约对不上**，典型如：
- 后端接口入参 3 个、前端只传 2 个（或反之）；
- 字段命名 / 类型不一致（如后端 `orderNo` 前端 `order_id`、后端 `number` 前端 `string`）；
- **字段术语不一致（大小写 / 命名风格 / 同义词）**：前端写 `A` 后端写 `a`、前端驼峰 `orderNo` 后端下划线 `order_no`、同一字段前端叫 `userId` 后端叫 `uid`；
- 路径 / 方法不一致（`GET` vs `POST`、`/api/users` vs `/api/user`）；
- 枚举 / 分页结构不一致（`{ list, total }` vs `{ data, count }`）；
- 共享类型被绕过：`libs/shared` 已有类型，前后端却各写一份。

### 4.2 做（结构性评审）

契约一致 · 可运行性 · 架构合规 · 代码质量 · 安全与数据 · 六大闭环结构。

### 4.3 不做（Out-of-Scope）

**业务逻辑正确性**——某条业务规则算得对不对、边界条件判得对不对，本 Skill 不评，交由后续测试流程。因此「测试闭环」只查 **测试可运行 + 测试先行 + 标注 AC 编号**，不评「用例业务覆盖是否充分」。

## 五、评审维度

### 5.1 六大闭环（代码层定义）

| 闭环类型 | 代码层含义 | 典型断点 |
|---|---|---|
| 需求闭环 | 每条 AC 有代码承接 + 测试标注 AC 编号；每段代码可追溯 AC | AC 漏实现；实现无 AC 来源；测试未标 AC |
| 流程闭环 | 业务流程入口→出口在代码中贯通 | 只写创建不写查询；只写成功路径；事件 / 回调无人消费 |
| 状态闭环 | 状态机有初态 / 终态 / 合法流转，无死状态 | 缺终态；流转无触发方；状态枚举前后端各写一份 |
| 数据闭环 | 字段产生→传输→消费全链路一致 | 后端字段前端未消费；前端入参后端未定义；分页 / 枚举 / 时间格式不一致 |
| 异常闭环 | 异常有定义→抛出→捕获→反馈→可恢复 | 空 catch 吞异常；错误码未分段；前端缺空 / 错 / 加载态；事务未回滚 |
| 测试闭环 | 测试先行、可运行、标注 AC（不评业务覆盖） | 先实现后补测试；`pnpm test` 跑不通；用例无 AC 编号 |

### 5.2 五大正确性

| # | 维度 | 核查点 | 依据 |
|---|---|---|---|
| 1 | 可运行性（静态验证） | install → `tsc --noEmit` → build → test → lint | `static-verification-guide.md` |
| 2 | 架构合规 | 后端四层单向依赖 / 微服务边界；前端分层 pages→components→hooks→api / 组件抽离铁律 | `backend-checklist.md` / `frontend-checklist.md` |
| 3 | 接口契约一致（核心） | 路径 / 方法 / 入参个数与类型 / 出参字段 / 错误码 / 分页 / 枚举 / **字段术语（大小写 / 风格 / 同义词）**，双向 + 共享类型单一源 | `contract-checklist.md` |
| 4 | 代码质量 | 单一职责、无魔法值、注释讲 why + 传参必注、统一响应、配置外置、无密钥硬编码 | 同左 |
| 5 | 安全与数据 | 入参校验、鉴权、SQL 注入 / XSS、金额整数分、事务 / 幂等 / 并发 | 同左 |

## 六、评审流水线（端到端闭环）

```
用户输入（代码 + PRD/原型/TDD/FTDD 路径 / 粘贴内容）
        │
        ▼
[1] 输入解析：定位代码 + 四类文档，识别 AC 编号与接口清单
        │
        ▼
[2] 静态验证：前后端分别跑 install/tsc/build/Test/lint 取证（跑不了→降级读码并明示未取证）
        │
        ▼
[3] 双视角并行评审：后端按 backend-checklist、前端按 frontend-checklist 逐条找断点
        │
        ▼
[4] 接口契约一致性专项核查（contract-checklist，三方比对）
        │
        ▼
[5] 两份角色评审文档落盘（后端代码评审.md / 前端代码评审.md）
        │
        ▼
[6] 汇总去重：合并所有断点，标出「前后端契约错误」共性项
        │
        ▼
[7] 归档 .spec/代码评审/
```

### 步骤 1：输入解析
- 定位被审代码：后端代码目录、前端代码目录、`libs/shared`（或等价共享包）；
- 定位四类文档（PRD / 原型 / TDD / FTDD），缺失则提示用户补充或回退粘贴内容；
- 抽取评审基线：AC 编号清单、TDD 接口清单、FTDD fetch 对接表、原型页面清单。

### 步骤 2：静态验证（取证）
按 `references/static-verification-guide.md` 对前后端分别执行：
- 后端：`pnpm install` → `tsc --noEmit`（或 `build`）→ `test` → `lint`；
- 前端：`pnpm install` → `tsc --noEmit` → `build` → `test` → `lint`；
- **命令跑不起来**（缺依赖 / 无环境 / 未授权）→ 降级为静态读码，并在报告中**明示「未取证」**，不阻塞评审；
- 静态验证只证伪"可编译 / 可测试 / 可 lint"，**不做端到端联调冒烟**（归测试流程）。

### 步骤 3：双视角并行评审
- **后端代码评审**：按 `references/backend-checklist.md` 逐条评审；
- **前端代码评审**：按 `references/frontend-checklist.md` 逐条评审；
- 两个视角独立产出自己的"断点清单"，不参考对方结论（保证视角隔离）；
- **独立 review 中间层（review 独立性）**：两视角各自在**独立上下文**（subagent / 新会话）中评审，互不可见对方结论，也绝不参考代码的生成过程——评审对象是成品代码，只认代码与四类文档原文（不被生成过程锚定）；条件允许时可用不同模型交叉审查同一份代码。

### 步骤 4：接口契约一致性专项核查
按 `references/contract-checklist.md` 做三方比对：**前端 fetch ↔ 后端实现 ↔ 共享类型**，逐接口核对路径 / 方法 / 入参个数与类型 / 出参字段 / 错误码 / 分页 / 枚举；命中项归因到后端 / 前端 / 双方。

### 步骤 5：两份角色评审文档落盘
按 `assets/role-review-template.md` 各写一份，落盘到 `.spec/代码评审/`：
- `后端代码评审.md`
- `前端代码评审.md`
- P0 问题按 `assets/patch-template.md` 附「建议补丁」（代码块，仅写报告，**不落盘源码**）。

### 步骤 6：汇总
按 `assets/summary-template.md` 生成 `代码评审汇总报告.md`：
- 合并两份清单，去重；重点标出「前后端契约错误」跨端共性问题；
- 按严重度统计（P0/P1/P2）。

### 步骤 7：生成评审任务清单 + 用户确认（闭环入口）
按 `assets/issue-list-template.md` 生成 `.spec/代码评审/任务清单.md`：
- 把「代码评审汇总报告」去重后的问题逐条落到任务清单，状态先填 `待确认`，并按归因填好 `修改方`（后端 → Backend-Dev，前端 → Frontend-Dev，双方 → 双方）；
- **每条问题必附「修复判据」**——一句话写清修到什么表现算修复完成（修改方与再评审共用同一把尺子，防止「改不干净」死循环）；
- 向用户**逐条列出问题点与优化点**，请用户确认：要改 → `已确认`；不改 → `已忽略` 并附理由；
- **分级冻结**：P0 / P1 为「问题点」（阻断项，未清零不放行）；P2 为「优化点」（不阻塞闭环，可留后续迭代）；
- **再评审只验上一轮清单**：复核仅核对已确认问题是否按判据修复，不无限新增同级新问题——新发现降为 P2 留后续，或经用户同意进下一轮单独批次；
- **轮次上限 3**：再评审轮次达 3 仍未收敛（仍有 P0/P1 未修）即停止循环，向用户汇报阻塞并交由用户裁决后续处置，防「评审-改-再评审」无限循环；
- 本 Skill 只审不改，用户确认后任务清单交对应 Dev skill 后续逐条修改并回填状态（P0 补丁见角色评审文档第四节，不重复贴进任务清单）。

### 步骤 8：归档
所有文档（角色评审文档 + 汇总报告 + 任务清单）落盘到 `.spec/代码评审/` 目录，交付给用户。

## 七、静态验证规程（B 档）

> 权威命令见 `references/static-verification-guide.md`。核心约定：
- **验证目标**：证伪"可编译 / 可测试 / 可 lint"，不证业务正确性；
- **前后端分别跑**，结果分别记入对应角色文档；
- **跑不了 → 降级**：环境缺失 / 依赖未装 / 未授权时，改为静态读码，报告标注「本项未取证（原因：{{原因}}）」；
- **不阻塞评审**：静态验证失败是 P0/P1 证据，验证不可执行只是"未取证"，不是"通过"。

## 八、严重度分级（只标注，不设门禁）

| 严重度 | 含义 | 典型情形 |
|---|---|---|
| **P0 致命** | 接口契约对不上导致无法联调；代码无法编译 / 启动；共享类型被绕过各写一份 | 后端入参 3 个前端传 2 个；字段名 / 类型不一致；`tsc` 报错 |
| **P1 重要** | 契约字段命名不一致但类型兼容、错误码分段缺失、前端三态缺失、架构越层、测试跑不通 | 缺错误态 / 空态；跨层调用；`pnpm test` 失败 |
| **P2 建议** | 命名不统一、注释缺失 / 冗余、魔法值散落、非关键细节缺失 | 术语中英混用；裸字符串散落 |

## 九、评审铁律（强制）

1. **只审不改 · 分工明确**：评审的本质是**找问题**，不做任何修改——只指出"哪里对不上 / 跑不起来 / 越界、为什么、建议往哪个方向补"，**绝不替用户改源码**；P0 补丁只写在报告里、不落盘。**改代码是 `Backend-Dev` / `Frontend-Dev` 的职责**（通过 `.spec/代码评审/任务清单.md` 交接），本 Skill 只产出问题清单，不碰源码。
2. **定位到代码**：每个断点必须标注**出处**（哪个文件、哪一行 / 哪个接口 / 哪个字段），引用关键代码片段，可追溯。
3. **零幻觉**：严禁编造"代码里没有的问题"；所有结论基于代码与四类文档原文。区分「缺失（该写没写）」与「越界（写了不该写的）」。
4. **视角隔离 + 独立上下文**：后端问题归后端、前端问题归前端；契约问题归因到应负责的一方（或双方），不交叉、不代劳；双视角评审各自用独立上下文（subagent / 新会话），互不可见结论，只认成品代码与四类文档原文、不参考其生成过程。
5. **不设门禁**：只输出问题清单，不判定代码"通过 / 不通过"。是否修改、由谁修改，交给用户决策。
6. **不评业务逻辑**：业务规则算得对不对、边界判得对不对，一律不评（归测试流程）；测试闭环只查"可运行 / 先行 / 标 AC"。
7. **成因必写**：每个断点除写明"哪里对不上 / 跑不起来"，必须写明**成因**——为什么会产生该 bug / 契约不一致（如：后端改字段未同步共享类型、分支只走成功路径）。成因须能从代码与文档上下文推得；**推不出明确成因时标「成因未明」，禁止臆造**（呼应铁律 3 零幻觉）。

## 十、常见错误对照表

| 常见错误 | 纠正方式 |
|---|---|
| 评审时顺手改了源码 | 只记录问题，P0 补丁写报告里，不动源码 |
| 两个视角结论混在一起 | 严格分视角成文，汇总时再合并 |
| 只审前端不审后端（或反之） | 后端 / 前端两份文档都要审 |
| 漏掉接口契约一致性 | 步骤 4 专项核查，逐接口三方比对 |
| 把业务逻辑正确性当评审项 | 归测试流程，本 Skill 只查契约与结构闭环 |
| 静态验证跑不了就写"通过" | 降级为读码，标注「未取证」，不写"通过" |
| 问题没有出处 | 定位到文件:行 / 接口 / 字段 |
| 把"代码不该写的"当成"缺失" | 区分「缺失」与「越界」，分别标注 |
| 结论笼统（"这里有问题"） | 写明"哪里对不上 / 为什么" + "建议往哪个方向补" |
| 只列现象没写明成因 | 补上成因（为什么会出 bug / 契约不一致），可考才写、不臆造 |
