# 根因定位方法论（证据链三段）

> 用途：Bug-Fix 步骤 4 的落地细则。
> 心法：修 bug 最贵的是把「症状当根因」。每一条结论都要能回答「证据是什么、在哪个代码位置」；答不出就标【假设】继续收敛。

## 一、心智模型：像剥洋葱

```
现象（用户看到什么）            ← 只在这层就开修 = 治标
   ↓ 问：什么直接触发了它？
直接原因（哪次调用/哪个分支/哪条数据引发）
   ↓ 问：为什么会走到这一步？
根因（代码层：哪个文件哪个函数哪条语句，因什么前提不成立）
```

- 每下一层都要**新证据**支撑（日志行/代码/数据），不允许用「应该」「可能」跨层。
- 判定「到根因」的标准：该语句被改正后，现象在逻辑上必然消失，且不是靠猜。

## 二、根因五类模板（归因时对照，防漏方向）

| 类型 | 特征信号 | 常见真相 |
|---|---|---|
| 数据问题 | 特定数据才出错、空值、格式错 | 上游入参未校验、边界数据（空/超长/特殊字符）、脏数据/缺迁移 |
| 状态问题 | 偶发、刷新/重进后消失 | 初始化缺失、缓存未失效、持久化恢复缺字段、顺序依赖 |
| 竞态/并发 | 偶发、并发操作触发 | 异步未 await、共享可变状态、重复提交、token 过期窗口 |
| 契约不一致 | 前端传的与后端收的对不上、联调环境才现 | 共享 DTO/枚举漂移、版本不一致、字段大小写/命名差异 |
| 环境/依赖 | 换环境才现、超时 | 配置项、依赖服务版本/不可用、网络、权限 |

> 定位优先按「证据指向」归因，再用五类模板做查漏（尤其偶发问题，五类逐项排除）。

## 三、定位五步法

### 1. 圈定第一异常点
从日志解析结果中挑**时间线上最早、最底层**的异常（错误栈最内层、最先返回非 2xx 的调用），不追表象链末端的衍生报错。

### 2. 收敛代码位置
错误栈 → 文件:行；无栈 → 用「报错文案 + 触发操作」在代码中定位抛出点。读到可疑语句时对照上下文（入参来源、前置 if、调用方）。

### 3. 验证假设（证据优先）
对每条候选根因，用**可验证手段**而非推理下结论：
- 读代码沿调用链走一遍（入参 → 处理 → 出参），标出与预期不符的点；
- 复现实验：改数据/入参复现；后端可打印入参对比；
- 对照契约：前端传参与 TDD/FTDD 定义逐字段核对；
- 对照近期变更：git log 最近改动是否引入（发版后出现的高嫌疑）。

### 4. 最小化因果链
得到候选根因后，用一句「如果…那么…」自检闭环：
`当 {条件} 时，{代码位置} 因 {前提不成立} 而 {出错}；修正 {X} 后必然消失。`
闭环不了 → 回第 2/3 步，不硬写结论。

### 5. 影响面与严重度
- 影响面：哪些功能/页面/端/用户群受影响；触发频率（必现/偶发/特定数据）。
- 严重度：P0 阻断主流程/数据损坏/大面积不可用；P1 明显功能错误/高频；P2 边缘/低影响。
- 复现条件写清（数据前置、操作步骤、环境），作为后续回归判据输入。

## 四、复现不了怎么办

1. 拉长日志时间窗、补打关键点日志（本次修复流程内允许临时加日志定位，改完删除）；
2. 用五类模板排查「偶发」成因（状态/竞态/环境最可疑）；
3. 仍无法复现 → 结论标【未复现】+ 置信度（高/中/低）+ 依据，交用户裁决下一步（继续蹲复现 / 按高置信根因预防性修复并过 Gate）；
4. **未复现不进入修复**（铁律 2），防止改错点或引入新缺陷。

## 五、修改方向建议怎么写

给开发 skill 可执行、可验收的方向：

| 要素 | 要求 | 示例 |
|---|---|---|
| 位置 | 文件:函数:行 + 一句现状 | `UserService.login() L42` 未判用户封禁态 |
| 改法 | 怎么改、加什么守卫/校验/分支 | 进入签发前先查 `status`，封禁直接抛 403 |
| 影响 | 改动波及面、是否动契约/表 | 仅 Service 内新增判断，不动接口与表 |
| 风险 | 引入回归风险点 | 注意 `login` 还被「自动登录」路径调用 |
| 判据 | 修到什么表现算过 | 封禁用户登录返回 403，正常用户不受影响 |

> 写建议时不替代技术方案：方案 skill 会产出正式增量 TDD/FTDD，本处只给方向性输入。
