# 本地会话 rollout 记录不含全量历史轮次——挖掘输入不能只靠它

> 归属：`../../issue/Skill-Optimizer/` ｜ 来源：挖掘 ｜ 状态：待处理
> 日期：2026-09-15 ｜ 标签：工具依赖、流程缺陷 ｜ 等级：P2

## 现象

按用户指令「获取当前项目下的所有会话记录，总结问题点」挖掘 learning-assistant 时发现：
- `~/.zcode/cli/rollout/model-io-*.jsonl` 每行是一次模型调用快照，**历史轮次会被轮转/压缩**——本会话最早的用户指令（首条任务书、AskUserQuestion 答复）在全部 103 条 user 消息中不存在，只有最近一条用户消息的全量重放；
- 同目录混存**其他项目**的会话（sess_6a6abe07 实为另一项目的 CODE 批次），按文件名无法辨别归属；
- 唯一可靠的完整问题史在**项目自身的 `.spec/` 产物**（PIPELINE 交接记录、各轮评审任务清单、测试问题文档）与 git 历史——它们恰恰是各会话问题点的已蒸馏形态。

## 期望 vs 实际

- 期望：挖掘模式可以从本地会话记录还原「这个项目发生过什么问题」的全貌；
- 实际：rollout 只提供近段过程证据（错误签名统计、近期返工实录），全量问题史必须依赖项目 `.spec/` 产物。

## 修复方向

1. `Skill-Optimizer` 模式②（挖掘）输入源优先级写明：**① 项目 `.spec/` 各轮评审/测试问题文档 + git log → ② rollout jsonl（仅近段行为证据/错误签名统计）→ ③ ../../chats/ 手工导出**；
2. `../../chats/README.md` 补一段「会话记录自带口径」：rollout 轮转 + 跨项目混存两 caveats，引导导出时标注项目名；
3. 挖掘产物标注证据来源类型（spec 产物 / rollout 签名 / git 提交），供后续复核。

## 双向落点

不涉及评审闭环（来源=挖掘），单端记录；若采纳修复方向 1/2，属 Skill-Optimizer 自身优化（模式③，先己后人）。
