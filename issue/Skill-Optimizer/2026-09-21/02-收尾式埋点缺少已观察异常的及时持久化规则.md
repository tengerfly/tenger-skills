## 现象与证据

- `Other/Skill-Optimizer/references/instrumentation-guide.md` §一将埋点限定为产物落盘 / 交付后的收尾；§五明确「埋点是收尾动作，不是执行中动作」。
- 同文件 §五「不确定算不算问题 → 不记」未区分「已观察到的失败事实」与「尚未确认的根因 / 普遍性」。容易因根因未知而遗漏真实异常线索。
- `shared/execution-profiles.md` §二允许单次任务摘要只留会话，计划暂停或交接才落盘；未明确已观察到的失败在下一安全点写入现有记录。
- 正式流程具备 BLOCKED / Failure Route，并不等于轻量和独立 Skill 的异常信息都会自动持久化。

## 期望 vs 实际

- **期望**：已经观察到的错误在可安全写入时留下最小证据，后续即使任务暂停仍可恢复；根因未知标待确认，不编造归因。
- **实际**：规则依赖正常收尾，存在收尾前阻塞 / 中断造成线索只留会话的风险。仓库没有后台捕获服务，不能承诺强制终止或宿主崩溃也绝不丢记录。

## 修复方向与验收判据

1. 已观察到的失败在下一安全点记录时间、任务 / 步骤、脱敏现象或命令与退出码、影响、证据位置、未决项、下一步；轻量复用同一任务摘要。
2. 区分事实记录与通用经验提炼：事实先记，根因和是否沉淀可保持待确认。
3. 正常收尾补结果；已修复仍保留原始证据，复核通过才关闭，未验证不能写已闭环。
4. 模拟「命令失败后暂停，再恢复」与「根因未知」两个场景，确认能从文件定位问题并继续；没有写权限时明确报告未落盘，提供待记录内容，不静默成功。
5. 明示纯 Agent 规则不保证捕获未被观察的宿主崩溃；不为此引入新的监控服务或强制重型流程。
