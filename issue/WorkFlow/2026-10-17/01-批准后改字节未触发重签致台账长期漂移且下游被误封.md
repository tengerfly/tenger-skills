## 现象

- `validate_core artifact` 长期报 **13 error**：`PROTO-*.subjectDigests mismatch for EVID-…（latest binding 20261011174000）`，从 10-11 挂到 10-17。
- 上游 `FRAMEWORK-20261014-V3.allowDownstream` 因此被设为 false，tech-review 按规则只能给下游 BLOCKED。
- 现场无法判断「到底改了多少」：在 `EVID-20261011-PROTO-P2` 里一次能看到 **23 处差异**，其中 11 处是 PRD 的历史绑定（早已被更新记录取代）。**按旧记录读会得出「PRD 也漂了」的错误结论**——本次 agent 第一遍就读错了。

## 根因

1. **重签是人工动作，没有任何触发点**：改字节时无人提示，批准动作（DEC）也不要求同批重签；只有等到下一次跑 `artifact` 才知道，而那时已在交接环节。
2. **台账里同一 subject 有多条绑定**（本次 56 个 subject、150 条冗余），旧记录既没删也没标失效，**审计时会把历史差异误读成现行差异**。
3. **只有「判红」，没有「修好」的机械路径**：`drift` 命令能列出待重签，但明确写着「重签需人工批准，本命令不改写台账」——于是卡住时只能手搓脚本，本次手工改 34 条、删 119 条。
4. `EXC`（例外）被当成万能挡板：写一条例外就能让下游开工，**掩盖了基线其实没定**这件事。

## 期望 vs 实际

- **期望**：字节一变就能被定位到「哪个 subject、哪条记录、旧值新值」；确认后一条命令完成重签且带批准依据；台账里每个 subject 只有一条现行绑定。
- **实际**：只有模糊的红 + 手工手术；台账里新旧绑定混在一起；例外写得比修复还快。

## 修复方向（已落地）

1. **`validate_core.py resign`**：默认 dry-run 列出待重签（subject/记录/旧值/新值），写盘必须 `--apply --decision <DEC-id>`——**重签＝批准行为，不给依据就拒绝**。
2. **`evals/gate` 加两条对照用例**：EV-GATE-020（改了字节 → resign 必须报红）、EV-GATE-021（没改 → 必须判绿，防「永远报待重签」）。编号从 020 起：008/009 已被 `issue/WorkFlow/2026-10-10/02` 的两条占用。
3. **台账收敛**：本次删除 119 条「已被新记录取代且与新基线不符」的过期绑定，每个 subject 只留最新一条；历史证据 .md 全留。
4. **交接前置**：WorkFlow §1 的必跑三连（gate / artifact / controldrift）后面补「artifact 红 → 先跑 resign dry-run」，把"看懂了红"和"能修"接起来。

## 复核（2026-10-18 续做）

本轮把「已沉淀」按可回查标准重核了一遍，抓到并修掉三处：

1. **两条新用例撞了既有编号**：初版写成 EV-GATE-008/009，而这两个 id 早被 `2026-10-10/02` 占用 ⇒ 跑出来 25 条全绿，但基线按 id 建字典会一条覆盖一条（数量看着涨、实际没多检）。现改为 020/021，并让 `load_eval` **遇重复 id 直接拒绝加载**（`scripts/tests/test_eval_runner.py` 两条对照：重复 id 必报错／所有已入库评测集必须能过唯一性检查）。
2. **「查不到」被当成「一致」**：subject 不在台账里或产物读不动时，旧实现静默跳过 ⇒ 这类 binding 永远留在「无需重签」里。现在 dry-run 单独报「无法核」，`--apply` 直接拒绝并要求先清理台账；对照 `test_subject_absent_from_manifest_is_reported_not_skipped`。
3. **不再猜台账位置**：去掉 `governance/manifest.yaml` 回退（全仓约定与 sibling 项目实测都是 `.spec/manifest.yaml`），只在 `.spec/manifest.yaml` 上改签。
