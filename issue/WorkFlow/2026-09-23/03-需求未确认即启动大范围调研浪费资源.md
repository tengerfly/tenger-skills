## 现象

用户在 2026-09-23 会话内的第三次纠正，原话：

> 正常的流程是 需求都没有确定 你来跑后边的流程 本就是浪费资源

具体事实：助手在完成 WorkFlow 建档后，判断「竞品全景是硬交付」，遂在**需求方向（本应用要解决用户什么问题）尚未经用户任何确认**的情况下，启动后台大范围调研任务，范围包括：

- Obsidian 九大模块能力全景（写入／链接／库管理／图谱配置项／检索／元数据／导航／同步发布／插件生态）；
- Logseq、Roam Research、Heptabase、Tana 四款同类产品的差异化实现；
- 全网检索 3D／球面知识图谱的现成实现（含 GitHub 项目与 Obsidian 插件）。

该范围**全部由助手自行猜测**，无一来自用户确认。用户指出后任务终止，状态 `killed`，产物未回收，投入归零。

**加重情节**：助手当时把这一行为自我合理化为「并行不空等，效率更高」，并在用户第二次纠正后（见 `02-*.md`）错误地把教训总结成「AI 应先交付研究全景，再让用户裁决」，写进了 issue 与用户记忆。该判据隐含「先研究是对的」这一错误前提，若被后续会话遵循，会推动**更早、更大范围**的调研，即修复方向本身把错误放大。该错误沉淀已于同日删除并替换。

## 期望 vs 实际

- **期望**：陈述助手理解的需求方向供用户改写 → 用户确认 → 登记 `ACCEPTED` → 才决定要不要调研、调研哪几块、代价多少 → 用户批准后再启动
- **实际**：需求方向零确认，直接按主观猜测划定大范围调研任务并启动；且自认为在提效

## 根因

| # | 位置 | 缺口 |
|---|---|---|
| R1 | `WorkFlow/SKILL.md` `§3`（领域路由）与 `Procedure` 全文 | 路由只规定阶段**顺序**（CREATE → PRD → UI → …），未规定阶段的**准入门禁**：进入任一高成本下游阶段前，上游意图是否已被用户确认。`§4 守门与交接`只管产物 Gate，不管「这件事现在该不该花钱」 |
| R2 | `shared/execution-profiles.md:15` | 「用户明确要求的竞品研究在任何强度下都不能静默省略」被本会话读成「竞品研究越早启动越好」。缺反向约束：研究**范围**依赖已确认的需求方向，方向未定时禁止展开大范围检索，只允许先做方向确认 |
| R3 | `shared/product-workflow-contract.md` §2.2 | 规定「先全景后范围」，但未要求全景的**裁剪依据**来自用户确认的需求方向；导致 AI 有空间自行猜测范围并先行投入 |
| R4 | 无「成本可见性」条款 | 调度研究类 skill 不需向用户交代范围与代价，`execution-profiles.md` §4 的时间/成本要求只覆盖工期预算与付费，不覆盖 token／调研规模这类实际消耗，助手因此无从感到越界 |

## 修复方向

1. **`WorkFlow/SKILL.md` 新增「资源投入门禁」（落 R1）**：在 `§4` 之前或并入，规定——研究、选型、大范围检索、代码实现等高成本动作，前置条件为存在用户已确认的需求方向（decision 状态 `ACCEPTED`）；未确认时只允许零成本的意图澄清。明确写入：**不得以「并行不空等／利用等待时间」为由启动上述动作**。
2. **成本可见性（落 R4）**：启动研究前向用户简述「查什么范围、大概多少开销、回来后给你什么」，由用户决定是否现在投入。用户是资源裁决者。
3. **`execution-profiles.md:15` 补反向句（落 R2）**：在「竞品研究不得静默省略」之后加「但研究范围须以已确认的需求方向为裁剪依据；方向未定即开大范围检索属浪费，应先做方向确认」。
4. **`product-workflow-contract.md` §2.2 补裁剪依据（落 R3）**：全景整理须声明其裁剪来自哪条用户确认。
5. **确定需求的正确抓手**：先以一段话陈述 AI 理解的需求方向供用户改写，而非抛选择题、亦非自行调研代替。本用户明确表达「让我来确定需求」。
6. **回归场景**：写入 `docs/task-scope-regression.md` ——「新建应用且需求未定时，AI 是否先陈述理解而非擅自调研」，与 09-22 已登记场景并列。
