## 现象

用户 2026-09-23 核对 travel-agent 产物时提问：

> 这个我看已经都在TDD了 为什么没有UI设计稿？UI设计稿应该在技术方案之前的

核对后果然成立，且**不是执行时漏跑，而是编排契约里不存在这个节点**：

1. **契约枚举止于原型**：`shared/product-workflow-contract.md` §2 阶段责任列表最后一项是 `PROTOTYPE_REVIEW`（第 37 行），**无 `UI_UX_DESIGN` / `UI_UX_REVIEW`**；§2.1 单一职责表（第 41–51 行）更是止于 `prd-review`，连 prototype 都未入表。按此契约推进，`PROTOTYPE_REVIEW` 之后合法后继直接就是技术设计。
2. **路由层只有抽象词**：`WorkFlow/SKILL.md:79` 为 `CREATE -> PRD -> UI -> Tech Design -> DEV -> auto-test -> Release`，其中 `UI` 是**没有节点定义、没有准入判据的抽象领域名**，不绑定「必须先有设计稿才能进 Tech Design／DEV」。
3. **skill 本身是齐的**：`UI-UX-Design`、`UI-UX-Review` 两个 skill 在仓内存在且完备 —— 缺的只是把它们注册进主链，因此它们**无从被经过**，而非被跳过。

项目侧证据链（`travel-agent/.spec/`）：

- `executions/` 序列：`EXE-20260922-017` / `EXE-20260922-018-019`（prototype-review）→ `EXE-20260923-020`（高德 L1 实测）→ `EXE-20260923-021`（TDD overview）。**中间无任何 UI-UX 执行记录**，`EXE-001~026` 编号连续无缺号，即从未起过该节点。
- `manifest.yaml` 的 `owner` 从 `prototype-design` 直接跳到 `backend-tech-design`；`decisions/` 32 条 DEC 中**没有任何一条记录「主动裁掉设计稿」**——不是裁决掉的，是漏掉的。
- `原型/V1/README.md:45` 当时明确写着「allowDownstream: true（技术方案可并行启动，但 **UI 设计稿与实现须待 prototype-review 通过**）」——即产出方**意识到了**设计稿应在此之后，但契约无此节点，这句话**没有任何门禁能够执行它**。「有意识、无抓手」是本漏点的直接成因。
- `技术方案评审/后端技术方案评审.md:16` 输入基线记「设计稿：无（本批不涉及视觉）」；`技术方案评审汇总.md:10` 记「批次 ⑩-后（只审 TDD；**FTDD 未产出**）」。

**代价已实际显形，不是假设风险**：前端契约无承接方，后端把版式决策顺手定掉了 —— TECH/BE-14（`canEdit/canPublish` 幽灵字段）、BE-18（接口归属需与 FTDD 共定）、BE-25/26/29/30（后端写前端渲染策略 3 处：两阶段渲染、`禁 dangerouslySetInnerHTML`、隐藏"换个走法"、`routeOptionsAvailable` 驱动前端显隐）。评审自身已判 BE-T8「越界（前端实现/加戏）……建议与 FTDD 划界」，汇总第 40 行也承认这些是「⑩-前 批次三方对账的必查项」。**本产品为 chat-first C 端（DEC-021）**，对话流内行程卡／地图／降级态的排布属设计层决策，低保真原型撑不住，缺视觉稿会把还原度风险整体推到开发期。

## 期望 vs 实际

- **期望**：`PRD → 原型 → 原型评审 → UI-UX-Design → UI-UX-Review → TDD + FTDD → 技术方案评审（⑩-后／⑩-前 双批）→ DEV`；设计稿是 FTDD 的视觉基准输入、是 frontend-dev 还原度与 fidelity-review 的唯一比对源
- **实际**：`PRD → 原型 → 原型评审 → （L1 实测）→ 后端 TDD → tech-review ⑩-后`，UI 两节点与 FTDD 三度空缺；`WorkFlow` 第 79 行的 `UI` 领域全程无产物落地，直到技术评审把「FTDD 未产出」写成批次说明才可见

## 修复方向

1. **契约补节点（落 R1，主修）**：`shared/product-workflow-contract.md` §2 增加 `UI_UX_DESIGN`（把批准原型转成视觉与交互设计稿 / `.spec/设计稿/`）与 `UI_UX_REVIEW`（设计稿独立四维复审），并在 §2.1 职责表补两行，写明「不在此做」列（design 不做选型、review 不改稿）。
2. **注册必经边（落 R2，边按前后端分档，勿一刀切）**：`WorkFlow/SKILL.md` §3 把 `UI` 展开为可门禁的具体节点序列。必经关系应定义为 **`UI_UX_DESIGN`/`UI_UX_REVIEW` → `FRONTEND_TECH_DESIGN` → `DEV`**（前端链硬前置）；`PROTOTYPE_REVIEW → BACKEND_TECH_DESIGN` 可保留，但须要求该批次**显式声明视觉基线状态**（有稿／或登记「后端批次不依赖视觉」并链到 DEC），不得靠 `输入基线：设计稿：无` 一句话自行降级。
   > 判据校准依据（2026-09-23 用户裁决，`travel-agent` DEC-20260923-033）：本项目选择 **TDD 先于设计稿**，理由是后端方案输入为 PRD/原型结构/blueprint、不吃视觉稿；同时确认硬约束在「设计稿是 FTDD、frontend-dev、fidelity-review 的前置」。若按本条原写法把 UI 阶段设为一切技术设计的直连阻断边，会无谓挡住后端批次并把主链拉长一档 —— **写过头同样是缺陷**，故此处按前后端分档。
3. **禁止静默降级（防复发的检出侧）**：凡输入基线出现「设计稿：无」「本批不涉及视觉」「缺省回退低保真原型」字样，必须同时登记 EXC 并附用户批准出处，否则 Gate 不得 `PASS`／`CONDITIONAL`。当前 `frontend-tech-design` 与 `fidelity-review` 描述里都内置了「缺省回退原型」的静默退路，这正是让漏点一路无感传到开发期的通道，须在两处 skill 内补「回退须授权」限定。
4. **回归场景**：写入 `docs/task-scope-regression.md` ——「新项目走完整流程时，是否在原型评审与技术设计之间产生 `.spec/设计稿/` 与 `.spec/设计评审/` 产物；缺失时是否报错停下而非继续」。
5. **本项目处置（用户 2026-09-23 已裁决，`DEC-20260923-033`）**：`travel-agent` 按 `⑩-后 收尾 → ui-ux-design（B 路径本地自写）→ ui-ux-review → frontend-tech-design → tech-review ⑩-前 → DEV` 重排。已定稿 TDD 不回退（后端不吃视觉稿），FTDD 阶段承接设计稿并回收 `BE-14/18/25/26/29/30` 划界。
   > **数据订正（二次，教训版）**：本条初版写「P0 残留 4 项（TECH-02/04/05/25）」，与 `复核-第2轮.md` §三 一致、**是对的**；修订时被 `技术方案评审/任务清单.md` 状态列里 `TECH-01~05` 全标「部分修复」带偏，改成了「P0 残留 5 项」，属二次错误。真实关系是**两个不同口径**：「判据未满足（须再改）」= TECH-01~05 + 十余项 P1/P2；「P0 阻塞（挡放行）」= 复核员 §三 认定的 **TECH-02 / 04 / 05 / 25 四项**（其中 TECH-25 在清单里定级 P1，但因属权限面未收口而被复核员列入 P0 阻塞）。
   > **可复用教训**：同一份清单中「判据未满足」≠「P0 阻塞」，跨文件引用状态时必须**标明取自哪个口径及其文件锚点**，否则会把评审员的阻塞认定 silently 替换成机械标记的并集。此教训与 R 层结论同源：状态摘要与被摘要对象会漂移，判据须回单一事实源逐条核。

## 追加修复（2026-09-23 本次落地时新查到的同源旁路）

核对本条时发现比「`PROTOTYPE_APPROVED → TECH_DESIGN` 缺边」更严重的漏洞：`governance/state-registry.yaml` 的 **TR-015（`INTAKE_READY → TECH_DESIGN_IN_PROGRESS`）lifecycle 含 `CREATE`，且 `requiredArtifacts`/`requiredEvidence` 均为空**——即新建应用可以从一句 intake **合法地**直落技术设计，把 PRD、原型、UI 三阶段整体绕过。本条原修复只文档化了「原型评审后必经 UI」，堵不住这条边，因此同批把 `CREATE` 从 TR-015 的 lifecycle 移除（CHANGE/DEFECT/REFACTOR/INCIDENT/OPTIMIZE 保留，它们复用已批准基线属合法短路径）。CREATE 仍经 TR-011 `INTAKE_READY → PRD_IN_PROGRESS` 进入产品序列，`scripts/validate_core.py graph` 复验通过（状态可达性与可终结性无破坏）。

> 该旁路不在本条原 R1/R2 范围内（原诊断聚焦契约枚举与路由抽象词），属同根因「UI/需求阶段无准入门禁」的第二条合法路径，记录于此避免后续只按契约文本核查而漏掉注册表。
