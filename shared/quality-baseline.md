# Quality Baseline v1

## 1. 质量目标

质量恒定指不同模型生成的结果必须经过同一组最低门槛，而不是要求生成文本或代码完全相同。最低门槛覆盖：可读性、边界、正确性、测试、可观测性、可回滚性和追踪完整性。

## 2. 代码可读性

- 模块有单一职责，边界可解释；
- 命名表达业务含义，不依赖模型上下文；
- 控制流不过度嵌套，错误处理统一；
- 外部输入、权限、状态和副作用清晰；
- 不允许无来源的魔法数字、重复实现、巨型函数和无意义抽象；
- 注释解释“为什么”，不是重复“做什么”；
- 日志包含关联键且不泄露敏感信息。

## 3. 反 AI 味检查

发现以下信号必须登记为 finding：占位代码、伪造成功、吞异常、宽泛 catch、重复生成的相似模块、未使用参数、注释与实现不一致、过度封装、硬编码环境值、测试只断言 happy path、以 TODO 代替决策。

## 4. 最低验证层

每次代码变更按项目 profile 执行适用检查：格式化、类型检查、静态分析、单元测试、集成测试、关键链路回归、构建、可观测性冒烟。没有执行条件时标记 `OPEN` 或 `CONDITIONAL`，不得声称已通过。

## 5. 运行质量

发布后应能从 `web-monitor`、`server-log`、`server-monitor` 关联到版本和请求/会话。关键指标至少包括错误率、核心链路成功率、延迟、资源健康、告警数和回滚状态。巡检关注趋势而非只看单次绿灯。

## 6. 例外

例外必须有决策记录、风险、责任人、截止时间和补证动作。技术债不删除，只能降级、关闭并保留原因。
