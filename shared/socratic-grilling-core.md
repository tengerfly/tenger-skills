# 选型拷问协议（通用核心）

> 适用：Backend-Tech-Design / Frontend-Tech-Design（TDD/FTDD 决策点拷问）；其他方案类 skill 可参照。
> 领域专属节（链路节点拷问 / 数据流交互节点拷问、领域示例清单）见各 skill 自身 `references/socratic-grilling.md`，本文件不重复。
> ⛔ BLOCKING：决策点未过「收敛证明」前，禁止写入 overview 或模块文档。

## 一、心智模型：决策树

- 每个决策点是一棵决策树：答案会解开依赖它的下一层问题。
- 每轮只问「前置已定、现在就能答」的 frontier 问题；一次一问，答后消化再进下一轮。
- 用户回答冒出的新问题进下一轮；frontier 清空才算该点收敛。
- 未获用户拍板的默认（容量/版本兼容/状态归属/超时策略等）标为待验证或【方案假设】，安排回访裁决，不得静默消化。

## 二、提问纪律

1. 每个问题写成「问题 + 推荐答案 + 理由」；无方向时给 2~3 个差异化选项 + 场景例子。
2. 推荐答案只是建议，最终仍须用户逐点拍板。
3. **一次一问**：不连环轰炸、不提前抛出依赖未定的问题。同一决策点内部的子维度（如上传：存储位置/传输方式/大小上限/断点续传/并发）可按清单逐项过，但跨决策点仍一次一问。
4. 回答质量门槛：抽象/口号回答（看情况、尽量、后续优化）一律不放行，追问到能落到具体组件/页面、量级或规则。
5. 只给结论不给理由时追问：为什么现在就需要？不用会怎样？哪条链路会先撑不住？

## 三、固定三问（每个决策点至少各过一轮）

1. 这个方案在什么场景下会失败/不成立？（领域失败场景见各 skill 专属节）
2. 数据量/并发/调用量涨 10 倍，这套方案还成立吗？
3. 漏掉了什么？（领域检查项见各 skill 专属节）

## 四、边界拷问（框架）

- 这版明确不做/不引入的是什么？说不出 → 边界未想清。
- 归属与权限：数据/状态归谁、谁能改、冲突时谁优先怎么裁决？
- 失败兜底做到哪一步为止？哪些失败不自动恢复、需要告警给人？

（领域边界问题清单见各 skill 专属节。）

## 五、收敛证明（一个决策点何时算定稿）

同时满足四条才允许定稿：

1. 结论可落到具体组件/页面、版本与量级承诺，不是「看情况/尽量」。
2. 已记录：方案 + 理由 + 备选 + 已拷问的失败/涨 10 倍/漏项。
3. 待验证项有验证动作与回退方案；【方案假设】有归属点与回访时机。
4. 用户对定稿复述点头。

## 六、雷区（出现即自查补问）

- 用户回答一两句，就开始写 overview/模块文档 → 收敛证明未齐。
- 把上游文档没写、本方案新增的决策当「默认/继承」直接定稿 → 新增决策必须单独拷问。
- 只问选型正向，不逼失败/涨 10 倍/漏项 → 补固定三问。
- 关键链路只画成功主路径 → 逐节点补失败/超时/重试/补偿。
- 把「推荐答案」当最终答案 → 仍要用户逐点拍板。
