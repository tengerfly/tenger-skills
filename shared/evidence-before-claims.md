# 完成声明的证据门禁（跨 skill 公共约定）

> 适用：所有会做出「完成 / 通过 / 修好 / 没问题 / 已验证」声明的 skill——Code-Review、Testing、Backend-Dev、Frontend-Dev、Bug-Fix、Fidelity-Review、Workflow 门禁判定。
> 来源：superpowers/verification-before-completion（MIT），2026-09-10 吸收。

## 铁律

**没有新鲜的验证证据，不许做完成声明。**

- 本条消息里没有**实际运行**过那条验证命令并看到输出，就不能说它通过。
- 「应该可以了」「大概率没问题」「看起来对」——**都算违规**。
- 覆盖范围：原话、同义改写、暗示成功、任何表达满意的措辞。
- **违反字面就是违反精神**——换个说法不改变违规性质。

## 声明前五步（Gate）

1. **IDENTIFY**：哪条命令能证明这个声明？
2. **RUN**：完整跑一遍（新鲜、全量，不用上次结果）
3. **READ**：读完整输出，看退出码，数失败数
4. **VERIFY**：输出支持这个声明吗？不支持 → 陈述实际情况 + 证据；支持 → 带证据陈述
5. **只有到这一步**，才可以声明

跳过任何一步 = 在撒谎，不是在验证。

## 声明 ↔ 需要的证据

| 声明 | 需要的证据 | 不够的 |
|---|---|---|
| 测试通过 | 测试命令输出：0 失败 | 上次跑的结果、「应该能过」 |
| lint 干净 | lint 输出：0 错误 | 部分检查、推断 |
| 构建成功 | 构建命令：退出码 0 | lint 通过、日志看着正常 |
| bug 修好了 | **重跑原始症状**：通过 | 改了代码、假定好了 |
| 回归测试有效 | **红→绿循环**（先见它失败） | 测试跑过一次通过 |
| 子 agent / 并行评审完成 | **VCS diff 或产物实际内容** | 对方汇报「成功」 |
| 需求满足 | **逐条对照 AC / 清单** | 测试通过 |

## Red Flags（命中即停）

- 用「应该 / 大概率 / 似乎 / 看起来」
- 在验证之前表达满意（「搞定了」「完美」）
- 未验证就要提交 / 推送 / 建 PR
- 直接采信子 agent 或并行评审的成功汇报
- 只做了部分验证
- 想「就这一次」
- 累了、想赶紧结束
- 任何暗示成功但没跑验证的措辞

## 借口与现实

| 借口 | 现实 |
|---|---|
| 「现在应该能跑」 | 去跑验证 |
| 「我有信心」 | 信心 ≠ 证据 |
| 「就这一次」 | 没有例外 |
| 「lint 过了」 | lint ≠ 编译器 |
| 「子 agent 说成功了」 | 独立验证（看 diff / 产物） |
| 「我累了」 | 疲劳 ≠ 理由 |
| 「部分验证够了」 | 部分证明不了什么 |
| 「换个说法规则就不适用」 | 精神高于字面 |

## 落地要求

1. 每个会做完成声明的 skill：在收尾处写清「声明前必须跑什么命令、看什么输出」；
2. 子 agent / 并行评审的结论**必须由主线独立复核**（看产物 / diff / 截图），不得直接采信汇报；
3. 拿不到证据时，声明必须降级为「未取证（原因）」——见 Code-Review 静态验证的既有口径。
