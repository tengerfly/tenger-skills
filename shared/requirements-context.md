# 需求按需读取与任务上下文

目标：少读但不漏业务依据。现有 PRD 是唯一需求源，Wiki/速查表只是导航，不另写一套可独立修改的需求摘要。此规则适用于 PRD、原型、设计、技术设计、开发和测试。

## 1. 读取顺序

1. 定位本次已确认版本。正式流程从 manifest/批准记录定位；轻量任务使用用户明确确认的需求、验收点及已有基线，不把草案或最新修改时间自动当作批准。
2. 先读 `PRD速查表.md` 的元数据/相关索引和 overview 的全局约束、术语、范围。无索引则从目录/标题建立本次最小导航，不为小任务全文重写 PRD。
3. 按 REQ/AC、模块和页面读取**源文档相关完整条目**：规则、前置条件、异常、边界、验收标准、精确文案。索引摘要不替代原文，不能只取搜索命中的一句话。
4. 沿条目引用补读关联模块及权限、共享状态、跨模块约束，直到本次验收的依赖闭合；不默认加载无关模块。索引未列清依赖时，在相关原文中定向检索并确认；禁止声称索引天然完备。
5. 在已有任务摘要/正式执行记录中记下本次上下文。实现、评审和测试复用相同版本及条目，不从聊天记忆补业务事实。

## 2. 上下文的最小字段

不要求新格式或独立文件，在现有记录内使用以下小节即可：

```text
需求基线：版本 + 批准/用户确认来源
来源指纹（文件来源）：相关源文件路径 + 内容 SHA-256（或不可变 commit + 确认相关文件无差异）
会话来源（无文件时）：用户确认的原话与可定位的消息/任务记录；不为生成 hash 强制创建 PRD
本次条目：REQ/AC 编号；无编号的小任务用明确验收点，不伪造编号
读取范围：源文件的稳定锚点/章节、精确规则与文案引用
相关依赖：权限、共享状态、跨模块条目及其源位置
不改内容：业务/结构/接口边界
开放项：缺少什么、谁确认、是否阻塞本次验收
```

仅使用会话验收点的 Demo 不要求文件指纹；续做时核对确认记录，无法恢复则澄清而非凭记忆补写。

hash 只做失效检测，不代表批准。不能只记录可移动 branch 或含未提交变更的 commit 来证明版本一致。任务上下文是派生视图，任何新决定回写唯一权威源或明确的需求变更记录，不只改摘要。

## 3. 变更、冲突与失效

- PRD-Design 修改模块时同步刷新受影响索引与 REQ↔AC/依赖引用，保留历史批准版本。速查表仍按源文档生成，不手工独立维护。
- 源文件/全局约束/依赖改变时，相应上下文与下游证据失效；重新核对差异和影响，不静默混用新旧版本。正式批准新版本后再重绑定引用。
- 续做、交接和验收前核对来源指纹；一致时不用重读全量文档，不一致时定向刷新。若无法确定影响范围，扩大读取相关依赖并说明原因。
- 索引与原文冲突：先核对版本。以该任务已批准源版本为准，修正派生索引；两个已批准来源矛盾则停下澄清，不能任选其一。
- 无 PRD 的实验 Demo 只需确认目标、范围、验收点和假设；不要求先建 Wiki。进入长期维护/正式交接时，再把已确认内容纳入现有需求结构。

## 4. 边界

需求全面评审、新项目全局建模或影响范围无法确定时，可以分批覆盖全量需求；按需读取不是漏掉全局约束的理由。短摘要只负责导航，精确文案和业务判据必须查源。Wiki 页面或搜索工具可选，不要求部署知识库、向量库或新增服务。
