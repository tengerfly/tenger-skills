# 防评审死循环三招 + 严重度分级（评审类公共约定）

> 适用：6 个评审类 skill（PRD-Review / Prototype-Review / UI-UX-Review / Tech-Review / Code-Review / Fidelity-Review）；Bug-Fix 清单类收尾沿用同参数。
> 本文件是定义唯一权威；各 skill 只保留差异参数（超限动作、新发现处理、修改方映射），正文引用此处即可，不再重复定义。

## 一、防评审死循环三招

1. **修复判据**：每条问题附「修到什么表现算修复完成」的可检查判据；修改方与复核共用同一把尺子。无判据的问题不得进任务清单。
2. **分级冻结**：P0/P1 未清零不放行（不进入收尾归档；节点放行由编排侧 Workflow 判定）；复核只验本轮已确认清单，不无限新增同级问题；新发现降 P2 留后续，或经用户同意进下一轮单批。
3. **轮次上限 3**：同批「修复 → 复核」超 3 轮不收敛 → 停止循环，交用户裁决（接受现状 / 忽略 / 转人工），不硬跑。

## 二、严重度分级（P0/P1/P2）

| 级别 | 定义 | 处理 |
|---|---|---|
| P0 | 阻断性：流程/契约断头、核心对象或入口缺失、无法开工/联调/交付 | 阻断；必须修复并通过复核 |
| P1 | 重要：明显影响交付一致性或可运行性，须进任务清单 | 原则上全修 |
| P2 | 建议：润色、次要细节、非关键缺失 | 记录，由用户裁决，不阻塞 |

各 skill 严重度表中的「典型示例」为其领域判定参考；定义与处理以本表为准。

## 三、任务清单状态机（单一事实源）

`待确认` →（用户逐条裁决：要改 → `已确认`；不改 → `已忽略` + 理由）→（修改方回填）→ `已修复`（+ 修改说明）。

全量问题去重后只收口一份任务清单；修改方按各评审 skill 的回退映射执行；复核只验本轮 `已确认` 项。
