# OSS / GitHub 研究策略

技术方案不是凭经验拍板。凡是新建核心模块、选择关键基础设施、设计高风险数据流或引入非熟悉库，必须先执行一次有边界的 OSS 研究；研究的目的是验证实现路径和取舍，不是复制代码。

## 适用范围与复用

沿用已验证技术栈、局部业务修改、样式或文案修正，没有新增选型/架构问题时，不强制 OSS-Radar；说明复用的基线即可。已有研究可在版本、许可证、问题与适用边界仍有效时复用。存在首段风险触发项则仍须研究；执行强度不是跳过核验的理由。

## 最小流程

1. 从 PRD、关键用户旅程和技术约束提取检索词；
2. 优先查 GitHub 官方仓库、官方文档、发布记录和测试目录；必要时再查高质量二手资料；
3. 记录至少两个可比较的实现样本，注明仓库、commit/tag、许可证、活跃度和适用边界；
4. 阅读入口、核心抽象、错误处理、测试和部署/迁移相关代码，不只看 README；
5. 将观察到的做法分为 `FACT`、`INFERENCE`、`ASSUMPTION`，对不确定内容标 `OPEN`；
6. 输出“采用 / 借鉴 / 不采用”的决策，并把证据位置写入决策记录；
7. 技术方案完成后再开始 TDD/FTDD；如果方案发生变化，重新核对研究结论。

## 研究记录最低字段

```yaml
repository: owner/name
sourceUrl: <GitHub 页面或官方文档引用>
ref: <tag/commit/branch>
license: <已核实许可证或 OPEN>
observedAt: YYYY-MM-DD
question: <要验证的实现问题>
observations: []
adopt: []
adapt: []
reject: []
verification: []
```

## 禁止事项

- 不把“GitHub 上很多项目都这样写”当证据；
- 不复制带有不清晰许可证、密钥、客户数据或无法解释的代码；
- 不以 stars、README 复杂度或模型推荐代替源码/测试核验；
- 没有网络或无法取得可信源码时，保留 `OPEN`，不得伪造研究结论；
- OSS 研究不能替代用户对产品范围、风险接受和架构例外的确认。
