# 评审契约（v4 唯一事实源）

> 适用：`skills/review/` 与一切需要「独立评审」的任务。评审规则只在本文件定义，Skill 只写怎么做，不重复定义。
> 一句话：在隔离上下文里，用判据和证据判断「做没做对」，产出带证据的分级问题清单与三值结论。

## 1. 评审定位：为什么厚收

- 评审是判断，不是复述：核对交付物是否满足 AC、契约、可运行、安全、可清理、性能边界。
- 为什么厚收：模型越强，产出越像样，「说得像真的」越难辨，判断成本反而上升。判据、证据、独立评审、缺陷模式是长期资产，随真实缺陷积累而升值。
- 只审不改：问题进清单，改动归产出方；P0 可附建议补丁，只写在报告里，不落盘源码。
- 不评业务逻辑正确性：算得对不对、边界判得对不对，归测试与验收；评审只判「是否承接 AC 与契约」。
- 不设格式检查岗：格式、类型、lint 交给可运行命令；评审只看判断类问题。
- 不代产出方思考：不提供完整实现方案，只给问题、成因、修复判据与建议方向。
- 核心立场：宁可漏判标「未验证」，也不臆造问题；每条结论挂证据。

## 2. 风险三档

| 档位 | 适用 | 最少做什么 |
|---|---|---|
| 轻量 | 文案/样式/单文件小改 | 自检 + 1 次快速评审（新上下文可）+ 验收清单勾选 |
| 标准 | 一般功能开发 | 独立评审（fresh 上下文）+ 测试证据 + 验收清单 |
| 完整 | 生产/发布/迁移/权限/资金 | 全部 + owner 签收 + 回滚验证 |

- 由 Lead 按改动面自动判档；拿不准往高一档。档位写进评审包与报告。
- 三档只裁剪程序性动作（文档量、评审单元数、复核形式），不裁剪：隔离、证据、只审不改、P0 不放行。
- 轻量档不强制 fresh 子代理，但必须换新上下文；产出者本人「再看一眼」不算评审。建议轻量档 ≤10 分钟，防评审拖死交付。
- 完整档必须 owner 签收，并验证变更可回滚（改了什么、怎么退）。
- 档位可手动覆盖，但要在报告写明理由。

## 3. 独立评审隔离

- 铁律：产出者不评审自己的产出。参与产出、修改、自检或评审调度的上下文只做编排，不做评审判断。
- 隔离方式：fresh 子代理（首选）或新会话。同一会话换个角色不算隔离。
- 只给评审包：任务与范围、被审对象（路径 + 版本/commit + 摘要）、判据（AC/技术方案/契约/测试证据）、模板、边界、上轮已确认项。
- 不给：产出过程对话、草稿、自检结论、「哪里可能有问题」的提示、未确认猜测。
- 评审者可读仓库文件，但不得读产出会话记录；不得参考本任务的自检结论。
- 报告必须写隔离信息四项：评审者 id、上下文类型（fresh 子代理/新会话）、输入清单（路径与 sha256）、时间。
- 隔离不成立或隔离信息缺失：不得给 ACCEPT/FIX，结论只能 REJECT，写明补隔离后重审。
- 无隔离能力：停下要能力（停等），不许自己读一遍当评审，也不许把自查包装成评审。
- 派发：角色由 Lead 定，不默认 spawn。标准档 1 个评审者；完整档可拆多个评审单元（如后端/前端/契约），各单元独立上下文、互不可见，再由独立汇总合并。

## 4. 判据清单

### 4.1 AC 逐条

- 每条 AC 必须有交付物承接，逐条核对、逐条给结论；不得用「整体完成」代替。
- AC 缺失或不可测：记 P1（不可验收），要求补 AC 或写明解释。
- 交付物出现 AC 之外的新行为：记 P1（越界），先确认是否属需求变化。
- 实现与 AC 冲突：记 P0（交付错），不自行改判需求。
- AC 的测试证据要标注对应关系，不能只贴一条「测试全过」。

### 4.2 契约一致性（评审核心）

- 逐接口比对：路径、方法、入参个数与类型、出参字段、错误码、分页、枚举、共享类型单一源。
- 三方比对：前端调用 ↔ 后端实现 ↔ 共享类型；字段名大小写敏感。
- 归因：前端调了不存在的接口 → 前端；后端字段无人消费 → 双方核对；字段名/类型不一致 → 双方。
- 列表出参形态统一，禁止裸数组与包裹结构混用；枚举收敛到唯一常量源，禁止两端各写一套。
- 契约以技术方案与 AC 为准；文档与代码冲突时记问题，不擅自选边。
- 无共享 DTO 的项目：把「前端手写类型断言出参」列为 P0 风险抽查项。
- 契约专项结论要写「比对过哪些接口、多少条」，不能只写「已检查」。

### 4.3 可运行性

- 命令链：install → typecheck/build → test → lint，逐条跑并贴命令与退出码。
- 跑不了（缺环境、缺依赖）：标「未取证（原因）」，按 P1 记，不得写「通过」。
- 测试证据看四件事：命令、退出码、失败数、覆盖了哪些 AC。
- 只证伪「能编译、能测、能 lint」，不证业务正确性。
- 可运行性不是可选项：它是最低证据门槛，缺失时其余判据的结论都要降级说明。

### 4.4 安全与数据

- 入参校验、鉴权与越权、注入/XSS/SSRF、路径穿越、密钥硬编码、敏感字段回传与落日志。
- 金额用整数分；时间/时区/格式统一；事务、幂等、并发竞态、check-then-act。
- 命中「可利用漏洞」或「数据错误」→ P0；缺校验但需要额外前置条件 → P1。
- 前端不可信：权限收敛不能只靠隐藏按钮。
- 安全结论必须给出攻击路径或复现条件，不能只写「有风险」。

### 4.5 清理（删除候选）

- 扫死代码、未用依赖、重复实现、调试残留、关闭的开关与旧兼容分支。
- 分「现在可安全删」与「需延后（前置条件/迁移/验证/回滚）」；只出计划，不代删。
- 新增重复实现而未复用既有能力 → P1；纯命名、注释冗余、样式残留 → P2。
- 删除候选要有消费方核查结论，不能凭「看起来没人用」。

### 4.6 性能与边界

- 性能：N+1 查询、无分页全量拉取、大对象序列化、阻塞调用、循环内重计算。
- 边界：空值、空集合、超长文本、数值边界、分页越界、并发、重试、降级。
- 不要求压测；有性能声明时要求可复现测量（命令、环境、数据量）。
- 性能问题按影响面分级：主链每请求必触发 → P1 起；理论隐患 → P2 并写触发条件。

### 4.7 缺陷模式库作为检出清单

- 评审前读 [bug-patterns/README.md](../bug-patterns/README.md) 与各模式卡，逐条对照；命中即入本轮清单。
- 模式库只收「一类错」+ 可执行的检出方法；一次性问题不进库。
- 评审收尾把新发现的、会再犯的模式回填 `bug-patterns/`（按问题反哺环契约）。
- 每次缺陷逃逸都要问：该补哪条模式；模式库是评审检出力的长期台账。
- 对照结果要写进报告（对照了几条、命中几条），没有对照记录视为未执行本节。

## 5. 问题分级

| 级别 | 定义 | 处置 |
|---|---|---|
| P0 | 主链不可用/不安全/契约对不上无法联调/数据错误 | 阻塞：不得 ACCEPT |
| P1 | 重要缺失或不可验证：异常/边界/错误码/架构越层/测试缺失 | 修完复验；不得默认放行 |
| P2 | 非关键质量：命名/注释/重复/小瑕疵 | 可留，须登记 owner 与去向 |

- 每条必填：编号、位置（文件:行/接口/页面）、现象、成因（可考才写，否则「成因未明」）、修复判据（修到什么表现算过）、建议方向、级别。
- 无出处、无修复判据的条目不进清单；同一问题只记一条。
- 分级只标事实，不代替结论；结论看残留分布。
- 不评个人风格偏好；无判据的偏好最多记 P2 一句。
- 问题归属到修改方（前端/后端/文档/测试），归因不明写「双方核对」。

## 6. 证据标准

只认六类：可复现命令与输出、测试报告、构建产物、真实运行/截图、日志、文件 sha256。

不认：模型自述、口头描述、旧截图、旧命令输出、子代理的「已通过」汇报。

- 每条结论挂证据路径或命令；无证据的结论写成「未验证」。
- 未取证 ≠ 通过；未取证项必须出现在报告的未覆盖或风险里。
- 证据要新鲜：本轮生成、能复现；环境、版本、数据写清楚。
- 证据可被复核：命令能直接重跑；文件用 sha256 标定版本；截图附路径。
- 评审者不得只描述现象而省略复现方式。

## 7. 结论三值

| 结论 | 含义 | 判定条件 |
|---|---|---|
| ACCEPT | 放行 | 无 P0/P1；AC 全过；证据齐；隔离记录齐 |
| FIX | 可修后复验 | 有 P1/P2 残留且可修；P0 已清零 |
| REJECT | 阻塞 | P0 残留；或证据缺失无法判断；或隔离不成立 |

- 结论必须与本轮清单一致：写 ACCEPT 就不能有 P0/P1 残留。
- P0 残留一律 REJECT，不得「先放行后补」。
- P1 残留不得自行 ACCEPT，默认 FIX；owner 明确签收风险（风险、责任人、期限）才可转 ACCEPT，并由验收登记遗留风险。
- P2 残留可接受，须登记 owner 与去向。
- 无问题也要写覆盖边界：查了什么、没查什么、残余风险；禁止一句「无问题」收尾。
- 评审结论是放行建议；完整档 owner 签收后生效；最终交付结论归验收。

## 8. 复核与 3 轮上限

- 复核由隔离评审者做，只验本轮已确认项是否按修复判据修好；不得由修复方自验。
- 复核不重新全量评审；本轮新发现降一档记录（P0 按实际级别）。
- 同一批问题最多 3 轮（含首轮）。第 3 轮后：
  - P0 残留 → REJECT；
  - P1 残留 → 不得 ACCEPT，结论记 FIX，升级 owner 决策：继续修或由验收登记遗留风险；
  - P2 可留，登记 owner 与去向。
- 不自动开第 4 轮；开新轮须 owner 明确授权并写进报告。
- 轮次写入报告（第 n 轮，上限 3），并回填 loop-log。

## 9. 报告与落点

- 评审包：`.spec/tasks/<YYYY-MM-DD>-<slug>/review-package.md`，模板 [review-package.md](../skills/review/templates/review-package.md)。
- 评审报告：`.spec/tasks/<YYYY-MM-DD>-<slug>/review-report.md`，模板 [review-report.md](../skills/review/templates/review-report.md)。
- 报告固定六节：`## 0. 隔离信息`、`## 1. 评审包与判据`、`## 2. 证据核对`、`## 3. AC 逐条核对`、`## 4. 问题清单`、`## 5. 结论`。
- `## 5. 结论` 必须出现 ACCEPT、FIX、REJECT 三值，并给出本次选择与依据。
- 问题清单一表到底（编号、位置、级别、现象、成因、修复判据、建议方向），不再另建第二份清单。
- 报告交验收；验收只认报告与证据，不认口头转述。
- 报告不写产出过程、不写自检结论、不写「我认为」。

## 10. 缺陷逃逸复盘

- 验收后 2 周内漏出的 P0/P1，必须回填一条复盘：评审为什么没抓到。
- 三个必答：缺哪条判据、缺哪项证据、缺哪个缺陷模式；不许写「疏忽」。
- 结论落到三处：补判据（本文件）、补模式（`bug-patterns/`）、补测试门禁（auto-test 契约）。
- 复盘写进 issue 卡或报告附录；随验收指标一起算缺陷逃逸率。
- 同一类逃逸第 2 次出现 → 升级为判据或门禁，不得只口头提醒。

## 11. 指标回填

- 评审侧只回填三件事：结论、评审发现数、复核轮次；一次通过按首轮结论 ACCEPT 计。
- 指标定义与算法归验收契约（§8），评审不另立口径；两个数分开看。
- 指标难看先查判据缺口，不要先加流程。

## 12. 反模式

| 反模式 | 纠正 |
|---|---|
| 同一会话写完自己看一遍 | 换 fresh 子代理或新会话 |
| 把产出过程、自检结论给评审者 | 只给评审包 |
| 用「无问题」收尾 | 写覆盖边界与残余风险 |
| 评审时顺手改源码 | 只记录，P0 附建议补丁 |
| 只贴截图不贴命令 | 命令 + 退出码 + 产物 |
| 采信子代理「已通过」汇报 | 核验报告与证据文件 |
| 有问题先放行后补 | P0 残留 REJECT |
| 无限复核对同一批问题 | 3 轮上限，只验本轮 |
| 只评风格 | 先契约与可运行，风格记 P2 |
| 漏看缺陷模式库 | 每轮逐条对照并记录结果 |

## 13. 与验收的分工

| 维度 | 评审（review） | 验收（acceptance） |
|---|---|---|
| 回答 | 做没做对 | 能不能收 |
| 依据 | AC/契约/证据/缺陷模式 | 评审结论 + DoD + 证据 |
| 结论 | ACCEPT/FIX/REJECT（放行建议） | ACCEPT/FIX/REJECT（交付结论）+ owner 签收 |
| 产物 | review-package.md + review-report.md | acceptance-report.md |
| 不重复 | 不评业务价值与范围决策 | 不重评技术细节 |

- 验收不得推翻评审的 P0 结论；要推翻必须 owner 明确签收并记录风险。
- 评审通过 ≠ 可交付；验收通过才算交付完成。
