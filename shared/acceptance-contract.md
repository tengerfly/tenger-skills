# 验收契约（v4 唯一验收口径）

> 适用：所有交付前的验收动作。Skill 与 workflow 只说「验收」，判据只认本文件。
> 一句话：验收不重复评审，只回答一件事——这份交付能不能收、现在能不能收。
> 与 `review-contract.md` 共用同一套判据、证据标准、风险三档、结论三值与复验轮次上限；分工口径见评审契约 §13。

## 1. 定位与分工

| 环节 | 谁做 | 回答什么 | 产出 | 结论 |
|---|---|---|---|---|
| 评审 review | 独立评审者 | 质量与问题：AC 之外还有没有错 | 评审报告 + 问题清单 | ACCEPT / FIX / REJECT |
| 验收 acceptance | 未参与产出的验收执行者（完整档含 owner） | DoD 与放行：问题是否清零、证据是否够、风险是否明示 | 验收清单 + 验收报告（含签收） | ACCEPT / FIX / REJECT |

- review 管「检查与判断」，acceptance 管「最终 DoD 核对与放行/签收」。
- 两契约判据与结论值必须一致：ACCEPT 放行、FIX 可修后复验、REJECT 阻塞；不得使用旧体系门禁值或自造词。
- acceptance 不重新找问题。评审问题未清、或验收中新发现 P0/P1 时，回评审/修复流程，不靠验收兜底。
- 顺序固定：开发自测 → 独立评审 → 修复与复验 → 验收 → 交付/签收。验收是交付前最后一道，之后只有交付动作，不再改交付物。

验收的输入（缺哪项按 §5 结论规则处理）：

| 输入 | 要求 |
|---|---|
| 任务与 AC | 有明确任务单/需求，AC 可逐条判定；AC 缺失或模糊 → 先补需求 |
| 交付物 | 路径明确，含本次变更范围与基线 |
| 评审报告与问题清单 | `.spec/tasks/<YYYY-MM-DD>-<slug>/review-report.md`；P0/P1 逐条有状态与证据；评审带 P1 owner 签收风险的，验收要复核登记 |
| 测试/验证证据 | 本轮生成，能追溯到本次交付物 |
| 变更与回滚说明 | 改了什么、怎么退、退到什么基线 |
| 遗留风险 | 已登记或声明「无」，不接受口头带过 |

## 2. DoD 五条

五条全部成立才可能 ACCEPT。逐条核对记录进验收清单与报告 §1。

| # | DoD | 判据（可判真假） | 不成立时 |
|---|---|---|---|
| 1 | AC 逐条对应 | 需求 AC 每条都有实现位置与验证证据；无「未覆盖」「口头满足」「部分完成未说明」 | FIX |
| 2 | 无未决 P0/P1 | 无 P0；P1 全部修复并复验，或 owner 已明确签收风险并登记为遗留风险（未签收即未决）；P2 已登记 | FIX |
| 3 | 证据可复现 | 关键验证命令本轮重跑过；有命令、工作目录、退出码、输出、环境版本 | FIX；核心证据缺失可 REJECT |
| 4 | 可回滚 | 报告写清改了什么、回退到什么基线、怎么退、谁负责；不可回滚的变更必须显式说明并获 owner 接受 | FIX；完整档无回滚验证可 REJECT |
| 5 | 风险显式 | 遗留风险在报告 §3 登记：风险、影响、等级、owner、截止、处置 | FIX |

- AC 来自需求或任务单，不得验收现场新造；AC 缺失时先补需求，验收只能 FIX/REJECT。
- P1 默认 FIX，不默认放行；只有 owner 明确签收风险、写清责任人与期限，才算「已签收」，报告必须登记。
- 测试全绿不等于 DoD 成立；文件存在不等于交付完成；提交成功不等于可回滚。

## 3. 证据核验清单

只认六类证据形态，其余按未验证处理：

| 证据形态 | 核验动作 | 不合格示例 |
|---|---|---|
| 可复现命令与输出 | 本轮原样重跑：命令、工作目录、退出码、关键输出 | 只贴命令不贴输出；贴别人的输出 |
| 测试报告 | 看用例数、失败数、跳过数与时间，与代码版本对应 | 旧版本报告；只写「全部通过」 |
| 构建产物 | 产物存在、时间晚于最后一次改动、能追溯到本次变更 | 产物被清空仍宣称构建成功 |
| 真实运行/截图 | 本轮时间戳、可辨认页面/入口、与 AC 场景对应 | 旧截图；截图无时间；只截局部 |
| 日志 | 原文与时间，能定位到任务/请求；脱敏但不删关键行 | 手工摘抄；加工过的「正常」日志 |
| 文件 sha256 | 对被验交付物/报告/产物计算摘要并复算比对 | 只写哈希不写算法与文件；抄哈希不复算 |

核验四步，缺一步按未取证：

1. **存在**：路径真实可打开，不是描述；
2. **新鲜**：生成时间在本次变更之后，旧证据未失效；
3. **可复现**：换执行者按同命令能得同结论；
4. **支撑结论**：证据内容确实证明该条 AC/DoD，不是相关但不等价。

- sha256 用法：被验交付物、证据文件、评审/测试报告各算一次；摘要写进报告 §2；复核时复算比对，不一致按基线已变处理，要求重验。
- 复算命令：Windows `Get-FileHash <path> -Algorithm SHA256`；Linux/macOS `sha256sum <path>`。
- 不认：模型自述、口头描述、转发结论、旧截图、无退出码的命令、「应该没问题」。
- 证据不足时结论只能 FIX/REJECT，不得降级为口头保证。

验收证据包（归档到任务工作区，缺件不算完成）：

- 验收报告（含 §2 证据清单与摘要）与验收清单；
- 交付物清单 + 各自 sha256；
- 评审报告与问题清单（P0/P1 状态）；
- 本轮测试/运行证据（命令、输出、截图、日志）；
- 签收记录（完整档）。

## 4. 验收流程

1. **收输入、冻范围**：确认 AC 版本、交付物、变更范围与基线；范围不清先停下澄清，不边收边改。
2. **逐条核 DoD**：五条逐条打勾或打叉，每条附证据位置，不做整体印象判断。
3. **抽核证据**：重跑关键命令、复算 sha256、看截图/日志时间戳；抽核要覆盖核心 AC，不只抽最容易的。
4. **清问题与风险**：确认 P0/P1 状态为已修复并复验或已签收；遗留风险逐条进报告 §3，owner 接受与否写清。
5. **出结论**：按 §5 判 ACCEPT/FIX/REJECT，写明触发依据；不写「基本通过」。
6. **签收与回填**：完整档完成签收；归档证据包；回填 loop-log；验收发现的问题入问题池。

## 5. 结论三值

结论唯一合法取值：`ACCEPT` / `FIX` / `REJECT`。

| 结论 | 含义 | 触发条件 | 后续动作 |
|---|---|---|---|
| ACCEPT | 放行/可交付 | DoD 五条成立；无 P0；P1 已清或 owner 已签收风险并登记；证据足且复算一致 | 签收（完整档）、归档证据包、回填 loop-log、可交付 |
| FIX | 可修后复验 | P0 已清但有可修项：AC 小缺口、证据不足、P1 未清或未获签收、P2/风险未登记 | 问题清单交回产出方；修复后只复验本轮项；最多 3 轮 |
| REJECT | 阻塞 | 无 AC/基线/授权；核心证据缺失或造假；存在未处理 P0；范围失控；完整档拒绝签收 | 停止交付，写明缺什么与下一步 owner，升级用户/Lead |

- 判定顺序：先查 REJECT 条件 → 再逐条查 DoD → 最后出 ACCEPT/FIX。有未处理 P0、或不可回滚且 owner 不接受时，其余再好也不得 ACCEPT。
- 复验最多 3 轮（与评审同一上限）。第 3 轮后：P0 残留 → REJECT；P1 残留 → FIX，由 owner 决策继续修或签收风险后转 ACCEPT 并登记；不得开第 4 轮，不得「先放行后补」。
- 与评审契约 §7/§8 同一口径：评审签收的 P1 风险由验收复核并登记；验收不得推翻评审的 P0 结论，要推翻必须 owner 明确签收并记录风险。
- 报告结论与评审报告结论必须一致；不一致时以证据为准，冲突升级用户/owner，不得各写各的。
- 验收方不得自判通过：产出方自检、自述、自签一律不构成验收。

## 6. 签收

签收 = owner 对「本次范围 + 结论 + 遗留风险」的明确接受，不是客套确认。

- 完整档：必须 owner（用户本人或其明确授权的责任人）签收；缺签收只能 FIX（待签），不能 ACCEPT。
- 标准档：由用户指定人或产出方负责人签收；未指定时记「待签」并回填 loop-log。
- 轻量档：不要求签收，验收清单自检记录即算。
- 签收写进报告 §4：签收人、结论、遗留风险接受范围、决策/记录 id、日期。AI 不得代签；owner 不在场就停在待签。
- 签收后发现交付物变化：改动范围内的重新验收；范围外变更按新任务处理，不得沿用旧签收。

## 7. 遗留风险与豁免

| 字段 | 要求 |
|---|---|
| 风险/遗留项 | 具体到现象与位置，不写「一些小问题」 |
| 等级 | P0/P1/P2 三档；P0 不可豁免 |
| 影响 | 什么场景会出问题、影响谁 |
| owner | 具体人/角色，不是「团队」 |
| 截止 | YYYY-MM-DD，到期未处置触发重新验收 |
| 处置 | 修复、监控、回滚或明确不做（写明理由） |
| 是否阻塞交付 | 是/否；「否」必须由 owner 明确接受 |

- 默认无豁免：P1 豁免 = owner 明确签收风险 + 补证计划 + 到期，报告 §3 登记，结论记 ACCEPT 并注明「有条件接受」；未签收只能 FIX。
- 豁免没写进报告 §3 视为不存在；P0 任何情况下不得豁免。
- 风险到期未处置：重新验收，结论按实际证据重出；不得沉默续期。

## 8. 指标与回填

每个验收任务回填 [loop-log.md](../loop-log.md) 一行，至少含「日期、任务、评审发现数、一次通过、新增问题、已修复、复发、Skill 改动」。

| 指标 | 定义 | 口径 |
|---|---|---|
| 一次验收通过率 | 首次验收即 ACCEPT 的任务数 / 同期完成验收的任务数 | 每任务只算一次，取首次结论；复验通过不算一次通过；轻量/标准/完整都计入 |
| 缺陷逃逸率 | 验收后 2 周内发现的 P0/P1 数 / 同期已交付任务数 | 只算属于该交付范围的缺陷；环境或需求变更不计 |
| 评审发现数/任务 | (评审问题数 + 验收发现数) / 验收任务数 | P0/P1/P2 分列；同一问题不重复计 |
| 复发率 | 同类问题再次出现次数 / 已修复问题数 | 按问题卡类别归并 |

- loop-log「一次通过」列填首次结论即 ACCEPT（评审或验收）；一次验收通过率只统计验收结论，评审侧口径见评审契约 §11，两个数分开看。
- 样本 < 3 只记录，不解读趋势、不排名。
- 缺陷逃逸必须复盘：回填「评审/验收为什么没抓到」，可复用判据经 issue 流程补进评审 Skill 或 [bug-patterns/README.md](../bug-patterns/README.md)。
- 指标用于改进评审验收本身，不用于给产出方打分。

## 9. 报告与清单

- 验收报告按固定五节写：`## 0. 任务与范围`、`## 1. DoD 核对`、`## 2. 证据核验`、`## 3. 遗留风险与豁免`、`## 4. 结论`；标题不许改。
- `## 2. 证据核验` 必须含 sha256（至少一条，自己复算过）。
- `## 4. 结论` 必须只出现一个三值结论，并含签收字段（完整档）。
- 验收清单逐项打勾，不空项；不适用写「不适用 + 原因」，不写「略」。
- 报告与清单放进任务工作区 `.spec/tasks/<YYYY-MM-DD>-<slug>/`，与本任务一一对应。

## 10. 常见失败模式

- 把测试全绿当 DoD 成立。
- 拿文件存在、提交成功当交付。
- 用上一次输出或旧截图充当本轮证据。
- 产出方自审自签，验收执行者参与过产出。
- P1 留在聊天里，没进报告和问题清单；或把未签收的 P1 写成「已接受」。
- FIX 直接改写为 ACCEPT 放行。
- 无回滚说明或回滚未验证。
- 报告结论只写「通过/基本没问题」，不写三值。
- 验收现场新造 AC，或改 AC 迁就实现。
