# 接收评审的纪律（产物方公共约定）

> 适用：所有会接收评审任务清单的产物方 skill——PRD-Design / Prototype-Design / UI-UX-Design / Backend-Tech-Design / Frontend-Tech-Design / Backend-Dev / Frontend-Dev（以及 Bug-Fix 的修复环节）。
> 来源：superpowers/receiving-code-review（MIT），2026-09-10 吸收。

## 原则

**先验证再实施，先提问再假设；技术正确性 > 社交舒适。**
评审是技术输入，不是情绪表演。

## 六步响应

1. **READ**：完整读完，先不反应
2. **UNDERSTAND**：用自己的话复述要求（不懂就引用澄清协议问）
3. **VERIFY**：对照代码库 / 产物实际情况核实
4. **EVALUATE**：对**本项目 / 本产物**是否成立
5. **RESPOND**：技术性确认，或有理有据地反驳
6. **IMPLEMENT**：一次一项，逐项测

## 禁止的回应（AI 通病）

**绝不说**：「你说得完全对！」「好建议！」「谢谢指出！」——任何感谢表达都算。
**改为**：复述技术要求 / 直接改并在产物中体现 / 有异议给技术理由。

## 不清楚就先停

任何一条不清楚 → **停下来，不要先做其他条目**。条目之间可能相关，部分理解 = 错误实施。

```
❌ 错：先做 1、2、3、6，回头再问 4、5
✅ 对：「1、2、3、6 我理解，4 和 5 需要先澄清再动。」
```

## 先查 YAGNI，再「按规范正经实现」

评审建议「完整/规范实现」时，先 grep 有没有真实使用：

- 没人用 → 反问：「这里没有调用方，是否直接删除（YAGNI）？」
- 有人在用 → 再按规范实现。

## 什么情况下应该反驳

- 建议会破坏现有功能
- 评审方缺上下文
- 违反 YAGNI（功能没人用）
- 对本技术栈不正确
- 有兼容 / 遗留原因
- 与用户既有架构决策冲突

反驳方式：技术理由 + 具体问题 + 引用可运行的测试 / 代码；架构级冲突先找用户。

## 实施顺序

1. 先澄清所有不清楚项
2. 再按：阻塞项（破坏 / 安全）→ 简单修复 → 复杂修复
3. **逐项测**（不要一批改完再测）
4. 验证无回归

## 承认自己推错

简短陈述事实即可：「查了 X，确实是 Y，我原来的判断错了。已改。」
不要长篇道歉、不要为「当初为什么反驳」辩解。

## 与门禁闭环的衔接

- 回填 `已修复` 前必须逐项自测通过（见仓库根 `shared/evidence-before-claims.md`）；
- 改完触发复核，不自判通过（见仓库根 `shared/anti-deadloop.md` §一）。
