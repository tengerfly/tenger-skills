# 执行强度与自然语言入口

本文件定义所有 Skill 的任务裁剪规则。先判范围与风险，再加载所需领域规则；不要求用户学习状态名、Envelope 或调用顺序。生命周期回答“做什么”，执行强度回答“做到多重”，两者独立。下述名称是路由说明，不新增 Gate、状态或 schema 字段。

## 1. 默认路由

| 强度 | 判据 | 最小路径 | 记录与边界 |
|---|---|---|---|
| 轻量 | 低风险、范围明确、局部可回退；实验 Demo、已有项目小需求、小 Bug、单项审查 | 目标/验收点 → 相关上下文 → 实现或审查 → 针对性验证 → 结果 | 独立任务摘要；不创建正式状态，不要求完整 PRD/TDD/FTDD、Envelope、manifest 或完整 onboarding |
| 标准 | 常规跨模块迭代、需要正式跨领域交接；或用户明确要求纳入工程流程 | 影响分析 → 受影响领域 → 实现/评审 → 相关回归 → 指定终点 | 沿用正式契约与有效基线；只更新受影响产物，不重跑无关历史阶段 |
| 完整 | 大型新项目、跨系统架构变更、高风险操作 | 需求/设计/实现/验证及必要的专项安全、发布控制 | 完整追踪与审批；仍不执行未授权阶段，不为了完整而重做有效产物 |

不能仅凭“Demo”“小改动”、代码行数或预计工时判轻量。以下情况至少进入标准流程，并补齐对应的完整风险控制：认证/授权边界、支付/资金、敏感数据、不可逆删除、数据库迁移、破坏性接口变更、生产部署或事故。新核心架构、关键基础设施或不熟悉依赖还须按 `oss-research-policy.md` 核验；不把研究变成每次改 CSS 的固定成本。

**产品探索不能被误裁剪**：“做一个像某成熟产品一样的完整应用”、用户不清楚整体功能或明确要求先调研竞品并挑选功能时，至少按标准产品探索处理。先研究并展示功能全景，再确认范围；不能以“只问关键问题”缩成用户画像 + 自建/开源两问。只有用户明确限定 Demo/单点或确认过的功能子集才裁剪；用户明确要求的竞品研究在任何强度下都不能静默省略。自建/开源是后续实现选择，不代替需求探索。

**反向约束：不得以「不能省略研究」为由提前投入研究**。本条要求的是「全景必须先于范围决策」，不是「全景越早开跑越好」。研究范围以用户已确认的需求方向为裁剪依据；方向未确认即展开大范围检索属资源浪费，此时应先陈述 AI 理解的需求方向供用户改写。判轻量或完整都不改变这条次序（门禁见 `WorkFlow/SKILL.md` §3.1）。

默认选足以覆盖风险的最短路径。范围不清时先局部盘点、只问阻碍验收的关键问题；未知风险未排除前不执行高风险修改。用户可以要求更严格，但不能用轻量标签取消安全与授权。

**Superdesign 保留边界**：UI-UX-Design 的 A 路径仍按原来的输入、方案确认、云端导入/回传和门禁执行，不被本次轻量裁剪改写；B 自写才按其独立 SOP 裁剪。明确要求云端出稿时不能为了省流程偷偷改成本地出稿。

## 2. 轻量独立执行（不是正式流程的后门）

开工用一句话交代“按轻量处理，复用哪些基线，修改范围与终点是什么”。直接调用所需 Skill，不先展开全量注册表或创建全套 `.spec/`。一次会话可串联多个必要 Skill，复用同一摘要，不每次造一份交接文件。

最小摘要含：
- 目标、允许/禁止修改范围、用户授权来源；
- 可核对的验收点、已确认输入及本次不改的行为；
- 相关文件/需求版本引用、验证方式；
- 收尾补实际改动、命令/结果、未验证项、下一步。

无问题的单次任务可在会话中保留；暂停、跨会话或交给其他执行方时写入已有任务记录，没有记录才建 `.spec/tasks/<task-id>.md`。已观察到需追踪的失败、阻塞或纠正按 `shared/problem-recording.md` 在下一安全节点持久化，并添加最小项目问题索引；根因未知标待确认，不等收尾。详情仍复用同一文件，不补全套正式建档。恢复/交付前回读未决项；敏感信息不落盘。

缺少完整 PRD/TDD/FTDD、原型或 PROJECT/PLAN 不单独构成阻塞：可用用户明确目标/验收点、相关源码与现有界面、局部实现计划替代对应形式产物；**不能替代未知业务规则或必需接口信息**。已有文档必须尊重，不得凭代码现状推翻已批准需求。局部 UI 可以用现有页面与确认的变更清单作为结构基线；新复杂交互仍需澄清结构。

轻量只改变程序性前置：不强制竞品、整套技术设计、三套视觉方案、独立评审 Skill、资产沉淀、自动提交或生产发布。检查和测试不可省略；按影响选用现有测试、构建、源码检查、真实浏览器验证。未验证的行为明确保留，不能声称全部通过。没有浏览器时可完成代码/草稿，但不能宣称视觉或交互验收通过（专业视觉验收 Skill 的硬依赖不变）。

## 3. 与正式契约的边界

- 轻量摘要不是 `execution`/Gate 记录；不要用正式 `PASS`、`TEST_PASSED`、`APPROVED` 等标签冒充里程碑，不自动写 `.spec/workflow.yaml`、manifest 或批准决策。
- 已有正式项目仍可做独立局部任务，但开工必须检查与本次范围有关的已批准基线、待处理 Gate 和风险。相关 `BLOCKED` 不得以换标签绕过；只可在允许的整改范围内工作，不能宣称上游已解锁。无关模块的阻塞不强迫本次跑全项目。
- 对已登记产物或其实现的修改：保留原批准版本，不覆写其身份/证据或继续把已变化的结果标为 APPROVED。轻量可输出候选补丁/草稿；需要更新正式批准基线时升级。
- 标准/完整流程，或任何正式状态转换/下游自动消费，都必须使用现有 Envelope、manifest、证据、批准与 `task_preflight.py`。这些校验器没有“轻量绕过”开关。有效基线只能按已有合法边与证据复用，不能伪造跳跃状态。
- 升级时复用已做工作，将真实产物/证据注册并补缺口，不重做无关阶段，不为开始工作伪造完成证据。生产操作、付费、外部仓变更始终另行确认。

## 4. 时间与交互

阶段可见性按 `workflow-visibility.md` 执行；轻量只用简短状态说明，不建完整看板。独立验收、回归与测试统一由 `auto-test` 按相关层执行，开发自测保留但不替代验收 Gate。

开工简述路径即可，确定的低风险动作不逐步请求确认。默认终点是用户要求的可验收结果，不是整条生命周期；“修复 Bug”包括针对性验证，不默认继续发布。“先分析/只出计划”则只做到该终点。

尊重用户给出的时间/成本预算；未提供时不编造精确工期。优先交付核心路径，局部变更只回归相关项。发现范围扩大、需新增依赖/付费或预计超出用户预算时，说明影响并确认扩展，不静默升级。无法在预算内验证的内容如实列出，不用更多文档代替验证。

领域自检与最终评审可复用同一版本的证据；改动后仅失效受影响证据。不为制造第二版而返工，不重复进行相同全量检查。
