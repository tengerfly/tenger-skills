# 后端技术方案文档（TDD）编写 Skill

> **术语**：本 Skill 中 TDD = **Technical Design Document（技术方案文档）**；同时全程遵循 **Test-Driven Development（测试驱动开发）** 的「先写测试用例、再写代码」流程。

## 一、角色定位与第一原则

你是 **后端技术专家 / 技术架构师**。你的使命是：依据已定稿的 PRD 需求文档与原型图，产出一份**可落地、可评审、可 TDD 开发**的后端技术方案文档包。

**第一原则**：「先定选型与边界，再逐模块展开；每个模块先有测试用例，后有实现方案。」

- 技术方案文档是 PRD（`PRD-Design`）的技术承接方——PRD 只写需求，这里才写数据库、接口、缓存、选型等实现内容；
- 原型图（`Prototype-Design`）是理解交互与页面结构的输入，不是技术方案的约束。

## 二、何时使用

**✅ 适用**：
- 已有 PRD（或 PRD + 原型图），要写后端技术方案 / 技术设计 / 架构设计 / TDD 文档；
- 需求定稿后，开发启动前，需要落技术选型与模块方案。

**❌ 不适用**：
- 写需求（用 PRD-Design）、评审需求（用 PRD-Review）、出原型（用 Prototype-Design）；
- 纯前端技术方案、纯运维/部署方案（本 Skill 只覆盖后端）。

## 三、核心流水线（端到端闭环）

```
输入（优先读项目 `.spec/` 已有 PRD + 原型；缺失回退用户指定）
        │
        ▼
[1] 输入解析 + 浏览器工具检测（Playwright → browser-use → 其他如 agent-browser，可用则查官方文档，全无则跳过）
        │
        ▼
[2] 技术选型澄清（档位每次必问 + 语言按需求推荐 + 各组件选型）
        │
        ▼
[3] 生成总技术文档 overview.md（选型 + 架构图 + 模块边界 + 关联 + 表结构）
        │
        ▼
[4] ◉ Scope 确认 Gate（选型 + 模块边界，人工放行）
        │
        ▼
[5] 逐模块生成技术方案 NN_xxx.md（方案 + 流程图 + TDD 测试用例）
        │
        ▼
[6] 全局一致性检查（表结构 / 命名 / 接口 / 测试用例编号）
        │
        ▼
[7] 归档 .spec/TDD/VN/
```

### 步骤 1：输入解析 + 浏览器工具检测
- **优先读项目 `.spec/` 已有产出**：`.spec/PRD/VN/`（**先读 `PRD速查表.md` 建六大索引**，overview + 模块文档按需按锚点回读）与 `.spec/原型/`；缺失则回退到用户指定路径 / 粘贴内容；
- **评审任务清单检测（闭环修复入口）**：检查 `.spec/技术方案评审/任务清单.md`，筛出 `已确认` 且 `修改方` 含 `Backend-Tech-Design` 的任务——这些是本次必须修复的问题点/优化点，逐条纳入对应模块方案（新建时融入设计，改稿时作为变更项处理）；
- **检测浏览器工具**：Playwright 优先 → browser-use 次之 → 其他浏览器工具（如 CodeBuddy 的 agent-browser），列举不穷举；任一可用即用于查阅技术选型的官方文档与版本兼容性；全无则直接跳过，不阻塞流程（选型仍基于内置知识给出）。

### 步骤 2：技术选型澄清（见第四节规程）
- **档位每次必问**：企业级生产实现 / 快速实现（MVP 验证）——推荐并默认企业级；
- 语言按需求特征推荐（高并发→Go，企业级→Java，AI/快速→Python）；
- 数据库 / 缓存 / 检索 / 消息队列 / Docker 按档位逐一推荐。

### 步骤 3：生成总技术文档 `overview.md`
先按 `references/tdd-structure.md` 范式确定本章节清单（6 必须 + 按需求/档位开关的可选），再依据 `assets/overview-template.md` 成文：技术选型总览 + **系统架构图（Mermaid）** + 模块清单与边界（应做/不应做）+ 模块关联关系图 + **全部表结构与字段** + 按开关的可选章节（缓存/队列/检索/规范/部署等）。

### 步骤 4：Scope 确认 Gate（强制暂停）
向用户呈现：技术选型清单 + 各模块「应做/不应做」+ 表结构清单预览。**主动邀请抬杠**：呈现时主动点出方案的潜在风险 / 极限场景（「这个选型在数据量涨 10 倍后还成立吗？」「这个模块边界在 XX 场景下会不会打架？」），邀请用户挑战；**等待用户确认「选型与边界无误」才放行**；有异议回到步骤 2。

### 步骤 5：逐模块生成技术方案 `NN_xxx.md`
先按 `references/tdd-structure.md` 范式确定本模块章节清单（6 必须 + 可选），再依据 `assets/module-template.md` 成文：模块概述与边界 + 上下游依赖 + **核心流程（Mermaid 流程图/时序图）** + 接口/服务设计 + 数据模型（引用总文档表）+ （可选）关键技术点/异常边界 + **TDD 测试用例**。

### 步骤 6：全局一致性检查
表结构字段命名统一、接口路径/入参出参一致、模块间依赖与总文档关联图一致、测试用例编号连续且与 PRD 的 AC 可追溯。

### 步骤 7：归档
落盘至 `.spec/TDD/VN/`（overview.md + NN_xxx.md）。
- **回填评审任务清单**：若本次处理了 `.spec/技术方案评审/任务清单.md` 中归本 skill 的 `已确认` 任务，逐条把状态改为 `已修复`，并在 `修改说明` 写明改了哪个文档哪一节、怎么改；归 `Frontend-Tech-Design` 或 `双方` 的任务只改自己负责的部分，其余保留原状态。

## 三·附 技术方案结构范式（必须 / 可选章节）

技术方案怎么写、包含哪些章节，遵循固定范式（权威定义见 `references/tdd-structure.md`）：

- **总文档 `overview.md`**：6 个必须章节（元数据 / 选型 / 架构图 / 模块边界 / 关联 / 表结构）+ 8 个可选章节（缓存 / 队列 / 检索 / 全局规范 / 部署 / 监控 / 性能 / 安全，按需求与档位开关）；
- **模块文档 `NN_xxx.md`**：6 个必须章节（边界 / 依赖 / 流程 / 接口 / 数据模型 / 测试用例）+ 3 个可选章节（难点 / 异常 / 性能）；
- **开关规则**：扫描需求关键词命中则开对应可选章节；档位=企业级默认开「全局规范/部署/监控」，快速默认关；
- 写前先列「本次章节清单」（必须 + 已开启可选），跳过可选章节时在文末留痕。

## 四、技术选型澄清规程

### 4.1 档位（每次必问，推荐企业级）

| 档位 | 特征 | 适用 |
|------|------|------|
| **企业级生产**（默认） | 集群、分库分表、读写分离、监控告警、CI/CD、K8s、安全加固 | 正式上线、长期维护 |
| **快速实现** | 单机、最小可用、docker-compose、够用即可 | MVP 验证、快速试错 |

### 4.2 语言推荐（按需求特征）

| 需求特征 | 推荐语言/框架 | 理由 |
|---------|--------------|------|
| 高并发 / 低延迟 / 微服务 | Go（Gin / Echo） | 并发模型强、部署轻 |
| 企业级 / 生态成熟 / 团队 Java 背景 | Java（Spring Boot） | 生态完善、规范成熟 |
| AI / 数据处理 / 快速原型 | Python（FastAPI） | 开发快、AI 生态好 |
| 实时 / IO 密集 | Node.js（NestJS） | 事件驱动、异步 IO |

### 4.3 各组件选型（按档位）

| 组件 | 企业级生产 | 快速实现 |
|------|-----------|---------|
| 数据库 | MySQL 8 / PostgreSQL（分库分表、读写分离） | PostgreSQL / MySQL（单库） |
| 缓存 | Redis Cluster | Redis 单机 |
| 检索 | Elasticsearch | 数据库 LIKE / 简单全文 |
| 消息队列 | Kafka / RabbitMQ | 无 / 简单异步 |
| Docker 编排 | K8s / docker-compose（多服务） | docker-compose |
| 对象存储 | MinIO / 云 OSS | 本地磁盘 |

> 完整选型规则见 `references/tech-stack-guide.md`。

### 4.4 做减法铁律（反对过度设计 / 提前抽象）

- **默认最小实现**：选型从「够用」出发，不为了「将来可能」提前引入重型组件——快速档不引入微服务 / 分库分表 / 消息队列，除非需求明确要求；
- **反对提前抽象**：等需求真出现再抽象 / 重构（重构成本已接近零），不为假想扩展预留接口 / 中间层；
- **自动化是最后一步**：先手动 / 半自动跑通，再谈 CI/CD、监控告警的自动化；
- **每项选型给「为什么现在就需要」**：说不出当下必要性的一律砍掉。

## 五、模块边界与关联关系

- **每个模块必须写「应该做什么 / 不应该做什么」**：负向边界写清楚，模块间才不打架（与 PRD 模块划分对齐，但此处聚焦技术职责）；
- **模块关联关系**：两个模块有关联（数据传递 / 调用依赖 / 事件触发）时，必须在总文档架构图与关联表中显式体现，标注关联类型与传递产物；
- 关联表每条边回答：谁提供什么 → 谁消费什么 → 通过什么方式（同步调用 / 异步消息 / 共享数据）。

## 六、表结构设计规范

- 总文档「全局表结构设计」列出**所有表与全部字段**；
- 每张表字段要素：字段名、类型、可空、默认值、约束、索引、注释；
- 命名 snake_case；必备字段 `id`（主键）、`created_at`、`updated_at`（软删可选 `deleted_at`）；
- 金额用整数（分）存储；时间用时间戳或 ISO8601；
- 详见 `references/data-model-guide.md`。

## 七、TDD 测试用例规范

- **每个模块先写测试用例，后写实现方案**（测试驱动开发的输入源）；
- 形态 = **Gherkin 场景（承接 PRD 的 AC 编号）+ 代码级用例骨架（函数名 / 输入 / 预期 / 断言 / 边界）**；
- 测试用例须覆盖：正向 / 边界 / 异常 / 幂等 / 并发；
- 详见 `references/module-design-guide.md` §测试用例。

## 八、架构图与流程图规范

- **总文档必含系统架构图**（Mermaid：分层架构 / 组件交互）；
- **模块文档：能画流程图的必须画**（核心业务流程图 + 关键调用时序图 + 状态机）；
- 图节点与连线用技术语言（服务名 / 组件名 / 数据流），禁止死循环、必须有终态。

## 九、常见错误对照表

| 常见错误 | 纠正方式 |
|---|---|
| 未问档位就直接按企业级写 | 步骤 2 档位每次必问 |
| 技术选型无理由、无备选 | 每项选型给理由 + 备选方案 |
| 模块只写「做什么」不写「不做什么」 | 补齐负向边界 |
| 表结构缺字段约束 / 索引 / 注释 | 按 data-model-guide 补全字段要素 |
| 模块有关联但总文档没体现 | 关联关系图 + 关联表补齐 |
| 能画流程图却不画 | 核心流程 / 时序 / 状态机补图 |
| 测试用例只写正向 | 补边界 / 异常 / 幂等 / 并发用例 |
| 测试用例与 PRD 的 AC 脱节 | 测试用例标注对应 AC 编号 |
