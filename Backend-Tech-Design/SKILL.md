# 后端技术方案文档（TDD）编写 Skill

> TDD = Technical Design Document；全程遵循测试驱动开发：先写测试用例，后写实现方案。

## 一、角色与第一原则

**角色**：后端技术专家 / 架构师。

**第一原则**：先定选型与边界，再逐模块展开；每模块先有测试用例，后有实现方案。

- TDD 承接 PRD：PRD 只写需求，这里写数据库、接口、缓存、选型等实现内容。
- 原型图用于理解交互与页面结构，不是约束。

## 二、适用范围

- 适用：已有 PRD（±原型），写后端技术方案/设计/架构/TDD；需求定稿后开发前落选型与模块方案。
- 不适用：写/评审需求（PRD-Design/PRD-Review）、原型（Prototype-Design）、纯前端或纯运维方案。

## 三、流水线

```
输入 → 解析 + 浏览器检测 → 选型澄清（一次定全）→ overview.md → ◉ Scope Gate → 逐模块 NN_xxx.md → 全局一致性 → 归档 .spec/TDD/VN/
```

1. **输入解析 + 浏览器工具检测**：
   - 优先读 `.spec/PRD/VN/`（先读 `PRD速查表.md` 建索引）与 `.spec/原型/`；缺失回退用户路径/粘贴。
   - 检查 `.spec/技术方案评审/任务清单.md`：`已确认` 且修改方含本 skill 的任务逐条纳入（新建融入、改稿作变更）。
   - 检测浏览器工具（Playwright → browser-use → 其他）：可用则查官方文档与版本兼容；全无则跳过，不阻塞。

2. **选型澄清（一次定全，开发期零决策）**：
   - 所有技术决策本步敲定、步骤 4 确认后定稿：语言/框架、服务拆分、通信方式、ORM、包管理与仓库形态、DB、缓存、检索、消息队列、对象存储、测试框架、部署（含开发实施选型）。
   - 档位每次必问：企业级生产（默认）/ 快速实现。
   - 验收标准：Backend-Dev 可直接从 TDD 拿到全部选型，开发期间不再出现技术栈决策。

3. **生成 overview.md**：按 `references/tdd-structure.md` 定章节清单，按 `assets/overview-template.md` 成文：选型总览 + 系统架构图（Mermaid）+ 模块清单与边界 + 关联图 + 全部表结构字段 + 可选章节。

4. **Scope 确认 Gate（强制暂停）**：呈现选型清单（全部定稿无悬空）+ 各模块应做/不应做 + 表结构预览；主动点出风险/极限场景（数据量涨 10 倍、模块边界冲突）邀用户挑战；确认后才放行，异议回步骤 2。

5. **逐模块 NN_xxx.md**：按 `references/tdd-structure.md` + `assets/module-template.md` 成文：边界 + 上下游依赖 + 核心流程（Mermaid）+ 接口/服务设计 + 数据模型（引用总文档）+ **实现细节与决策（可编码粒度）** + 可选难点/异常/性能 + **TDD 测试用例**。

6. **全局一致性**：表结构命名统一；接口路径/入参出参一致；模块依赖与总文档关联图一致；测试编号连续且可追溯 PRD AC。

7. **归档 + 回填**：落盘 `.spec/TDD/VN/`；处理过的评审任务改 `已修复` + 写修改说明；只改本 skill 负责部分。

## 三·附 技术方案结构范式

- 总文档：6 必须（元数据/选型/架构图/模块边界/关联/表结构）+ 8 可选（缓存/队列/检索/规范/部署/监控/性能/安全，按需求与档位开关）。
- 模块文档：7 必须（边界/依赖/流程/接口/数据模型/实现细节与决策/测试用例）+ 3 可选（难点/异常/性能）。
- 开关：需求关键词命中即开；企业级默认开规范/部署/监控，快速档默认关。跳过可选章节在文末留痕。

## 四、技术选型澄清规程

### 档位

| 档位 | 特征 | 适用 |
|---|---|---|
| 企业级生产（默认） | 集群、分库分表、读写分离、监控、CI/CD、K8s、安全加固 | 正式上线、长期维护 |
| 快速实现 | 单机、最小可用、docker-compose | MVP、快速试错 |

### 语言推荐

| 需求 | 推荐 |
|---|---|
| 高并发/低延迟/微服务 | Go（Gin/Echo） |
| 企业级/生态成熟 | Java（Spring Boot） |
| AI/数据处理/快速原型 | Python（FastAPI） |
| 实时/IO 密集 | Node.js（NestJS） |

### 组件选型

| 组件 | 企业级 | 快速 |
|---|---|---|
| 数据库 | MySQL 8/PostgreSQL（分库分表、读写分离） | PostgreSQL/MySQL 单库 |
| 缓存 | Redis Cluster | Redis 单机 |
| 检索 | Elasticsearch | LIKE/简单全文 |
| 消息队列 | Kafka/RabbitMQ | 无/简单异步 |
| 编排 | K8s/docker-compose | docker-compose |
| 对象存储 | MinIO/云 OSS | 本地磁盘 |

完整规则见 `references/tech-stack-guide.md`。

### 做减法铁律

- 默认最小实现：从「够用」出发，不为「将来可能」引入重型组件；快速档不引入微服务/分库分表/消息队列。
- 反对提前抽象：需求真出现再抽象；不为假想扩展留接口/中间层。
- 自动化最后一步：先跑通再谈 CI/CD、监控。
- 每项选型必须能回答「为什么现在就需要」，说不出一律砍。

### 开发实施选型（必须本阶段定稿）

| 项 | 企业级 | 快速 |
|---|---|---|
| 服务拆分 | 微服务（按业务域） | 单体/少量服务 |
| 服务间通信 | gRPC/消息队列 | HTTP REST（无微服务须显式声明） |
| ORM | Prisma/TypeORM | Prisma |
| 包管理/仓库 | pnpm + Monorepo（apps/server-*、libs/shared） | 单仓单应用 |
| 测试 | Jest + Supertest，五类覆盖 | Jest 核心路径 |
| 部署/CI | K8s/docker-compose + CI/CD | docker-compose |

- §四全部选型经 Scope Gate 确认后写入总文档「技术选型总览」，含结论+理由+版本/关键配置；不得留空、不得写「开发时再定」。

### 引导式澄清与确认清单

- **前置继承**：PRD 已明确的业务规则/边界/上限直接继承，不重复问；只问前置未明确且本方案必须定的点。
- **引导式提问**：用「问题 + 2~3 个选择项 + 理由」一次问透（如上传：存哪、怎么传、过大、断点、并发/类型/安全）；用户说的可能错，以专家视角纠正。
- **确认点逐条列清单**：所有需拍板点编号成清单在 Scope Gate 一次性呈现；确认后逐条记结论，未确认不推进。

## 五、模块边界与关联

- 每模块必写「应做/不应做」；负向边界防模块打架。
- 有关联（数据/调用/事件）必须在总文档架构图与关联表显式体现；每条边回答：谁提供什么 → 谁消费什么 → 通过什么方式（同步/异步/共享数据）。

## 六、表结构规范

- 总文档列全部表与字段；每字段含名、类型、可空、默认、约束、索引、注释。
- snake_case；必备 `id`/`created_at`/`updated_at`（软删可选 `deleted_at`）；金额整数分；时间用时间戳/ISO8601。
- 详见 `references/data-model-guide.md`。

## 七、TDD 测试用例规范

- 每模块先写测试用例后写实现；形态 = Gherkin 场景（承接 PRD AC）+ 代码级骨架（函数名/输入/预期/断言/边界）。
- 覆盖：正向/边界/异常/幂等/并发。

## 八、图规范

- 总文档必含系统架构图；模块能画流程图的必须画（流程 + 时序 + 状态机）。
- 节点连线用技术语言；禁死循环、必有终态。

## 九、常见错误对照表

| 错误 | 纠正 |
|---|---|
| 实施选型留到开发期 | 步骤 2 一次定全并写总文档 |
| 不问档位 | 每次必问 |
| 选型无理由/备选 | 给理由 + 备选 |
| 只写做什么 | 补负向边界 |
| 表缺约束/索引/注释 | 按 data-model-guide |
| 有关联总文档没体现 | 架构图 + 关联表 |
| 可画图不画 | 补图 |
| 测试只写正向 | 补边界/异常/幂等/并发 |
| 测试与 AC 脱节 | 标注 AC 编号 |
