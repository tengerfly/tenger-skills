# 模块技术方案编写指南

> 用途：指导每个模块 `NN_xxx.md` 的写法——边界、流程图、接口设计、TDD 测试用例。

---

## 一、模块边界写法

每个模块必须写清「应该做什么 / 不应该做什么」：

| 应做 | 不应做 |
|------|--------|
| 本模块核心职责（技术视角，如：订单的创建、状态流转、库存扣减） | 明确排除（如：不负责支付回调，由支付模块承接） |

- 边界要**技术化、可执行**——写清"这个模块管哪些表、提供哪些接口、消费哪些事件"；
- 负向边界越清楚，模块间越不打架；与 PRD 模块划分对齐，但此处聚焦**技术职责**。

## 三、核心流程图规范

**能画流程图的必须画**，三类图按场景选用：

| 场景 | 图型 | 必含要素 |
|------|------|---------|
| 模块内业务处理逻辑 | `flowchart TD` | 判断菱形双出口、终态收敛 |
| 跨模块/跨系统调用 | `sequenceDiagram` | 参与者、消息、异常分支 |
| 对象生命周期 | `stateDiagram-v2` | 唯一起始、全部终态、流转触发条件 |

**示例（业务流程）**：
```mermaid
flowchart TD
    Start([接收创建订单请求]) --> Check{库存是否充足}
    Check -->|否| Fail([返回库存不足])
    Check -->|是| Lock[预扣库存]
    Lock --> Create[创建订单记录]
    Create --> Pay{是否立即支付}
    Pay -->|是| PayFlow[进入支付流程]
    Pay -->|否| Wait[待支付状态]
    PayFlow --> Done([完成])
    Wait --> Done
```

## 四、接口 / 服务设计

- 每个对外能力写清：接口路径 / 方法 / 入参 / 出参 / 异常码（快速档可简化）；
- 内部服务方法同理：方法签名 + 入参出参 + 异常；
- 与 PRD 的「业务信息清单」对应——接口字段来自业务信息项，这里补类型与校验。

## 五、实现细节与决策（逐功能点展开到可编码）

> 目标：让开发拿到的方案"可直接编码"，不必回头确认。把每个功能点"每一步怎么实现"写清楚，凡真实工程会遇到的决策点都要给出结论，不能一句话带过。

### 5.1 逐功能点展开（功能点 → 实现步骤 → 决策点）

对模块内每个功能点，按三栏展开——功能点 + 实现步骤（每一步怎么做）+ 关键决策点与结论：

| 功能点 | 实现步骤（每一步怎么做） | 关键决策点 + 结论 |
|---|---|---|
| 文件上传 | ① 前端选文件 → ② 后端校验类型/大小 → ③ 上传到对象存储 → ④ 落库记录 → ⑤ 返回可访问 URL | 存哪=MinIO/云 OSS；怎么传=直传/走后端中转；大小上限=100MB（超限拒绝）；断点续传=需要/不需要；并发=分片上传；安全=类型白名单+鉴权 |

### 5.2 常见工程决策点清单（逐个过一遍，缺一不可）

写每个涉及的功能点时，主动过一遍下列决策点：能确定的写结论、前置已明确的标「继承 PRD」、确实无法确定的才标「待用户确认」：
- 数据存哪、以什么格式存；
- 怎么传/怎么处理（同步 / 异步 / 消息队列）；
- 大小 / 数量 / 时长等上限是多少，超限怎么办；
- 要不要断点续传 / 重试 / 补偿；
- 并发 / 竞态怎么控制（锁 / 幂等 / 版本号）；
- 安全与权限（谁有权、怎么校验、敏感数据怎么处理）；
- 失败兜底（失败怎么办、能不能恢复）。

## 六、关键技术点

每个模块写清 1~3 个关键难点及其方案：
- 并发控制（悲观锁 / 乐观锁 / 分布式锁）；
- 事务边界（跨服务事务 / 最终一致性 / 补偿）；
- 缓存策略（Cache-Aside + 双删 + 过期兜底）；
- 幂等设计（唯一索引 / token / 状态机）。

## 七、TDD 测试用例规范（核心）

### 7.1 总则
- **先写测试用例，后写实现方案**——测试用例是开发 TDD 先写测试的直接输入源；
- 形态 = **Gherkin 场景（承接 PRD 的 AC 编号）+ 代码级用例骨架**；
- 覆盖：正向 / 边界 / 异常 / 幂等 / 并发五类。

### 7.1·附 Anti-Happy-Path 强约束（⛔ CRITICAL）

> 每个功能点（业务切片）**必须记录并测试至少三条失败场景**，拒绝只覆盖 Happy Path：
> 1. **竞态条件**：并发写入、超卖、重复提交；
> 2. **数据完整性违规**：唯一约束冲突、脏数据、外键断裂；
> 3. **边界失败**：空数据、超限、溢出、依赖超时。
> 缺失败场景的实现方案视为 P0，退回补问（详见 `decision-rules.md` §九）。

### 7.2 Gherkin 场景（业务可读）
```gherkin
Feature: 创建订单
  # 承接 PRD 的 AC-M03-001
  Scenario: 库存充足正常创建【P0】
    Given 商品库存为 10
    When 用户提交创建订单（数量 2）
    Then 订单创建成功，库存扣减为 8

  Scenario: 库存不足拦截【P0】
    Given 商品库存为 1
    When 用户提交创建订单（数量 2）
    Then 创建失败并返回「库存不足」，库存不变

  Scenario: 重复提交幂等【P1】
    Given 已存在一笔待支付订单
    When 用户用相同幂等键再次提交
    Then 不产生新订单，返回原订单
```

### 7.3 代码级用例骨架（可执行）
```go
// CreateOrder 创建订单
// 用例：TestCreateOrder
func TestCreateOrder(t *testing.T) {
    cases := []struct{
        name     string
        stock    int    // 输入：库存
        qty      int    // 输入：购买数量
        wantErr  bool   // 预期：是否报错
        wantStock int   // 预期：扣减后库存
    }{
        {"正常创建", 10, 2, false, 8},
        {"库存不足", 1, 2, true, 1},
        {"库存刚好", 2, 2, false, 0},
    }
    for _, c := range cases {
        t.Run(c.name, func(t *testing.T) {
            // 断言 c.wantErr / c.wantStock
        })
    }
}
```

> 语言随选型：Go 用 table-driven，Java 用 JUnit `@Test` + 断言，Python 用 pytest。

### 7.4 覆盖矩阵

| 测试用例编号 | 对应 AC | 类型 | 场景描述 |
|-------------|---------|------|---------|
| TC-Mxx-001 | AC-Mxx-001 | 正向 | 正常创建 |
| TC-Mxx-002 | AC-Mxx-002 | 边界 | 库存刚好 |
| TC-Mxx-003 | AC-Mxx-003 | 异常 | 库存不足 |
| TC-Mxx-004 | AC-Mxx-004 | 幂等 | 重复提交 |
| TC-Mxx-005 | AC-Mxx-005 | 并发 | 并发扣减不超卖 |
