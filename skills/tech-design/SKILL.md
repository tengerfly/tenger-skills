# tech-design — 技术方案

## 何时用

- AC 已冻结、进入实现前；或本次改动新增模块、接口、表、第三方依赖。
- 输入：`task.md`（AC）、原型/设计稿（前端）、现有代码与既有技术栈、[bug-patterns](../../bug-patterns/README.md) 相关模式、依赖官方文档。
- 不适用：局部小改直接开发，不补形式文档；需求未冻结回 [requirements](../requirements/SKILL.md)；方案评审交 [review](../review/SKILL.md)。
- 合并旧 backend-tech-design + frontend-tech-design：一份方案覆盖前后端，不写框架教程。

## 交付物

- `.spec/tasks/<YYYY-MM-DD>-<slug>/design.md`：任务工作区的技术方案。
- 必含七项：
  1. 选型与理由：只定本次需要的；不可逆项给结论 + 备选 + 代价 + 退路。
  2. 架构与模块边界：谁做什么、不做什么、依赖方向。
  3. 接口契约：路径/方法/入参/出参/错误码/分页/枚举；前后端同一来源。
  4. 数据模型：表/字段/约束/索引 + 迁移与回滚。
  5. 异常与回滚：超时/重试/幂等/降级/补偿，变更怎么退。
  6. 测试策略：每条 AC 的验证层与用例编号。
  7. AC 映射表：AC → 模块 → 接口/页面 → 用例；无承接的 AC 显式列出。
- 不交付：需求变更、代码、评审结论。

## 验收判据

- AC 全部有承接：映射表覆盖 task.md 全部 AC（集合求差为空），无承接即不通过。
- 无「待定/TBD」：选型与开放问题只允许进「未决项」，并注明谁裁决。
- 契约唯一：后端接口与前端调用引用同一份字段定义；字段名/类型/错误码无两套。
- 数据变更可回滚：迁移可重复执行，回滚步骤可操作。
- 关键链路有失败路径：只写成功路径即不通过。
- 开发可开工：开发 Skill 只读 design.md 与 task.md 就能实现，无「开发时再定」。
- 做减法：不写框架教程、通用最佳实践与全量目录模板。

## 停等点

只停等下面三类；能从现有代码、文档与版本信息查到的，自行查证并记录，不无脑发问。

1. 不可逆选型要用户拍板：数据库、框架/端形态、部署形态、对外接口、数据迁移。
2. 方案阶段发现需求缺口或 AC 冲突：回 requirements，不自行改需求。
3. 外部依赖/合规/预算边界不清：第三方服务、版本兼容承诺、许可。
   其余默认「给建议 + 记假设 + 继续」。

## 证据要求

- 选型证据：官方文档链接 + 版本，或实测数据、同类项目调研；写在选型条目旁。
- 契约证据：接口与字段从 AC 和现有代码逐条核对，错误码/枚举有出处。
- 映射核对：AC 编号集合与映射表集合求差，贴出命令或逐条核对结果。
- 方案评审：交 review 独立评审，不用自审代替。
- 模型推断与「业界惯例」不算证据；必须落到来源或标为假设。
