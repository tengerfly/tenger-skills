# bug-fix：日志驱动的诊断与修复委托

> 铁律：根因未确认，不给修复方向；本 skill 只诊断与委托——不改码、不做深度测试、不产方案文档。
> 闭环：日志解析 → 复现确认 → 根因（证据链三段）→ 最小修复（委托）→ 同场景回归 + 相关回归 → 问题卡 / 模式沉淀。

## 何时用

- 触发：前端 console / network 异常、后端错误栈 / 5xx / 慢查询、测试或线上发现的功能 bug、用户报障要「查日志找原因」。
- 日志双通道：前端看 console / network / 白屏；后端看错误栈 / access 日志 / DB 慢查询；有 traceId 就串全链路，先定链路归属。
- 输入三要素（缺即停）：代码位置、日志（粘贴 / 文件 / 导出 / 可复现运行）、现象（操作路径 + 期望 vs 实际 + 环境版本）。
- 先定预期：读 AC / PRD，实现不符 = 代码 bug；PRD 本身不合理 = 退 requirements，不按 bug 硬修。

## 交付物

产物放被修项目 `.spec/tasks/<YYYY-MM-DD>-<slug>/`：

- `问题定位报告.md`：现象 / 证据链三段 / 根因一句话（什么条件下、哪段代码、因何而错）/ 影响面 / 严重度 P0-P2 / 修复方向与判据。
- 修复任务清单：每项含修复判据（修到什么表现算完成）、回归范围、处理结果与证据位置。
- 复现步骤：可执行的最小复现，作为回归判据。
- 回归证据：原场景重跑结果（前端截图）+ 相关回归结果。
- 问题卡：skill / 流程问题写本仓 `issue/NNN-slug.md`（模板 [000-template.md](../../issue/000-template.md)），规则见 [issue-loop.md](../../shared/issue-loop.md)。
- 缺陷模式卡：有预防价值的一类错沉淀到 [bug-patterns/README.md](../../bug-patterns/README.md)。

## 验收判据

- 复现确认：能给出稳定复现步骤；复现不了标「未复现」+ 置信度 + 下一步，不进入修复。
- 根因三段证据：现象 → 直接原因（日志 / 调用）→ 根因（代码位置），每段有依据；缺依据标「假设」，不硬断。
- 修复最小：一处根因一处改动，不夹带重构；跨端根因逐条列明。
- 同场景回归通过：原复现步骤不再现，本次实测，不认「改好了」的口头结论。
- 相关回归通过：受影响模块既有用例 + 按需调 [auto-test](../auto-test/SKILL.md) 分层回归。
- 不改需求边界：需求该变就退 requirements，不在修复里顺手改口径。
- 修 3 次仍不过：停下质疑根因 / 方案，不试第 4 次。
- 无法复现且无法收敛：保持卡 `open` 并记账，写明缺什么证据。

## 停等点

- 根因 Gate：定位报告给用户确认后才委托修复；根因有误回诊断。
- 无法复现 / 日志不全 / 代码位置不明：给选项与推荐，不猜。
- 修复要动接口契约、表结构或需求口径：先问，允许才动并同步文档。

## 证据要求

- 只认：日志原文与时间窗、trace / requestId 链路、代码位置（文件 + 行）、复现命令与输出、回归截图、文件 sha256。
- 不认：症状描述当证据、「可能是 X」式猜测、旧截图、改完不测。
- 每条根因结论挂证据；未验证项在报告里单列，不混进结论。
