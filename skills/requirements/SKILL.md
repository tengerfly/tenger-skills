# requirements — 需求澄清

## 何时用

- 新功能、需求变更、Bug 暴露的需求缺口，进入主链第一步。
- 输入：用户原话与附件、已有代码与文档、相关 issue、运行数据。
- 不适用：缺陷修复交 bug-fix；技术选型交 [tech-design](../tech-design/SKILL.md)；AC 已冻结只做实现交开发 Skill。
- 合并旧 6 个产品 Skill（idea-intake / product-discovery / product-definition / feature-decision / prd-design / prd-review），只留「澄清到可测 AC」；旧竞品、蓝图、PRD 评审已冻结进 `archive/frozen-skills/`，真需要时再从 archive 启用，不复刻旧流程清单。

## 交付物

- `.spec/tasks/<YYYY-MM-DD>-<slug>/task.md`：任务工作区里唯一的需求基线，含目标用户、目标、场景、范围与非目标、AC 清单、风险与未决项、状态。
- AC 编号从 `AC-01` 起；每条写「前置 → 操作 → 可观察结果」（或 Given/When/Then），一条只判一个结果。
- 范围变更：改版本号并标受影响 AC，不另建第二份需求文档。
- 不交付：技术方案、接口/表结构、页面结构、代码。评审与验收不在本 Skill：见 [review](../review/SKILL.md)、[acceptance](../acceptance/SKILL.md)。

## 验收判据

- 每条 AC 都能照做验证：给出命令、接口调用、页面操作或数据断言，测试者可直接判真假。
- 无不可判定词：「友好」「合理」「尽快」「适当处理」出现即不通过。
- 覆盖正常、边界、失败三类；涉及权限/资金/数据一致性时另有 AC。
- 范围闭合：目标、非目标、排除项齐全；AC 之外不隐含需求。
- 每条 AC 标来源：用户原话、issue 编号、数据或文档位置。
- 抽检可测性：任选 3 条 AC，未参与澄清的人能独立写出验证步骤；不能 ⇒ 不通过。
- 命名一致：对象、字段、角色与已有代码/文档同名同义。
- 不含实现决策：task.md 出现表结构、接口签名或组件拆分即违规。

## 停等点

只停等下面三类；能查代码、文档或资料得到答案的，自行查证 + 记账 + 继续，不拿来提问。

1. 范围或优先级要用户取舍（做/不做、版本边界）——AI 不替用户拍板。
2. 不可逆约束未确认：合规、预算、外部依赖、兼容承诺。
3. AC 的判定口径只能由用户或业务侧给：阈值、计费规则、文案口径、验收环境。
   同一问题澄清 3 轮不收敛，保留缺口请求裁决。

## 证据要求

- 来源证据：每条 AC 标来源；用户原话要引用，issue 给编号，数据给路径与日期。
- 假设与未决项显式登记，不得写成已确认结论。
- 确认证据：范围与 AC 的用户原话或确认记录；说「已确认」必须能指到具体记录。
- 可测性抽检记录：抽检人、AC 编号、能否独立复现。
- 模型自述、旧纪要、推断 = 未验证。
