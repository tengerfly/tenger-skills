# Acceptance（验收）

> 只回答一件事：这份交付能不能收。判据、证据标准、签收规则见 [shared/acceptance-contract.md](../../shared/acceptance-contract.md)，此处不复述。

## 何时用

- 任务走到交付前最后一步：评审已出结论、问题已处理或已登记，准备交付/发布。
- 用户说「能不能交付 / 验收一下 / 收尾检查 / 发布前确认」。
- 不适用：纯咨询、不产生交付物的问答；不硬走验收。
- 前置输入：任务与 AC、评审报告与问题清单（`.spec/tasks/<日期>-<slug>/review-report.md`）、本轮测试/运行证据、变更范围与回滚说明、遗留风险。
- 缺前置输入时不硬验收：先补输入，或直接按契约出 FIX/REJECT。

三档验收最少做什么（档位定义与评审共用，见 [shared/review-contract.md](../../shared/review-contract.md)）：

- 轻量：验收清单自检 + 关键命令输出；不要求独立执行者与签收。
- 标准：独立验收（未参与产出）+ 评审/测试证据 + 验收清单 + 三值结论。
- 完整：标准档全部 + owner 签收 + 回滚验证 + 遗留风险逐条登记。

## 交付物

- `.spec/tasks/<YYYY-MM-DD>-<slug>/acceptance-report.md`：按 [templates/acceptance-report.md](templates/acceptance-report.md) 填，五节标题不改。
- `.spec/tasks/<YYYY-MM-DD>-<slug>/acceptance-checklist.md`：按 [templates/acceptance-checklist.md](templates/acceptance-checklist.md) 逐项打勾，不空项。
- 结论回填 [loop-log.md](../../loop-log.md) 一行（评审发现数、一次通过、新增问题等列）。
- 完整档签收记录写进报告 §4，不另建文件。
- 验收发现的问题按 [shared/issue-loop.md](../../shared/issue-loop.md) 入问题池。

证据包（归档到任务工作区，缺件不算完成）：

- 验收报告与验收清单；
- 交付物清单 + 各自 sha256；
- 评审报告与问题清单（P0/P1 状态）；
- 本轮测试/运行证据（命令、输出、截图、日志）；
- 签收记录（完整档）。

## 验收判据

DoD 五条全部成立才可能 ACCEPT（定义见契约 §2，此处只列核对动作）：

1. **AC 逐条对应**：每条 AC 指到实现位置与本轮验证证据；无「未覆盖」「口头满足」。
2. **无未决 P0/P1**：无 P0；P1 已修复复验，或 owner 明确签收风险并登记为遗留风险（未签收即未决）；P2 已登记。
3. **证据可复现**：关键命令本轮重跑过，有命令、退出码、输出、环境；报告 §2 有至少一条自己复算过的 sha256。
4. **可回滚**：报告 §0 写清改了什么、怎么退、退到什么基线。
5. **风险显式**：遗留风险在报告 §3 登记，有等级、owner、截止、处置。

核对写法：逐条打勾或打叉，每条附证据位置；打叉写清原因与 owner；不写「整体没问题」「基本可用」。
本 Skill 自身合格判据：报告五节齐全、§4 只出现一个三值结论、完整档含签收、清单无空项、结论有证据支撑。

## 停等点

1. 结论要写 ACCEPT 但完整档 owner 未签收 → 停，等签收；不得代签，不得改用「口头同意」。
2. 出现 P0、范围/基线/授权变化，或要出 REJECT → 停，交回用户或 Lead 定范围与后续。
3. 要豁免 P1 或条件放行 → 停，由 owner 明确签收风险（责任人 + 期限 + 补证计划）并写进报告；验收方不得自行放宽。

其余默认：裁决 + 记账 + 继续，不逐条等确认。

## 证据要求

只认可复现物：命令与输出、测试报告、构建产物、真实运行/截图、日志、文件 sha256。
每份证据过四步：存在 → 本轮新鲜 → 可复现 → 支撑结论；缺一步按未取证。
不认：模型自述、口头描述、转发结论、旧截图、「应该没问题」。
核验过但结论不支持的证据要如实写进报告，不许删。
复核时复算 sha256；摘要对不上按基线已变处理，要求重验。
截图/日志带本轮日期或任务 id；报告 §2 的证据表至少覆盖命令、测试报告、sha256 三类。
（唯一口径见 [shared/acceptance-contract.md](../../shared/acceptance-contract.md)。）

## 验收流程

1. 收输入、冻范围：确认 AC 版本、交付物、变更范围与回滚基线；输入不全先补，不边收边改。
2. 逐条核 DoD：五条打勾/打叉，每条附证据位置。
3. 抽核证据：重跑关键命令、复算摘要、看截图与日志时间戳；抽核覆盖核心 AC。
4. 清问题与风险：P0/P1 状态核实，遗留风险逐条登记，owner 接受与否写清。
5. 出结论并签收：按契约判 ACCEPT/FIX/REJECT；完整档完成 owner 签收。
6. 回填与归档：loop-log 一行、证据包归档、问题入池。

## 结论与处置

- **ACCEPT**：放行/交付；归档证据包；loop-log「一次通过=是」；交付后 2 周内出现 P0/P1 要回填逃逸复盘。
- **FIX**：问题清单交回产出方，逐项修复；复验只验本轮项，最多 3 轮；超限按 REJECT 升级。
- **REJECT**：不交付；写明缺什么、下一步 owner、需要谁决策；问题按 [shared/issue-loop.md](../../shared/issue-loop.md) 入池。
- P1 签收与复核口径与评审契约 §7/§8 一致：评审签收的 P1 风险由验收复核并登记；验收不得推翻评审的 P0 结论。
- 结论与评审报告不一致时以证据为准，冲突升级用户/owner，不各写各的。
- 常见驳回原因：AC 没逐条落证据、拿旧证据充数、P1 没进清单或未签收却写成已接受、无回滚说明、验收方参与过产出。
