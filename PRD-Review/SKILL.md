# PRD 检测 / 评审 Skill

> **定位**：只做评审，不改稿。找出 PRD 里"逻辑不通畅"的点，记录成文档，不替用户改需求。

## 一、这是什么

本 Skill 是一个 **PRD 需求文档检测器**。它不写需求，只审需求：把一份已经写好的 PRD，分别交给 **前端开发专家、后端开发专家、测试专家** 三个独立视角去评审，找出其中"逻辑不通畅、无法落地"的点，分角色记录，再汇总归档。

**一句话原则**：「审出问题，不改问题；问题定位到原文，结论可追溯。」

## 二、三专家角色定义（评审立场互相隔离）

三个角色各自只从自己的专业立场出发评审，**互不越界、互不代劳**：

| 角色 | 评审立场（唯一标准） | 关心什么 | 不关心什么 |
|---|---|---|---|
| **前端开发专家** | 能否照着 PRD 独立写完前端页面 | 页面/入口、功能区块、交互闭环、状态覆盖、流程断点 | 数据库、接口、服务端逻辑 |
| **后端开发专家** | 能否照着 PRD 独立完成服务端与数据设计 | 业务对象、数据规则、状态机闭环、异常边界、数据一致性 | 控件、视觉、测试用例 |
| **测试专家** | 能否照着 PRD 直接写出可执行测试用例 | 验收可测性、覆盖完整性、可追溯性、歧义 | 实现方式、页面布局 |

> 各角色的详细检查清单见 `references/`，评审时**逐条对照执行**，不得凭感觉跳过。

## 三、何时使用

**✅ 适用**：
- 用户提供一份已写好的 PRD（文件路径或直接粘贴内容），要求评审 / 检测 / 审查 / 走查；
- 需求文档在进入开发前，想做一轮"前端 / 后端 / 测试"三方会审。

**❌ 不适用**：
- 要"写"需求文档（用 PRD-Design）；
- 要"改"需求文档（本 Skill 只审不改）；
- 竞品分析、技术方案设计等非 PRD 内容。

## 四、评审流水线（端到端闭环）

```
用户输入（PRD 文件路径 / 直接粘贴内容）
        │
        ▼
[1] 解析 PRD：通读全貌，识别模块与需求结构
        │
        ▼
[2] 三角色并行评审：各自跑专属清单，逐条找不通畅点
        │
        ▼
[3] 三份角色评审文档落盘（前端评审.md / 后端评审.md / 测试评审.md）
        │
        ▼
[4] 汇总去重：合并所有不通畅点，生成汇总报告，标出共性问题
        │
        ▼
[5] 归档 .spec/需求评审/
```

### 步骤 1：解析 PRD
- 确认输入来源：用户给的是**文件路径**还是**粘贴内容**；
- 若 PRD 为 PRD-Design 产出且含 `PRD速查表.md`，先读它建立结构地图（模块/页面/AC 定位），评审仍须逐节通读原文；
- 通读全文，识别：需求背景、模块划分、各模块的流程 / 状态 / 验收标准；
- 记录评审基线：文档清单、模块清单、各模块章节覆盖情况。

### 步骤 2：三角色并行评审
- **前端开发专家**：按 `references/frontend-checklist.md` 逐条评审；
- **后端开发专家**：按 `references/backend-checklist.md` 逐条评审；
- **测试专家**：按 `references/test-checklist.md` 逐条评审；
- 每个角色独立产出自己的"不通畅点清单"，不参考其他角色的结论（保证视角隔离）。

### 步骤 3：三份角色评审文档落盘
按 `assets/role-review-template.md` 为每个角色各写一份，落盘到 `.spec/需求评审/`：
- `前端评审.md`
- `后端评审.md`
- `测试评审.md`

### 步骤 4：汇总
按 `assets/summary-template.md` 生成 `评审汇总报告.md`：
- 合并三份清单，**去重**（同一处问题多角色命中则合并，标出"命中角色"）；
- 标出**共性问题**（多个角色同时发现的问题，说明是系统性缺陷）；
- 按严重度统计（P0/P1/P2）。

### 步骤 5：生成评审任务清单 + 用户确认（闭环入口）
按 `assets/issue-list-template.md` 生成 `.spec/需求评审/任务清单.md`：
- 把「评审汇总报告」去重后的问题逐条落到任务清单，状态先填 `待确认`；
- **每条问题必附「修复判据」**——一句话写清修到什么表现算修复完成（修改方与再评审共用同一把尺子，防止「改不干净」死循环）；
- 向用户**逐条列出问题点与优化点**，请用户确认：要改 → `已确认`；不改 → `已忽略` 并附理由；
- **分级冻结**：P0 / P1 为「问题点」（阻断项，未清零不放行）；P2 为「优化点」（不阻塞闭环，可留后续迭代）；
- **再评审只验上一轮清单**：复核仅核对已确认问题是否按判据修复，不无限新增同级新问题——新发现降为 P2 留后续，或经用户同意进下一轮单独批次；
- **轮次上限 3**：再评审轮次达 3 仍未收敛（仍有 P0/P1 未修）即停止循环，向用户汇报阻塞并交由用户裁决后续处置，防「评审-改-再评审」无限循环；
- 本 Skill 只审不改，用户确认后任务清单交 `PRD-Design` 后续逐条修改并回填状态。

### 步骤 6：归档
所有文档（角色评审文档 + 汇总报告 + 任务清单）落盘到 `.spec/需求评审/` 目录，交付给用户。

## 五、严重度分级（只标注，不设门禁）

本 Skill **不做 Pass / Fail 裁决**，只给每个不通畅点标注严重度：

| 严重度 | 含义 | 典型情形 |
|---|---|---|
| **P0 致命** | 逻辑断头 / 无头、流程走不通、需求自相矛盾、缺失到某角色无法开展工作 | 某流程只有入口没有出口；核心对象无状态定义 |
| **P1 重要** | 描述模糊有歧义、状态 / 边界 / 异常未定义、数据不一致、验收不可测 | "友好提示""尽量快"；跨模块字段命名冲突 |
| **P2 建议** | 表达可优化、术语不统一、非关键路径细节缺失 | 术语中英混用、章节序号不连续 |

## 六、评审铁律（强制）

1. **只审不改 · 分工明确**：评审的本质是**找问题**，不做任何修改——只指出"哪里不通畅、为什么不通畅、建议往哪个方向补"，**绝不替用户改写 PRD 原文**。**改 PRD 是 `PRD-Design` 的职责**（通过 `.spec/需求评审/任务清单.md` 交接），本 Skill 只产出问题清单，不碰原文。
2. **定位到原文**：每个不通畅点必须标注**出处**（哪个文件、哪个章节、哪条需求 / 哪段话），引用原文关键句，可追溯。
3. **零幻觉**：严禁编造"PRD 里没有的问题"；所有结论必须基于 PRD 原文。原文确实没有的信息，要区分是「PRD 缺失」（该写没写）还是「超出 PRD 范畴」（不该写，不是问题）。
4. **视角隔离**：前端问题归前端、后端问题归后端、测试问题归测试，不交叉、不代劳。
5. **不设门禁**：只输出问题清单，不判定 PRD"通过 / 不通过"。是否修改、由谁修改，交给用户决策。
6. **成因必写**：每个不通畅点除写明"断在哪"，必须写明**成因**——为什么会产生该问题（如：状态机无终态定义、跨模块概念未注册致同义不同名、步骤流未推演到出口）。成因须能从 PRD 原文上下文推得；**推不出明确成因时标「成因未明」，禁止臆造**（呼应铁律 3 零幻觉）。

## 七、常见错误对照表

| 常见错误 | 纠正方式 |
|---|---|
| 评审时顺手改写了 PRD 原文 | 只记录问题，给出"建议补充方向"，不动原文 |
| 三个角色结论混在一起 | 严格分角色成文，汇总时再合并 |
| 问题没有出处，只写"整体感觉不通" | 定位到具体文件 / 章节 / 原文 |
| 把"PRD 不该写的技术内容"当成"PRD 缺失" | 区分「缺失（该写没写）」与「越界（写了不该写的）」，分别标注 |
| 结论笼统（"这里有问题"） | 写明"为什么不通畅" + "建议往哪个方向补" |
| 只列现象没写明成因 | 补上成因（为什么会不通畅），可考才写、不臆造 |

## 九、运行问题埋点（收尾自查）

执行收尾（产物落盘 / 交付之后）自查本次运行，把暴露的问题上报问题池（仓库根 `issue/<本skill名称>/<当天日期>/<序号>-<标题>.md`）：**方法论问题、用户否定信号、用户认可信号、明显会复现的产物问题**。字段、等级、标签与红线遵循 `Skill-Optimizer/references/instrumentation-guide.md`，模板用 `Skill-Optimizer/assets/issue-template.md`。不确定算不算问题 → 不记；不因记录打断主流程。
