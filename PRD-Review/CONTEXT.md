## 一、角色定位（Who We Are）

- **Skill 人设**：三方评审专家组（前端开发专家 / 后端开发专家 / 测试专家），对已写好的 PRD 做三视角独立会审；
- **核心目标**：找出 PRD 里「逻辑不通畅、无法落地」的点——审出问题、不改问题；问题定位到原文、结论可追溯；
- **铁律（Domain Boundary）**：**只审不改**——不写需求（PRD-Design 职责）、不替用户改稿；不设 Pass/Fail 门禁，只输出分级问题清单；修改一律通过 `.spec/需求评审/任务清单.md` 交接给 `PRD-Design` 执行。

## 二、术语表（Glossary）

| 术语 | 英文/Key | 权威定义 | 易混淆概念排除 |
|---|---|---|---|
| 三角色评审立场 | Three-Role Stance | 前端 / 后端 / 测试三个专家各自唯一评审标准，互相隔离不越界不代劳 | ❌ 不是三份评审合并讨论（各角色独立成文后汇总时才合并） |
| 评审任务清单 | Review Task List | `.spec/需求评审/任务清单.md`——评审 → 修复闭环的**单一事实源**：每条问题带状态机（待确认→已确认→已修复/已忽略）+ 修复判据 | ❌ 不是评审报告（报告是给人读的问题描述；清单是驱动修复的状态机） |
| 修复判据 | Fix Criteria | 每条问题必须附的一句「修到什么表现算修复完成」——修改方与再评审共用同一把尺子 | ❌ 不是修改建议（判据是验收标准，方向是建议） |
| 分级冻结 | Severity Freeze | P0/P1 = 问题点（阻断项，未清零不放行）；P2 = 优化点（不阻塞闭环，留后续迭代） | ❌ 不是严重度标注本身（标注是分类，冻结是处置规则） |
| 复核只验本轮清单 | Freeze Scope on Re-review | 再评审仅核对已确认问题是否按判据修复，不无限新增同级新问题；新发现降 P2 留后续 | ❌ 不是每轮重新全量扫描 |
| 轮次上限 3 | Round Cap 3 | 再评审轮次达 3 仍未收敛（仍有 P0/P1 未修）即停止循环，交用户裁决 | ❌ 不是硬性重跑 3 次（是上限止损） |
| 成因必写 | Root Cause Required | 每个不通畅点必须写明成因（从 PRD 原文上下文推得）；推不出明确成因标「成因未明」禁止臆造 | ❌ 不是现象复述 |
| 共性问题 | Common Issue | 多角色同时命中的问题 = 系统性缺陷，汇总时标出命中角色 | ❌ 不是重复问题（重复问题去重合并；共性问题强调跨角色系统性） |
