# PRD-Review —— PRD 检测 / 评审 Skill

> **状态**：✅ 定稿
> **定位**：只做评审，不改稿。

## 一、这是什么

一个把已写好的 PRD 交给 **前端开发专家 / 后端开发专家 / 测试专家** 三个独立视角评审的 Skill。它不写需求、不改需求，只找出需求文档里"逻辑不通畅、无法落地"的点，分角色记录，并汇总归档到 `.spec/需求评审/`。

**一句话原则**：审出问题，不改问题；问题定位到原文，结论可追溯。

## 二、核心设计

| 项 | 决定 |
|----|------|
| 名称 | `PRD-Review` |
| 输入 | 用户每次指定 PRD 文件路径，或直接粘贴 PRD 内容 |
| 输出 | 三份独立角色文档 + 一份汇总报告 |
| 评审维度 | 三角色各自定制专属检查清单 |
| 门禁 | 不设 Pass / Fail，只列问题清单 + 严重度（P0/P1/P2） |

## 三、三角色评审立场（互相隔离）

| 角色 | 唯一评审标准 |
|------|-------------|
| 前端开发专家 | 能否照着 PRD 独立写完前端页面 |
| 后端开发专家 | 能否照着 PRD 独立完成服务端与数据设计 |
| 测试专家 | 能否照着 PRD 直接写出可执行测试用例 |

三个角色各自只关心自己的专业领域，**互不越界、互不代劳**，保证评审视角的纯粹性。

## 四、评审流水线

```
用户输入 PRD ──► 解析 PRD ──► 三角色并行评审 ──► 三份角色文档落盘 ──► 汇总去重 ──► 生成任务清单 + 用户确认 ──► 归档到 .spec/
```

1. **解析 PRD**：通读全貌，识别模块与需求结构；
2. **三角色并行评审**：各自按 `references/` 下的专属清单逐条找不通畅点；
3. **三份角色文档**：`前端评审.md` / `后端评审.md` / `测试评审.md`；
4. **汇总**：去重合并所有不通畅点，标出共性问题，生成 `评审汇总报告.md`；
5. **生成任务清单 + 用户确认**：把问题逐条落进 `任务清单.md`（状态=待确认），请用户逐条确认要改（已确认）还是不改（已忽略）；
6. **归档**：全部落盘到 `.spec/需求评审/`，任务清单交 `PRD-Design` 后续按清单修改。

## 五、目录结构

```
PRD-Review/
├── SKILL.md                        # 主指令：三专家角色 + 评审流水线 + 严重度 + 铁律
├── README.md                       # 本文档
├── references/                     # 三角色专属检查清单（评审时逐条执行）
│   ├── frontend-checklist.md       # 前端开发专家检查清单
│   ├── backend-checklist.md        # 后端开发专家检查清单
│   └── test-checklist.md           # 测试专家检查清单
├── assets/                         # 输出模板
│   ├── role-review-template.md     # 单角色评审报告模板（三份共用）
│   ├── summary-template.md         # 汇总报告模板
│   └── issue-list-template.md      # 评审任务清单模板（评审 → 修复闭环单一事实源）
└── .spec/需求评审/                   # 评审产出物归档目录
    └── <需求名称>评审/
        ├── 前端评审.md
        ├── 后端评审.md
        ├── 测试评审.md
        ├── 评审汇总报告.md
        └── 任务清单.md
```

## 六、快速上手

1. 触发方式：把 PRD 文件路径（或直接粘贴 PRD 内容）发给我，说"帮我评审这份 PRD"；
2. Skill 会自动跑三角色并行评审；
3. 产出四份文档：三份分角色评审 + 一份汇总报告；
4. 每个不通畅点都标注了出处、严重度（P0/P1/P2）和"建议补充方向"，但不改动你的原文。

## 七、严重度分级

| 严重度 | 含义 |
|--------|------|
| **P0 致命** | 逻辑断头 / 无头、流程走不通、需求自相矛盾、缺失到某角色无法开展工作 |
| **P1 重要** | 描述模糊有歧义、状态 / 边界 / 异常未定义、数据不一致、验收不可测 |
| **P2 建议** | 表达可优化、术语不统一、非关键路径细节缺失 |

> 注意：本 Skill **不做通过 / 不通过的裁决**，只输出问题清单。是否修改、由谁修改，交给用户决策。
