# 后端开发专家评审检查清单

> **角色立场**：以「能否照着这份 PRD 独立完成服务端与数据设计」为唯一标准。
> **只关心**：业务对象、数据规则、状态机闭环、异常边界、数据一致性。
> **不关心**：控件、视觉、测试用例。

---

## 检查维度总览

| 编号 | 维度 | 一句话判定 |
|------|------|-----------|
| BE-1 | 业务对象完整性 | 核心对象及其属性 / 状态都定义清楚了 |
| BE-2 | 数据规则（业务信息清单） | 每个字段的含义与业务规则能支撑数据设计 |
| BE-3 | 状态机闭环 | 生命周期有初始态、有终态、无死循环 |
| BE-4 | 异常与边界 | 并发 / 越权 / 超限 / 空数据都定义了 |
| BE-5 | 数据一致性 | 跨模块字段 / 状态 / 枚举命名一致 |
| BE-6 | 越界提醒 | PRD 不该写字段类型 / API / 技术选型 |

---

## BE-1 业务对象完整性

**检查方法**：把 PRD 里出现的每个核心业务对象（订单 / 用户 / 计划 / 优惠券等）列出来，逐个追问「这个对象的属性、状态、生命周期是否定义清楚？」

**判定为"不通畅"的情形**：
- 出现一个业务对象，但其属性 / 状态 / 生命周期完全没有定义（**凭空对象**）；
- 某个流程里用到了对象，但 PRD 从未定义过这个对象（**缺失对象**）；
- 对象的核心状态缺失（如"订单"没有"已取消 / 已完成"等关键状态）。

---

## BE-2 数据规则（业务信息清单）

**检查方法**：对每个关键字段 / 信息项，追问「名称、含义、业务规则、校验规则是否明确？能否据此做数据设计？」

**判定为"不通畅"的情形**：
- 字段含义含糊，无法判断它代表什么；
- 业务规则缺失（如"金额"没说是单位元还是分、精度几位）；
- 校验规则缺失（长度、范围、格式未定义）；
- 业务上限 / 阈值未定义且未标注【设计假设】。

> 注意：后端专家要的是**业务含义与规则**，不是要 PRD 写"字段类型 / 索引"——那属于 BE-6 越界。

---

## BE-3 状态机闭环

**检查方法**：对每个有生命周期的对象，画状态流转图，检查四点：有初始态、有终态、无死循环、每个流转有触发条件。

**判定为"不通畅"的情形**：
- 状态机死循环（A → B → A，永远走不到终态）；
- 无终态（对象永远结束不了）；
- 状态流转无触发条件（什么条件下从 A 变 B 没说）；
- 非法逆向未定义（如"已取消"的订单能否重新激活没说）。

> 状态机不闭环通常判 **P0**，直接阻塞后端建模。

---

## BE-4 异常与边界

**检查方法**：从后端视角排查五类异常 + 本业务特有异常，逐条追问「系统如何处理、用户看到什么」。

**判定为"不通畅"的情形**：
- **并发 / 重复提交**：同一操作并发执行、重复提交时的幂等处理未定义；
- **越权访问**：谁有权限发起 / 查看 / 处理某业务，未定义；
- **超限极值**：数据超上限、极值场景的处理未定义；
- **空数据**：空数据、数据不存在时的处理未定义；
- **中断 / 失败**：流程中途失败、中断时的状态与恢复方式未定义。

---

## BE-5 数据一致性

**检查方法**：跨模块对照，检查同一概念的字段名、状态名、枚举值是否一致。

**判定为"不通畅"的情形**：
- **同义不同名**：同一个字段在不同模块叫不同名字（如 `plan_id` vs `learning_plan_id`）；
- **同名不同义**：同一个名字在不同模块含义不同；
- **未注册**：被多个模块引用的字段 / 状态未在总纲术语表统一注册定义。

---

## BE-6 越界提醒（PRD 写了不该写的）

**检查方法**：扫描 PRD 是否出现后端实现细节。这是"PRD 越界"而非"缺失"，单独标注为「越界」。

**判定为"越界"的情形**：
- 数据库字段类型 / 索引 / 存储方式（如"用 VARCHAR(255)"）；
- API 路径 / HTTP 方法 / 错误码 / 报文结构；
- 技术选型：中间件、缓存、消息队列、框架、协议（Redis / SSE / WebSocket 等）。

> 越界项标注为「建议移除 / 改写为业务表述」，严重度通常 **P2**。
