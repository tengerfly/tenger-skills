# 测试专家评审检查清单

> **角色立场**：以「能否照着这份 PRD 直接写出可执行测试用例」为唯一标准。
> **只关心**：验收可测性、覆盖完整性、可追溯性、歧义。
> **不关心**：实现方式、页面布局、服务端技术。

---

## 检查维度总览

| 编号 | 维度 | 一句话判定 |
|------|------|-----------|
| TE-1 | 验收标准可测性 | 每个需求都有可执行、可断言的验收标准 |
| TE-2 | 验收标准质量 | Then 断言明确、能判通过 / 不通过 |
| TE-3 | 覆盖完整性 | 正向 / 边界 / 异常用例都覆盖了 |
| TE-4 | 可追溯性 | 需求 ↔ 验收标准双向对应，无孤儿 |
| TE-5 | 歧义检查 | 无"尽量快 / 友好提示 / TBD"类模糊表述 |
| TE-6 | 可执行性 | 用例能 1:1 转自动化或人工判定 |

---

## TE-1 验收标准可测性

**检查方法**：把每个需求（REQ）列出来，逐个追问「它有没有对应的验收标准？这个验收标准能不能执行、能不能断言？」

**判定为"不通畅"的情形**：
- 某个需求没有对应验收标准（**有需求无验收**，直接漏测）；
- 验收标准只是描述性文字，无法执行（如"系统应该好用"）；
- 验收标准缺关键断言，无法判断通过 / 不通过。

---

## TE-2 验收标准质量（若用 Gherkin）

**检查方法**：若 PRD 采用 `Given-When-Then`，逐条检查三段完整性与 Then 断言质量。

**判定为"不通畅"的情形**：
- `Given / When / Then` 缺段；
- `Then` 断言的是实现细节（DOM / 控件 / 内部状态），而非业务结果；
- `Then` 无量化条件，无法客观判定（如"应显示正确"——什么是"正确"没说）；
- 验收标准未标注优先级，测试排期无依据。

---

## TE-3 覆盖完整性

**检查方法**：对照每条流程，检查三类用例是否都覆盖：正向、边界、异常。

**判定为"不通畅"的情形**：
- 只有正向用例，缺边界用例（0 条 / 超长 / 超限）；
- 缺异常用例（失败 / 中断 / 越权 / 重复操作）；
- 关键分支（如权限分支、状态分支）漏了用例。

---

## TE-4 可追溯性

**检查方法**：双向核对「需求 ↔ 验收标准」的映射关系。

**判定为"不通畅"的情形**：
- **有需求无验收**：写了需求，没写验收标准；
- **有验收无需求**：出现一个验收标准，但对应不上任何需求（孤儿用例）；
- 需求编号与验收编号无法对应，追溯链断裂。

---

## TE-5 歧义检查

**检查方法**：全文扫描模糊表述，判断能否转成明确的测试断言。

**判定为"不通畅"的情形**：
- 出现「尽量快 / 友好提示 / 适当展示 / 较多 / 一般」等无法量化的词；
- 出现「待定 / TBD / 后续再议」等未决尾巴；
- 阈值 / 上限 / 文案未明确，测试无法确定断言值。

---

## TE-6 可执行性

**检查方法**：判断每个用例能否 1:1 转自动化脚本，或至少能人工客观判定。

**判定为"不通畅"的情形**：
- 断言依赖主观感受，无法自动化也无法人工客观判定；
- 前置条件（Given）不可构造或不可控；
- 验收标准引用了 PRD 中未定义的对象 / 状态 / 数据。
