# 微服务架构与模块化规范

> 用途：后端代码「怎么分层、怎么拆服务、怎么组织 Monorepo」的权威规范。维护性的第一落地手段就是清晰的分层与服务边界。
> 本规范是权威；`assets/` 模板是本规范的骨架，二者冲突时以本规范为准。

---

## 一、总体结构（微服务 = 服务内分层 + 服务间解耦）

后端整体是**微服务架构**，但两层都要管好：

```
Monorepo（前后端同仓库）
├── 服务内：四层分层（Controller → Service → Repository → Entity），依赖单向向下
└── 服务间：微服务边界（只走对外接口，禁直连他服务库/内部实现）
```

> 微服务绝不等于放弃分层——服务内部同样要清洁、可维护。

---

## 二、服务内四层分层（依赖单向向下）

```
┌─────────────────────────────────────────────────────────┐
│  Controller  （接口层 / 消息处理层）                      │
│  职责：路由/消息处理、参数校验、鉴权、调用 Service、统一响应  │
│  禁止：写业务逻辑、直接碰 SQL / Repository                │
├─────────────────────────────────────────────────────────┤
│  Service  （业务层）                                     │
│  职责：核心流程、业务规则、事务编排、跨服务编排             │
│  禁止：碰传输层、写 SQL、直接操作数据库                     │
├─────────────────────────────────────────────────────────┤
│  Repository / DAO  （数据访问层）                         │
│  职责：表的增删改查、SQL/ORM 查询、数据映射               │
│  禁止：写业务规则、碰传输层                               │
├─────────────────────────────────────────────────────────┤
│  Entity / Model  （数据模型）                            │
│  职责：与表结构一一对应的纯数据载体                        │
│  禁止：包含任何业务逻辑                                    │
└─────────────────────────────────────────────────────────┘
```

### 2.1 各层职责边界

| 层 | 做什么 | 不做什么 | 判错口诀 |
|----|--------|---------|---------|
| Controller | 收请求 → 校验参数 → 调 Service → 统一响应 | 业务判断、循环处理、SQL | 接口层里出现 if 业务分支 = 越界 |
| Service | 编排业务流程、事务边界、业务规则 | 传输层解析、SQL、直接 DB | 业务层里出现 `SELECT`/`prisma.` = 越界 |
| Repository | 数据读写、条件查询、分页 | 业务规则、状态流转判断 | 数据层里出现业务 if = 越界 |
| Entity/Model | 字段 + 类型 + 表映射 | 任何逻辑 | 实体里出现含逻辑的方法 = 越界 |

### 2.2 接口解耦

- Service 层**面向接口编程**：上层依赖抽象接口，不依赖具体实现——便于单测 mock、便于替换实现（如换缓存、换仓储）；
- NestJS 落地：`@Injectable()` 类 + `interface`/抽象类 + 构造器注入（DI 容器管理），仓储定义成 interface，Service 注入 interface。

## 三、服务间微服务边界

### 3.1 服务拆分（对齐 TDD 模块清单）

- TDD「模块清单」是微服务拆分**候选边界**，默认一模块一服务；
- 是否合并/拆分由**业务耦合度**决定：强耦合模块可合并进同一服务，弱耦合拆开；
- 拆分不确定时用**选择项**让用户确认（如「一拆一 / 合并为 N 个服务 / 先单体后拆」）。

### 3.2 服务间通信铁律

| 禁止事项 | 正确做法 |
|---------|---------|
| 跨服务直连对方数据库 | 表归属服务明确，访问走对方对外接口 |
| 跨服务直接 import 对方 Repository/Entity | 只通过对外接口（HTTP/gRPC/NATS/队列）交互 |
| 服务间循环依赖 | 抽 `libs/shared` 或事件解耦 |
| 服务间共享数据库写操作 | 一表一主，其它服务只读或走接口 |

### 3.3 服务间交互方式（对齐 TDD 关联关系图）

| 交互方式 | 适用 | 落地 |
|---------|------|------|
| HTTP（网关） | 对外统一入口 | Gateway 路由到各服务 |
| gRPC | 服务间同步调用、强契约 | `@nestjs/microservices` + proto |
| NATS/Kafka | 异步解耦、事件驱动、最终一致 | 消息队列（按 TDD 选型） |
| 共享数据 | 读多写少 | 共享表/缓存（注明归属方） |

> 每个服务的上下游依赖必须与 TDD 模块方案的「上下游依赖」、总文档「模块关联关系图」一致。

## 四、Monorepo 组织（前后端同仓库 + 多人协作）

### 4.1 目录组织原则

```
repo/                              # 前后端同仓库（monorepo）
├── apps/
│   ├── web/                       # 前端（Frontend-Tech-Design 落地目标）
│   └── server/
│       ├── gateway/               # API 网关（HTTP 入口）
│       ├── <service-a>/           # 微服务 A（与 TDD 模块对应）
│       └── <service-b>/           # 微服务 B
├── libs/
│   └── shared/                    # 共享：DTO/枚举/常量/契约/工具
├── package.json                   # pnpm workspace 根
├── pnpm-workspace.yaml
├── tsconfig.base.json
└── .env.example
```

### 4.2 共享代码下沉 `libs/shared`（契约单一事实源）

| 共享内容 | 说明 |
|---------|------|
| DTO | 前后端共用的请求/响应类型，禁止各写一份 |
| 枚举/常量 | 状态值、错误码分段、业务枚举 |
| 服务间契约 | gRPC proto / 消息事件结构 |
| 通用工具 | 校验、格式化等无业务语义的纯函数 |

- 前端通过 workspace 引用同一份 DTO/枚举，接口契约以 `libs/shared` 为**单一事实源**，减少前后端不一致；
- 共享包只放「无业务归属」的通用物，业务逻辑一律留在各自服务内。

### 4.3 多人协作友好（multi 开发）

- **服务边界清晰** → 不同人/团队改不同服务互不冲突、互不阻塞；
- **约定先行**：目录结构、命名、接口契约、错误码分段在动手前统一（必要时用选择项确认）；
- **减少合并冲突**：共享包改动小步提交、契约变更先对齐文档再改代码。

## 五、服务内模块化（按业务域分包）

- 服务内部再按「业务域」分包（如用户服务内的 `auth`、`profile` 子模块），与 TDD 模块细分对应；
- 通用能力（鉴权、日志、错误、统一响应、配置、中间件）下沉 `common`/`shared`，业务模块复用，避免重复造轮子；
- 服务内模块间只通过对外 Service 接口交互，禁止循环依赖。

---

## 六、数据模型落地规范

- **表结构 → Entity/Model**：TDD「全局表结构设计」的每张表逐字段映射，字段名/类型/可空/默认值/约束/索引/注释保持一致；
- **约定照搬 TDD**：金额整数（分）、时间 DATETIME/时间戳、枚举 TINYINT + 注释、软删除 `deleted_at`、逻辑外键（不强制物理外键）；
- **实体纯净**：Entity/Model 只做数据载体，业务规则一律放 Service；
- **表归属服务**：每张表归属唯一服务（写入方唯一），跨服务访问走接口，不直连他服务的库；
- **迁移脚本**：建表用 migration（Prisma migrate / TypeORM migration / SQL），可重复执行、可版本管理，禁止手工改库。

---

## 七、事务与边界约定

- **事务边界在 Service**：单服务内需要多表一致性时，事务开启/提交/回滚放 Service 方法；Repository 不做事务控制；
- **跨服务一致性**：单库内用本地事务；跨服务/跨库按 TDD 方案走最终一致性 + 补偿（消息队列 + 重试 + 幂等），不在代码里硬造分布式事务；
- **幂等**：有幂等要求的写操作，按 TDD 方案用唯一索引 / 幂等键 / 状态机兜底，落地成代码而非注释承诺。

---

## 八、架构自检清单

- [ ] 服务内四层齐全，依赖只向下、无跨层调用？
- [ ] Controller 只做路由/校验/调 Service/响应，无业务逻辑？
- [ ] Service 面向接口编程，无 SQL、无传输层解析？
- [ ] Repository 只有数据读写，无业务判断？
- [ ] Entity/Model 纯数据，无业务逻辑？
- [ ] 服务拆分与 TDD 模块清单对齐，边界清晰？
- [ ] 无跨服务直连数据库、无跨服务 import 内部实现、无循环依赖？
- [ ] Monorepo 目录规范，共享 DTO/枚举下沉 `libs/shared`？
- [ ] Entity 与表结构逐字段一致，表归属服务明确，迁移可重复执行？
- [ ] 事务边界在 Service，跨服务一致性按 TDD 方案，幂等/并发方案已落地成代码？
