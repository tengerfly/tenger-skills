# 技术方案评审 Skill

> **定位**：只做评审，不改稿。找出后端技术方案（TDD）与前端技术方案（FTDD）里"没有闭环"与"关联关系错误"的点，记录成文档，不替用户改方案。
> **术语**：TDD = Technical Design Document（后端技术文档）；FTDD = Frontend Technical Design Document（前端技术文档）。

## 一、这是什么

本 Skill 是一个 **技术方案检测器**。它不写方案、不改方案，只审方案：把已经写好的后端技术文档（TDD）与前端技术文档（FTDD），分别以 **后端技术方案评审** 与 **前端技术方案评审** 两个视角，对照 **需求文档（PRD）** 与 **原型文档** 逐一评审，找出其中"没有闭环、关联关系错误、无法落地"的点，分视角记录，再汇总归档。

**一句话原则**：「审出问题，不改问题；问题定位到原文，结论可追溯到需求。」

## 二、评审对象与输入基线

| 输入 | 角色 | 说明 |
|---|---|---|
| 需求文档（PRD） | 评审基线 | 需求与技术方案的"对齐基准"，判断技术方案是否完整承接需求 |
| 原型文档 | 评审基线 | 前端页面 / 交互的直接基准，判断前端技术方案是否覆盖原型 |
| 后端技术文档（TDD） | 评审对象 | 后端选型、架构、模块、表结构、接口、测试用例 |
| 前端技术文档（FTDD） | 评审对象 | 前端选型、架构、页面、组件、hooks、fetch 接口、测试用例 |

> 评审时，PRD 与原型是"尺子"，TDD 与 FTDD 是"被量物"。

## 三、两大评审视角（立场隔离）

| 视角 | 唯一评审标准 | 关心什么 | 不关心什么 |
|---|---|---|---|
| **后端技术方案评审** | TDD 能否完整承接 PRD 且内部闭环 | 需求承接、数据模型、状态机、流程、接口、模块关联、异常边界 | 前端页面 / 组件 / 交互 / 视觉 |
| **前端技术方案评审** | FTDD 能否完整承接 PRD + 原型 + TDD 且内部闭环 | 页面承接、交互闭环、状态覆盖、hooks 数据流、fetch 对接、组件关联 | 数据库、表结构、服务端实现 |

> 前后端"关联关系"（接口 / 数据 / 状态 / 权限）由两个视角各自从己方立场核查，命中谁归谁，双方都命中则双方都记。

## 四、评审两大核心目标（本 Skill 重点）

### 4.1 找出"没有闭环"的点

| 闭环类型 | 含义 | 典型断点 |
|---|---|---|
| 需求闭环 | 每条 PRD 需求都有技术方案承接，每个技术设计都能追溯到需求 | 需求无人承接（漏做）；设计无需求来源（凭空设计） |
| 流程闭环 | 每条业务流程 / 交互链路有入口有出口 | 断头链路（只进不出）；无头链路（只出不进） |
| 状态闭环 | 状态机有初始态、终态、无死循环 | 无终态；死循环；流转无触发条件 |
| 数据闭环 | 数据从产生 → 传输 → 消费 → 反馈全程闭环 | 后端返回字段前端未消费；前端请求字段后端未定义 |

### 4.2 找出"关联关系错误"

| 关联类型 | 核查点 | 典型错误 |
|---|---|---|
| 后端模块关联 | TDD 总文档关联图 ↔ 各模块文档上下游依赖 | 总文档有边、模块文档没写；模块文档写了依赖、总文档没画 |
| 前端模块关联 | FTDD 总文档关联图 ↔ 各模块文档 | 同上 |
| 前后端接口关联 | FTDD fetch 接口 ↔ TDD 接口清单 | 前端调的接口后端没有；后端定义的接口前端没用；方法 / 路径 / 参数不一致 |
| 页面—原型关联 | FTDD 页面清单 ↔ 原型页面 | 原型有页面、方案没写；方案写了页面、原型没有 |

## 五、何时使用

**✅ 适用**：
- 用户提供已写好的后端技术文档（TDD）/ 前端技术文档（FTDD）（文件路径或直接粘贴），要求评审 / 检测 / 审查 / 走查；
- 需求与原型定稿后、开发启动前，想做一轮技术方案"闭环 + 关联"会审。

**❌ 不适用**：
- 写技术方案（用 Backend-Tech-Design / Frontend-Tech-Design）；
- 评审需求文档（用 PRD-Review）；
- 改技术方案（本 Skill 只审不改）。

## 六、评审流水线（端到端闭环）

```
用户输入（PRD + 原型 + TDD + FTDD 路径 / 粘贴内容）
        │
        ▼
[1] 输入解析：定位四类文档 + 检测 browser-user
        │
        ▼
[2] 双视角并行评审：后端按 backend-checklist、前端按 frontend-checklist 逐条找断点
        │
        ▼
[3] 前后端关联一致性专项核查（integration-checklist）
        │
        ▼
[4] 两份角色评审文档落盘（后端技术方案评审.md / 前端技术方案评审.md）
        │
        ▼
[5] 汇总去重：合并所有断点，标出"前后端关联错误"共性项
        │
        ▼
[6] 生成评审任务清单（.spec/技术方案评审/任务清单.md，状态=待确认）+ 用户逐条确认
        │
        ▼
[7] 归档 .spec/技术方案评审/
```

### 步骤 1：输入解析 + browser-user 检测
- **优先读项目 `.spec/` 已有产出**：
  - PRD：`.spec/PRD/VN/`；
  - 原型：`.spec/原型/`；
  - 后端 TDD：`.spec/TDD/VN/`；
  - 前端 FTDD：`.spec/FTDD/VN/`；
  - 缺失则回退到用户指定路径 / 粘贴内容。
- **检测 browser-user（浏览器）**：可用则用于核验 TDD / FTDD 中技术选型的版本兼容性、弃用 API、官方最佳实践；不可用则直接跳过，不阻塞评审（评审核心是文档交叉比对，不依赖浏览器）。

### 步骤 2：双视角并行评审
- **后端技术方案评审**：按 `references/backend-checklist.md` 逐条评审；
- **前端技术方案评审**：按 `references/frontend-checklist.md` 逐条评审；
- 两个视角独立产出自己的"断点清单"，不参考对方结论（保证视角隔离）。

### 步骤 3：前后端关联一致性专项核查
按 `references/integration-checklist.md` 核查接口契约、数据模型、状态枚举、数据流、权限错误处理的一致性，**命中项归因到后端 / 前端 / 双方**。

### 步骤 4：两份角色评审文档落盘
按 `assets/role-review-template.md` 各写一份，落盘到 `.spec/技术方案评审/`：
- `后端技术方案评审.md`
- `前端技术方案评审.md`

### 步骤 5：汇总
按 `assets/summary-template.md` 生成 `技术评审汇总报告.md`：
- 合并两份清单，去重；重点标出「前后端关联错误」这类跨方案共性问题；
- 按严重度统计（P0/P1/P2）。

### 步骤 6：归档
所有文档落盘到 `.spec/技术方案评审/` 目录，交付给用户。

## 七、严重度分级（只标注，不设门禁）

本 Skill **不做 Pass / Fail 裁决**，只给每个断点标注严重度：

| 严重度 | 含义 | 典型情形 |
|---|---|---|
| **P0 致命** | 需求无承接、流程 / 状态机断头、前后端接口对不上导致无法联调 | 核心需求无技术方案；前端调用后端未定义的接口；状态机无终态 |
| **P1 重要** | 关联关系不一致、数据字段命名冲突、异常边界缺失、数据流断链 | 总文档关联图与模块文档不一致；前后端字段命名不一致；空态 / 失败态缺失 |
| **P2 建议** | 表达可优化、术语不统一、越界内容、非关键细节缺失 | 技术方案写了前端视觉 / 后端实现细节；命名风格不统一 |

## 八、评审铁律（强制）

1. **只审不改**：只指出"哪里没闭环 / 关联错、为什么、建议往哪个方向补"，**绝不替用户改写 TDD / FTDD 原文**。
2. **定位到原文**：每个断点必须标注**出处**（哪个文件、哪个章节、哪段话 / 哪个接口 / 哪张表），引用原文关键句，可追溯。
3. **零幻觉**：严禁编造"文档里没有的问题"；所有结论必须基于 TDD / FTDD / PRD / 原型原文。原文确实没有的信息，要区分是「方案缺失」（该写没写）还是「超出方案范畴」（不该写，不是问题）。
4. **视角隔离**：后端问题归后端、前端问题归前端；前后端关联问题归因到应负责的一方（或双方），不交叉、不代劳。
5. **不设门禁**：只输出问题清单，不判定方案"通过 / 不通过"。是否修改、由谁修改，交给用户决策。

## 九、常见错误对照表

| 常见错误 | 纠正方式 |
|---|---|
| 评审时顺手改写了方案原文 | 只记录问题，给出"建议补充方向"，不动原文 |
| 两个视角结论混在一起 | 严格分视角成文，汇总时再合并 |
| 只审前端不审后端（或反之） | 后端 / 前端两份文档都要审 |
| 忽略了前后端接口一致性 | 步骤 3 专项核查接口契约，双向比对 |
| 问题没有出处 | 定位到具体文件 / 章节 / 接口 / 表 |
| 把"方案不该写的内容"当成"方案缺失" | 区分「缺失」与「越界」，分别标注 |
| 结论笼统（"这里有问题"） | 写明"哪里没闭环 / 关联错在哪" + "建议往哪个方向补" |
