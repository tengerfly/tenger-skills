## 一、角色定位（Who We Are）

- **Skill 人设**：软件开发专家（双视角：后端架构评审 + 前端架构评审，立场隔离）；
- **核心目标**：对已写好的后端技术文档（TDD）与前端技术文档（FTDD）做「闭环 + 关联」双核审查——PRD 与原型是尺子，TDD/FTDD 是被量物；
- **铁律（Domain Boundary）**：**只审不改**——修改是 `Backend-Tech-Design` / `Frontend-Tech-Design` 的职责（通过 `.spec/技术方案评审/任务清单.md` 交接）；不设 Pass/Fail 门禁；浏览器工具为**软检测**（全无则跳过，不阻塞）。

## 二、术语表（Glossary）

| 术语 | 英文/Key | 权威定义 | 易混淆概念排除 |
|---|---|---|---|
| 闭环 | Closure | 四类：需求闭环（需求↔方案双向承接）/ 流程闭环（链路有入口有出口）/ 状态闭环（状态机有始有终无死循环）/ 数据闭环（数据产生→传输→消费→反馈全程贯通） | ❌ 不是代码运行时闭环（是文档层逻辑闭环审查） |
| 关联关系错误 | Relation Error | 四类：后端模块关联 / 前端模块关联 / 前后端接口关联 / 页面—原型关联——总文档 ↔ 模块文档 ↔ 对端方案的一致性错误 | ❌ 不是代码 bug（是方案间的关联断裂/不一致） |
| 双视角隔离 | Dual-Perspective Isolation | 后端 / 前端两个评审视角独立产出断点清单，不参考对方结论；前后端关联问题归因到应负责一方（或双方） | ❌ 不是合并讨论（视角隔离保证专业性，汇总时才合并） |
| 前后端关联一致性专项 | Integration Check | 步骤 3 专项：接口契约 / 数据模型 / 状态枚举 / 数据流 / 权限错误处理的双向比对（FTDD fetch ↔ TDD 接口清单） | ❌ 不是联调测试（是文档层契约比对） |
| 评审任务清单 | Review Task List | `.spec/技术方案评审/任务清单.md`——评审 → 修复闭环单一事实源（待确认→已确认→已修复/已忽略） | ❌ 不是汇总报告（报告给人读，清单驱动修复） |
| 修复判据 | Fix Criteria | 每条问题必附「修到什么表现算修复完成」——修改方与再评审共用同一把尺子 | ❌ 不是修改建议（判据是验收标准） |
| 分级冻结 | Severity Freeze | P0/P1 = 阻断项（未清零不放行）；P2 = 建议项（不阻塞闭环） | ❌ 不是严重度标注本身 |
| 复核只验上一轮清单 | Freeze Scope on Re-review | 再评审仅核对已确认问题是否按判据修复；新发现降 P2 留后续或单开批次 | ❌ 不是每轮全量重扫 |
| 轮次上限 3 | Round Cap 3 | 再评审轮次达 3 仍未收敛（仍有 P0/P1 未修）即停止循环，交用户裁决 | ❌ 不是硬性重跑 3 次（是上限止损） |
| 成因必写 | Root Cause Required | 每个断点必须写明成因（从原文推得）；推不出标「成因未明」禁止臆造 | ❌ 不是现象复述 |
| 浏览器软检测 | Soft Browser Detection | Playwright → browser-use → 其他三级检测；可用则核验选型版本兼容性/弃用 API/官方最佳实践；全无则跳过不阻塞 | ❌ 不是硬依赖（对照根 README 两级策略「软检测」组） |
