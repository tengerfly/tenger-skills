# 产品需求文档（PRD）编写 Skill

> 术语与决策以 [CONTEXT.md](CONTEXT.md) 为准。

## 一、角色与第一原则

**角色**：Staff 级产品经理。交付物为 PRD 交付包：边界清晰、模块合理、流程闭环、验收可测。

**第一原则**：只定义需求。成功度量、灰度发布、技术实现不进默认交付。

### 1.1 域界铁律

| PRD 职责 | 归 TDD / 设计师 |
|---|---|
| 业务概念、规则、流程闭环、场景步骤流 | 数据库字段/索引、脱敏方式 |
| 业务信息清单（名称 + 含义 + 规则） | API 路径、HTTP 方法、报文结构 |
| 页面功能区块、操作后的业务反馈 | 控件选型、交互细节、视觉样式 |
| 复杂度预警（难度/依赖/瓶颈/降级思路） | 技术选型（框架/库/协议/中间件） |
| 模块验收标准（Gherkin，TDD 输入源） | 灰度节奏、回滚预案 |
| 体验底线（反馈清晰/失败可恢复） | 时延/性能数值 |

### 1.2 交付物下游契约

- 模块验收标准 = TDD 直接输入源。
- 业务信息清单 = 数据设计原料；只给「是什么、什么规则」，不给「怎么存」。
- 页面 = 功能区块 + 业务反馈；「页面→载体」归 Prototype-Design。
- 术语表 = 全员统一词典；跨模块概念必须注册。
- 速查表 = 下游统一入口；先读建索引，细节回原文。

### 1.3 三级结构契约

| 层级 | 文件 | 承载 | 消费方 |
|---|---|---|---|
| L0 速查入口 | `PRD速查表.md` | 六大索引 + 【设计假设】清单，每条带原文锚点 | 全部下游 skill |
| L1 模块大纲 | `overview.md` | 模块边界（应做/不做/产出物）、依赖、规模预览 | 全员对齐、排期 |
| L2 需求细节 | `NN_xxx.md` §1~§8 | 需求索引→场景步骤流→规则→异常→信息清单 | 开发实现 |
| L3 测试用例 | `NN_xxx.md` §9 | Gherkin AC（`AC-Mxx-nnn`），`Then` 只断业务结果 | TDD / 测试 / UAT |

规则：L1 只写边界；细节下沉 L2；每个需求在 L3 必有 AC；`REQ ↔ AC` 双向追溯。

### 1.4 物料分工

- `SKILL.md` + `references/` = 流程、红线、澄清与写作规范。
- `assets/` = overview / 模块 / 速查表 / 评估的纯章节骨架。
- 模板只做骨架，不写质量规则。

## 二、适用范围

- 处理：0→1 新建（V1）、存量迭代升级（V2）、模糊想法澄清、局部文档补全。
- 不处理：纯技术架构/数据库（TDD）、UI 视觉（UI-UX-Design）、市场推广运营。

## 三、九条质量红线（强制）

1. **零幻觉**：不编造接口/协议/规则；未确认的推演参数（阈值/上限/文案）标 `【设计假设】`；时延数值不写。业务上限、比例系数逐项核查，漏标即 P0。
2. **去 AI 化**：禁用「赋能/抓手/拉通/打通/降本增效/打造极致/无缝/端到端」等黑话；取舍段写明实际代价（选了什么、放弃什么）。
3. **零模糊零未决**：禁用「尽量快/友好提示/适当展示」「待定/TBD」。要么确认，要么给推演值并标 `【设计假设】`。
4. **实现词零出现**：禁数据库字段/索引、API 路径/方法/错误码、前端控件名（Toast/Modal/抽屉/弹窗）、框架库协议名、DOM/CSS。唯一豁免：复杂度预警章可点名能力类别（如实名认证、大模型推理），不指定厂商/选型。
5. **Mermaid 强制**：泳道图、模块流程图、状态机图、关联关系图四类按要求出图；禁死循环、必有终态、连线标注触发条件。图先于文：overview 前出总览两图并过 Gate，模块正文前出模块图并确认。
6. **交互 = 信息结构 + 场景步骤流**：只写功能区块；每场景按 `①入口→②动作→③业务结果提示→④流向` 推到出口；入口/出口必须成对，无头/断头即 P0。
7. **异常全覆盖**：空数据、超限、等待过久/中断、重复、无权五类 + 业务特有异常；每条写明业务语言下的「用户看到什么、还能做什么」。
8. **Gherkin 单源**：每模块只有一个验收章节，AC 编号 `AC-Mxx-nnn` 并标优先级；`Then` 只断业务结果，禁 DOM/CSS；该章节即 TDD 输入，不另设 UAT 表。
9. **跨模块注册制**：被 ≥2 个模块使用的概念必须在总纲术语表注册；同名不同义/同义不同名即 P0。

## 四、标准流水线

```
输入
  → S1 解析与判型
  → S2 澄清①（锁定 7 点）
  → S3 图先于文：总览两图 + overview.md
  → S4 流程与范围 Gate ◉（强制暂停）
  → S5 逐模块：澄清② → 模块图 → 字段确认 → 成文 + 内联自检
  → S5d 速查表
  → S6 全局 Pass Gate
  → S7 终审 Gate ◉ → 归档
```

### S1 输入解析

- 项目目录未知先问；产物统一落 `.spec/PRD/`。
- V1 新建 → `.spec/PRD/V1/`；V2 迭代 → 先通读旧档，出 `.spec/PRD/V2/`（全量归档 + Diff）。
- `.spec/需求评审/任务清单.md` 中 `已确认` 条目逐条纳入修复范围，其余跳过。
- 输入以用户想法为第一依据；竞品报告可选。
- 澄清前复述确认：V1 用一句「做 X，面向 Y，解决 Z」；V2 先复述旧档现状理解。

### S2 澄清①（总览期）

先按第五节第 6 条引导竞品/参考，再收敛 7 点，缺一不放行：

| # | 收敛点 | 标准 |
|---|---|---|
| 1 | 目标用户与痛点 | 谁、什么场景、痛什么 |
| 2 | 核心价值主张 | 换来什么结果、为何非做不可 |
| 3 | 核心主流程闭环 | 入口到出口无断点 |
| 4 | 入口与导航结构 | 首屏、一级入口、列表—详情层级 |
| 5 | MVP 范围边界 | 做什么/不做什么 |
| 6 | 模块划分草案 | 每模块：应做/不应做/产出物 |
| 7 | 效果度量开关（可选） | 不做则写 Out-of-Scope |

第 7 点之外不主动展开度量。

### S3 图先于文

总览两图（规范见 `references/mermaid-patterns.md`）：

- 主流程泳道图（`sequenceDiagram`）：呈现收敛点 3，含 ≥1 条 `alt/else` 异常分支；
- 模块关联关系图（`flowchart LR`）：呈现收敛点 6，节点与边标注业务产物。

节点/连线须可追溯到澄清结论；未确认的标 `【设计假设】`。两图过 S4 Gate 后，按 `assets/overview-template.md` 生成 overview.md（十一章）。

### S4 流程与范围 Gate（强制暂停）

展示并确认：① 泳道图 ② 关联图 + 注记 ③ 各模块应做/不做/产出物 ④ In/Out-of-Scope ⑤ 【设计假设】清单。

- 图有异议 → 回 S2 重推演/改图。
- 范围有异议 → 回 S2 继续澄清。

### S5 逐模块展开

每模块依次执行，逐模块确认，不批量放行：

1. **澄清②**：把每个需求的触发、处理、分支出口推演至闭环；模块拆错回 S4。
2. **模块图**：先画业务流程图（`flowchart TD`：菱形双出口 + 终态）；有核心生命周期对象再加状态机图（`stateDiagram-v2`）。确认后才成文。
3. **字段确认**：基于已确认图给出业务信息清单草案（名称/含义/规则）并确认。
4. **成文 + 内联自检**：按模块九章模板落 `NN_xxx.md`，随即跑内联 Pass Gate，P0 不过就地返工。

### S5d 速查表

从已成文文档汇总六大索引（术语/页面·视图/模块/业务规则与状态机/业务信息/Gherkin AC）+ 【设计假设】清单，每条带原文锚点。只汇总、不改写；矛盾回溯修正。页面索引只汇总各模块 §3.1，载体归并交 Prototype-Design。

### S6 全局 Pass Gate

按第八节执行，并做一致性专项：引用/命名对照术语表；速查表锚点可达；索引数 = 源文档实测数。放行条件：P0=0 且 P1(Open)=0。

### S7 终审与归档

用户确认后归档 `.spec/PRD/VN/`（overview + 速查表 + NN_xxx + 验收说明），并回填评审清单：`已确认` 改 `已修复` + 写明改动位置；未处理条目保留原状态并说明原因。

### 回炉

模块划分错误（多切/漏切/错切）→ 冻结 → 修订总纲与关联图 → 重过 S4 → 再展开。

## 五、内联澄清规程

1. 一次一问，答后再问。
2. 默认给「推荐答案 + 理由」；无方向时给 2~3 个差异化选项。
3. 主动抛反方/极端场景逼边界，直到能一句复述并获得认可。
4. 概念敲定后立即写入术语表，正文只用注册名称。
5. 收敛纪律：7 点未锁不写 overview；总览图未确认不写正文；模块图未确认不进字段方案。
6. 竞品/参考引导：问「有无竞品/参考？有哪些功能？你要不要？上下游是谁？」；用「问题 + 选项 + 例子」帮用户想全，不照单全收，错误以专家视角纠正。
7. 待确认点列清单，逐条关闭后再推进。

## 六、模块拆分判据与共享下沉

满足任一条件即拆为独立模块：

- 有专属生命周期；
- 有独占核心对象；
- 可独立排期验收；
- 构成应用级聚合入口/导航视图（登记总纲导航章，不硬拆为业务模块）。

共享资产下沉总纲：术语表、跨模块生命周期、角色权限、共享信息项；模块私有内容留各 `NN_xxx.md`。

## 七、迭代归档（V2/V3…）

- 每版本独立目录 `.spec/PRD/VN/`，自成体系。
- 未变更模块原样复制，页首标注「本模块 V1→V2 无变更，仅随版本归档」。
- 差异矩阵逐模块标 `[新增]/[变更]/[沿用-未变]` + 变更摘要。
- 兼容影响只写需求侧（存量数据认领、老用户衔接、过渡期）；工程迁移归 TDD。

## 八、Pass Gate（三段式）

| 段 | 检查内容 |
|---|---|
| 1 结果是什么 | 章节覆盖、图表完备、AC 实测计数 |
| 2 结果缺什么 | AI 禁词、模糊未决、假设漏标、实现词越界、断头/无头、状态机死路、跨模块断点、UAT 表残留 |
| 3 优化什么 | P0/P1/P2 缺陷清单 + 状态 `[Fixed]/[Open]/[Disclosed]` |

放行：P0=0 且 P1(Open)=0；P0 一票否决。粒度：模块成文后内联轻扫，全部完成后全局三段式。

## 九、常见错误对照表

| 常见错误 | 等级 | 处理 |
|---|---|---|
| 出现 Toast/Loading/API 路径/字段类型等实现词 | P0 | 按红线 4 改写为业务表述 |
| 分支推演不到业务出口，或链路无头/断头 | P0 | 按红线 6 补到「用户看到什么、还能做什么」 |
| AC 的 Then 断言 DOM/元素 | P0 | 只断业务结果（红线 8） |
| 跨模块概念未注册或同义不同名 | P0 | 注册总纲术语表（红线 9） |
| 擅自定度量/灰度/NFR 指标 | P0/P1 | 删除；度量只在 S2 第 7 点开启后写 |
| 状态机死循环或无触发条件 | P0 | 补终态与守卫条件（红线 5） |
| 出现 TBD/「尽量快」等含糊表述 | P0 | 确认或标【设计假设】（红线 3） |
| 交付报告条目数与实际不符 | P1 | 重新实测计数 |
| 未画图先写 overview | P1 | 先出总览图过 S4 Gate |
| 模块图未确认就成文 | P1 | 先过 S5 第 2 步再成文 |
