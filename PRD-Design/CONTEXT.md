# CONTEXT.md —— PRD-Design 术语与决策记录

> PRD-Design 的术语对齐源与决策日志。SKILL/templates/references 概念必须与此一致；敲定概念即更新本文件。

## 一、角色与边界

- 人设：Staff 级产品经理。
- 目标：保证需求明确——边界清晰、模块合理、流程闭环、每模块有可测验收标准。
- 边界：只做需求；技术方案归 TDD；不给后端字段类型、不替前端定实现。

## 二、术语表

| 术语 | 定义 | 排除 |
|---|---|---|
| 业务信息清单 | 业务对象信息项，只含中文名称 + 业务含义 + 业务规则 | 不是数据字典；不含类型/Key/索引/脱敏 |
| 数据字典 | 已废除，被业务信息清单取代 | 禁再出现技术属性列 |
| 需求总纲 overview.md | 定需求边界、模块划分、应做/不做、产出物、模块关联 | 不含技术列 |
| 模块级澄清 | 模块展开前第二轮提问：推演路径与闭环，字段方案确认后才成文 | 不是一次性总澄清 |
| 信息结构 | 页面功能区块的轻量说明 | 不画控件线框/像素/视觉 |
| 场景操作步骤流 | ①入口→动作→②业务结果→③流向，到出口为止 | 禁控件/Loading/Toast 等实现词 |
| 模块验收标准 | 每模块唯一权威 Given-When-Then 场景集，`AC-Mxx-nnn` + 优先级；Then 只断业务结果 | 无独立 UAT 表；Then 禁 DOM/CSS |
| 业务度量事件 | 可选：用户开启效果度量才成章；不含工程事件定义 | 非默认章节 |
| 体验底线要求 | 总纲第 10 章：反馈清晰/失败可恢复的业务语义 | 不写时延数值 |
| 入口/出口 | 三级贯通的进入来源/办结去向 | 不是数据流或前置条件 |
| 入口出口对称律 | 入口与出口必须成对显式，缺一侧 P0 | 不只查出口 |
| 页面视图清单 | 已废弃（D-15），归并下沉 Prototype-Design | 历史术语仅追溯 |
| 苏格拉底拷问协议 | PRD-Design 澄清执行规范：决策树逐轮单步提问 + 边界/节点拷问 + 收敛证明 | 不是泛泛聊天；未过门槛不进下一环节 |
| 收敛证明 | 澄清点可关闭的四条件：结论可复述 + 决定/理由与已拷问的反方/边界/节点出口 + 设计假设有归属点与回访时机 + 用户认可 | 缺一即 P0，退回补问 |
| 节点拷问 | 对流程每个节点依次问触发/前置/动作/分支/异常/出口 | 禁止只走主干跳节点 |
| 方法论框架库 | case-library/frameworks.md：优先级/用户研究/发现/战略/度量/商业模式/规划/需求分析八类框架速查 | 只作「打开思路+专家纠偏」参考，不越域界不写技术 |
| 案例库 | case-library/：frameworks + prd-templates + zh-cases，按需加载 | 不照搬模板，本 skill 三级结构优先 |
