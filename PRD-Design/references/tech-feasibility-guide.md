# 复杂度预警 · 实现词汇负面清单 · 业务信息清单规范（Tech Feasibility Guide v2）

> 三合一指南：①产品层复杂度预警怎么写；②哪些词在 PRD 里禁写（域界红线 4 的执行细则）；③业务信息清单的编制标准。

---

## 一、产品层复杂度预警（防需求飘在天上）

### 1.1 定位边界
```
┌───────────────────────────────────────┬───────────────────────────────────────┐
│ ✅ PRD 只做预警                        │ ❌ 归 TDD / 研发                       │
├───────────────────────────────────────┼───────────────────────────────────────┤
│ 复杂度评级（高/中/低）                 │ 编程语言/框架选型                      │
│ 关键依赖「能力类别」                   │ 数据库物理表、索引、分库分表           │
│ 潜在瓶颈预警                           │ 缓存策略与队列选型                     │
│ 降级兜底的「业务思路」                 │ 降级的代码实现与服务治理               │
└───────────────────────────────────────┴───────────────────────────────────────┘
```

### 1.2 复杂度评级基准
| 评级 | 特征 | 典型场景 | 预警动作 |
|---|---|---|---|
| 低 | 成熟信息记录与查询逻辑，无实时协作与重计算 | 列表/表单/展示类 | 常规排期 |
| 中 | 跨多方协同、状态流转较多、依赖外部服务能力 | 多角色审批流、外部核验联动 | 提前确认外部方配合窗口 |
| 高 | 瞬时集中争抢、实时多端协作、AI 推理类、资金强相关 | 集中抢购、多人实时编辑、智能生成 | 必须给出降级兜底思路并考虑分期 |

### 1.3 示例（AI 配菜助手）
- 复杂度评级：`[高]`
- 关键依赖能力：大模型生成能力类别（响应存在不确定性延迟）；
- 潜在瓶颈：集中时段请求堆积，用户等待感知变差；
- 降级兜底思路：等待过久先给「经典推荐」占位结果，明确标注非个性化；失败给出可自行挑选的兜底入口。

## 二、实现词汇负面清单（红线 4 执行细则）

> PRD 全文禁止出现左列内容；写作时一律替换为右列业务表述。自检时逐行扫描。

| 类别 | ❌ 禁止出现 | ✅ 改写的业务表述 |
|---|---|---|
| 数据库/存储 | 字段类型、varchar/int/UUID、索引、分库分表、AES 加密、脱敏存储算法 | 「XX 信息」+ 业务规则（必填/可选值/上限） |
| API/协议 | `/api/v1/xxx`、HTTP 方法、错误码、SSE/WebSocket/gRPC | 「提交后系统受理」「流式呈现结果」 |
| 前端控件 | Toast/Modal/Dropdown/Radio/Button/Loading 态/骨架屏、浮层/浮窗/抽屉/弹窗/弹出式 | 「提示文案""」「可选项为固定列表」「以非侵入方式呈现」 |
| 缓存/客户端存储 | localStorage/sessionStorage/IndexedDB | 「最近一次填写的内容保留」 |
| 定时/调度 | setTimeout/cron/轮询周期实现 | 「按每日自动刷新节奏执行」「长时间无结果时提示可重试」 |
| 图表/渲染 | ECharts/D3/Canvas/WebGL | 「以图表方式呈现趋势」 |
| 大模型工程 | JSON Mode/Function Calling/Token 上限/RAG 组件名 | 「输出约束为结构化内容」「可引用知识范围」 |
| 幂等工程 | Client-Token/request_id 幂等机制 | 「重复触发只受理一次」 |
| 性能工程 | P95/P99/QPS/FCP、秒级时延数值、虚拟滚动方案名 | 归技术层（NFR），PRD 不出现；体验底线只写反馈清晰度/失败可恢复 |

**豁免区**：模块第 6 章「复杂度预警」内允许点名**能力类别**（如实名核验服务、地图定位能力），仍不得指定具体厂商与产品型号。

## 三、业务信息清单编制规范（替代数据字典）

### 3.1 三要素纪律
PM 只回答三件事：**有哪些信息 / 是什么意思 / 有什么业务规则**。规则 = 必填与否、可选值范围、上限口径。

### 3.2 好 vs 差 对照
| ❌ 差（越界到技术） | ✅ 好（纯需求） |
|---|---|
| `refund_amount_fen` Integer `1<=val<=order_paid_fen` 默认0 | 退款金额：想退回多少钱；必填；不超过该订单实付金额；精确到分 |
| `phone` String(11) 正则 `^1[3-9]\d{9}$` AES 存储 | 手机号：用于身份核对与结果通知；必填；11 位；界面展示隐去中间四位 |
| `coupon_id` FK → coupon.id 索引 | 所用优惠券：本次抵扣用了哪张券；选填；只能选本人可用列表中的券 |

> 差例中的翻译工作正是架构师拿「好例」去做的事——需求只给判定依据，不给物理设计。

### 3.3 与共享资产的分工
- 多个模块共用同一信息项 → 在总纲 §9.4 注册，各处引用；
- 模块独有项 → 写在本模块 §8；
- 出现"这个字段 A 叫 X、B 叫 Y"的分歧 → 以总纲术语表裁决，统一命名。

## 四、推演值的假设标注提醒

凡在规则、异常中出现你自己定下的业务上限类数值——次数上限、比例、容量——必须标注【设计假设】并在流程与范围确认 Gate 或字段方案确认环节请用户过目；时延性能数值（秒级）一律不写、不打【设计假设】，归技术层：
- 例：「提交后 15 分钟内未完成支付自动释放名额【设计假设：参考行业常见放单时长】」。（注：此处"15 分钟"是业务截止规则，属合法业务口径；区别于系统响应时延——后者不写）
