# PRD 架构深度指南（PRD Structure Guide v2）

> 指导 Senior PM 系统化构建需求总纲与模块规格，确保「需求边界清晰、流程闭环、与技术方案解耦」。
> 术语基准见 [CONTEXT.md](../CONTEXT.md)。

---

## 一、需求总纲 `overview.md` 十一章架构

总纲回答五个问题：为什么做、做给谁、拆成哪几块、块之间怎么衔接、全局规则是什么。

| 章 | 内容 | 质量要求 |
|---|---|---|
| 1 元数据与变更记录 | 项目/版本/参与人/变更历史 | 状态枚举完整 |
| 2 背景痛点与价值主张 | 业务动因、痛点、价值、取舍 | 取舍感真实：聚焦什么/放弃什么/代价；禁空洞口号 |
| 3 用户画像与 JTBD 场景 | 角色画像 + When/Want/So 场景矩阵 | 每个场景最终可追溯到一个 AC 编号 |
| 4 成功度量【可选】 | 北极星指标体系 | **开关章**：仅用户选择后保留；关闭则入 Out-of-Scope 留痕 |
| 5 全局主流程泳道图 | 角色 × 系统黑盒 × 外部方时序 | 业务动词消息；必须有异常分支 |
| 6 全局导航与入口结构（应用级 IA） | 一级入口清单 / 列表—详情层级 / 入口空态 | 入口在模块之前——导航决定模块如何被触达；只写「从哪进、怎么分层」，不画控件线框 |
| 7 模块清单与范围边界（L1 模块大纲核心） | 应做/不应做/产出物 + 上下游依赖 + 需求/AC 预览 + In/Out | 负向边界必须明确——PM 的价值在「不做清单」；只写边界不展开需求细节 |
| 8 模块间关联关系图 | Mermaid flowchart LR + 双向核对注记表 | 每条边标注传递产物，逐条验证闭环，断点 = P0 |
| 9 全局规范区 | 术语表 / 全局生命周期 / 角色权限 / 共享信息项 | 跨模块概念一律在此注册，模块只引用 |
| 10 体验底线要求 | 反馈清晰度 / 失败可恢复语义（不写时延数值） | 禁时延数值与 P95/QPS 类工程指标 |
| 11【V2】差异矩阵与兼容面 | Diff + 需求侧兼容三条 | 兼容只写使用习惯衔接，不写工程迁移方式 |

## 二、模块规格 `NN_xxx.md` 九章架构

```
┌──────────────────────────────────────────────────────────────┐
│                  模块详细规格九章结构 (v3)                    │
├─────────────────────────────┬────────────────────────────────┤
│ 1. 模块概述与边界            │ 2. 前置条件与后置影响          │
│    (定位/应做/不应做/        │    (关联关系标注+前置+后置)    │
│     ★需求索引 REQ/故事)      │                                │
│ 3. 信息结构与场景步骤流 ★   │ 4. ★模块结构图+流程图+状态机   │
│    (区块说明+推演到出口)     │                                │
│ 5. 业务逻辑与计算规则        │ 6. 复杂度预警(无选型)          │
│ 7. 异常分支矩阵(业务语言)    │ 8. 业务信息清单(名称/含义/规则)│
├─────────────────────────────┴────────────────────────────────┤
│ 9. 验收标准 (Gherkin 单源 · 按需求分组 · AC-Mxx-nnn)         │
│ A.【可选】效果度量事件清单(仅当总纲§4开关开启)               │
└──────────────────────────────────────────────────────────────┘
```

### 各章深度要求

1. **模块概述与边界**：定位一段话讲透；**负向边界表必填**——「不应做」写得越准，模块间越不冲突；**需求条目索引（REQ-Mxx-nnn）必填**——每个需求一条目，含优先级、对应场景、关联 AC，是本模块目录；每个用户故事挂 REQ 与 AC 编号。
2. **前置/后置**：先写**关联关系标注**（上游依赖谁、下游产出给谁，与总纲 §8 关联图一致）；前置写业务硬前提（身份/前序状态/信息完备）并写明「进入本模块的入口」（从哪个导航入口/上游业务进入）；后置写业务连锁反应（状态变化/驱动了哪些下游），禁止出现消息队列类表述。
3. **信息结构与步骤流（核心章）**：
   - 区块说明粒度 = 「页面有哪几个功能区、各承载什么」，到此为止；
   - 步骤流按场景编号（S1/S2…），标准六列表：步骤/从哪进入/谁/做什么/系统给出什么/流向哪里；
   - **每条主链路附异常推演子表**，一路推到「用户看到什么/还能做什么」的可见业务出口；
   - 判断断头三问：这一步之后用户知道发生了什么吗？知道该干嘛吗？能回到正轨吗？
4. **模块结构图与流程**：先画**模块结构图**（flowchart LR 展示模块内部功能区块构成）；flowchart TD 讲本模块处理逻辑；stateDiagram 讲核心对象从生到死；节点用语必须与术语表一致。
5. **业务逻辑与规则**：规则写到可直接判定对错；金额只定口径（币种/精确到分）不定存储方案；排序过滤默认值必须显式。
6. **复杂度预警**：四要素（评级/依赖能力类别/瓶颈/降级思路）；点名能力类别而非厂商产品。
7. **异常分支矩阵**：五类通用（空数据/超限/等待过久/重复操作/无权）+ 业务特有行；全部落到用户视角两栏「看到什么/还能做什么」。
8. **业务信息清单**：只有三列。编制规范详见 [tech-feasibility-guide.md](tech-feasibility-guide.md)；共享项引用总纲 §9.4。
9. **验收标准**：Gherkin 单源，**按需求分组**（每个 REQ 下挂其 AC），规范详见 [gherkin-guide.md](gherkin-guide.md)；本文档中它是开发 TDD 先行测试用例的输入源，`REQ ↔ AC` 双向可追溯。

## 三、两段式苏格拉底澄清指引

### 3.1 总览期澄清①（收敛 7 点）
单步提问法：每题带推荐答案与理由；模糊回答用极端场景压测；敲定的概念即时登记术语表。

| 点 | 提问切入点示例 |
|---|---|
| 1 目标用户与痛点 | "这个工具给谁用？他们现在没这个工具时是怎么熬的？" |
| 2 价值主张 | "做完之后谁的生活里少了什么麻烦？值不值得他专门来用一次？" |
| 3 主流程闭环 | "咱们从打开到拿到结果走一遍：第一步做什么…最后一步算办完了的标准是什么？" |
| 4 入口与导航结构 | "打开应用第一屏是什么？有几个一级入口？一个对象有多条数据时，总览列表在哪、单条详情从哪进？" |
| 5 MVP 边界 | "第一期如果只能留下一个功能，留哪个？哪些明说'这版不做'？" |
| 6 模块划分草案 | "这几件事是不是各自有各自的周期和对象？A 没上线 B 能不能单独发？" |
| 7 效果度量开关 | "本期要不要做效果度量（指标体系/埋点/画像分析）？不做就留给后续迭代。" |

### 3.2 模块级澄清②（流程闭环推演）
对每个模块依次拷问，**入口与出口成对追问**：
- 这条需求从哪里进入（从哪个导航入口/上游业务进入本模块）？
- 中途每一步用户的动作与系统的回应是什么？
- 所有可能的中断点（填错/超时/重复/无权/反悔）都走到出口了吗？
- 这条链路办结后流向哪里（下游模块/返回哪个入口）？出口是否承接了入口的下一跳？
- 推演完毕 → PM 给出该模块的业务信息清单草案 → 用户确认后才成文。

## 四、零歧义检查清单（模块成文后逐条过检）

- [ ] 是否存在「尽量快/友好提示/适当支持」类主观词？
- [ ] 每条步骤流是否都推到了可见的业务出口？「从哪进入」是否同样显式，入口与出口是否成对（无头链路 = P0）？
- [ ] 状态机每个流转是否都有触发事件与合法目标态？
- [ ] 所有推演的业务上限/阈值是否都打了【设计假设】？（时延性能数值是否已全部排除？）
- [ ] 全文是否零实现词汇（API/控件/字段类型/协议名）？
- [ ] 跨模块引用的概念是否都注册进了总纲术语表？
- [ ] 每个场景与异常行是否有对应 AC 编号？
- [ ] 每个 REQ 是否至少 1 条 AC，且 REQ ↔ AC 双向可追溯？
- [ ] 模块结构图是否覆盖本模块全部功能区块，无遗漏无冗余？

## 五、三级结构契约与两件套分层（v3 新增）

**三级结构契约**（交付物由粗到细，对应 SKILL.md §1.3）：
- **L1 模块大纲** = `overview.md`：只写模块边界（应做/不应做/产出物）+ 全局导航与入口结构 + 上下游依赖 + 需求/AC 预览，不展开需求细节；
- **L2 需求细节** = `NN_xxx.md` §1~§8：需求索引 → 场景步骤流 → 业务规则 → 异常 → 业务信息清单；
- **L3 测试用例** = `NN_xxx.md` §9：按需求分组的 Gherkin AC，`REQ ↔ AC` 双向追溯，开发 TDD 先写测试。

**两件套分层**（对应 SKILL.md §1.4）：
- **规范流程** = `SKILL.md` + `references/`（本文件即承接模板抽离的全部写作要求与深度规范）；
- **大纲目录** = `assets/` 模板（纯章节骨架，不再堆写作注释）。

> 因此 `references/` 是「怎么写」的唯一权威：模板里每个章节怎么写、写多深、红线怎么落地，一律以本文件与其余 references 为准；`assets/` 只负责「结构样式」的骨架。
