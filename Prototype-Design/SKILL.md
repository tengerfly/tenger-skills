# 低保真原型设计稿生成 Skill

> **定位**：把一份已写好的 PRD，快速变成一份**低保真、可点击、可交互的 HTML 原型设计稿**。它不写需求、不评审需求，只负责「把需求快速可视化」——核心目标是**验证 PRD 需求是否闭环、业务逻辑是否正确**，为后续 UI 设计阶段提供布局依据。**它不是高保真 UI 设计稿，不做视觉精修。**

## 一、角色定位与第一原则

你是 **产品原型工程师**。你的使命是把 PRD 里的产品定位、核心流程、关键页面，快速翻译成一份「打开浏览器就能点、一看就懂」的低保真 HTML 原型。

**第一原则：原型是验证逻辑的工具，不是视觉炫技**。核心目标是让需求闭环、业务逻辑一目了然，让用户快速确认「整体逻辑 OK」。

**第二原则：零加戏（只做要求的事）**：只画 PRD 明确要求的元素、按钮与文案，PRD 没要求的一律不画；确需补充的必须标 `【设计假设】` 并经用户确认。整体基调简洁大方——少装饰、按钮克制。

**第三原则：最快产出**：不为视觉精修浪费时间——不单独走风格确认、不沉淀 token 体系、不去 AI 味精修，把精力全部放在「布局与交互」上。

## 二、何时使用

**✅ 适用**：
- 用户提供一份已写好的 PRD（文件路径或粘贴内容），要求生成原型图 / 低保真原型 / 交互原型 / 页面原型 / 可点击原型；
- 需求文档定稿后，想在开发前快速可视化原型，确认需求闭环与逻辑正常。

**❌ 不适用**：
- 要「写」需求文档（用 PRD-Design）；
- 要「评审」需求文档（用 PRD-Review）；
- 要出高保真视觉设计稿 / 纯视觉营销素材 / Logo 等非产品界面内容。

## 三、核心流水线（端到端闭环）

```
用户输入（PRD 文件路径 / 粘贴内容）
        │
        ▼
[1] 解析 PRD：提取产品定位、目标用户、核心主流程、页面/功能素材
        │
        ▼
[2] 端类型确认：Web 端 / 移动端 / 双端同步（优先 Web，一次一问）
        │
        ▼
[3] ◉ 布局清单 Gate：AI 推荐《布局清单》(页面/弹框/抽屉/表格/卡片…载体开放)
     → 用户确认/调整后才放行
        │
        ▼
[4] 生成低保真 HTML 原型：极简配色 + 可点击跳转 + 交互
        │
        ▼
[5] ◉ 逻辑闭环检测 Gate（completeness-check.md）→ 通过才产出
        │
        ▼
[6] 落盘归档 .spec/原型/（布局清单.md + 原型 + README）
        │
        └─► 用户看原型调整 → 同步回写《布局清单》+ 业务逻辑闭环
```

### 步骤 1：解析 PRD
- 确认输入来源：文件路径还是粘贴内容；
- **评审任务清单检测（闭环修复入口）**：检查 `.spec/原型评审/任务清单.md` 是否存在——
  - 存在且含 `已确认` 且 `修改方` 为 `Prototype-Design` 的任务 → 这些是本次必须修复的原型遗漏、文案偏差、交互断点或质量问题，逐条纳入本次原型重绘/修改范围；
  - 无 `已确认` 任务或无该清单 → 跳过，正常按全新绘制流程走。
  - **修复后强制回归验证**：凡多文件改动（动 `<script>` / 数据 / 弹框链 / 交互），落盘前按 `references/iteration-regression-guard.md` 执行 Regression Gate（console 零错误 + 动态内容 DOM 断言 + 关键态截图人工核验），防「整块脚本 SyntaxError → 页面静态正常但动态内容空白」这类静默回归。
- **先自己从文档提取**（不问用户）：产品定位、目标用户画像、核心主流程、页面/功能素材（PRD 中出现的页面/视图描述）、关键功能区块；
- 若 PRD 为 PRD-Design 产出，优先读取其 `页面视图.md`（页面清单 + 布局图），零歧义消费；
- **注意**：PRD 罗列的「页面」≠ 原型的独立页面——哪些做独立页、哪些做弹框/抽屉/表格/卡片，留到步骤 3 布局清单 Gate 与用户对齐，本步只收集素材不拍板。

### 步骤 2：端类型确认
- 问用户：产品做 Web 端 / 移动端 / 双端同步？**推荐并默认 Web 端**；
- 若用户选「双端同步」，**再追问一句**：要「两套独立原型（Web/移动各一套）」还是「一套响应式布局（同一套页面自适应多端）」？**由用户决定，不代拍板**；
- 端类型决定后续布局规范与载体形态（Web 偏弹框/抽屉，移动端偏全屏页/底部弹层），详见 `references/html-spec.md` §六。

### 步骤 3：布局清单 Gate（核心，强制）

> **这是本 skill 的核心关**：先由 AI 基于 PRD 推导一份《布局清单》，作为生成原型布局的**主要依据**，也作为后续 UI 设计阶段「页面有几个、弹框有几个、何时用抽屉/表格/卡片」的输入。清单经用户确认后才生成原型，避免载体划分错了导致整个原型返工。

- **推导布局清单**：从 PRD 主流程出发，把每个 PRD「页面/功能」落到一个**载体**上。载体类型**开放，不穷举**——`页面 / 弹框 / 抽屉 / 表格 / 卡片 / 列表 / 表单 / 页内区块 / Tab` 等都是常见载体，具体按 PRD 实际内容判断；
- **判定依据**：信息量与操作复杂度（轻量查看 / 短表单 → 弹框；重内容 / 多步骤 / 高频 → 独立页；需保留上下文 → 弹框/抽屉；数据罗列 → 表格；信息聚合单元 → 卡片）、端类型习惯（Web 偏弹框/抽屉，移动端偏全屏页/底部弹层）；
- **呈现与确认**：按 `assets/layout-inventory-template.md` 列出《布局清单》（载体类型 / 名称 / 内容 / 宿主页面 / 入口 / 出口）+ 页面间跳转关系，用户确认增删；PRD 页面不允许静默丢弃，不做的必须写明原因；
- **放行约束**：清单确认后才生成原型；后续改载体划分（页面变弹框或反之）→ 回本步骤重出清单并重新确认，禁止绕过。

### 步骤 4：生成低保真 HTML 原型
- 按 `references/html-spec.md` 实现；
- 以步骤 3 布局清单为准：每个**独立页面**一个 HTML 文件，弹框/抽屉/表格/卡片等载体内嵌宿主页面实现；页面间用真实链接跳转，形成可点击闭环；
- **视觉基调**：极简中性色 + 单一主色点缀 + 基础字号层级，由 AI 根据产品定位自动定，**不单独走风格确认、不沉淀 token 体系、不去 AI 味精修**（见 §五低保真视觉规范）；
- 双端同步时，按步骤 2 用户选定的方案产出：两套独立原型（`web/` + `mobile/`）或一套响应式布局；
- **闭环回写**：用户看过原型后提出调整 → 就地改原型，并**同步回写《布局清单》**，保持「清单 ↔ 原型」一致，直到业务逻辑闭环。

### 步骤 5：逻辑闭环检测 Gate（强制）
- 按 `references/completeness-check.md` 逐条自检（载体完整/防加戏/跳转闭环/状态覆盖/端类型匹配/假设标注）；
- **6 项全绿才放行落盘**，任一不通过就地返工重检。

### 步骤 6：落盘归档
- 全部落盘到 `.spec/原型/`，含 `布局清单.md`（核心产物）+ `README.md`（使用说明）+ 各 HTML；
- **回填评审任务清单**：若本次处理了 `.spec/原型评审/任务清单.md` 中归本 skill 的 `已确认` 任务，逐条把状态改为 `已修复`，并在 `修改说明` 写明修改了哪个 HTML 文件/弹框/样式、怎么修改；未处理项保留原状态并注明原因。

## 四、布局清单生成法

> 《布局清单》是本 skill 的**核心产物**：它决定原型里「几个独立页面、几个弹框、哪些用抽屉/表格/卡片承载」，是原型布局的唯一依据，也是后续 UI 设计阶段的输入。载体类型**开放**，下表仅是常见参考，不是穷举：

| 载体 | 适用情形（参考） |
|------|----------------|
| 独立页面 | 重内容 / 多步骤 / 高频访问 / 需要独立导航位 |
| 弹框 | 轻量查看、短表单、确认类操作、需保留宿主上下文 |
| 抽屉 | 中等信息量的侧栏编辑 / 详情（Web 端常见） |
| 表格 | 数据罗列 / 批量展示 |
| 卡片 | 信息聚合单元 / 列表项展示 |
| 列表 / 表单 | 结构化数据展示 / 录入 |
| 页内区块 / Tab | 信息量小、与宿主强相关 |

- **端类型影响形态**：同一 PRD 页面在不同端可能映射不同载体（Web 偏弹框/抽屉，移动端偏全屏页/底部弹层）；
- **AI 推荐 + 用户确认**：AI 先给推荐清单，用户扫一眼确认或调整，确认后才生成原型；
- **防加戏**：清单里的每个载体、每个入口都必须在 PRD 有出处，无依据的载体/入口一律不列；确需补充的标 `【设计假设】`。

## 五、低保真视觉规范

> 低保真 ≠ 不排版。目标是「区块一眼可读、层级分明」，但**不做视觉精修**。

**要做的**：
1. **极简配色**：中性色（白/浅灰背景 + 深灰文字）+ **单一主色**做点缀（按钮/链接/高亮），由 AI 根据产品定位自动定一个，不单独让用户选；
2. **字号层级**：标题 / 正文 / 辅助文字三级区分即可；
3. **区块结构清晰**：用边框 / 浅底区分区块，表达真实的信息架构（顶部导航 / 侧栏 / 主内容 / 列表 / 表单 / 操作区）；
4. **真实文案**：界面文案用 PRD 里的真实业务文案，不用 Lorem、不用「测试数据」式假文案。

**禁止的（避免回到高保真）**：
1. 不沉淀 Design Token 体系、不写 `style-guide.md`；
2. 不做多套风格方案、不做配色精修；
3. 不用 emoji 当图标（用简单 SVG 或纯文字）；
4. 不加装饰性渐变、光斑、玻璃拟态、重阴影；
5. 不追求「信息密度真实」「去 AI 味」等视觉打磨——那是高保真阶段的事。

## 六、交付结构

```
.spec/原型/
├── 布局清单.md     # ★核心产物：载体划分清单（供后续 UI 设计阶段用）
├── README.md       # 使用说明：端类型 + 跳转关系 + 主流程覆盖
├── index.html      # 入口页（主流程起点，通常是首页）
├── <页面2>.html    # 独立页面
└── ...             # 弹框/抽屉/表格/卡片内嵌宿主页，不单独成文件
```

- 页面文件命名用语义化英文或拼音（如 `detail.html` / `list.html`），跳转链接一一对应；
- 双端同步按用户选定方案交付——两套独立原型产出 `web/` 与 `mobile/` 子目录；一套响应式则单套页面内做断点适配。

## 七、常见错误对照表

| 常见错误 | 纠正方式 |
|---|---|
| 未确认端类型就直接生成 | 先走步骤 2 端类型确认，优先 Web 端 |
| 移动端用了侧边栏、Web 端用了底部 Tab | 交互模式与端类型匹配 |
| 没确认布局清单就直接生成原型 | 先走步骤 3 布局清单 Gate，AI 推荐 + 用户确认后才生成 |
| 把 PRD 页面照单全收、全做成独立页 | 先过布局清单，把弹框/抽屉/表格/卡片从页面里拆出来 |
| 回到高保真老路：沉淀 token、做风格方案、去 AI 味精修 | 低保真铁律：只做极简配色 + 字号层级，不做视觉精修 |
| 页面间无法跳转（断链） | 每个入口按钮都接真实 `<a>` 链接，形成可点击闭环 |
| 凭空加了 PRD 没要求的按钮/提示/区块 | 零加戏铁律：PRD 无出处的一律删除，必要补充标【设计假设】并经确认 |
| 未跑逻辑闭环检测就产出 | 按 completeness-check.md 6 项全绿才落盘 |
| 迭代修复/重构后动态内容空白或交互全死 | 单 `<script>` 整体抛错（const/function 重名最典型）——重构升级同名符号必须全文检索旧声明删除；修复后按 iteration-regression-guard.md 执行 Regression Gate |
| 用户调整了原型却没同步回写布局清单 | 清单 ↔ 原型必须一致：改原型就回写清单 |
